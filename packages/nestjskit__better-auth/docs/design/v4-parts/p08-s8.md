## 8. Authorization

### 8.1 Model `[A][B][C]`

A handler declares **requirements**: values that carry their **policy** by reference (§4.4). After the principal is known, the evaluator judges them. Each policy is a thin adapter over a better-auth API. The evaluator owns composition only.

- **AND across the plan.** The instance's `defaultRequirements` come first (unless `@SkipDefaultRequirements()` applies), then class requirements (base class first; none for nested handlers), then method requirements, in declaration order (§7.6 step 4). Evaluation is sequential and stops at the first deny, which gives a deterministic cost and a deterministic error.
- **`anyOf(a, b, …)`.** Children are evaluated in order and the first allow wins. If every child denies, the status is 401 if any child denied with 401, otherwise 403. The `reason` is the first child's, and the `message` lists the children's labels `[C]`.
- **`allOf(…)`.** An explicit AND group, useful inside `anyOf`.
- **Principal-kind and delegation gate** `[R1:BA-r1-01, SEC-r1-02]`. Before a policy runs, the evaluator computes its admitted kinds: `requirement.principals ?? policy.requires.principals`.
  - If the list is set and the principal's kind is not in it, the requirement denies with 403 `PRINCIPAL_NOT_SUPPORTED`.
  - If the list is **not** set, the policy judges any principal **without** `delegation`. A delegated principal (API key, OAuth token) is denied 403 `PRINCIPAL_NOT_SUPPORTED`, so a policy that grants by `userId` never silently extends a narrow key or token to the owner's full rights.

  Both checks compare data (kind strings, and the presence of a `delegation` field), never a kind core knows about. A policy that names a delegated kind must AND its own decision with `principal.delegation.allows(…)`; the built-in ones do (Z5).

- **Scope.** Every policy call runs inside `handle.run({ cookies: call.cookies, forward: 'same-credential', inbound: call.headers, internal: true }, …)`. On cookie-capable transports, cookies produced by nested better-auth calls reach the client through the bridge, because those calls carry the caller's own credential. On cookie-less transports, refresh is suppressed (§7.4; EXP-B:E3).
- **Per-invocation decisions, per-request I/O** `[R1:NEST-r1-01]`. A decision is memoized by `(call.invocation, requirement expression)`, so a second guard binding on the same invocation re-uses it. It is never reused for another GraphQL field, alias, batched operation or WebSocket message, even when the requirement object is identical. Policies dedupe their better-auth I/O per logical request through `ctx.memo`, keyed by concrete inputs (Z6).
- **Invocation.** The evaluator calls each policy through `POLICY_INVOKER` (default: `policy.evaluate(params, context)`), so a test can stub decisions per policy without replacing the guard (`overrideDecisions`, §14.8) `[R2:NEST-r2-15]`.
- **Budget** `[R3:SEC-r3-08]`. `AuthorizationContext.memo` counts the distinct keys it computes for one logical request (`call.key`, per instance); memo hits are free. When a policy asks for a new key past `limits.maxAuthorizationCallsPerRequest` (default 100), the memo does not run the computation: the call rejects with the failure `AuthFailures.rejected({ status: 429, reason: 'TOO_MANY_AUTHORIZATION_CHECKS' })` (no `Retry-After`), which the safety net passes through as the requirement's answer (§13.2), so better-auth is never called. 100 is far above what one REST request needs and lets a GraphQL page of 100 items carry a distinct check per item; 500 aliased fields naming 500 organizations stop at the 101st instead of costing 1,000 to 1,500 storage reads (REV3-SEC, SEC-r3-08). `false` disables the bound.
- **Errors (S6).** Policies return decisions and never throw to deny. For policies that let a better-auth error escape, the safety net (Z2) maps it `[R2:BA-r2-03]` `[R3:BA-r3-01, BA-r3-05]`:
  - **A generic 401**: no body code, or code `UNAUTHORIZED`. Those are the shapes better-auth's session checks raise (`sessionMiddleware` and its siblings answer `{ code: 'UNAUTHORIZED' }`; several organization and admin endpoints use `APIError.fromStatus('UNAUTHORIZED')`, which has no body, LEAD-V43), and they mean "the session read on these headers came back empty". That read also swallows storage failures, because `getSessionFromCtx` catches every error into `null` (LEAD-V36): an organization call during a storage brownout, after the guard's read succeeded, answers exactly this 401, which v2 turned into a 403 "no permission" logged at debug (REV2-BA:`exp3-org-outage-401.mjs`). So:
    - when the principal came from a source that declares `sessionBacked` (the built-in session source), the evaluator reads once more through that one source (`ResolutionRequest.reclassify`), with `freshness: 'authoritative'` and no memo, at most once per invocation (a substituted resolver answers this read too; `overridePrincipal`'s answers `absent`, §14.8). The read throws → infrastructure (5xx), because storage is failing; it is `authenticated` → infrastructure (5xx), with the escaped `APIError` as the redacted cause: the session exists and better-auth's endpoint failed to read it; it is `absent` or `rejected` → 401 `UNAUTHENTICATED` with better-auth's code as `reason`: the session ended between the two reads. In a `customSession` app the read goes through `customSession`'s endpoint, which swallows a storage failure again (LEAD-V44), so an outage answers 401 there, like the guard's own read (RK2);
    - when the principal came from any other source (an API key, the §4.3.4 OAuth token), the request simply carries no better-auth session for the endpoint the policy called: 401 `UNAUTHENTICATED` with better-auth's code as `reason`, without a re-read. v3 re-resolved through the route's sources here, authenticated the OAuth principal again, and answered 5xx;
  - **A 401 with any other code** is better-auth denying an authenticated caller (`USER_IS_NOT_A_MEMBER_OF_THE_ORGANIZATION` from `hasPermission`, `YOU_ARE_NOT_ALLOWED_TO_DELETE_THIS_MEMBER`, `LINKING_NOT_ALLOWED`, `INVALID_TOKEN`, `USER_BANNED`, `KEY_DISABLED`, …): deny **403** with that code as `reason`. v3 sent every 401 through the re-read, so a third-party policy that let `hasPermission`'s non-member answer escape turned "no access" into an ERROR-logged 5xx that any authenticated caller could trigger (REV3-BA:`exp2-policy-401-and-custom-role.mjs`, LEAD-EXP-11). 403 rather than better-auth's own 401 keeps clients from signing a user out for a missing permission, and matches what the built-in organization policy already answered for its code (§17 Q28);
  - 403 becomes deny **403** with the better-auth code as `reason`, because the principal is authenticated;
  - 429 becomes 429;
  - another 4xx becomes `BetterAuthConfigurationError` (500, logged), because our own call was malformed;
  - ≥ 500 or a non-API error becomes infrastructure (5xx).

  Built-in policies map the 4xx outcomes they expect before the net sees them, and let every other `APIError` escape to it (§8.3). The reference library turned every error into 403 (R:ref-impl §6.1), which is exactly what S6 forbids.

- **Policy instances.** The evaluator calls the instance `PolicyResolver` returns for each requirement's reference, the same instance whose `requires` the planner read (§4.4.3) `[R3:NEST-r3-04]`.

### 8.2 Decorators and composition

```ts
@Require(freshSession()) // class: every handler needs a fresh session
@Controller("billing")
export class BillingController {
  @RequirePermission({ billing: ["read"] }) // AND with the class requirement
  @Get()
  list() {}

  @Require(
    anyOf(
      permission({ billing: ["refund"] }),
      orgPermission(
        { billing: ["refund"] },
        { organization: fromParam("orgId") },
      ),
    ),
  )
  @Post(":orgId/refund")
  refund() {} // system admin OR org-level refund right

  @Public() @Get("status") status() {} // explicit opt-out of the class requirement (§7.6)
}
```

- **Stacking accumulates.** Each requirement decorator **appends** `RequirementExpr`s to its target's _own_ metadata array instead of overwriting it. Plain `SetMetadata` overwrites, and the reference's `getAllAndOverride` model lost class requirements (R:ref-impl §6.1) `[A]`.
- **Reading.** The planner reads the own metadata of every class in the prototype chain (base first), then the handler. A subclass cannot silently drop a base-class requirement. It always stores arrays, which avoids `getAllAndMerge`'s nested-array behavior for mixed types (R:nest-di §3.2).
- **Sugar.** `@RequirePermission(p)` is `@Require(permission(p))`. Third parties get both forms through `definePolicy` (value policies) or `requirement(Class, params, options)` (DI policies) plus `Require(...)`.

**Notes:**

- **Admin permissions and headers.** The admin policy deliberately omits `headers`. With headers, better-auth performs its own authoritative session read (a second one, and a second API-key validation with `enableSessionForAPIKeys`) and ignores `body.userId`/`body.role` (R:ba-authz §2.1; LEAD-V24). Its 401 would also be ambiguous, because that read swallows storage errors (LEAD-V36). The reference's `@UserHasPermission({ userId, role })` options were silently ignored for exactly this reason. The authoritative session read plus the stored role reproduce `adminMiddleware` + `hasPermission`: the same session acceptance (§7.3, §17 Q21) and the same role, whatever shape `customSession` gives the session (§17 Q29) `[R2:BA-r2-06]` `[R3:BA-r3-02]`. The price of omitting headers is that better-auth must resolve a base URL without a `Host` header: a dynamic `baseURL` needs a `fallback` (B20, REV2-BA:`exp5-dynamic-baseurl-headerless.mjs`) `[R2:BA-r2-05]`.
- **No cheaper admin modes.** v2 offered `freshness: 'role'` (cookie-cache identity, role from the user row) and `'cached'` (cookie-cache identity and role). Both judged the session a non-authoritative read returned, which includes an API key's mocked session, with the owner's role: no better-auth admin endpoint ever does that. Both were removed rather than given a second credential check (ADR-36).
- **Policy ids** (diagnostics, `overrideDecisions`): `better-auth:session/fresh`, `better-auth:admin/permission`, `better-auth:organization/permission`, `better-auth:organization/member`, `better-auth:api-key/permission`. <!-- gitleaks:allow: public policy identifier -->
- **Plural `permissions`.** Requirement builders always send `permissions`. The deprecated singular `permission` key gives a 400 on the admin endpoint and a silent `false` on the org endpoint. Empty permission maps are rejected by `validate()` at boot.
- **Organization refs** `[R2:BA-r2-08, SEC-r2-06]`. A ref determines an organization **ID**; the policies always send it explicitly, and v2's "omit `organizationId`" path is gone:
  - `activeOrganization()`, the default, reads `session.activeOrganizationId` from the principal's session when it is a non-empty string (the base session, or a `customSession` shape that keeps it). When the field is absent and the `custom-session` plugin is installed, it asks better-auth: `getActiveMember({ headers })` (deduped per request) returns the member row with `organizationId` (LEAD-V40); 400 `NO_ACTIVE_ORGANIZATION` or `MEMBER_NOT_FOUND` means none. When it is `null` in the base shape, there is no active organization. Its `missingReason` is `NO_ACTIVE_ORGANIZATION`. Sending the ID explicitly checks the same organization better-auth's `hasPermission` would have taken from the same session, and it makes `@ActiveOrganizationId()` correct for `customSession` shapes, where v2 had nothing to publish;
  - `fromParam('orgId')` reads `call.param`: a route param, GraphQL arg, or WS/RPC payload field, holding an **organization ID**;
  - `fromHeader('x-organization-id')` reads a header;
  - `organizationRef(fn, { missingReason })` wraps any function.

  The evaluator of the org policies accepts a ref's result only when it is a non-empty string. Anything else (`undefined`, `''`, a number, an object or array from a JSON payload) is "no organization": 403 with the ref's `missingReason`, logged at debug, and never sent to better-auth. v2 passed payload values through, so `{ "orgId": { "$ne": null } }` from any authenticated socket made better-auth answer 400 `VALIDATION_ERROR`, which became an ERROR-logged 500 per message, and `""` silently checked the active organization instead (REV2-SEC:`probe-org-param-type.mjs`). I/O memo keys are tuples serialized with `JSON.stringify`, so no literal ID can collide with a sentinel such as v2's `'active'`.

  **Slugs are not IDs.** better-auth's `hasPermission` accepts only `organizationId` (`BA/plugins/organization/organization.ts:167-180`). The organization unit ships no slug ref. A route keyed by slug maps it to an ID in its own `organizationRef(...)`, preferably through better-auth: `auth.api.listOrganizations({ headers })` is a side-effect-free, session-scoped list of the caller's organizations with `id` and `slug` (`crud-org.ts:964-999`), so the ref can dedupe it with `ctx.memo` and return the matching `id`, and a slug the caller is no member of yields no organization (403). `getFullOrganization` is not suitable: for a non-member it clears the caller's active organization (LEAD-V40), a write no authorization check may cause. v3 pointed the hint at the application's own organization table, which reads better-auth's table past its adapter `[R3:BA observation on BA-r2-08]`. A present `activeOrganizationId` alone does not prove membership, because removed members keep it (R:ba-authz §1.2). The endpoint call is what checks.

- **The default ref and IDOR** `[R1:SEC decision]` `[R3:NEST-r3-10]`. A handler that acts on an organization it takes from its input while the requirement checks the session's _active_ organization authorizes the wrong organization. The organization unit's `advise()` warns (`W_ORG_PARAM_IGNORED`) for every handler whose claimed inputs (`AdvisedHandler.inputs`: HTTP route params, GraphQL `@Args` names) include `orgId`, `organizationId`, `organization` or `orgSlug` while an org requirement on it uses `activeOrganization()`. v3 read `RoutePlan.routeParams`, which core compiled from Nest's HTTP path metadata only, so a GraphQL mutation `deleteProject(@Args('orgId') orgId)` got no warning, and extending it would have meant teaching core GraphQL metadata (NEST-r3-10). WS and RPC payload fields are not known statically and are not covered. The hint names `fromParam('<input>')` for an ID input and, for `orgSlug`, says that the policies need an organization ID and shows an `organizationRef` that maps the slug through `listOrganizations` `[R2:BA-r2-08]`. The default stays because it is better-auth's own `hasPermission` behavior (§17 Q17).
- **Param decorators.** The resolved organization id and member role are published per invocation (`ctx.provide`) and exposed through `@ActiveOrganizationId()` and `@ActiveMemberRole()`, built with `defineInvocationParam`. They are valid after an org requirement ran on the same invocation, and return a `string`, never `undefined`. That fixes reference issue #163 without type gymnastics `[C]`. Two GraphQL fields that check different organizations each see their own id `[R1:NEST-r1-01]`.
- **Delegation.** No built-in policy judges a delegated principal unless the requirement names its kind. `permission()` and `apiKeyPermission()` then check the credential's grant (Z5). The org policies do not accept `'api-key'` at all, because the org endpoints need a session.

**Deliberately not shipped:**

- **A presence-only "active org" check.** It is unsafe: removed members keep `activeOrganizationId`, so only the endpoint call proves membership (§8.3, Organization refs).
- **The pure (in-process) org `hasPermission` export.** It saves the session read but writes to an unbounded process-global role cache (R:ba-authz pitfalls). Revisit after measuring (§17 Q9).
- **Role-name decorators.** better-auth has no "has role" API (§8.6).

#### 8.3.1 API keys (`./api-key`) `[R1:BA-r1-04, SEC-r1-05, BA-r1-05]` `[R2:SEC-r2-02, BA-r2-05, BA-r2-06]` `[R3:BA-r3-03, BA-r3-04, SEC-r3-01]`

`apiKeyPrincipal(options)` is a principal source with `kinds: ['api-key']`, `acceptance: 'explicit'`, `credentialHeaders: [options.header ?? 'x-api-key']` and `effects: { consumesQuota: true, writes: true }`. It calls `auth.api.verifyApiKey({ body: { key, configId? }, headers })` **once per request**, memoized through `r.memo`, and only on routes that accept `'api-key'` (§7.6). `headers` holds only the request's `host`, `x-forwarded-host` and `x-forwarded-proto`, those present: exactly the headers better-auth reads to resolve a dynamic base URL for a direct call (`getHostFromSource`, `getProtocolFromSource`, with `x-forwarded-*` honored only under `advanced.trustedProxyHeaders`, LEAD-V47). None of them matches a credential hook, so the key is not validated twice. v3 copied `Host` alone, so behind a proxy that better-auth is told to trust, where the public host arrives only in `X-Forwarded-Host`, every key request answered 500 while cookie traffic worked (REV3-BA:`exp3-apikey-host-only-proxy.mjs`) `[R3:BA-r3-04]`. Transports without a `Host` (RPC) declare that themselves (B20) `[R2:BA-r2-05]`. The principal never exposes the raw key.

`verifyApiKey` does not throw for validation outcomes: it returns `{ valid, error, key }`, and it reports any non-`APIError`, a storage outage included, as `INVALID_API_KEY`, the same code a missing key gets (LEAD-V20). The source maps results explicitly:

- **Telling a failure from a bad key** (`outageProbe`, default on) `[R2:SEC-r2-02]` `[R3:SEC-r3-01, BA-r3-03]`. On `INVALID_API_KEY` the source asks whether storage could have served the verification. `verifyApiKey` **writes** on every call (`claimUsageInDatabase`: guarded increments, then `update({ updatedAt })` on the key's own row, `AK/routes/verify-api-key.ts:169-221`), and turns any failure of either statement into `INVALID_API_KEY`. Two checks, in order:
  1. **Latency.** A verification that answered `INVALID_API_KEY` after more than `slowMs` (default 500 ms) is infrastructure (5xx). A key that does not exist fails on the indexed `key` lookup in about a millisecond (REV3-SEC on Postgres 15: 0 to 1 ms; LEAD-EXP-11: median 0.1 ms), while a lock or statement timeout on the key's own row needs at least the timeout (1003 ms under `lock_timeout = 1000`, REV3-SEC:`probe-apikey-row-lock.mjs`; 1002 ms for a 1000 ms stall in LEAD-EXP-11). The signal needs no knowledge of how keys are hashed or stored (R1). Its cost is a false 5xx for a genuinely unknown key while the whole service is slower than `slowMs`, which is itself an incident; a custom key hasher slower than `slowMs` needs a larger value, which the docs state.
  2. **Probe.** Otherwise the source checks that storage reads and writes at all, through the logical model name `apikey` (so the adapter applies any custom table name and field names), with a random UUID as the value of the `key` column, the indexed string column `verifyApiKey` itself looks keys up by (LEAD-V46):
     - `$context.adapter.findOne({ model: 'apikey', where: [{ field: 'key', value: <random UUID> }] })`;
     - `$context.adapter.updateMany({ model: 'apikey', where: [{ field: 'key', value: <random UUID> }], update: { updatedAt: new Date() } })`, a write that matches no row: `updateMany` returns a count and never throws for zero matches when the value fits the column (LEAD-V41), while a read-only or failing store throws. It changes no data (LEAD-EXP-9, LEAD-EXP-11); only a statement-level database trigger on the table could observe it, which the docs mention.

     v3 keyed both statements on `id`. Under better-auth's `generateId: 'serial'` the adapter converts id values with `Number()` (LEAD-V46), so a healthy Postgres rejected the random id (`invalid input syntax for type integer: "NaN"`) and every revoked, mistyped or scanned key answered 5xx (REV3-BA:`exp1-probe-id-format.mjs`); a non-UUID value fails the same way against a `uuid` column. A string compared with the hashed-key column is type-safe under every `generateId` mode and adapter (the same experiment: count 0 under default, `'serial'` and `'uuid'`), and a random UUID (36 characters) can neither equal a stored SHA-256 hash (43 base64url characters) nor, in practice, a raw key stored with `disableKeyHashing`.

  At most one probe runs per second per instance, and concurrent callers share its result, so a flood of invalid keys costs at most one read and one no-op write per second; the latency check costs nothing. A slow answer or a throwing statement turns the answer into `BetterAuthInfrastructureError` (5xx), so machine clients do not treat their keys as revoked during an outage and monitoring sees 5xx.

  **What neither check sees** (RK18): a failure confined to the key's own row that is **fast** (a row-level constraint or trigger error, a full volume where a zero-row update still succeeds but a real one does not), and keys stored only in secondary storage (`storage: 'secondary-storage'` without database fallback). Those still answer 401 `INVALID_API_KEY`. v3 claimed its probe covered "lock or statement timeouts"; it wrote a random row and saw a healthy store while the key's row was locked (SEC-r3-01). The probe is a health check, not a reimplementation of key validation: looking up the presented key's hash to prove it exists would reimplement the plugin's hashing and lookup (R1) and was not adopted. We will propose upstream that `verifyApiKey` rethrow non-`APIError` failures, which makes both checks unnecessary.

- **`references`** (default `'user'`, the plugin's default) tells the source what `referenceId` is. With `apiKey({ references: 'organization' })` it must be `'organization'` (or a function of `configId`), because the plugin object does not expose its configuration (`AK/index.ts:166-170`). Organization-owned keys get `userId: null`, so user-role policies that opt in to the kind (`permission(p, { principals: ['session', 'api-key'] })`, §8.3) deny them 403 `USER_REQUIRED` instead of mistaking an organization id for a user id. Policies that do not name the kind never see such a principal: the evaluator's gate denies it `PRINCIPAL_NOT_SUPPORTED` first (§8.1).
- **Logging.** better-auth logs `Failed to validate API key:` at ERROR for every failed verification (LEAD-V20). The docs point this out, because invalid-key traffic amplifies into ERROR logs; better-auth's `logger.level` or a log filter is the remedy (RK19).
- **`enableSessionForAPIKeys`.** With that option, better-auth itself turns a key into a user session on every endpoint that sees the header and reads the session through `sessionMiddleware`: ordinary and organization endpoints (LEAD-V21, LEAD-V38). Its admin and sensitive endpoints do **not** accept it: they re-read the session without hooks (LEAD-V36), and a key alone gets 401 there (REV2-BA:`exp6-apikey-session-admin.mjs`). The design follows the same split `[R2:BA-r2-06]`: routes with the default freshness accept the key session as a principal of kind `'session'` with no delegation, and authoritative routes (`@RequirePermission`, any `freshIdentity` requirement, `@RequireAuth({ authoritative: true })`) do not (§7.3). No `./api-key` unit takes part in this: an app that relies on key sessions typically registers only the built-in session source and never imports `./api-key`, and `advise()` is collected only from registered units and from policies that plans reference (§4). The two warnings therefore belong to the **session unit** (`better-auth:session`, §7.3), which is registered whenever such a session can reach a handler. Its `advise()` (`costHints`) emits:
  - `W_API_KEY_FULL_SESSION` when `context.hasPlugin('api-key')`: key permissions are not enforced on session routes with the default freshness (ordinary and organization requirements), while authoritative routes reject key sessions, as better-auth's admin endpoints do;
  - `W_API_KEY_SESSION_MULTIPLIER` when `context.hasPlugin('api-key')` **and** `BootAdviceContext.policies` holds a policy with `requires.presentsCredentials` (the org policies): each such check spends the key's quota again (REV-BA:`probe-apikey-policy.mjs`). The message lists those policy ids.

  **The trigger is the plugin's presence, not the option.** The plugin object is `{ id, version, $ERROR_CODES, hooks, endpoints, schema }` (`AK/index.ts:166-170`), so no unit can read `enableSessionForAPIKeys`. The runtime option `session.apiKeySessions` (§2.2.1) lets the user state it:
  - unset (default): both messages are conditional, e.g. "If any apiKey() configuration sets enableSessionForAPIKeys, an API key becomes a full user session on session routes and its permissions are not enforced there. Set session.apiKeySessions to false if none does.";
  - `false`: the user asserts that no configuration sets the option, and both are dropped. The unit cannot verify the assertion, as with `rpcTransport({ inheritAppConfig: true })` (§9.4);
  - `true`: both are worded as facts.

  Both hints recommend `apiKeyPrincipal()` plus `@RequireApiKeyPermission` for key traffic, where acceptance and delegation apply. The `./api-key` units emit neither code, so an app that also registers `apiKeyPrincipal()` sees each warning once. An instance without a session source (`session: false` and no `sessionPrincipal()`) gets neither, correctly: no key can become a session principal there.

### 8.4 Freshness (cookie cache) stance `[A][B][C]` `[R1:SEC-r1-04]`

- **Identity** honors the cookie-cache policy the user configured in better-auth on ordinary routes: 0 storage reads on a hit, staleness up to `cookieCache.maxAge` (default 300 s). That is better-auth's own performance/staleness trade-off, and it belongs in `auth.ts`.
- **Admin-grade decisions read identity authoritatively.** A requirement with `freshIdentity` (the admin `permission()`) raises its route to one `getSession` with `disableCookieCache: true` when a server-side store exists, keyed in the memo by the plan's freshness, so it is one read, not two. The read accepts only a session the get-session endpoint produced (§7.3). Both halves are what better-auth's own admin endpoints do (`adminMiddleware` uses `getAuthoritativeSessionFromCtx`, LEAD-V24, LEAD-V36). v1 claimed parity while reading identity from the cookie cache, and REV-SEC:`probe-stale-admin.mjs` showed the gap: after admin A was banned (0 session rows left), the guard still authenticated A from the cache and `userHasPermission(userId)` succeeded, while better-auth's `listUsers` answered 401. With the authoritative read, A's next request finds no session: 401. v2 still let a hook-supplied session through (an API key's mock under `enableSessionForAPIKeys`, REV2-BA:`exp6-apikey-session-admin.mjs`); since v3 it does not, and the design has no cheaper admin mode that would reopen either gap (§8.3, §17 Q16) `[R2:BA-r2-06]`.
- **Connections.** On WebSockets and GraphQL connections, a principal TTL never applies to an authoritative plan: every message or operation on such a handler reads identity again, so a banned or demoted admin is locked out on the next message, not after `principalTtlMs` (§7.2) `[R2:SEC-r2-07]`.
- **Delegated credentials.** A ban deletes sessions, not API keys. Where a route opts delegated kinds into `permission()`, the admin policy reads the owner's stored row on every request and denies an owner under an active ban (401 `USER_BANNED`), and a demotion takes effect through the stored role. "Locked out on the next request" therefore holds for every principal the design admits to admin routes, also where better-auth itself offers keys no admin access at all (§8.3) `[R3:SEC-r3-06]`.
- **Other authorization data** is read fresh wherever better-auth reads it fresh. The org policies call the org endpoints, which read member rows fresh and resolve the session as better-auth's org endpoints do, so promotions and demotions take effect immediately.
- **Session revocation** on non-admin routes is only as fresh as the cookie cache, as in better-auth. Routes that must see a revocation immediately use `@RequireAuth({ authoritative: true })`, or `session: { freshness: 'authoritative' }` globally `[C]`.

### 8.5 Plugin-prerequisite validation

1. **At compile time** (registered programs). `AdminPermissions` and `OrgPermissions` are derived from the plugin endpoints' body types, which better-auth computes from the user's access-control statements. Unknown resources or actions are compile errors. If the registered instance lacks the plugin, the argument type is `never` and the decorator cannot be called (EXP-C2 cases 3, 4, 8; EXP-A:`types/`) `[A][C]`.
2. **At boot** (B13). `BootValidator` (U13) collects `requires.plugins` from every policy the scanned plans reference and every principal source, and checks `$context.hasPlugin(id)`; the evaluator only runs at request time. That check accounts for plugins added through `init`. A missing plugin fails boot and lists the affected handlers. The reference instead feature-detected per request with `typeof auth.api.x === 'function'` and returned 403 via `console.error` (R:ba-authz §4.2 #9) `[A][B][C]`.

### 8.6 Stance on role decorators `[B][C]`

The 1.0 release has no built-in `@Roles()`. better-auth has no "has role" API and steers users to access-control permissions. A faithful role check would have to reproduce comma splitting without trimming, `defaultRole`, `adminUserIds`, `creatorRole`, and the rule that grants are not combined across roles. Otherwise it silently diverges, and the reference's `@Roles` diverges on all of these (R:ba-authz §4.2 #2–3). Permission requirements are the better-auth way and are fully typed.

§15.3 shows a short `definePolicy` recipe for teams that need role names now. Draft A recommended shipping an exact-mirror role policy as an opt-in export of `./admin`. That is a genuine product trade-off, recorded as §17 Q1.
