### 6.8 Client IP for rate limiting `[A][B][C]`

better-auth reads the client IP **only from headers**; the default is `x-forwarded-for`. With no usable IP in production, rate limiting falls back to one shared bucket per path, and sign-in is limited to 3 per 10 s for everyone (`CORE/utils/ip.ts:353-383`; `BA/api/rate-limiter/index.ts:342, 442-451`). A Web `Request` cannot carry the socket address, so the host must supply it. The design splits the job so that proxy trust is configured once, in the platform, for the whole app:

1. **The platform decides trust.** Express `req.ip` honors `app.set('trust proxy', …)`; Fastify `request.ip` honors `trustProxy`. Each platform accepts a `clientIp` override.
2. **The plugin declares the header.** `nestjs()` returns `{ options: { advanced: { ipAddress: { ipAddressHeaders: [header] } } } }` from `init()`. better-auth merges plugin options with `defu(userOptions, pluginOptions)` (LEAD-V4), so this is a construction-time _default_, not a mutation (S1). A user-configured list stays first and ours is appended. The merged options feed both the rate limiter and session IP recording (`db/internal-adapter.ts:501`).

   **Interaction with better-auth's own proxy trust** `[R2:BA-r2-04]`. When the user set no `ipAddressHeaders`, ours becomes the **only** header better-auth reads, so `X-Forwarded-For` is no longer consulted, and better-auth still applies `advanced.ipAddress.trustedProxies` to our header's value (`CORE/utils/ip.ts:311-331, 364-377`). With the platform's trust off behind a load balancer inside `trustedProxies`, the value is the balancer's address, which better-auth discards: every client resolves to no IP and shares one bucket (REV2-BA:`exp4-trustedproxies-header.mjs`: plain better-auth `203.0.113.7`, with the plugin `null`, with the platform's trust on `203.0.113.7`). With the platform's trust set, the value is the client's address and `trustedProxies` is harmless. A deployment configured the better-auth way therefore sets the platform's trust proxy when it adds `nestjs()`, or keeps better-auth's chain parsing with `nestjs({ clientIpHeader: false })`. B18 warns in production about exactly this combination.

3. **The header name is unguessable** `[R1:SEC-r1-18]`. By default `nestjs()` generates `x-nsba-ip-<32 hex chars>` once per `nestjs()` call with `globalThis.crypto.randomUUID()` (Web Crypto, so the plugin stays runtime-agnostic): one name per plugin instance, so an app with named instances (§5.5) has several. The name never leaves the process. A code path that forwards raw client headers to better-auth, such as a custom controller calling `auth.handler(new Request(url, { headers: req.headers }))` or `auth.api.signInEmail({ headers: fromNodeHeaders(req.headers) })`, therefore cannot be abused to pick a rate-limit bucket or a recorded IP. A fixed name is used only when `clientIpHeader` is set explicitly (for a trusted sidecar that calls `auth.handler` itself).
4. **Core strips and sets.** `AuthExchange` deletes any client-supplied copy of the header, and any `x-nsba-ip-*` header, then sets it from `inbound.clientIp`. For app routes the kernel does the same on `TransportCall.headers()` using `call.clientIp`, so direct `auth.api.signInEmail({ headers })` calls record the right IP. `BetterAuthService.headersFrom(req)` does it too. The name is read from the plugin's protocol object (`handle.clientIpHeader`), so the plugin is the single source of truth.
5. **Verified end to end** (with the v1 fixed name; the random name changes nothing on this path). EXP-A:`exp-e2e.mjs` covers Nest 11/12 × Express/Fastify; EXP-B:E9 and EXP-C7 ran with `NODE_ENV=production`:
   - better-auth sees the trust-proxy-resolved IP;
   - a spoofed header is ignored;
   - the third request from one IP gets 429 while another IP gets 200;
   - a user list is kept first: `["cf-connecting-ip", <our header>]`.
6. **Proxy-trust diagnostics** `[R1:SEC-r1-06]`. The two classic misconfigurations are silent. better-auth's own "shared bucket" warning fires only in the `trustedProxies` case of item 2, where the IP resolves to none; otherwise the platform always supplies a valid, wrong IP `[R2:BA-r2-04]`:
   - _trust off behind a proxy_: every client gets the proxy's IP (or, with better-auth's `trustedProxies` covering it, no IP), so one attacker sending 3 sign-ins every 10 s locks out every user;
   - _trust everything_: `req.ip` is the client-chosen left-most `X-Forwarded-For` value, so rotating it bypasses the limit.

   Platforms therefore report `proxyTrust()` (Express from `app.get('trust proxy')`, Fastify from `initialConfig.trustProxy`). The boot summary prints it. B27 warns when it is `'all'` in production. In production, the first auth-route request that carries `x-forwarded-for`, `forwarded` or `x-real-ip` while trust is `'none'` logs `W_PROXY_UNTRUSTED` once, naming the socket IP and what better-auth made of it (§6.3 step 7). Migration step 8 (§15.1) walks through the setting.

7. **Opt-out.** `nestjs({ clientIpHeader: false })`. The user then configures `advanced.ipAddress` themselves (better-auth's `trustedProxies` with `X-Forwarded-For`), and B18 warns in production if nothing is configured.

### 6.9 CORS, global prefix and versioning

**CORS stays with the host** `[A][B][C]`. better-auth emits no CORS headers and answers preflight with 404; `trustedOrigins` is its CSRF check, not CORS (R:ba-integrations §0.2). The library configures no CORS. Its job is to make sure host CORS reaches auth routes:

- **Express:** the dispatcher is registered after `enableCors()` and `app.use()`.
- **Fastify:** the auth route is a real Fastify route answered through `reply`, so `@fastify/cors` hooks and preflight apply, including on the canonical 413.

Preflight 204 with ACAO, and ACAO on 200, 302 and 413, were verified on both platforms and both majors (EXP-B:E1/E4, EXP-A:`exp-e2e`, EXP-C4/C6, LEAD-EXP-2). We never call `enableCors` ourselves: Fastify throws on double registration (#52) and Express would apply it app-wide (#69, #95).

**`betterAuthCorsOrigin(auth, { allowPatterns? })`** is a `cors` / `@fastify/cors` origin callback for teams that want CORS to follow better-auth's trusted origins `[C]` `[R1:BA-r1-11, SEC-r1-17]`:

- **The trusted set is the post-init one** (`TrustedOrigins`, U17). `(await auth.$context).trustedOrigins` is computed before plugins' `init()` run, and plugin-contributed origins (for example `expo()` adding `exp://` in development) live only in the post-init `ctx.options.trustedOrigins` (LEAD-V17). The helper therefore merges `ctx.trustedOrigins` with the post-init array. It matches through better-auth's own matcher, `ctx.isTrustedOrigin.call({ trustedOrigins: merged }, origin)`, which keeps better-auth's wildcard and custom-scheme semantics. The origin check (§7.10) uses the same resolver.
- **Exact origins only by default.** `trustedOrigins` exists for CSRF and redirect allow-listing. By default the helper allows an origin only if it equals a trusted entry that is an exact `http(s)` origin with no wildcard. Exact `http:` origins are kept because development uses `http://localhost:3000`. Wildcard and custom-scheme matches need `allowPatterns: true`. This default excludes **only** wildcard and custom-scheme entries: without it, every origin a pattern such as `https://*.vercel.app` (preview deployments) matches would gain credentialed read access wherever the helper applies.
- **Every exact trusted origin gains credentialed CORS wherever the helper applies.** The helper cannot tell why an origin is trusted. A partner origin listed exactly in `trustedOrigins` only so that it is accepted as a `callbackURL` is, to the helper, an allowed origin like any other, so it can read the responses of every route the helper covers with the user's cookies. That is why the helper belongs on the auth mount (next bullet) and app routes get their own allow-list.
- **Function-valued `trustedOrigins(request)`** cannot be evaluated without a request, and a CORS origin callback receives none, so the helper throws at first use with a hint to supply your own `origin` function `[C]`. That is safer than silently using init-time values.
- **Scope.** The docs recommend an explicit CORS allow-list for app routes, and show how to scope the helper to the auth mount: on Express `app.use(basePath, cors({ origin: betterAuthCorsOrigin(auth), credentials: true }))` when app routes need no CORS, or one `cors` middleware whose per-request options delegate picks the helper for paths under the mount and the allow-list elsewhere (§15.1 step 4); on Fastify an `@fastify/cors` `delegator` keyed on the request path. An app-wide `app.enableCors({ origin: betterAuthCorsOrigin(auth), credentials: true })` is documented only with the caveat of the previous bullet. Case `LIB-cors-helper` (§14.5) tests the helper.

**Global prefix and versioning** `[A][B][C]`. Auth routes live at better-auth's own path, outside `setGlobalPrefix` and `enableVersioning`, because raw platform routes are subject to neither (R:nest-platform §5).

- There is one source of truth: better-auth's client, OAuth callbacks and `trustedOrigins` all derive from `baseURL`/`basePath`.
- To serve auth under `/v1`, set better-auth's `basePath: '/v1/api/auth'` or put the path in `baseURL`.
- We read `ApplicationConfig.getGlobalPrefix()`, a public API, only for the boot summary. We never mutate `ApplicationConfig`, because a later `setGlobalPrefix(p, opts)` would overwrite it (R:nest-platform §2.5).
- This fixes the reference's `/api/api/auth` regressions (PR #80) by construction.
