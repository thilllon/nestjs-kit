## 14. Testing strategy

### 14.1 Conformance kits (the LSP proof, reusable by third parties) `[A][B][C]`

The kits live in `nestjs-slightly-better-auth/testing/conformance`. They are **runner-agnostic**: each returns `ConformanceCase[]`, and `runConformance(cases, { describe, it })` registers them with vitest, jest or `node:test`. Assertions use `node:assert/strict`. The same kits run in our CI for every built-in unit, which makes "Express and Fastify behave the same" a tested property rather than a claim. Every kit builds its better-auth instances with `advanced.disableOriginCheck: false` set explicitly, so the origin cases test what they claim under any runner and environment: better-auth's `isTest()` is true under vitest whatever `NODE_ENV` says (vitest sets `TEST=true`, LEAD-V48), and would otherwise switch off the origin rules the kits test, for the kits' own runs and for third parties running them `[R3:SEC-r3-07]`.

Each HTTP case boots a real Nest app, under both `NestFactory.create` and `Test.createTestingModule().createNestApplication()`. It uses a real better-auth instance (memory adapter) that includes `conformanceProbePlugin()` (and the explicit `disableOriginCheck: false` above). The probe plugin provides these endpoints:

- `/probe/echo-raw`: `disableBody` + `ctx.request.text()`, echoing the received bytes and headers;
- `/probe/multi-cookie`: three cookies;
- `/probe/redirect`: 302 with a cookie;
- `/probe/stream`: three chunks with delays;
- `/probe/html`;
- `/probe/put`, `/probe/patch`, `/probe/delete`;
- `/probe/url`: echoes `request.url`;
- `/probe/ip`: echoes `getIP(request)`;
- `/probe/throw-api-error`, `/probe/throw-error`.

The probe plugin also contributes a trusted origin through `init()` (`https://probe-plugin.example`), so trusted-origin cases exercise the post-init set (LEAD-V17). The kit also adds a throwing `around` interceptor, an app controller `/app/echo` that returns `{ body, rawBody }`, and a global `APP_FILTER` that records what it sees.

### 14.3 Cookie-session end-to-end `[A][B][C]`

The current repo tests only bearer tokens (R:current-repo). This suite uses a real cookie jar:

1. Sign up and sign in over JSON **and** `application/x-www-form-urlencoded`, then call a protected controller route. With `session.updateAge: 0`, the app-route response carries the refreshed `session_token` `Set-Cookie` with a new max-age, the DB expiry matches, and there is no `cache-control`.
2. With `cookieCache.enabled`, the first guarded response carries `session_data`.
3. Stateless mode (no database): the refresh-cache branch re-issues cookies over HTTP. Over WS, GraphQL subscriptions and RPC nothing is issued.
4. A GraphQL query over HTTP refreshes cookies (Apollo on Express and on Fastify, Mercurius). Subscription and WS messages do not move the DB expiry.
5. Direct calls:
   - a controller with `@ForwardAuthCookies()` calling `auth.api.signInEmail` / `signOut` sets or clears the caller's cookies through the plugin bridge;
   - without it, the same calls leave the response's cookies untouched;
   - an admin handler calling `signUpEmail` for another user never changes the admin's cookies;
   - the same call in a WS handler does not refresh.
6. An expired cookie gets 401 on required routes, with cleanup cookies forwarded.
7. API-key principal:
   - an invalid key on a `@Public()` route is never resolved (200);
   - on a route that does not accept keys it is never verified (usage counter unchanged; 401 without a cookie);
   - on a required route that accepts keys it gets 401 with `reason: INVALID_API_KEY`;
   - on `@OptionalAuth()` it gets 401, never anonymous;
   - a rate-limited key gets 429 with `Retry-After`;
   - `verifyApiKey` is called once per request (usage counter).

### 14.4 Security end-to-end (origin check ON) `[A][B][C]`

better-auth disables origin/CSRF checks under `isTest()` (`NODE_ENV=test` or a truthy `TEST`, which vitest always sets, LEAD-V48) and falls back to IP 127.0.0.1 in dev/test (R:ba-core §3.3, §3.5). This suite therefore runs with `NODE_ENV=production`, sets `advanced.disableOriginCheck: false` explicitly (the environment variable alone does not survive vitest's `TEST=true`), uses a production-grade secret, and sets a static `baseURL` except where a case says otherwise `[R3:SEC-r3-07]`. Cases:

- **Auth routes:**
  - a cross-origin POST with a session cookie → 403 `INVALID_ORIGIN`;

### 14.7 Architecture fitness tests `[B]`

- `overrideAuthGuard` calls both `overrideProvider(BetterAuthGuard)` (the `APP_GUARD` alias) and `overrideGuard(BetterAuthGuard)` (the injectables `@UseBetterAuth()` creates per host module), and does the same for the scope interceptor. Either one alone misses a set of call sites (`core/injector/module.js:344-356`). `overridePrincipal` remains the preferred tool, because it keeps the real guard, acceptance, origin check and policies `[R1:NEST-r1-08]`.
- **Policies under `overridePrincipal`** `[R2:NEST-r2-15]` `[R4:NEST-r4-05]`. Policies that decide from the principal alone (`apiKeyPermission`, `freshSession`, most third-party policies) work unchanged. The admin policy needs real data: `userHasPermission` reads the user stored under the fixed principal's `userId`, so a fixed principal without a stored row answers 401 `USER_NOT_FOUND`, and a seeded user is judged by its stored role, whatever the fixed session's `user.role` says; seed the user with `testUtils()` or stub the decision with `overrideDecisions`. v4's list still named the admin policy among those that decide from the principal alone. The organization policies call better-auth with the request's headers, which carry no session under a fixed principal, so better-auth answers 401. That 401 is the generic one. A fixed principal whose `source` is not a registered session-backed source is answered 401 at once; one that copies the session source's id gets the re-classification read (`ResolutionRequest.reclassify`, §8.1), which `overridePrincipal`'s resolver answers `absent`, because the headers better-auth read carry no session, while it answers every other resolution with the fixed principal `[R3:BA-r3-01]`. The route therefore denies 401 with better-auth's code as `reason`. Answering the fixed principal there would turn every such test into a 5xx infrastructure error. Organization requirements need a real session (`authHeadersFor`) or `overrideDecisions`. Tests of the re-classification itself use the real resolver (`Z-policy-session-lost`). `overrideDecisions(builder, decide)` overrides the `POLICY_INVOKER` provider with a wrapper that asks `decide(policy.id, params, principal)` first and runs the real policy when it returns `undefined`; acceptance, the delegation gate, the origin check and the decision memo still run. v2 had no seam: policies travel by reference in metadata, which `TestingModuleBuilder` cannot replace.
- **Where a replaced guard publishes the principal** `[R1:NEST-r1-08]`. A stand-in guard has no plan and no transport, so it cannot record readings the way the real guard does (§7.8), and WebSocket messages have no lineage at all. `stampPrincipal()` and the `{ principal }` stand-in therefore write a **test stamp** (§7.8 item 4): a record on the invocation's args array and its object elements, accepted only by a reader whose args have the same elements. Guards and interceptors of a WS message, GraphQL field or RPC message share the args array itself, and HTTP guards and interceptors share its elements (LEAD-V7, LEAD-V34). Both the real scope interceptor, when its lookup finds no recorded reading for the instance (§7.8 item 4), and the stand-in interceptor copy the stamp into the scope they open, which is where the param decorators and `BetterAuthService` look first. The stand-in interceptor always opens that scope, on every transport.
- **Cases** (this repository's suite, `LIB-` ids, §14.5), each on a socket.io gateway and a ws gateway that carry `@UseBetterAuth()` with a handler reading `@CurrentSession()` and `BetterAuthService.getPrincipal()`, and on an HTTP controller with `globalGuard: true`:
  - `LIB-testing-override-principal`: `overrideAuthGuard(builder, { principal })` delivers the principal to both readers, performs no better-auth call (adapter call counter), and concurrent messages on one socket each see the principal their own invocation stamped;
  - `LIB-testing-stamp-mock-guard`: a hand-written guard installed with `overrideAuthGuard(builder, new MockGuard())` that calls `stampPrincipal(ctx, user)` boots with `globalGuard: true` (B16 counts the replaced global guard by identity) and delivers `user` to both readers `[R4:NEST-r4-02]`; the same guard without the call makes `@CurrentSession()` throw `NO_AUTH_RESULT` with the generic message (§7.8 item 5);
  - `LIB-testing-override-decisions`: under `overridePrincipal`, a `@RequireOrgPermission` route is allowed by a `decide` that answers `allow()` for the organization policy and denied 401 without it (the re-classification read answers `absent`, so never a 5xx), and a `decide` that returns `undefined` runs the real admin policy, which answers 401 `USER_NOT_FOUND` for a fixed principal without a stored user, never a 5xx, and the stored role's verdict for a seeded one `[R2:NEST-r2-15]` `[R4:NEST-r4-05]`.
- `initTestApp` closes a previous test app still bound to the same better-auth instance before initializing, and a failed `init()` leaves a binding the next app takes over with a warning (B06). Apps built in `beforeEach` therefore work with exclusive binding `[R1:SEC-r1-15]`.
