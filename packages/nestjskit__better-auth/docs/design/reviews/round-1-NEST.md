# Round 1 review: NEST (NestJS correctness, packaging, SOLID)

Input: `design-v1.md`. Verdict: **reject**.

## Summary

I reviewed design v1 through the NestJS-correctness, packaging and SOLID lens and ran experiments on Nest 11.1.17 and 12.0.1 (in tmp-review-NEST-r1/). The design is strong in most places: tokens and metadata keys use Symbol.for, the module is hand-written instead of using ConfigurableModuleBuilder, the guard never returns false, errors are mapped per transport, and HTTP denials and GraphQL denials both use IntrinsicException subclasses. I still found 1 blocker and 6 majors.

The blocker is in authorization. Decisions are memoized per request by requirement-object identity, but on GraphQL (and on WS when principalTtlMs > 0) that memo key spans several handler invocations. Two aliased root fields asking about different orgs therefore share one allow, which is an authorization bypass.

Three majors come from wrong lifecycle assumptions, each confirmed by experiment:

- HttpAdapterHost.init$ does fire for createMicroservice and createApplicationContext, with a null adapter, so the MountCoordinator crashes or reports NO_PLATFORM on standalone microservices and application contexts.
- Under NestFactory the replayed init$ callback runs inside the MountCoordinator constructor, before any forRoot kernel that waits on an async dependency has been built. Platform selection fails in production, but under @nestjs/testing everything works, so CI passes.
- On Fastify, the auth plugin registered with `await` in onModuleInit captures Fastify's default error handler. Infrastructure errors skip Nest's global filters and are never logged, and the 413 body differs from the Express one. The research experiment cited as evidence registered the plugin without await, so it does not cover this case.

The other three majors:

- Two fail-open coverage gaps are only documented. Hybrid RPC without inheritAppConfig and GraphQL @ResolveField handlers both run with no guard, whereas the equivalent WebSocket gap fails boot.
- Core still branches on or names extension concepts (a `principal.kind !== 'session'` check, the plugin-name hints in B21, the apolloTransport hint in the no-transport error, and the RPC reminder in B22). This breaks R4 and the design's own literal-ban fitness test.

The minors cover:

- testing overrides that miss @UseBetterAuth() sites;
- platform and transport lists de-duplicated by id;
- a name clash between @Session() and @nestjs/common's Session;
- an overstated claim that the global core module always initializes first;
- no way for extensions to export injectables (WsConnectionAuth is never provided);
- a WebSocket coverage probe that depends on an unrelated API.

## Findings

### NEST-r1-01 (blocker): Per-request decision memo keyed by requirement identity lets one GraphQL field's (or one WS message's) allow authorize another with different inputs

- **Section:** §8.1 Memoization; §7.2 memo-key table; §8.3 ActiveOrganizationId/ActiveMemberRole; §9.2; §9.3 principalTtlMs
- **Failure scenario:** Resolver: `@Query(() => [Project]) @RequireOrgPermission({ project: ['read'] }, { organization: fromParam('orgId') }) projects(@Args('orgId') orgId: string)`. A member of org_A only sends `query { a: projects(orgId: "org_A") { id } b: projects(orgId: "org_B") { id } }`. The guard runs once per root field, and both runs share call.key, which is the HTTP request (by design, so the principal is resolved once). The requirement object is created once, when the decorator is evaluated. The per-request decision memo ('by requirement object identity') stores field a's promise before it settles, and field b gets the same allow. auth.api.hasPermission is never called for org_B, and the user reads org_B's projects. Inside field b, @ActiveOrganizationId() returns org_A. The same bypass happens with Apollo batched HTTP operations, and with any fromParam/fromHeader ref. On WebSockets with principalTtlMs > 0 the memo key is the socket (§7.2 table). A socket that sent `join {orgId:A}` can then `join {orgId:B}` using the cached allow for the life of the connection.
- **Evidence:** Design §8.1 (line ~2171): 'Decisions are memoized per request by requirement object identity, so a requirement shared by several GraphQL root fields ... is evaluated once'. §7.2 table (lines 1973-1979): the GraphQL query key is 'the underlying HTTP request key, shared with the HTTP transport', and the WS key is 'the socket when principalTtlMs > 0'. §3.1 U3: RequestState holds the 'decision memo'. §8.3 (line ~2218): fromParam reads 'a route param, GraphQL arg, or WS/RPC payload field'. §8.3 (line ~2223): org id and member role are 'memoized per request'. T2/ADR-10: '3 root fields → 1 resolution'.
- **Suggested fix:** Separate the two memo scopes. Keep the principal memo on call.key (logical request or connection). Key decisions by a per-handler-invocation identity supplied by the transport, for example a new TransportCall.invocation: the HTTP req; for GraphQL the field's info or args object; for WS the per-message args; for RPC the context. Never key decisions by a connection. Alternatively, key them by (requirement, resolved inputs) through an optional policy cacheKey(params, ctx). Built-in policies should dedupe their I/O through ctx.memo keyed by concrete inputs (orgId + permissions), so repeated identical checks stay cheap. Make @ActiveOrganizationId() and @ActiveMemberRole() per invocation. Add conformance cases: two aliased root fields, batched operations with different org args, and a WS TTL socket joining two orgs must each yield independent decisions.

### NEST-r1-02 (major): init$ does fire (with a null adapter) for createMicroservice and createApplicationContext, so the MountCoordinator breaks D2 standalone RPC and worker contexts

- **Section:** §4.1.3 last bullet; §5.7 Lifecycle step 1; §6.1
- **Failure scenario:** `NestFactory.createMicroservice(AppModule, { transport: Transport.TCP })`, or `NestFactory.createApplicationContext(AppModule)` for a worker or CLI. AppModule contains `BetterAuthModule.forRoot({ auth, platforms: [expressPlatform()], transports: [rpcTransport()] })`. init$ is a ReplaySubject, so it replays synchronously inside the MountCoordinator constructor with httpAdapter === null. The callback 'selects the platform', calling expressPlatform().supports(null), which throws a TypeError. Thrown inside an RxJS subscriber, it is re-thrown asynchronously as an uncaught exception and kills the process. If the error is caught instead, zero platforms match and B08 NO_PLATFORM fails boot. Under @nestjs/testing, Test.createNestMicroservice() emits nothing, so tests pass while production microservices cannot start.
- **Evidence:** EXP tmp-review-NEST-r1/exp1-init-emission.cjs, Nest 11.1.17 and 12.0.1. createApplicationContext and createMicroservice gave `[{"adapter":"null"},{"supportsThrows":"Cannot read properties of null (reading 'getType')"}]`. Test.compile and Test.createNestMicroservice gave `[]`. Source: nest-factory.js initialize() calls container.setHttpAdapter(httpServer) with the default httpServer = null (11.1.17 L94-105; 12.0.1 same code). The HttpAdapterHost setter calls `_init$.next(); _init$.complete()` (helpers/http-adapter-host.js). The design says 'Apps without an HTTP adapter (createMicroservice, createApplicationContext) never emit init$' (line 1027) and 'No adapter ... means no emission' (§5.7).
- **Suggested fix:** In the init$ callback, and in B08's 'app has an HTTP adapter' test, treat httpAdapterHost.httpAdapter == null as 'no HTTP adapter'. Never call supports, prepare or mount with null, and set TransportKit.http = null. Correct §4.1.3 and §5.7. Add matrix and conformance cases that boot createMicroservice and createApplicationContext through NestFactory, where the emission actually happens, not only through @nestjs/testing.

### NEST-r1-03 (major): The platform select and prepare step in the init$ replay runs before async forRootAsync kernels exist under NestFactory: breaks in production, passes in tests

- **Section:** §5.7 Lifecycle step 1; §3.1 U4/U14/U15 and the BetterAuthCoreModule paragraph; §6.1; invariant H9
- **Failure scenario:** §5.1 shape (3): `forRootAsync({ platforms: [expressPlatform()], imports: [PrismaModule], inject: [PrismaService], useFactory: (p) => ({ auth: createAuth(p) }) })`, where PrismaService (or a ConfigService or secrets lookup) resolves asynchronously. Nest instantiates modules concurrently, so the static global core module's MountCoordinator can be constructed while the forRoot InstanceKernel is still awaiting that dependency. The kernel carries the instance, options and platforms (§3.1). Under NestFactory, init$ replays synchronously inside the MountCoordinator constructor, so the callback sees no kernels and no platforms. Either B08 NO_PLATFORM fails boot, or Express phase A is never installed. In that case body-parser consumes auth-route bodies: H3/H4 break and raw-signature endpoints (Stripe, SAML) fail. Under @nestjs/testing, init$ fires later in createNestApplication(), after every provider exists, so CI stays green.
- **Evidence:** EXP tmp-review-NEST-r1/exp3b-core-module-order-async.cjs: a static @Global core module whose MountCoordinator subscribes to init$ in its constructor, plus two forRoot dynamic modules whose kernel factory injects an async options provider. On 11.1.17 and 12.0.1, NestFactory gave `["init$ callback sees kernels=[] adapter=yes","kernel default registered","kernel admin registered"]`, while Testing registered both kernels first. With synchronous factories (exp3) the order happened to be correct, which shows the result depends on scheduling. Source: @nestjs/core injector/instance-loader.js:38-47 creates instances with Promise.all across all modules.
- **Suggested fix:** Remove the dependency on construction order. MountCoordinator records the adapter from init$, and platform registries register themselves with the coordinator from their own factories. Those factories must not depend on the async runtime options; state that in §5.2 and make it a boot error. Call prepare() exactly once, when both the adapter and the platforms are known, whichever arrives last. Both events happen before NestFactory.create() resolves and before init() registers the body parsers, and under testing before createNestApplication() returns. Add an H9 conformance case with an async forRootAsync factory booted through NestFactory.

### NEST-r1-04 (major): Fastify auth routes registered with `await instance.register()` in onModuleInit capture Fastify's default error handler, bypassing Nest filters and logging

- **Section:** §6.1 Fastify row; §6.4.2; §6.6; §6.10; invariants H4/H8; ADR-04
- **Failure scenario:** Fastify app. The database is down, so auth.handler throws a non-APIError. AuthExchange rejects with BetterAuthInfrastructureError inside the encapsulated plugin. That plugin was loaded synchronously by `await instance.register(...)` in onModuleInit. Nest only calls setErrorHandler later, in registerRouterHooks, so the plugin's route context captured Fastify's default error handler. Result: Fastify's own 500 body, no global APP_FILTER runs (Sentry, custom formatting), and nothing is logged, because Nest creates Fastify with logging off. The Fastify body-limit 413 goes through the same default handler, so it returns Fastify's FST_ERR_CTP_BODY_TOO_LARGE body instead of binding.payloadTooLarge(). H4 requires the same 413 on every platform.
- **Evidence:** EXP tmp-review-NEST-r1/exp2-fastify-error.cjs (11.1.17 and 12.0.1, both NestFactory and Testing): `/api/auth/x 500 {"statusCode":500,"error":"Internal Server Error","message":"infra-from-auth-route"} filterSaw= []`. In the same run, a root route registered in the same onModuleInit and a controller route both reached the APP_FILTER (status 599). exp2b (no filter, Nest logger on): Nest's ExceptionsHandler logged the root-route and controller errors and printed nothing for the auth route. In both majors init() calls callInitHook before registerRouterHooks (12.0.1 nest-application.js:103-124; 11.1.17 :93-104). The cited research experiment (tmp-nest-platform/exp11/exp9-errors.js) registers its child plugin without await, so the plugin loads at ready(), after Nest's handler is set. It does not cover the awaited registration the design specifies.
- **Suggested fix:** Inside the Fastify platform's encapsulated scope, set a child error handler that delegates at request time: `scope.setErrorHandler((err, req, reply) => err.code === 'FST_ERR_CTP_BODY_TOO_LARGE' ? sendWebResponse(reply, binding.payloadTooLarge(), false) : root.errorHandler(err, req, reply))`. The root's current handler is Nest's by then. Alternatively, keep route contexts unresolved until ready(). Add Fastify conformance cases for H8 (the global filter sees the error and it is logged) and H4 (the 413 body equals payloadTooLarge()) using the awaited registration.

### NEST-r1-05 (major): Hybrid RPC without inheritAppConfig leaves message handlers silently unguarded (fail-open), unlike the WS equivalent, which fails boot

- **Section:** §9.4 Guard registration; §9.5; §5.4 B22
- **Failure scenario:** Hybrid app on Nest 11 or 12 calls `app.connectMicroservice({ transport: Transport.NATS, options })` without `{ inheritAppConfig: true }`, which is Nest's default. It registers `transports: [rpcTransport()]` and a handler `@MessagePattern('billing.refund') @RequirePermission({ billing: ['refund'] }) refund()`. Nest gives that microservice a fresh ApplicationConfig, so the APP_GUARD never runs for it. Any NATS publisher can invoke refund with no credentials, and boot only prints an info line (B22). For the analogous WS gap the design fails boot (B16, ADR-18: 'secure by default').
- **Evidence:** @nestjs/core 11.1.17 nest-application.js:125-131 and 12.0.1 :207-213: `const applicationConfig = inheritAppConfig ? this.config : new ApplicationConfig();`. Design §9.4: 'Hybrid apps apply it only with ... inheritAppConfig ... The boot summary prints this reminder'. §5.4 B22 is info level.
- **Suggested fix:** Give rpcTransport() a validate() coverage check that mirrors gatewayCoverage. When the app has an HTTP adapter (so it can be hybrid) and message or event handlers exist (PATTERN_METADATA from @nestjs/microservices), fail boot by default for handlers with neither @UseBetterAuth() nor @Public() at class or method level. Skip the check when the user asserts `rpcTransport({ hybrid: 'inheritAppConfig' })`, and offer an 'error' | 'warn' | 'off' setting. Assert this in the Hybrid RPC matrix job.

### NEST-r1-06 (major): Requirements that apply to GraphQL @ResolveField handlers are silently not enforced under default GraphQL options

- **Section:** §9.2 Guard coverage; §9.0; §5.4 (no check)
- **Failure scenario:** `@Resolver(() => User) @RequirePermission({ user: ['read-email'] }) class UserResolver { @Query(() => User) me() {...} @ResolveField() email(@Parent() u) {...} }` with default GqlModuleOptions. A less-protected root query in another resolver, such as `project { owner { email } }`, returns a User. The `email` field resolver then runs with no guard, so neither the class-level requirement nor any method-level requirement is evaluated and the email leaks. The same happens for @RequireOrgPermission placed directly on a @ResolveField. Boot passes silently; the design only documents the limitation.
- **Evidence:** @nestjs/graphql 13.2.4 dist/services/resolvers-explorer.service.js:90-104: property resolvers get `guards: fieldResolverEnhancers.includes('guards')`, and fieldResolverEnhancers defaults to []. Design §9.2: 'Requirements on field resolvers are enforced only then, and the docs say so.' The design treats the analogous WS gap as a boot error (B16).
- **Suggested fix:** In the validate() of apolloTransport and mercuriusTransport, read GqlModuleOptions (token 'GqlModuleOptions', exported as GRAPHQL_MODULE_OPTIONS). If 'guards' is missing from fieldResolverEnhancers, fail boot (default 'error', configurable) for every field resolver (RESOLVER_PROPERTY_METADATA 'graphql:resolve_property') whose effective plan, from its method or inherited class metadata, carries requirements or reads the session. The message should suggest `fieldResolverEnhancers: ['guards', 'interceptors']` or `@Public()`. Once the fix is in, per-invocation decisions (NEST-r1-01) make built-in policies dedupe their I/O through ctx.memo.

### NEST-r1-07 (major): Core still branches on or names extension concepts, which violates R4 and the design's own literal-ban fitness test

- **Section:** §7.1 guard flow; §4.2.3; §5.4 B21/B22; §4.3.1 AuthHandle.userIdOf; §2.2.2 RoutePlan.readsSession; §3.2 rule 5; §14.7
- **Failure scenario:** (a) BetterAuthGuard (core unit U10) runs `plan.readsSession && principal.kind !== 'session'`, an if on a principal-kind literal. A third-party principal kind that also carries a better-auth session (say an impersonation or OAuth-session kind) cannot satisfy @Session() without editing core. (b) The NO_TRANSPORT message ('add apolloTransport() from nestjs-slightly-better-auth/graphql') needs a context-type-to-package table in core, so a new transport (tRPC) cannot get a hint without a core edit. (c) B21 in BootValidator (core unit U13) inspects the options of the jwt, bearer and api-key plugins, so adding a hint for a new plugin means editing core. (d) B22 prints the hybrid reminder 'when the RPC transport is registered', so core must recognize RPC. Every one of these needs a literal that §3.2 rule 5 and §14.7 ban ('session', 'graphql', 'api-key', 'rpc'). Implemented as written, the architecture test fails; otherwise these features get silently dropped during implementation.
- **Evidence:** Design §7.1 (line ~1954): `plan.readsSession && principal.kind !== 'session' → throw ...`. §4.2.3 (line ~1198): the NO_TRANSPORT message naming apolloTransport and the ./graphql subpath. §5.4 B21 and B22 rows. §3.2 rule 5 and §14.7 literal ban. R4: 'Core must not switch/if on platform names, transport names or policy kinds'.
- **Suggested fix:** (a) Have @Session() and @CurrentUser() write a data value into plan metadata, such as `requiresPrincipal: SESSION_PRINCIPAL_KIND` exported by the session-source unit (E1). The guard then compares principal.kind with plan.requiredKind. Move userIdOf out of AuthHandle into the session source's options. (b) Make NO_TRANSPORT generic: the context type, the registered transport ids and a docs link. (c, d) Add an optional `advise?(ctx): BootAdvice[]` member to PrincipalSource, AuthorizationPolicy and AuthTransport, or a small BootAdvisor extension point, so ./api-key, the RPC transport and others contribute their own hints and reminders.

### NEST-r1-08 (minor): overrideAuthGuard misses @UseBetterAuth() sites, and a replaced guard makes @Session() throw

- **Section:** §14.8 overrideAuthGuard; §5.7 'Guard registration and overriding'; §7.8
- **Failure scenario:** A Nest 11 gateway carrying @UseBetterAuth() (mandatory under B16), or an app with globalGuard: false plus @UseBetterAuth(). `overrideAuthGuard(builder, { canActivate: () => true })` uses overrideProvider (§5.7), which replaces only the provider behind APP_GUARD. @UseGuards(BetterAuthGuard) creates a separate injectable per host module, and only overrideGuard replaces those, so the real guard still runs. The reverse also holds: the usual `.overrideGuard(BetterAuthGuard)` does not replace the APP_GUARD alias. Where the override does take effect, every handler with @Session() or @CurrentUser() throws BetterAuthConfigurationError ('BetterAuthGuard did not run'), because a stand-in guard has no way to publish a resolution.
- **Evidence:** @nestjs/core injector/module.js:344-356: replace() with isProvider touches providers only, and without it touches injectables only. Design §7.8 step 3 (the throw) and §14.8 ('works because APP_GUARD uses useExisting').
- **Suggested fix:** Have overrideAuthGuard call both overrideProvider and overrideGuard, and do the same for the scope interceptor. Let it take an optional principal and stamp the resolution, or export a public stampPrincipal(ctx, principal) for hand-written mocks. Document overridePrincipal as the preferred tool, and add a consumer-testing case that covers @UseBetterAuth() sites.

### NEST-r1-09 (minor): Merging every instance's platforms and transports and de-duplicating by id silently drops configured units

- **Section:** §5.5 'Platforms and transports are app-wide'; §4.1.1 id
- **Failure scenario:** The default forRoot lists `socketIoTransport({ credentials: (c) => ({ authorization: 'Bearer ' + c.handshake.auth.token }) })` and the admin forRoot lists `socketIoTransport()`. Both have the same id, so one is dropped silently. Depending on the order of the union, bearer-token sockets start getting 401. Two unrelated third-party transports that pick the same id also lose one without any diagnostic. This contradicts §4.1.1, which says core 'prints it and never compares it'.
- **Evidence:** Design §5.5: 'the union of every instance's platforms and transports, de-duplicated by id'. §4.1.1: `id` is 'Diagnostic id ... Core prints it and never compares it'.
- **Suggested fix:** Declare platforms and transports once per app: only on the default instance or in one app-level option, rejected on named instances. Alternatively, dedupe by reference identity and fail boot when two non-identical refs share an id.

### NEST-r1-10 (minor): @Session() clashes with the Session export of @nestjs/common; an auto-import mistake silently injects req.session

- **Section:** §2.2.3 Parameters; ADR-24
- **Failure scenario:** The controller file already imports from '@nestjs/common', and IDE auto-import adds `Session` to that import. `@Session() s: AuthSession` still compiles, because any annotation compiles (§11.1 #4). It injects req.session instead, which is undefined without express-session or @fastify/session. readsSession is never set, so B15 and the SESSION_REQUIRED checks silently do not apply, and the handler fails at runtime.
- **Evidence:** @nestjs/common exports a `Session` route-param decorator. ADR-24 renames things specifically to avoid the AuthGuard and AuthModule collisions but keeps `Session`.
- **Suggested fix:** Rename it to @CurrentSession(), matching @CurrentUser() and @CurrentPrincipal(). Or keep the name and have the boot scan warn when a guarded handler uses Nest's SESSION route-param type. See userDecisions.

### NEST-r1-11 (minor): The 'global core module initializes first' guarantee does not cover other global modules, so seeding can run before hooks are bound

- **Section:** §5.4 intro; §10.3 intro; §10.6
- **Failure scenario:** A `@Global() DatabaseModule` whose `SeedService.onModuleInit()` calls `auth.api.signUpEmail(...)` is imported before BetterAuthModule.forRoot. All global modules get distance MAX_VALUE and run in insertion order, so the seeding runs before HookBinder binds. The plugin is inert until binding, so @BeforeDatabase('user.create') normalization and audit hooks are silently skipped for the seeded users.
- **Evidence:** @nestjs/core injector/container.js:104-109 sets distance = Number.MAX_VALUE for every global module. nest-application-context.js getModulesToTriggerHooksOn uses a stable sort by distance, so equal-distance modules keep insertion order.
- **Suggested fix:** Narrow the claim to non-global modules. Have the plugin count dispatches that happen before bind, and have BootValidator warn ('N better-auth calls ran before Nest hooks were bound'). Document onApplicationBootstrap as the place for seeding.

### NEST-r1-12 (minor): Extension units cannot export injectables, and nothing provides WsConnectionAuth

- **Section:** §2.2.1 ExtensionDefinition; §2.2.13 WsConnectionAuth; §9.3 item 5
- **Failure scenario:** A user gateway declares `constructor(@Inject(WsConnectionAuth) wsAuth)`, as shown in §9.3. No module provides or exports WsConnectionAuth. ExtensionDefinition has only use, providers and imports, with no exports, so even if socketIoTransport's definition added the class it would stay private to the forRoot module. Boot fails with UnknownDependenciesException. WsConnectionAuth also takes no instance argument for named instances, and it has to reuse the transport's credential mapping, but nothing specifies how. Third-party extensions hit the same wall when they want to expose helper services, which is an open/closed gap.
- **Evidence:** Design §2.2.1 ExtensionDefinition shape (lines 295-303); §2.2.13; §9.3 constructor example.
- **Suggested fix:** Add `exports?: readonly InjectionToken[]` to ExtensionDefinition; the forRoot module re-exports those tokens, globally when isGlobal. Provide WsConnectionAuth from the socket.io and ws definitions under a Symbol.for token alias, with an instance option.

### NEST-r1-13 (minor): The WS coverage probe keys on an unrelated HTTP-adapter API, so it can fail open

- **Section:** §9.3 Design consequences item 3; RK9; ADR-18
- **Failure scenario:** Suppose a future Nest 11.x release backports AbstractHttpAdapter.prototype.mapException (an HTTP-adapter feature) without changing the WS context creators. The probe then reports 'global enhancers reach gateways', B16 is skipped, and Nest 11 gateways without @UseBetterAuth() run unguarded. The design fails closed only when the probe is inconclusive, not when it gives a false positive. Nest 11.2.0 through 11.2.3 are already published and were not part of the verified set (11.0.0 and 11.1.17).
- **Evidence:** @nestjs/websockets 11.1.17 and 11.2.3 socket-module.js have getContextCreator(container), with no config, so no global enhancers reach gateways; 12.0.1 has getContextCreator(container, config, exceptionFiltersContext). @nestjs/core 11.2.3 adapters/http-adapter.js has no mapException today, but that API has nothing to do with the WS code path. npm dist: 11.2.0-11.2.3 are published.
- **Suggested fix:** Probe the fact that actually matters. For example, read @nestjs/websockets' package.json through its resolved entry path and treat major 12 or later as covered, or check the arity of SocketModule's context creator. Alternatively, require explicit coverage on both majors. Add the 11.2.x line to the matrix.

## Proposed user decisions

- **Keep the @Session() decorator name, which @thallesp users know but which clashes with @nestjs/common's Session, or rename it as part of the D3 clean break?**
  - Option: Keep @Session() and add a boot warning when a guarded handler uses Nest's own Session route-param
  - Option: Rename it to @CurrentSession(), matching @CurrentUser() and @CurrentPrincipal(), and note the rename in the migration guide
  - Recommendation: Rename to @CurrentSession(). It removes a silent wrong-decorator trap in files that already import from @nestjs/common. The migration cost is a single rename.

- **How strict should boot be about surfaces the global guard cannot reach (hybrid RPC without inheritAppConfig, GraphQL field resolvers without fieldResolverEnhancers: ['guards'])?**
  - Option: Fail boot by default ('error'), with an explicit per-transport opt-out or assertion, consistent with the WS gatewayCoverage check
  - Option: Warn by default and let users opt into 'error'
  - Recommendation: Fail boot by default. The design already chose fail-closed for Nest 11 gateways, and both surfaces otherwise silently skip every requirement.

- **With named instances, where are HTTP platforms and transports declared?**
  - Option: Once, on the default instance's forRoot or in a single app-level option; named instances cannot declare them
  - Option: On every forRoot, merged app-wide, de-duplicated by reference, with a boot error when ids collide
  - Recommendation: Declare them once. There is exactly one HTTP adapter and one transport registry per app, so per-instance lists only create merge ambiguity.
