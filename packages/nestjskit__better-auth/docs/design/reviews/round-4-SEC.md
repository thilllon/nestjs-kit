# Round 4 review: SEC (security / SRE)

Input: `design-v4.md`. Verdict: **reject**.

Experiments: `scratchpad/tmp-r4-review-SEC/`. better-auth 1.7.4 and @nestjs/core 11.1.17 (copied from the round-3 install); `gql/`: @nestjs/common, core and platform-express 11.1.17, @nestjs/graphql 13.2.4, @nestjs/apollo 13.2.4, @apollo/server 4.13.0; package sources of @nestjs/bullmq 12.0.0, @nestjs/schedule 12.0.2 and @nestjs/apollo 13.2.4 (`pkgs/`). Probe outputs are saved as `*.out` next to each script.

## Summary

v4 closes every round-3 SEC finding. The latency signal stops the row-lock 401 (SEC-r3-01, and with it the long-open SEC-r2-02). Dynamic `baseURL` configs no longer trust a leg origin built from `X-Forwarded-Host` (SEC-r3-02). Native clients get boot advice and a WARN line (SEC-r3-03). The per-call-site forwarding switch is gone (SEC-r3-04). An unrecognized GraphQL context fails closed (SEC-r3-05). A banned owner's key is denied on the delegated admin path (SEC-r3-06). Environment detection fails closed and reports effective flags (SEC-r3-07). Logs and policy I/O are bounded per request (SEC-r3-08). The fixes are proportionate and introduce no contradiction I could find, with the two gaps in SEC-r3-03's and SEC-r3-08's fixes listed below as minors.

Three new majors, each reproduced:

1. **SEC-r4-01, shutdown (probe).** The kernel unbinds the plugin in `onApplicationShutdown`, and an unbound plugin silently skips every Nest hook. Nest runs global modules' shutdown hooks in reverse insertion order, so a BullMQ worker registered ahead of `BetterAuthModule` finishes its active jobs after the unbind. In the probe, a job's `signUpEmail` for a blocked domain was created, although the same call was rejected while bound.
2. **SEC-r4-02, CSRF (probe).** "Public means no identity" covers `BetterAuthService` but not direct calls. A `@Public()` unsafe handler that passes `headersFrom(req)` to `auth.api.*` acts as the victim with no origin check: `updateUser` and `revokeSessions` succeeded cross-site, while the router answered 403 `INVALID_ORIGIN` to the same request.
3. **SEC-r4-03, identity confusion (probe).** With a static `context` object in `GraphQLModule`, Nest keeps the first request of the process in `context.req`. The Apollo transport recognizes it as a platform request, so every later caller, anonymous ones included, resolved as the first caller.

Two minors: the re-classification read is per invocation and outside the memo and the budget, so aliases multiply reads and ERROR lines during a brownout (SEC-r4-04); the origin-denial WARN cap can be exhausted for the life of the process, and it logs a `Referer`'s path and query (SEC-r4-05).

Checked and not raised:

- B29 compares only the primary secret. better-auth signs cookies with `ctx.context.secret` alone (`BA/cookies/index.ts`), and older `secrets` entries only decrypt.
- For an unset `baseURL` with `allowRequestDerivedBaseURL` under `trust proxy`, HTTP legs trust an `X-Forwarded-Host` origin, exactly as the router does. That is the router parity my round-3 fix proposed.
- A lock or statement timeout shorter than `slowMs` (500 ms) still answers 401. That is a tuning note for the docs (see SEC-r3-01 below), not a defect of the mechanism.

## Findings

### SEC-r4-01 (major): The plugin is unbound in the core module's `onApplicationShutdown` and is then silently inert, so background work that a global module drains later in the same shutdown bypasses every Nest hook, security hooks included

- **Section:** §5.7 step 4 ("`onApplicationShutdown` ... Unbind the plugin handles ... This runs after the HTTP server has stopped accepting requests, so in-flight requests keep their hooks"); §10.2 "Inert before binding and after unbinding"; §10.6 "Bind and unbind"; §10.4 ("A rule that must hold everywhere ... a `@BeforeDatabase('session.create')` hook, which sees every sign-in path"); B26.
- **Failure scenario:** An app enforces an invariant with a Nest hook, for example `@BeforeDatabase('user.create')` returning `false` for addresses outside an allowed domain, or an `@AfterDatabase('user.update')` audit hook. It processes invitations or SCIM updates in a BullMQ worker (`@nestjs/bullmq`), and the first module that calls `BullModule.registerQueue(...)` is imported ahead of `BetterAuthModule.forRoot(...)`, for example `imports: [BullModule.forRoot(…), InvitesModule, BetterAuthModule.forRoot(…)]`. `registerQueue` imports Bull's global core module, which holds the worker explorer.
  1. A rolling deploy sends SIGTERM while a job is active, and the app uses `enableShutdownHooks()`, as graceful shutdown requires. `app.close()` runs destroy hooks, before-shutdown hooks, `dispose()` (HTTP server closed), then `callShutdownHook`.
  2. Nest calls `onApplicationShutdown` in **reverse** distance order, and global modules share `distance = MAX_VALUE`, so among globals the one inserted **last** shuts down **first**. `BetterAuthCoreModule` was inserted after Bull's global core module, so its shutdown hook runs first and unbinds every plugin handle.
  3. Bull's `BullExplorer.onApplicationShutdown` then calls `worker.close()`, which waits for the active job. The job calls `auth.api.signUpEmail(...)` (or `internalAdapter.createUser`, `banUser`, ...).
  4. The plugin is unbound: the endpoint matchers return `false` and the DB dispatchers return `undefined` (§10.2, §10.6). The domain rule does not run and the account is created; the audit hook does not run either. The only trace is `unboundDispatches++`, which only B26 reads, at the next boot.

  The same holds for any work that a global module registered ahead of `BetterAuthModule` drains in its own `onApplicationShutdown` (a Kafka or RabbitMQ consumer, an outbox relay), and, for the short window until Nest's signal handler kills the process, for handlers that nothing awaits (`@nestjs/schedule` 12.0.2 only stops its cron jobs in `beforeApplicationShutdown`). The design reasons only about HTTP requests ("in-flight requests keep their hooks"), and nothing checks module import order.

- **Evidence:**
  - `probe-shutdown-unbind.mjs` (better-auth 1.7.4 memory adapter, @nestjs/core 11.1.17, the §10.6 DB dispatcher reduced to `user.create.before`; output in `.out`):
    - imports `[QueueModule, BetterAuthCoreModule]` (both global): `[live request while bound] signUpEmail early@blocked.example -> REJECTED FAILED_TO_CREATE_USER`, then `[core] onApplicationShutdown: unbound`, `[worker] onApplicationShutdown: waiting for active job`, `[job] signUpEmail for intruder@blocked.example -> CREATED`, `users in store: [ 'intruder@blocked.example' ] | unbound writes counted: 1`;
    - imports `[BetterAuthCoreModule, QueueModule]`: the job's sign-up is `REJECTED FAILED_TO_CREATE_USER`, because the worker drains before the unbind.
  - @nestjs/core 11.1.17 `nest-application-context.js`: `close()` = `callDestroyHook` → `callBeforeShutdownHook` → `dispose()` → `callShutdownHook`; `callShutdownHook` iterates `[...getModulesToTriggerHooksOn()].reverse()`; `getModulesToTriggerHooksOn` sorts by `b.distance - a.distance`; `injector/container.js:106-108` sets global modules to `Number.MAX_VALUE`.
  - @nestjs/bullmq 12.0.0 `dist/bull.module.js:301-310` `coreModuleDefinition = { global: true, ..., providers: [BullExplorer, ...] }`, imported by `registerQueue` (`:102`, `:119`); `dist/bull.explorer.js:29-30` `onApplicationShutdown(signal) { return Promise.all(this.workers.map((worker) => worker.close())); }` (BullMQ's `close()` waits for active jobs by default).
- **Suggested fix:**
  1. Do not make the plugin inert at shutdown. `onApplicationShutdown` marks the binding `closed`; the plugin keeps dispatching Nest hooks for a closed binding until another application binds. `bind()` replaces a `closed` or never-bootstrapped binding (B06 treats `closed` like a failed `init()`, without a warning). Sequential test apps, the reason for unbinding, keep working, and a hook whose dependencies are already gone throws, which fails the better-auth call closed instead of skipping the rule.
  2. Keep "inert" only for a plugin instance that was never bound (scripts and the CLI sharing `auth.ts`). If a plugin that was bound with a non-empty hook table is ever dispatched while unbound, throw (`HOOKS_UNBOUND`: an `APIError` 500 from the endpoint matcher, an error from the DB dispatcher) and log it at ERROR once.
  3. Correct §5.7 step 4 and §10.6, and add `LIB-shutdown-hooks`: a global worker module imported before `BetterAuthModule` completes a job after `close()` starts; the job's `user.create` is denied by the Nest hook.

### SEC-r4-02 (major): A `@Public()` unsafe handler that passes the caller's headers to `auth.api.*` acts as the victim with no origin check; "public means no identity" holds for the service but not for direct calls, which the design equips with `headersFrom(req)`

- **Section:** §7.1 (`public` plans return before the origin check); §7.6 "Public means no identity" and §17 Q27; §7.5 "Direct credential endpoints bypass better-auth's router protections"; §2.2.2 `BetterAuthService.headersFrom(platformRequest)`; §10.2 plugin entry 5 (`sameCredential`); §15.2 (`@AllowAnonymous()` → "`@Public()` if the handler never reads the session"); ADR-34, ADR-57.
- **Failure scenario:** better-auth's documented cross-domain cookies (`sameSite: 'none'`), or an attacker on a sibling subdomain, as in SEC-r1-01. An app migrated from the reference library keeps a custom endpoint that was `@AllowAnonymous()` because it "does its own auth" by handing the request's headers to better-auth. The migration table maps it to `@Public()`, because it reads no `@Session()`:

  ```ts
  @Public() @Post('account/email')
  change(@Req() req, @Body() body) { return this.auth.api.changeEmail({ headers: this.auth.headersFrom(req), body }); }
  ```

  (or `updateUser`, `revokeSessions`, `deleteUser`, `linkSocial`, an organization invite).
  1. A cross-site page auto-submits a form to `/account/email` with `newEmail` set to the attacker's address. The browser attaches the victim's cookie and sends `Origin: https://evil.example`.
  2. The plan is `public` in `'cookie'` mode, so the guard returns before `checkOrigin` (§7.1), and nothing else runs the check.
  3. `auth.api.changeEmail` runs as the victim, because better-auth's origin check is router-only (LEAD-V16). The same request sent to better-auth's own `/change-email` through the mount is rejected with 403 `INVALID_ORIGIN`.
  4. Unless the app enables `changeEmail.sendChangeEmailConfirmation` (a confirmation to the old address), the verification mail goes to the attacker's address (`BA/api/routes/update-user.ts:744-830`). The attacker verifies it, resets the password through the new address and takes over the account. With `updateUser` or `revokeSessions` the effect is data tampering or a forced logout.

  Nothing warns. Q27 made `getPrincipal()`/`getSession()` return `null` in public handlers, precisely so that "a cross-site form post to a `@Public()` unsafe route" cannot act as the victim (SEC-r2-04). The same request still acts as the victim one line away, through `auth.api` with `headersFrom(req)`. §7.5 discusses direct calls only as credential-less sign-ins that skip the rate limiter. `defaultAccess: 'public'` makes every route of an instance behave this way.

- **Evidence:** `probe-public-direct-call-csrf.mjs` (better-auth 1.7.4, `NODE_ENV=production`, `disableOriginCheck: false`, static `baseURL`, `trustedOrigins: ['https://app.example.com']`; output in `.out`):
  - `[router] POST /update-user cross-site -> 403 {"message":"Invalid origin","code":"INVALID_ORIGIN"}`;
  - `[direct call in @Public() handler] updateUser cross-site -> {"status":true}`, `stored name: pwned-via-public-handler`;
  - `[direct call in @Public() handler] revokeSessions cross-site -> {"status":true} | sessions left: 0`.

  Design: §7.1 guard flow (`if plan.access === 'public' && plan.originCheck !== 'form' … return true` precedes the check); §7.5 step 2 (the interceptor opens a scope for public plans too, with `inbound: call.headers`); §10.2 `credentialOf`/`sameCredential` (the plugin already recognizes a call that carries the scope's own session cookie).

- **Suggested fix:** make "public means no identity" hold for direct calls too, where the plugin can already see them:
  1. The scope interceptor records in the scope whether the invocation's origin verdict was skipped: a `public` plan in `'cookie'` mode on a browser leg with `enforce` and a cookie. Plugin entry 1 (or a new before-hook entry, bound only while such a scope is current) checks non-router, non-internal calls. When the call carries the scope's own session-token cookie (the `credentialOf` triple, first element), the before-hook throws `BetterAuthConfigurationError.atRequest('PUBLIC_HANDLER_USED_CALLER_SESSION')`, which the direct call rethrows, so the handler answers the generic 500. The hint reads "use `@OptionalAuth()` (the guard checks the origin) or `@ForwardAuthCookies()` for a login proxy". This fails closed and loud. It is not a second origin check, and safe methods, cookie-less callers and calls with other credentials are untouched.
  2. If the lead prefers availability over the throw, run the same memoized `handle.checkOrigin(browser, 'cookie')` for that call and throw its 403. Both keep one rule.
  3. §7.5 and the §15.2 `@AllowAnonymous()` row: a handler that passes the caller's headers to `auth.api` uses `@OptionalAuth()`. Add a §14.4 row: a cross-site form post to a `@Public()` handler calling `auth.api.updateUser({ headers: headersFrom(req) })` changes nothing.

### SEC-r4-03 (major): With a static `context` object in `GraphQLModule`, the Apollo transport's positive recognition accepts the **first** request of the process as every later operation's request: every GraphQL caller authenticates as the first caller, and the origin check reads the first caller's headers

- **Section:** §9.2 "Carrier first, operation kind second" (the HTTP branch "only on positive recognition: `kit.http.isRequest(context.req)`") and the Apollo/Mercurius table; §4.1.1 `HttpRequestAccessor.isRequest`, `key`; H10; §7.2 memo (principal keyed by `requests.key(req)`); §7.10 (browser leg over HTTP = that request); §9.2 "Selection and the driver" (`validate()` already reads `GqlModuleOptions`); ADR-61.
- **Failure scenario:** `GraphQLModule.forRoot({ driver: ApolloDriver, autoSchemaFile: true, context: { loaders } })`. The `context` option is typed `any`, and a plain object is accepted.
  1. Nest's `wrapContextResolver` turns a non-function `context` into `async (r) => assignReqProperty(originalOptions.context, r.req ?? r)`. That is the **same object** for every request. `assignReqProperty` sets `ctx.req` only when `ctx.req` is not already an object, so the first request after boot is stored there and kept.
  2. Alice's request is the first one. Bob's request then reaches the guard with `context.req === <Alice's request>`. It is a real Express request carrying `res`, so `isRequest` answers true and the transport takes the HTTP branch. `key` is Alice's request, whose principal promise is already memoized, and `headers()` are Alice's headers.
  3. Bob, and every anonymous caller, is resolved as Alice for every query and mutation until the process restarts. If Alice's first request came from a trusted origin, `browser.headers()` are hers too, so a cross-site mutation also passes the origin check.

  v4 made an unrecognized context fail closed (SEC-r3-05). This shape is recognized, and it fails open across users. The reference library reads the same `getContext().req`, so a migrated app keeps the defect, and nothing at boot mentions it, although the GraphQL units' `validate()` already reads these options for the driver check.

- **Evidence:** `gql/probe-static-context.mjs` (Nest 11.1.17, @nestjs/graphql 13.2.4, @nestjs/apollo 13.2.4, @apollo/server 4.13.0, Express; an `APP_GUARD` that follows §9.2's HTTP branch and §7.2's memo: `isRequest` = an `IncomingMessage` with `method` and `res`, `key = req`, credentials from `req.headers`; output in `.out`):
  - `context: ({ req }) => ({ req })`: `session=alice -> principal=alice`, `session=bob -> principal=bob`, `no session -> principal=null`, `principal resolutions: 3`;
  - `context: { loaders }`: `session=alice -> principal=alice reqEnded=false`, `session=bob -> principal=alice reqEnded=true`, `no session (anon) -> principal=alice reqEnded=true`, `principal resolutions: 1`.

  Source: @nestjs/apollo 13.2.4 `dist/drivers/apollo-base.driver.js` `wrapContextResolver` (the `else` branch for a non-function `context`) and `assignReqProperty` (`if (… ctx.req && typeof ctx.req === 'object') return ctx;`).

- **Suggested fix:**
  1. Both GraphQL units' `validate()`: when `GqlModuleOptions.context` is set and is not a function, fail boot with `GRAPHQL_STATIC_CONTEXT`, hint `context: ({ req }) => ({ req, loaders: createLoaders() })`. Check the Mercurius driver's handling of a static `context` the same way.
  2. Runtime defense in depth, because a user context function can also return a cached object: `HttpRequestAccessor` gets `isLive(req)` (Express: `!req.res.writableEnded`; Fastify: `!reply.sent` through the request map), and the HTTP branch requires it. A finished request fails with `GRAPHQL_CONTEXT_STALE_REQUEST` (500, fail closed).
  3. Add H10/T8 rows and a GraphQL job case: a static context fails boot, and a context function returning a cached object gives 500 on the second request, never the first caller's principal.

### SEC-r4-04 (minor): The re-classification read runs once per invocation, outside the memo and the authorization budget, so N GraphQL aliases during a storage brownout cost N uncached session reads and N ERROR log entries: the retry storm and log amplification that SEC-r3-08's fix bounded elsewhere

- **Section:** §8.1 "Errors (S6)", first bullet ("at most once per invocation"); Z2 ("outside the memo, once per invocation"); ADR-59 ("reading and writing no memo entry, at most once per invocation"); §8.1 "Budget" (counts `AuthorizationContext.memo` keys only); §7.1 and §13.4 (`repeated` = "meets the same memoized error"); §7.2 ("a failing database sees no retry storm"); `T-internal-error-logged-once`; ADR-68.
- **Failure scenario:** The default better-auth configuration (no cookie cache), an organization-scoped GraphQL API, and a database brownout in which some queries fail.
  1. A client sends `query { a1: project(orgId: "O", id: "1") … a300: project(orgId: "O", id: "300") }`. The root field carries `@RequireOrgPermission(p, { organization: fromParam('orgId') })`, so all 300 aliases share the org and permissions.
  2. The guard's session read succeeds and is memoized for the request. The org policy's `hasPermission` call, deduped to one call by the memo key `['org:hasPermission','O',p]`, meets a failed read inside `getSessionFromCtx`, which swallows it into `null` and answers the generic 401 `UNAUTHORIZED` (LEAD-V36). The memo shares that one rejection with all 300 invocations, and the budget counts one key.
  3. Each of the 300 invocations reaches the safety net, sees a generic 401 from a `sessionBacked` principal, and runs its own authoritative re-read through `ResolutionRequest.reclassify`, "reading and writing no memo entry". That is 300 parallel `getSession({ query: { disableCookieCache: true } })` calls against the failing database, from one request. The budget does not see them, because they do not go through `AuthorizationContext.memo`.
  4. Each re-read throws or still authenticates, and each produces a **new** `BetterAuthInfrastructureError`. `repeated` is true only for "the same memoized error", so every invocation throws the loggable `BetterAuthGraphqlInternalError`: 300 ERROR entries with cause stacks for one request.

  A list of 300 items with a guarded org field resolver behaves the same way, and so does a client that retries the page. §7.2 promises that "a failing database sees no retry storm". `T-internal-error-logged-once` does not catch this, because its adapter fails every call, so the guard's own resolution fails first and no policy runs.

- **Evidence:** design text as cited: §8.1 bullet one and "Budget"; Z2; ADR-59 _Decision_; §13.4 ("a later invocation of the same request that meets the same memoized error passes `repeated: true`"); §14.1 `T-internal-error-logged-once` ("with the adapter failing"). better-auth: `BA/api/routes/session.ts:453-523` (`getSessionFromCtx` catches every error into `null`, LEAD-V36), `:540-603` (401 `UNAUTHORIZED`, LEAD-V43). `session.cookieCache.enabled` defaults to `false`, so the endpoint's own session read hits storage.
- **Suggested fix:**
  1. Memoize the re-classification per logical request: key `(call.key, instance, sourceId)` in `RequestScope`, with the promise stored before it settles, like the principal. One re-read per request decides for every invocation, and its outcome (a 401 failure or one infrastructure error object) is shared, so `repeated` applies from the second invocation on.
  2. Count that read against `limits.maxAuthorizationCallsPerRequest`, so every better-auth call a request can cause sits under one bound.
  3. Add a `T-internal-error-logged-once` variant whose adapter fails only after the guard's resolution (for example, every session read after the first). Twenty aliases then give 20 generic errors, at most one re-read, and one ERROR entry.

### SEC-r4-05 (minor): The WARN line for origin denials, the fix for SEC-r3-03, can be switched off for the life of the process by 100 anonymous requests, and it logs a `Referer`'s path and query

- **Section:** §7.10 "Denials are visible without flooding"; §13.4 first bullet; §12.5 item 6 ("the 100-pair cap of origin-denial WARN lines", per application); RK21 mitigation; migration step 12; ADR-34 _Revised in v4_.
- **Failure scenario:**
  - **Exhausting the cap.** The origin check runs before any resolution and needs only _some_ `Cookie` header on an unsafe request. An anonymous client, or ordinary scanner noise, sends 100 requests such as `POST /anything` with `Cookie: x=1` and `Origin: https://r<i>.example`, i = 1…100. Each is a new `(INVALID_ORIGIN, origin)` pair and takes one WARN slot. The set lives "once per application" and never resets, so from then on every new pair goes to debug until the process restarts. A week later a mobile release ships without an `Origin` header, or the web frontend moves to a domain missing from `trustedOrigins`. Every unsafe request of those users answers 403, and the server log shows nothing above debug. That is the failure SEC-r3-03 described ("a mobile client broken by the default rule looked healthy from the server").
  - **Logging a Referer.** When `Origin` is absent, the value validated is the `Referer` (§7.10 step 1), a full URL. The WARN line logs "the origin", truncated to 100 characters, which for a `Referer` includes the path and the query string: for example `https://app.example.com/reset-password?token=…` from a frontend whose origin is missing from `trustedOrigins`. v4 adds this log line in production on app routes. better-auth's router logs the same value at ERROR on its own routes (`origin-check.ts:290`), but the new line need not copy that.
- **Evidence:** §7.10: "The first denial for each distinct `(reason, origin)` pair is logged at WARN, once per application, with the origin sanitized (control characters removed, at most 100 characters) … after 100 distinct pairs further ones go to debug". §7.1: the origin check precedes resolution, and the `'cookie'` rule triggers on any `cookie` header. `BA/api/middlewares/origin-check.ts:230` (`originHeader = origin || headers.get("referer") || ""`), `:269` and `:290` (`Invalid origin: ${originToValidate}`).
- **Suggested fix:**
  1. Make the cap a window instead of a lifetime set: for example, at most 100 distinct pairs per hour at WARN, and when the window closes one WARN summary line ("N further origin denials in the last hour: counts per reason, the most frequent origins"). A misconfiguration that starts later then surfaces within the hour, whatever junk came before, and an attacker who keeps filling the window still produces the summary line, which carries the counts.
  2. Log `new URL(value).origin` for a `Referer` (the matcher compares origins anyway), never the path or query.
  3. Extend the §14.4 native-app row: 100 junk-origin denials first, then the native request still produces a WARN line.

## Proposed user decisions

- **What should happen when a `@Public()` handler's direct `auth.api.*` call carries the caller's own session cookie on an unsafe operation?** (Fix of SEC-r4-02. This is not §17 Q27, which covers the service's `getPrincipal()`/`getSession()` only.)
  - Option (a), fail closed: throw `PUBLIC_HANDLER_USED_CALLER_SESSION` (generic 500, logged), with the hint `@OptionalAuth()` or `@ForwardAuthCookies()`. One rule, loud, and no second origin-check path. The cost: a public handler that deliberately acts on the session breaks until it switches to `@OptionalAuth()`, which costs one read (or one cookie-cache hit) per request.
  - Option (b), check lazily: run the memoized `checkOrigin(browser, 'cookie')` at that call and throw its 403 on failure. Such handlers keep working, but the origin check now has a second entry point, which the lead avoided in Q27 and SEC-r3-04.
  - Recommendation: (a). "Public means no identity" is already the documented model, and a loud error during development is cheaper than a CSRF path that only a security review finds.
