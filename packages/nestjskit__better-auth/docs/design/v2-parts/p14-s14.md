## 14. Testing strategy

### 14.1 Conformance kits (the LSP proof, reusable by third parties) `[A][B][C]`

The kits live in `nestjs-slightly-better-auth/testing/conformance`. They are **runner-agnostic**: each returns `ConformanceCase[]`, and `runConformance(cases, { describe, it })` registers them with vitest, jest or `node:test`. Assertions use `node:assert/strict`. The same kits run in our CI for every built-in unit, which makes "Express and Fastify behave the same" a tested property rather than a claim.

Each HTTP case boots a real Nest app, under both `NestFactory.create` and `Test.createTestingModule().createNestApplication()`. It uses a real better-auth instance (memory adapter) that includes `conformanceProbePlugin()`, which provides these endpoints:

- `/probe/echo-raw`: `disableBody` + `ctx.request.text()`, echoing the received bytes and headers;
- `/probe/multi-cookie`: three cookies;
- `/probe/redirect`: 302 with a cookie;
- `/probe/stream`: three chunks with delays;
- `/probe/html`;
- `/probe/put`, `/probe/patch`, `/probe/delete`;
- `/probe/url`: echoes `request.url`;
- `/probe/ip`: echoes `getIP(request)`;
- `/probe/throw-api-error`, `/probe/throw-error`.

The probe plugin also contributes a trusted origin through `init()` (`https://probe-plugin.example`), so trusted-origin cases exercise the post-init set (LEAD-V17). The kit also adds a throwing `around` interceptor, an app controller `/app/echo` that returns `{ body, rawBody }`, and a global `APP_FILTER` that records what it sees.

/** One fixture handler the kit supplies; the harness exposes it as a controller route, resolver field, gateway message or message pattern. */
export interface FixtureHandler {
  /** Method decorators to apply, in order (access, acceptance, requirements). */
  readonly decorators: readonly MethodDecorator[];
  /** Parameter decorators by parameter index, e.g. [CurrentSession()]. */
  readonly params: readonly ParameterDecorator[];
  /** 'read': HTTP GET, GraphQL query, RPC request. 'unsafe': HTTP POST, GraphQL mutation. WS messages are always enforced (§7.10). */
  readonly operation: "read" | "unsafe";

  readonly optional: FixtureHandler; // @OptionalAuth()

  readonly forbidden: FixtureHandler; // a requirement whose kit policy always denies (T-error-shape, T-no-error-log)

  readonly unguarded: FixtureHandler; // @CurrentSession() + @ActiveOrganizationId(); no @UseBetterAuth(), booted with globalGuard: false (T-internal-error-generic)
}
export interface PrincipalSourceConformanceOptions {
  source: ExtensionRef<PrincipalSource>;
  credentials: {

    rateLimited?(): Promise<Headers>;
  };
}

  allowingPrincipal(): Promise<AuthPrincipal>;

### 14.3 Cookie-session end-to-end `[A][B][C]`

The current repo tests only bearer tokens (R:current-repo). This suite uses a real cookie jar:

1. Sign up and sign in over JSON **and** `application/x-www-form-urlencoded`, then call a protected controller route. With `session.updateAge: 0`, the app-route response carries the refreshed `session_token` `Set-Cookie` with a new max-age, the DB expiry matches, and there is no `cache-control`.
2. With `cookieCache.enabled`, the first guarded response carries `session_data`.
3. Stateless mode (no database): the refresh-cache branch re-issues cookies over HTTP. Over WS, GraphQL subscriptions and RPC nothing is issued.
4. A GraphQL query over HTTP refreshes cookies (Apollo on Express and on Fastify, Mercurius). Subscription and WS messages do not move the DB expiry.
5. Direct calls:
   - a controller with `@ForwardAuthCookies()` calling `auth.api.signInEmail` / `signOut` sets or clears the caller's cookies through the plugin bridge;
   - without it, the same calls leave the response's cookies untouched;
   - an admin handler calling `signUpEmail` for another user never changes the admin's cookies;
   - the same call in a WS handler does not refresh.
6. An expired cookie gets 401 on required routes, with cleanup cookies forwarded.
7. API-key principal:
   - an invalid key on a `@Public()` route is never resolved (200);
   - on a route that does not accept keys it is never verified (usage counter unchanged; 401 without a cookie);
   - on a required route that accepts keys it gets 401 with `reason: INVALID_API_KEY`;
   - on `@OptionalAuth()` it gets 401, never anonymous;
   - a rate-limited key gets 429 with `Retry-After`;
   - `verifyApiKey` is called once per request (usage counter).

### 14.4 Security end-to-end (origin check ON) `[A][B][C]`

better-auth disables origin/CSRF checks when `NODE_ENV=test` and falls back to IP 127.0.0.1 in dev/test (R:ba-core §3.3, §3.5). This suite therefore runs with `NODE_ENV=production`, sets `advanced.disableOriginCheck: false` explicitly, uses a production-grade secret, and sets a static `baseURL` except where a case says otherwise. Cases:

- **Auth routes:**
  - a cross-origin POST with a session cookie → 403 `INVALID_ORIGIN`;
  - a missing Origin with `sec-fetch-mode: cors` → 403 `MISSING_OR_NULL_ORIGIN` (Node's `fetch` sends that header, so tests set `Origin` explicitly);
  - a cross-site navigation form login → 403;
  - an untrusted `callbackURL` → 403.
- **App routes, GraphQL and WebSockets** `[R1:SEC-r1-01, BA-r1-03]`:
  - `sameSite: 'none'` cookies: a cross-site form POST to a guarded Nest route → 403 `INVALID_ORIGIN`;
  - the same from a trusted origin → 200;
  - a cross-site GraphQL mutation → `FORBIDDEN`/`INVALID_ORIGIN`; a query → allowed;
  - a cross-site socket.io and ws connection with the victim's cookie → every message denied and `WsConnectionAuth` rejects;
  - an SSR-style server call with a forwarded cookie and no `Origin` → 403 `MISSING_OR_NULL_ORIGIN`, and with a trusted `Origin` → 200.
- **Principals and authorization** `[R1:SEC-r1-02, SEC-r1-04, BA-r1-01]`:
  - a leaked narrow-scope API key cannot reach `@RequirePermission` routes or authenticated-only routes that did not accept keys;
  - a banned admin with a warm cookie cache is denied immediately.
- **Transport and deployment configuration** `[R1:SEC-r1-06, SEC-r1-07, SEC-r1-11]`:
  - per-IP rate limiting with two clients, behind `trust proxy` on and off; spoofed client-IP headers (fixed name and `x-nsba-ip-*`) and `x-forwarded-for` are ignored; `W_PROXY_UNTRUSTED` fires once with trust off;
  - `Host` header injection with a static `baseURL` changes neither URLs nor cookies;
  - with **no** `baseURL` in production, boot fails with `UNSAFE_BASE_URL`; with `http.allowRequestDerivedBaseURL` boot succeeds with `W_REQUEST_DERIVED_BASE_URL`, and the case reproduces REV-SEC:`probe-unset-baseurl.mjs` (a reset link following `Host: evil.example`) to keep the warning's text honest;
  - two named instances sharing a cookie prefix fail boot with `COOKIE_NAME_COLLISION`.
- **Robustness:**
  - an oversized body → 413 before better-auth runs, same body on both platforms;
  - an adapter throwing → 500 on protected routes, 200 on `@Public()` routes (the #159 regression), and no token in the logs (`S-log-redaction` on the real app);
  - HTTP/2 requests do not crash (Fastify).

  .post("/projects")

    stampPrincipal(ctx, testUser);
    return true;
  }
}

// beforeEach-friendly: closes the previous test app bound to the same instance, then init() (+ Fastify ready())
beforeEach(async () => {
  app = await initTestApp(
    moduleRef.createNestApplication(new FastifyAdapter()),
    { closeWith: afterEach },

- `overrideAuthGuard` calls both `overrideProvider(BetterAuthGuard)` (the `APP_GUARD` alias) and `overrideGuard(BetterAuthGuard)` (the injectables `@UseBetterAuth()` creates per host module), and does the same for the scope interceptor. Either one alone misses a set of call sites (`core/injector/module.js:344-356`). `overridePrincipal` remains the preferred tool, because it keeps the real guard, acceptance, origin check and policies `[R1:NEST-r1-08]`.
- **Where a replaced guard publishes the principal** `[R1:NEST-r1-08]`. A stand-in guard cannot write the real guard's carrier stamp, and WebSocket messages have no carrier at all. `stampPrincipal()` and the `{ principal }` stand-in therefore write a **test stamp** (§7.8 item 3): a record on the invocation's args array and its object elements, accepted only by a reader whose args have the same elements. Guards and interceptors of a WS message, GraphQL field or RPC message share the args array itself, and HTTP guards and interceptors share its elements (LEAD-V7, LEAD-V34). Both the real scope interceptor, when `peek()` has nothing for the instance, and the stand-in interceptor copy the stamp into the scope they open, which is where the param decorators and `BetterAuthService` look first. The stand-in interceptor always opens that scope, on every transport.
- **Cases** (this repository's suite, `LIB-` ids, §14.5), each on a socket.io gateway and a ws gateway that carry `@UseBetterAuth()` with a handler reading `@CurrentSession()` and `BetterAuthService.getPrincipal()`, and on an HTTP controller with `globalGuard: true`:
  - `LIB-testing-override-principal`: `overrideAuthGuard(builder, { principal })` delivers the principal to both readers, performs no better-auth call (adapter call counter), and concurrent messages on one socket each see the principal their own invocation stamped;
  - `LIB-testing-stamp-mock-guard`: a hand-written guard installed with `overrideAuthGuard(builder, new MockGuard())` that calls `stampPrincipal(ctx, user)` delivers `user` to both readers; the same guard without the call makes `@CurrentSession()` throw `NO_AUTH_RESULT` with the generic message (§7.8 item 4).
- `initTestApp` closes a previous test app still bound to the same better-auth instance before initializing, and a failed `init()` leaves a binding the next app takes over with a warning (B06). Apps built in `beforeEach` therefore work with exclusive binding `[R1:SEC-r1-15]`.

The docs explain that `NODE_ENV=test` disables better-auth's origin checks (and, through the same flags, this library's origin check, §7.10), when to switch them back on, and that closing apps is required by exclusive binding (B06).
