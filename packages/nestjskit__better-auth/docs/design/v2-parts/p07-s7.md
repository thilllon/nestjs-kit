## 7. Authentication (principal resolution)

Authentication answers "who is calling". It produces an `AuthPrincipal`, a discriminated union over the augmentable `PrincipalKinds`. Authorization (§8) answers "may they" and never re-resolves identity.

### 7.1 Guard flow `[A][B][C]`

```
BetterAuthGuard.canActivate(ctx)
 ├─ transport = transports.select(ctx)          // first handles(ctx); none → BetterAuthConfigurationError NO_TRANSPORT (500), never allow
 ├─ plan      = planner.get(ctx)                // cached per handler: instance, access, accepts, requirements, freshness, principalParams, originCheck
 ├─ kernel    = instances.get(plan.instance)
 ├─ call      = transport.describe(ctx, kit)    // sync, no I/O; headers lazy
 ├─ if plan.access === 'public':
 │     stamp(call, plan.instance, { outcome: 'absent', skipped: 'public' }); return true          // zero auth I/O
 ├─ result = await resolver.resolve(call, { auth: kernel.handle, freshness: plan.freshness, accepts: plan.accepts })  // 7.2
 ├─ stamp(call, plan.instance, result)
 ├─ result.outcome === 'rejected' → throw transport.toException(result.failure, ctx)               // never downgraded
 ├─ result.outcome === 'absent'   → plan.access === 'optional' ? return true
 │                                                                : throw toException(AuthFailures.unauthenticated())
 ├─ !plan.accepts.has(principal.kind)          → throw toException(forbidden('PRINCIPAL_NOT_SUPPORTED'))   // P4 safety net (7.6)
 ├─ for (c of plan.principalParams) principal.kind !== c.kind → throw toException(forbidden(c.reason))    // e.g. SESSION_REQUIRED; safety net behind B15 (7.6 step 6)
 ├─ plan.originCheck && call.browser?.enforce  → failure = await originCheck.check(call, kernel)          // 7.10
 │     failure → throw toException(failure)                                                             // 403 INVALID_ORIGIN / MISSING_OR_NULL_ORIGIN
 ├─ decision = await evaluator.evaluate(plan.requirements, principal, call, kernel)                  // per invocation (7.2)
 │     deny → throw transport.toException(failureOf(decision), ctx)
 └─ return true
 (BetterAuthInfrastructureError / request-time BetterAuthConfigurationError:
    throw transport.toInternalException?.(error, ctx) ?? error        → 5xx on every transport, generic on GraphQL (§13.3))
```

The guard **never returns `false`**. A `false` return makes Nest throw an HTTP `ForbiddenException` on every transport, which Mercurius, WS and RPC then mis-deliver (R:nest-di §3.4, §5). The guard always throws the transport-native error.

Every comparison in this flow is between values extensions supplied: `principal.kind` against `plan.accepts` (source `kinds`, `@AcceptPrincipals`, `requires.principals`) and against the kinds param decorators recorded. Core names no kind `[R1:NEST-r1-07]`.

### 7.2 Resolver contract and memoization (S7) `[A][B][C]` `[R1:NEST-r1-01, SEC-r1-13]`

The port is in §2.2.2. The default `ChainPrincipalResolver` keeps three memo scopes apart:

| Scope                                                                 | Keyed by                                                                                                         | Holds                                                                                  | Lifetime                                                  |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **Principal**                                                         | `(call.key, instance, freshness, source set)`; `(call.connection, …)` instead when `principalTtlMs > 0`          | the resolution promise                                                                 | the logical request; a connection entry until `expiresAt` |
| **Policy I/O** (`AuthorizationContext.memo`, `PrincipalRequest.memo`) | `(call.key, instance, key)` where the key names concrete inputs (e.g. `org:hasPermission:<orgId>:<permissions>`) | promises of better-auth calls                                                          | the logical request, **never** a connection               |
| **Decision and per-invocation values**                                | `(call.invocation, instance, requirement expression)`                                                            | the requirement's decision; values policies `provide()` (the resolved organization id) | one handler invocation                                    |

- **Storage.** `WeakMap<object, RequestState>` inside the singleton `RequestScope`. There is no module-level state and no DI request scope.
- **The principal promise is stored before it settles** `[A][B]`. GraphQL runs the guard once per root field, three times for three root fields in one request (R:nest-di §3.4; EXP-B:E8: 3 guard calls → **1** resolution). Concurrent invocations share one `getSession`. A rejection is memoized for the same request key too, so every root field fails the same way and a failing database sees no retry storm.
- **Decisions are per invocation, never per request or connection.** A requirement object is created once, when the decorator is evaluated, so v1's "memoize by requirement identity per request" let two aliased root fields asking about different organizations share one allow, and let a WebSocket connection with a principal TTL reuse an allow across messages. v2 keys decisions by `call.invocation`: the GraphQL field's `info`, the WS message's `args`, the HTTP request, the RPC context. Two guard runs of the **same** invocation (global guard plus `@UseBetterAuth()`) still share one decision. Policies that want cheap repeats dedupe their better-auth calls through `memo` keyed by their concrete inputs, so two identical checks cost one call and two different organizations cost two (Z6).
- **Source set.** The chain is filtered by the route's accepted kinds (§7.6). The filtered list's identity is part of the principal key, so a GraphQL request whose root fields accept different kinds resolves each distinct set at most once.
- **Chain.** Resolution runs inside `handle.run({ cookies: call.cookies, forward: 'same-credential', inbound: call.headers, internal: true }, …)`, the same scope shape the evaluator uses (§8.1). That makes every nested better-auth call of every source cookie-aware (P2): refresh is suppressed where the transport cannot deliver cookies (§7.4), a `Set-Cookie` produced by a call that carries the request's own credential or none reaches the client through the bridge where it can, and the call is marked internal for hooks (§10.4). The built-in session source is the one exception, and it makes it itself: it wraps its `getSession` in a nested `run({ forward: 'none' })` and forwards that call's cookies through `returnHeaders`, so they are delivered exactly once (§7.3, ADR-09). A third-party source that also forwards a call's cookies by hand does the same; if it forgets, the kernel's cookie sink de-duplicates identical `Set-Cookie` values. The sources run in order: skip those whose `appliesTo` is false, stop at the first `authenticated` or `rejected`, and return `absent` if none applies (§4.3.3).
- **Connection entries** (WS, subscriptions with `principalTtlMs > 0`). They store only settled `authenticated` and `absent` results, with an `expiresAt`. A `rejected` result (for example a transient 429) and an infrastructure failure are memoized per message only, and an infrastructure failure evicts the connection entry. A database blip therefore costs one failed message, not the TTL `[R1:SEC-r1-13]`.
- **`peek(call, request)`** returns the settled result without I/O. The scope interceptor and decorators use it.

| Transport                            | `call.key` (principal, I/O memo)                                                                                                                                                                                    | `call.invocation` (decisions)                                                        | `call.connection` (TTL reuse)                                                                                                                                       | Carrier (stamp fallback, §7.8)                                                         |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| HTTP (Express, Fastify, third-party) | the platform's `requests.key(req)` (Express `req`; Fastify `request.raw`)                                                                                                                                           | same                                                                                 | —                                                                                                                                                                   | the Nest request object (`args[0]`)                                                    |
| GraphQL query/mutation               | the underlying HTTP request key, **shared with the HTTP transport**                                                                                                                                                 | the field's `info` (`args[3]`), distinct per root field, alias and batched operation | —                                                                                                                                                                   | the GraphQL context (`args[2]`) for the principal; `info` for per-invocation values    |
| GraphQL subscription                 | the subscription operation's context object (Apollo: graphql-ws calls a function-valued `context` once per subscribe message, graphql-ws 6.0.7 `server.ts`; Mercurius: a new copy per subscription start, LEAD-V35) | `info`                                                                               | the connection's upgrade request (Apollo `extra.request`; Mercurius the object `mercuriusSubscriptionContext()` stores), only with `subscriptionPrincipalTtlMs > 0` | the GraphQL context                                                                    |
| WebSocket (socket.io, ws)            | the per-message `args` array (shared by all guards of a message, LEAD-V7)                                                                                                                                           | same                                                                                 | the socket                                                                                                                                                          | **none**: decorators read the scope (the socket would race across concurrent messages) |
| RPC                                  | `switchToRpc().getContext()` (one object per message; gRPC: the per-call `Metadata`)                                                                                                                                | same                                                                                 | —                                                                                                                                                                   | the same object                                                                        |

### 7.3 Built-in session source (S2) `[A][B][C]`

```ts
export const SESSION_PRINCIPAL_KIND = "session" as const;

export const sessionPrincipal = <S = AuthSession>(
  options: SessionPrincipalOptions<S> = {},
) =>
  definePrincipalSource<SessionPrincipal>({
    id: "better-auth:session",
    kinds: [SESSION_PRINCIPAL_KIND],
    acceptance: "default", // every authenticated route
    credentialHeaders: ["cookie", "authorization"], // cookie is ambient; see 7.10
    async resolve(r) {
      const ctx = await r.auth.context();
      const stateful = Boolean(
        ctx.options.database || ctx.options.secondaryStorage,
      ); // mirrors hasServerSessionStore
      const query: { disableCookieCache?: true; disableRefresh?: true } = {};
      if (r.freshness === "authoritative" && stateful)
        query.disableCookieCache = true; // stateless: the cookie IS the session
      if (r.cookies === null) query.disableRefresh = true; // belt; the plugin's skip flag is the braces (7.4)

      let result: { headers: Headers; response: unknown };
      try {
        // forward: 'none' → this call's cookies are forwarded exactly once, through returnHeaders (no bridge duplicate)
        result = await r.auth.run(
          { cookies: r.cookies, forward: "none", internal: true },
          () =>
            r.auth.api.getSession({
              headers: r.headers,
              returnHeaders: true,
              query,
            }) as Promise<{ headers: Headers; response: unknown }>,
        );
      } catch (e) {
        const failure = AuthFailures.fromAPIError(e); // 401/403/429 (bad x-api-key, failed refresh, api-key rate limit + Retry-After)
        if (!failure) throw e; // ≥500 or non-APIError → infrastructure (S6)
        const cleanup = apiErrorSetCookies(e); // e.headers + hidden better-call:api-error-headers
        if (r.cookies && cleanup.length) r.cookies.append(cleanup);
        return rejected(failure);
      }
      if (r.cookies) {
        const setCookie = result.headers.getSetCookie(); // ONLY set-cookie: never cache-control / pragma
        if (setCookie.length) r.cookies.append(setCookie);
      }
      if (result.response == null) return absent();
      const userId = (options.userId ?? defaultUserId)(result.response as S); // default s.user?.id; customSession → session.userId option
      if (userId === null)
        throw BetterAuthConfigurationError.atRequest(
          "SESSION_USER_ID",
          "session.userId returned null for a resolved session",
        );
      return authenticated({
        kind: SESSION_PRINCIPAL_KIND,
        source: "better-auth:session",
        userId,
        session: result.response as S,
      });
    },
    // jwt without disableSettingJwtHeader, bearer without requireSignature, and (api-key plugin present) W_API_KEY_FULL_SESSION /
    // W_API_KEY_SESSION_MULTIPLIER, which also reads ctx.policies and options.apiKeySessions (7.9, 8.3.1)
    advise: (ctx) => costHints(ctx, options),
  });
```

- **`returnHeaders: true`** keeps the refresh and cookie-cache `Set-Cookie`s that a plain call drops. There are 9 code paths (R:ba-core §4.3). EXP-C1's baseline with `updateAge: 0` emits `session_token`. It works for `customSession` too, because it is a dispatch-level feature (`BA/api/dispatch.ts:467-477`).
- **Only `set-cookie` is forwarded.** `getSession` also returns `cache-control: no-store` and `pragma: no-cache`, which must not leak onto app responses (R:ba-core §4.3). EXP-A:`exp-e2e.mjs` verified one `session_token` and `cache-control=null` on a guarded route on all four platform × major combinations.
- **Credential translation happens inside `getSession`.** Bearer, api-key session mocks (`enableSessionForAPIKeys`), jwt side effects, multi-session and `customSession` all take effect through better-auth's own hooks, so the source never parses credentials (R1). Hooks see the original request: the bearer plugin's cookie rewrite happens inside the dispatch and is invisible to other before-hooks (LEAD-V23).
- **`authoritative`** bypasses the cookie cache only when a server-side store exists. That mirrors better-auth's own authoritative read (`BA/api/routes/session.ts:520-539`) `[C]`.
- **The user-id mapping lives in the source** (`session.userId` runtime option), not in `AuthHandle`, so core has no notion of a session shape `[R1:NEST-r1-07]`.

### 7.4 Cookie forwarding and refresh suppression per transport capability (S2)

`getSession` emits `Set-Cookie` on 9 code paths (R:ba-core §4.3). Two of them move server or cookie state:

- **row 7, sliding refresh:** the DB `expiresAt` is extended and `session_token` is re-set;
- **row 4, stateless refresh-cache:** `session_data` is re-issued and `session_token` is re-set, with no DB write.

If the cookie cannot be delivered, the browser cookie expires before the server session, which is the drift better-auth works to avoid (`BA/api/state/should-session-refresh.ts:3-10`; `nextCookies`). Where the transport can deliver cookies, they are forwarded. Where it cannot, the refresh itself is suppressed, not just its cookies dropped.

| Caller                                                                          | `call.cookies`                                                                                                               | Session source / call                       | Refresh                                                    | Forwarded to client                                                                                                                                             |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTP controller (Express, Fastify, third-party)                                 | platform sink                                                                                                                | `returnHeaders: true`                       | normal                                                     | `set-cookie` only                                                                                                                                               |
| GraphQL query/mutation over HTTP (Apollo, Mercurius)                            | the HTTP sink: Express `req.res`; Fastify `requests.responseFor(req)` (root `onRequest` map, LEAD-V8); Mercurius `ctx.reply` | same                                        | normal                                                     | `set-cookie` only                                                                                                                                               |
| GraphQL subscription                                                            | `null`                                                                                                                       | + `disableRefresh`, + skip flag             | **suppressed**                                             | none                                                                                                                                                            |
| WebSocket (socket.io, ws)                                                       | `null`                                                                                                                       | same                                        | **suppressed**                                             | none                                                                                                                                                            |
| RPC (all carriers)                                                              | `null`                                                                                                                       | same                                        | **suppressed**                                             | none                                                                                                                                                            |
| Library policies (org, admin) and third-party principal sources in a request    | the transport's sink or `null`                                                                                               | `auth.api.*` with the request's own headers | normal / **suppressed**                                    | `set-cookie` via the plugin bridge (same credential or none)                                                                                                    |
| Direct `auth.api.*` in a handler or service (under the scope interceptor, §7.5) | the transport's sink or `null`                                                                                               | the user's call                             | better-auth default / **suppressed** in cookie-less scopes | **none by default**; with `@ForwardAuthCookies()` / `forwardDirectCalls` / `forwardCookies(fn)`: `set-cookie` of calls carrying the caller's credential or none |
| Direct call outside any scope (cron, queue worker, bootstrap seeding)           | none                                                                                                                         | the user's call                             | better-auth default                                        | none. Use `returnHeaders`, or `service.withoutCookies(fn)` to suppress                                                                                          |

**How suppression works** `[A][B][C]`. It is construction-time plugin behavior, following the `nextCookies` precedent. The `nestjs()` plugin registers one before-hook:

- **matcher:** `ctx._flag !== 'router' && binding?.current()?.cookies === null`;
- **handler:** `await setShouldSkipSessionRefresh(true)`.

This is the only public way to set that flag. It lives in better-auth request state, which exists only inside a better-auth dispatch. `better-auth/api` exports the setter (LEAD-V2) but not `runWithRequestState`, which lives in `@better-auth/core/context`. A before-hook runs inside the dispatch's own store, so the flag lands exactly where `getSession` reads it (EXP-C1: "plugin skip-refresh set-cookie: []").

**Stateless refresh-cache branch.** Without a database or secondary storage, better-auth force-enables `cookieCache` with `refreshCache` (`BA/context/create-context.ts:104-116`). That branch checks **only** `getShouldSkipSessionRefresh()` (`BA/api/routes/session.ts:199-204`, LEAD-V3). `query.disableRefresh` returns early only later (`:309`), so on its own it does **not** stop the branch. EXP-A:`exp-plugin.mjs` and EXP-B:E2 show this:

- control, `disableRefresh` only: `session_data` and `session_token` emitted;
- with the skip flag: none emitted.

The session source still passes `disableRefresh: true` on cookie-less calls as a belt, because it also skips rows 6 and 9 (a pointless cookie-cache write).

**Why any path, not just `/get-session`.** `nextCookies` suppresses only on `/get-session` (LEAD-V14), but plugin endpoints that read the session internally slide it too. Policies call `hasPermission` and `getActiveMember`, for example. EXP-B:E3, re-run by A and C:

- without a scope, `getActiveMember` emits `session_token` and moves the DB expiry;
- inside a cookie-less scope, neither happens.

The matcher therefore covers every non-router call made inside a cookie-less scope.

**Cleanup cookies** (rows 1, 2, 3 and 5: expire a stale cache or delete an invalid token) are still computed by better-auth. On cookie-less transports they are dropped harmlessly, and the next cookie-capable request cleans up again.

**The plugin is mandatory** (B03). Without it the stateless branch and nested plugin-endpoint refreshes could not be suppressed, and the library's own policy calls could not forward the refreshed cookies they produce. That would be two behavior modes users cannot see (ADR-02).

### 7.5 Direct `auth.api.*` calls in application code `[A][C]` `[R1:BA-r1-02, SEC-r1-03]`

`BetterAuthScopeInterceptor`, a global `APP_INTERCEPTOR` registered with `useExisting`, handles each handler invocation:

1. It selects the transport and builds `call` (sync).
2. It opens `RequestScope.run({ cookies: call.cookies, forward: plan.forwardDirectCalls ? 'same-credential' : 'none', inbound: call.headers, internal: false, resolutions }, …)` around the _subscription_ to `next.handle()`:

```ts
intercept(ctx: ExecutionContext, next: CallHandler) {
  const scope = this.scopes.forExecution(ctx);                     // null when no transport handles ctx
  return scope ? new Observable((sub) => scope.run(() => next.handle().subscribe(sub))) : next.handle();
}
```

Nest invokes the handler and its param factories inside the interceptor chain (`router-execution-context.js:40-46`; WS: LEAD-V7), and `InterceptorsConsumer` binds each step with `AsyncResource`.

**Default: better-auth's server-call semantics.** A direct `auth.api.*` call from a handler or a service behaves as it does in plain better-auth: its `Set-Cookie` is **not** written to the caller's response. The one change is in cookie-less scopes (WS, RPC, subscriptions), where refresh is suppressed because nothing could deliver the cookie (S2). In plain better-auth a server call never touches the browser unless the developer adds a cookie plugin (`nextCookies`) or uses `returnHeaders`/`asResponse`. v1 forwarded every direct call, so an admin handler that ran `auth.api.signUpEmail({ body })` (auto sign-in is on by default) swapped the admin's browser session for the new user's (BA-r1-02), and a service that called `getSession` with a service-account bearer token could hand that session to the end user (REV-SEC:`probe-bridge-foreign.mjs`) `[R1]`.

**Opt-in forwarding** for handlers that proxy the caller's own login or logout:

- per handler or controller: `@ForwardAuthCookies()` (and `@ForwardAuthCookies(false)` to opt one handler out of a controller-level opt-in);
- per instance: `cookies: { forwardDirectCalls: true }` (B28 warns, because it applies to every handler);
- per call site: `service.forwardCookies(() => this.auth.api.signInEmail({ body, headers }))`.

**Credential matching** (plugin entry 4, §10.2). Where forwarding is on, the bridge forwards a direct call's `Set-Cookie` only if the call carried **no credential** (a login or sign-up) or **the caller's own credential**. The credential is compared as a triple: the session-token cookie, found by name through `$context.authCookies.sessionToken.name` and parsed with better-auth's `parseCookies`; the `authorization` header; and the values of every source's `credentialHeaders` (for example `x-api-key`). Anything else is dropped and logged once at debug with the endpoint path. Deliberate account switching (impersonation, "sign in as") uses `service.forwardCookies(fn, { anyCredential: true })`.

**Library-internal calls always forward.** The resolver chain (§7.2) and the evaluator (§8.1) both run in `forward: 'same-credential'` scopes. Policies and principal sources call `auth.api.*` with the request's own headers, so their cookies (for example a sliding refresh inside `hasPermission`) are the caller's own and reach the browser on cookie-capable transports: the credential always matches. A third-party source that presents a credential other than the request's gets that call's cookies dropped, like any foreign credential. The session source's own `getSession` is the one internal call that runs with the bridge off, because it forwards through `returnHeaders` (§7.3).

**Direct credential endpoints bypass better-auth's router protections.** A server-side `auth.api.signInEmail({ body })` skips better-auth's rate limiter and origin check, which run only in the router (`BA/api/index.ts:285-292, 310`; LEAD-V16). The docs therefore recommend letting clients call better-auth's own routes (through the mount) for sign-in, sign-up and password flows, and keeping direct credential calls for trusted back-office code. A handler that does proxy them should apply the app's own throttling. `@ForwardAuthCookies()` is required for its cookies to reach the browser at all, so the pattern is always an explicit choice.

- **Why an interceptor rather than a platform-level scope opened at `init$`** (drafts B, C; ADR-11):
  - it is transport-neutral;
  - it runs after body parsing;
  - it gives param decorators a race-free source on WebSockets, where the per-message `args` array is not visible to param factories (LEAD-V7);
  - it keeps the platform contract small.

  An early scope would survive Express parsing (LEAD-V11), but it would cover HTTP only.

- **Coverage gaps, documented.** Code in middleware and in other libraries' guards runs outside the scope. So do GraphQL field resolvers (their continuations run outside the root resolver's scope) and gateways without `@UseBetterAuth()` (which B16 rejects). Such code gets plain better-auth semantics; it can use `service.withoutCookies(fn)` or its own `returnHeaders`. Decorators there fall back to the carrier stamp (§7.8).
- **Opting out entirely.** `service.runOutsideScope(fn)` runs `fn` as if no scope existed: no forwarding and no suppression `[C]`.
- **Committed responses.** If a handler has already sent the response itself (`@Res()` plus a manual send), the sink reports `false`. The bridge then logs one debug line and drops the cookies.

### 7.6 Public, optional and required semantics; accepted principal kinds `[A][B][C]`

**Plan compilation** (`RoutePlanner`, cached per handler):

1. Read the access decorator (`@Public` / `@OptionalAuth` / `@RequireAuth`), `@AcceptPrincipals`, `@SkipOriginCheck`, `@ForwardAuthCookies` and the requirements at the **method** level and at the **class** level. For the class level, use the own metadata of each class in the prototype chain, most-derived first.
2. **Same-level contradiction** fails boot (B15). `@Public()` or `@OptionalAuth()` together with requirements at the same level is contradictory: an anonymous caller can never satisfy a principal requirement.
3. **Effective access** is decided by the closest level that says anything:
   - the method's access decorator; else
   - `'required'` if the method has requirements; else
   - the class's access decorator; else
   - `'required'` if the class has requirements; else
   - `defaultAccess`.
4. **Effective requirements.** If access is `'required'`, they are class requirements (base first) followed by method requirements, in declaration order. Otherwise there are none. A method-level `@Public()` or `@OptionalAuth()` is therefore an explicit, visible opt-out of class-level requirements (§17 Q3).
5. **Accepted kinds** `[R1:SEC-r1-02, BA-r1-01]`:
   - the kinds named by the closest `@AcceptPrincipals(...)` (method over class); otherwise the instance's _default kinds_, the `kinds` of every source with `acceptance: 'default'` (by default only `'session'`);
   - **plus** every kind that a requirement names, through `requirement.principals ?? policy.requires.principals`. `@RequireApiKeyPermission(p)` therefore admits `'api-key'` on its route without a second decorator, and only policies that can judge a kind make it reachable.

   A source whose kinds are all outside the set is not consulted for the route (§4.3.3). An API key or OAuth token therefore authenticates nothing on a route that did not ask for it: no quota is spent and the request is treated as if the header were absent.

6. **Principal param constraints.** Each `definePrincipalParam` decorator on the handler contributes `{ kind, reason }`. A handler that accepts kinds its param decorator rejects fails boot (B15 `PRINCIPAL_PARAM_CONFLICT`, hint: `@CurrentPrincipal()`). Every plan the planner compiles, lazily compiled ones included (§5.4), passes this check, and the acceptance gate runs before the param check, so on such a plan the guard's runtime comparison (§7.1) never fires. It remains as a safety net for the one plan the planner does not produce: a plan returned by a `BetterAuthGuard` subclass that overrides `planFor` (§2.2.2), for example to add a company-wide requirement that names another kind. There the guard denies 403 with the decorator's `reason` (`SESSION_REQUIRED`) instead of handing the handler a principal of the wrong kind. `T-reads-session` covers the boot error, and the planner unit tests (§14.5) cover the safety net.
7. **Freshness** is `'authoritative'` if `@RequireAuth({ authoritative: true })` is present at the effective level, `session.freshness` says so, or any effective requirement has `freshIdentity` (from the requirement or its policy; the admin policy by default, §8.4) `[R1:SEC-r1-04]`.
8. **Origin check** applies unless `@SkipOriginCheck()` (method or class) or `originCheck.mode: 'off'`. **Direct-call forwarding** follows `@ForwardAuthCookies` (method over class), else `cookies.forwardDirectCalls`.

| Effective access               | Principal I/O | No credentials        | Presented but invalid credential (e.g. bad `x-api-key` on a route accepting keys) | Infrastructure failure | `@CurrentSession()`   |
| ------------------------------ | ------------- | --------------------- | --------------------------------------------------------------------------------- | ---------------------- | --------------------- |
| `required` (default)           | yes           | 401 `UNAUTHENTICATED` | denial with better-auth's status and `reason`                                     | 5xx                    | `AuthSession`         |
| `optional` (`@OptionalAuth()`) | yes           | allowed               | **denial** (a bad credential is never downgraded to anonymous)                    | 5xx                    | `AuthSession \| null` |
| `public` (`@Public()`)         | **none**      | allowed               | not inspected                                                                     | cannot happen (no I/O) | boot error B15        |

`@Public()` doing zero I/O fixes reference issue #159: health probes no longer return 500 when the database is down. It also means a bad API key on a public route consumes no quota (R:ba-authz §4.2 #5). `@OptionalAuth()` is the "attach the session if present" mode. `BetterAuthService.getSession()` remains available to public handlers that explicitly ask for it.

```ts
@Controller("reports")
export class ReportsController {
  @Get() list(@CurrentSession() s: AuthSession) {} // sessions only (default kinds)

  @AcceptPrincipals("session", "api-key") // both; read the union
  @Get("export")
  export(@CurrentPrincipal() p: AuthPrincipal) {}

  @RequireApiKeyPermission({ reports: ["read"] }) // admits 'api-key' by itself
  @Get("feed")
  feed() {}
}
```

### 7.7 Error semantics (S6)

| Situation                                                                                                                                                                                                               | Result                                                                                                                                                      |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No principal on a required route                                                                                                                                                                                        | 401 `UNAUTHENTICATED`                                                                                                                                       |
| A source returns `rejected` (for example `APIError` 401/403 from `getSession` hooks, or an API-key result mapped per §8.3.1)                                                                                            | that status; `code` `UNAUTHENTICATED` (401) or `FORBIDDEN` (403); `reason` = better-auth code; cleanup cookies forwarded where possible; the chain stops    |
| Rate limited during resolution: an `APIError` 429 from `getSession` hooks (api-key with `enableSessionForAPIKeys`), or `verifyApiKey` reporting `RATE_LIMITED`/`USAGE_EXCEEDED`                                         | 429 `RATE_LIMITED`; `Retry-After` from the error's headers or from `details.tryAgainIn` (ms, rounded up to seconds) when present `[R1:BA-r1-04, SEC-r1-05]` |
| A principal of a kind the route does not accept, or rejected by a param decorator (reachable only through a `planFor` override, §7.6 step 6)                                                                            | 403 `PRINCIPAL_NOT_SUPPORTED` / the decorator's reason (`SESSION_REQUIRED`)                                                                                 |
| Ambient-cookie operation from an untrusted or missing origin                                                                                                                                                            | 403 `FORBIDDEN`, `reason` `INVALID_ORIGIN` / `MISSING_OR_NULL_ORIGIN` (better-auth's codes, §7.10)                                                          |
| `APIError` ≥ 500, `BetterAuthError`, DB or network errors, anything else                                                                                                                                                | `BetterAuthInfrastructureError` → 5xx, logged once with a redacted cause (§13.4); **never 401/403**                                                         |
| Configuration faults met at request time (unknown transport; `customSession` without `userId` at runtime; a lazily loaded handler with an invalid plan; a param decorator on a handler the guard did not run for, §7.8) | `BetterAuthConfigurationError.atRequest` → 500; the message is generic as thrown, so it stays generic on GraphQL even where no transport maps it (§13.3)    |
| Public route during a DB outage                                                                                                                                                                                         | unaffected (never resolves)                                                                                                                                 |

Detection is always `isAPIError` from `better-auth/api`, which accepts both `APIError` classes and `name === "APIError"` (LEAD-V5). It is never `instanceof`, because better-call's CJS and ESM copies have different classes (R:ba-core §4.2).

**Known upstream limitations.**

- RK2: `customSession` catches errors from its inner `getSession` and returns `null` (`BA/plugins/custom-session/index.ts:100-107`). For such apps a storage outage therefore looks like "no session" (401) instead of a 5xx. We cannot fix this without reimplementing `getSession`, which R1 forbids. It is documented, and we will propose an upstream change.
- RK18: `verifyApiKey` reports a storage outage as `INVALID_API_KEY` (LEAD-V20). `apiKeyPrincipal()` mitigates this with an outage probe (§8.3.1) and we will propose an upstream change.

### 7.8 Accessing the principal

**Param decorators are synchronous** (async factories only work without pipes, R:nest-di §4.3). `@CurrentSession()`, `@CurrentUser()`, `@CurrentPrincipal()` and any decorator built with `definePrincipalParam` look up the resolution for their instance in this order:

1. **The scope** opened by `BetterAuthScopeInterceptor`, which holds the resolutions `peek()`ed for this invocation and the invocation's published values. It is race-free on every transport `[L]`. Where `peek()` has no result for the instance, the interceptor fills the scope from a test stamp (item 3), so a replaced guard works on WebSockets too.
2. **The carrier stamp** `[A]`: scan `ctx.getArgs()` for `Symbol.for(…:resolution)` (a `Map<instance, PrincipalResult>` on the carrier) and `Symbol.for(…:invocation)` (per-invocation values on the invocation object, e.g. GraphQL `info`). The real guard writes it. This covers HTTP, GraphQL (including field resolvers outside the root scope) and RPC when the interceptor is not applied. WS has no carrier on purpose.
3. **The test stamp** `[R1:NEST-r1-08]`, written by `stampPrincipal()` and by the `overrideAuthGuard` stand-in guard (§14.8). Neither knows the transport, so the stamp is a record `{ elements, results }` under `Symbol.for('nestjs-slightly-better-auth:test-stamp')`, where `elements` is a copy of the stamping guard's `ctx.getArgs()` and `results` a `Map<instance, PrincipalResult>`. It is attached to that args array and to each of its extensible object elements. A reader (the scope interceptors and these decorators) looks on its own args array first, then on each object element, and accepts a record only if `elements` is element-wise identical (`===`) to its own `ctx.getArgs()`:
   - on GraphQL, RPC and WebSockets the guards and interceptors of one invocation share the args array itself (LEAD-V7, LEAD-V34), so the interceptor finds the record there and copies it into the scope it opens. This is the WebSocket path: gateways always have the interceptor (B16), and the socket-level copy is never needed;
   - on HTTP the router hands guards and interceptors separate `[req, res, next]` arrays with the same elements (LEAD-V34), so the record is found on `req` and still matches;
   - a record on a shared object (a socket, a GraphQL root value) does not match a sibling request, field or message, whose elements differ. The one theoretical collision, two concurrent messages with identical primitive payloads on one socket stamped with different principals, would matter only to a reader without the interceptor, which gateways never lack.

   Like every stamp, the record is symbol-keyed, so no parsed request payload can carry one.

4. **Otherwise** throw `BetterAuthConfigurationError.atRequest('NO_AUTH_RESULT', 'No authentication result: BetterAuthGuard did not run (globalGuard: false without @UseBetterAuth(), or a guard replaced in a test without stampPrincipal())', { site: 'SiteController.method' })`. This surfaces reference issue #12 as a clear error instead of an `undefined`. The decorator runs where the guard did not, so no transport's `toInternalException` can map this error, and a GraphQL driver copies `message` into the response. The error is therefore safe as thrown `[R1:SEC-r1-19]`: its `message` is the fixed `Authentication is misconfigured`, `extensions.reason` is `AUTH_MISCONFIGURED`, and the site, detail and hint are ordinary own properties, which Nest's exception layer logs (LEAD-V31) and neither GraphQL driver serializes (LEAD-EXP-7). A `defineInvocationParam` decorator with nothing published throws the same way, with its `missing` text as the `detail` (`NO_INVOCATION_VALUE`), and so does every other request-time configuration error, including one raised by `BetterAuthService.getPrincipal()` in a resolver body (§13.1). A boot check that every handler with such a decorator is guarded would not make the case unreachable: coverage cannot be proven for every call site (handlers in lazily loaded modules, guards applied through another library's composite guard, guards replaced in tests), so the error itself must be safe.

**What each decorator returns:**

- `@CurrentSession()` `[R1:NEST-r1-10]` returns `principal.session` for a principal of kind `'session'`, or `null` on an optional route with no principal. It is built with `definePrincipalParam({ kind: SESSION_PRINCIPAL_KIND, reason: 'SESSION_REQUIRED', project: (p) => p.session })` by the session unit. The planner records the kind as data. A route that could admit another kind fails boot (B15), and for a plan from a `planFor` override the guard denies another kind with 403 `SESSION_REQUIRED` (§7.6 step 6) instead of handing the handler a `null` typed as `AuthSession`. It is named `CurrentSession` rather than v1's `Session` because `@nestjs/common` exports a `Session` route-param decorator (it injects `req.session`), and an IDE auto-import into a file that already imports from `@nestjs/common` silently picked the wrong one.
- `@CurrentUser()` behaves the same way and returns `principal.session.user`.
- `@CurrentPrincipal()` returns `AuthPrincipal | null` and has no kind constraint.
- `@ActiveOrganizationId()` and `@ActiveMemberRole()` (`./organization`) are `defineInvocationParam` decorators. They return the value the org policy published for **this invocation** (§8.3), never a value from a sibling GraphQL field.

**Services** use `BetterAuthService.getPrincipal()` or `getSession()`. Inside a scope these resolve lazily through the same memo, so calling them in a guarded handler costs nothing extra. Outside any scope they return `null`.

### 7.9 Cost per protected request

- **Session resolution.** One `getSession` per request, shared by all guard invocations, decorators and services. That is 0 storage reads on a cookie-cache hit, otherwise 1 read, plus 1 write when a refresh is due (R:ba-authz §1.0). An authoritative route (admin permission by default, §8.4) always reads storage once.
- **Public routes.** Zero.
- **API keys through `apiKeyPrincipal()`.** One `verifyApiKey` per request, on routes that accept keys only. Each verification counts against the key's usage and rate limit and writes to storage (usage counter, `updatedAt`) `[R1:SEC-r1-14]`. Org policies deny `'api-key'` principals without calling better-auth.
- **Multipliers,** surfaced as boot advice (B21) by the units that know about them:
  - the jwt plugin without `disableSettingJwtHeader: true` signs a JWT and reads `jwks` on every `getSession` (session unit);
  - bearer without `requireSignature: true` pays a lookup for foreign tokens (session unit);
  - `apiKey({ enableSessionForAPIKeys: true })` validates the key on **every** better-auth call that carries it, not only `getSession` (LEAD-V21). A request that resolves the session and then evaluates `@RequireOrgPermission` and `@RequireOrgMember` spends the key's quota three times (REV-BA:`probe-apikey-policy.mjs`: `requestCount` 1 → 2 → 3). The **session unit** announces it, because it is the unit registered in exactly this setup (an app that uses key sessions usually never imports `./api-key`). Its `advise()` emits `W_API_KEY_SESSION_MULTIPLIER` when `context.hasPlugin('api-key')` and any referenced policy declares `presentsCredentials`, and recommends `apiKeyPrincipal()` for key traffic. The option itself cannot be read from the plugin object, so the message is conditional unless `session.apiKeySessions` states the fact (§8.3.1) `[R1:BA-r1-05]`;
  - a quota-consuming source (`effects.consumesQuota`) on a WebSocket transport with `principalTtlMs: 0` verifies on every message (`W_QUOTA_PER_MESSAGE`, §9.3).
- **Policy I/O** is deduped per request by concrete inputs (Z6): `@RequireOrgPermission(p, org A)` twice on one request is one call; for org A and org B it is two.

### 7.10 Origin check for cookie-authenticated operations `[R1:SEC-r1-01, BA-r1-03]`

better-auth protects cookie-authenticated requests on its own routes with an origin check, and that check is **router-only**. `validateOrigin` is registered as router middleware and returns early without `ctx.request` (LEAD-V16). Every `auth.api.getSession({ headers })` the guard makes is therefore unprotected, and v1 wrongly listed "origin/CSRF" as something `auth.handler` does for the whole app. In a probe, the guard's `getSession` accepted an evil-origin cookie request that the router rejected with 403 (REV-SEC:`probe-bridge-foreign.mjs`). With better-auth's documented cross-domain cookie settings (`sameSite: 'none'`), or with an attacker on a sibling subdomain (same-site), this allowed:

- cross-site form posts to Nest routes;
- cross-site GraphQL mutations;
- Cross-Site WebSocket Hijacking (browsers attach cookies to WebSocket upgrades, CORS does not apply, and the attacker reads the replies).

The kernel therefore applies **better-auth's own rule** to the cookie-authenticated surfaces this library creates.

**When it applies.** All of the following hold:

1. The route is not public, a principal authenticated, and the plan's origin check is on (not `@SkipOriginCheck()`, not `originCheck.mode: 'off'`).
2. The transport exposes a browser leg (`call.browser`), and `call.browser.enforce` is true:
   - HTTP: methods other than GET/HEAD/OPTIONS, better-auth's own split;
   - GraphQL: mutations (queries are read-only and a cross-site page cannot read their response);
   - WebSocket and GraphQL subscriptions: every message and subscription, because a hijacked socket can read replies.

   RPC has no browser leg.

3. The credential was **ambient**. The browser leg carried a `cookie` header on its own (`call.browser.ambientCookie`), and the request carries no explicit credential:
   - an `authorization` header with a `Bearer` or `DPoP` scheme (browsers attach only `Basic`/`Negotiate`-style credentials automatically);
   - or any header in `originCheck.explicitCredentialHeaders` ∪ every source's `credentialHeaders` other than `cookie` and `authorization` (by default `x-api-key`).

   A browser cannot attach those headers cross-site without a CORS preflight that the host's CORS policy approved.

4. better-auth's own skip flags do not disable it. `$context.skipCSRFCheck` (`advanced.disableCSRFCheck`), and the backward-compatible `skipOriginCheck === true && disableCSRFCheck === undefined` (which includes better-auth's test-environment default), turn it off exactly as on better-auth's routes (LEAD-V18). Path-array `skipOriginCheck` entries name auth-route paths and are ignored here.

**The rule** (mirrors `validateOrigin`, LEAD-V16):

1. The origin to validate is `Origin`, else `Referer`. `Origin: null` with `Sec-Fetch-Site: same-origin` is inferred from the browser leg's URL origin. better-auth's router does this from 1.7.2 on; the kernel applies it on every version in the peer range, which on 1.7.0 and 1.7.1 makes it more lenient than the router for this one same-origin case (LEAD-V33, RK20).
2. Missing or `null`: with `originCheck.missingOrigin: 'reject'` (default, better-auth's behavior) deny 403 `MISSING_OR_NULL_ORIGIN`. With `'allow-non-browser'`, allow only when `Origin`, `Referer` and `Sec-Fetch-Site` are all absent. Every current browser sends at least one of them on a cross-site unsafe request.
3. Otherwise the origin must be trusted by the instance, as computed by `TrustedOrigins` (U17):
   - `ctx.trustedOrigins`, the init-time list (baseURL origin, user `trustedOrigins`, `BETTER_AUTH_TRUSTED_ORIGINS`);
   - ∪ the post-init `ctx.options.trustedOrigins`, which carries the plugin-contributed origins (LEAD-V17). A function-valued one is evaluated with a lightweight `new Request(browser.url, { headers: browser.headers() })`, like better-auth's router does per request;
   - ∪ the browser leg's own origin when `ctx.baseURL` is empty (development without a `baseURL`, where better-auth derives it from the request).

   Matching is better-auth's `matchesOriginPattern`, reached through `ctx.isTrustedOrigin.call({ trustedOrigins: merged }, origin)`. It handles full Referer URLs, wildcards and custom schemes exactly as on auth routes. An untrusted origin is denied 403 `INVALID_ORIGIN`.

4. Denials are logged at debug, like every other denial (§13.4), so attack traffic cannot flood ERROR logs.

**Where it runs.** In the guard, after resolution and before policies (§7.1). For WebSockets the browser leg is the handshake request: `socket.io` uses `client.handshake.headers`, `ws` uses the recorded upgrade request (`withUpgradeRequest`), graphql-ws uses `extra.request`. `WsConnectionAuth` applies the same check at connect time, through `AuthHandle.checkOrigin` (§9.3).

**Non-browser clients.** Server-side callers that forward a user's cookie on unsafe requests, such as an SSR server calling the Nest API, must send an `Origin` header (a trusted one). That is the same requirement better-auth already imposes on its own routes when such a server calls, say, `/sign-out` with forwarded cookies. Node's built-in `fetch` sends `sec-fetch-mode: cors` and no `Origin` (LEAD-EXP-4), so a "no browser signals" exemption would not cover it anyway. Machine clients should use bearer tokens or API keys, which the check never touches. Routes that deliberately serve cookie-bearing server-to-server calls use `@SkipOriginCheck()`. §17 Q14 and Q15 record these defaults.
