**The key rule (S6).** Only a _denial value_ produces 401, 403 or 429. Detection uses `isAPIError` from `better-auth/api` (LEAD-V5), the status comes from `e.statusCode`, and the reason from `e.body?.code`. For `verifyApiKey`, which returns failures as values, the mapping is an explicit table with an outage probe (§8.3.1). Nothing in the library catches an arbitrary error and returns 401/403. The reference did that for every plugin error (R:ref-impl §6.1).

### 13.2 Normalization `[B][C]`

Sources and policies return values. The kernel's safety net normalizes anything they throw:

```ts
/** A policy's better-auth call answered 401: the evaluator re-resolves the principal before it answers 401 or 5xx (§8.1). */
type SessionLossCandidate = {
  readonly sessionLoss: unknown;
  readonly reason?: string;
};
function normalizeThrown(
  e: unknown,
  where: "source" | "policy",
  site: string,
  secrets: readonly string[],
): AuthFailure | SessionLossCandidate | never {
  if (isAuthFailure(e)) return e; // brand check, dual-package safe
  if (isInfrastructureError(e) || isConfigurationError(e)) throw e; // already classified (e.g. SESSION_USER_ID, the API-key outage probe): never re-wrapped
  if (isAPIError(e)) {
    // better-auth/api; never instanceof (S6)
    const status = e.statusCode,
      reason = (e.body as { code?: string } | undefined)?.code;
    if (status === 429) return AuthFailures.fromAPIError(e)!; // Retry-After from headers or body.details.tryAgainIn
    if (status === 401 && where === "policy") return { sessionLoss: e, reason }; // §8.1: the evaluator re-resolves before it answers 401 or 5xx [R2:BA-r2-03]
    if (status === 401 || status === 403)
      return where === "source"
        ? AuthFailures.rejected({ status, reason }) // presented credential rejected
        : AuthFailures.forbidden(reason ?? "FORBIDDEN"); // principal is authenticated → 403
    if (status >= 500) throw new BetterAuthInfrastructureError(e, { secrets });
    throw BetterAuthConfigurationError.atRequest(
      "BETTER_AUTH_REJECTED_CALL",
      `better-auth rejected the library's call (${status} ${reason})`,
      { site },
    );
  }
  throw new BetterAuthInfrastructureError(e, { secrets });
}
```

A 4xx other than 401, 403 or 429 means our own call was malformed, for example a validation error from `userHasPermission`. That is a bug or a misconfiguration, not a client error `[C]`. Built-in policies convert the better-auth outcomes they expect into decisions themselves before this net sees them:

- `USER_IS_NOT_A_MEMBER_OF_THE_ORGANIZATION` (401 → 403);
- `YOU_ARE_NOT_A_MEMBER_OF_THIS_ORGANIZATION` (403 → 403, as a decision rather than a thrown error);
- `NO_ACTIVE_ORGANIZATION` and `MEMBER_NOT_FOUND` (400) from `getActiveMember` in the default organization ref → no organization, 403 `NO_ACTIVE_ORGANIZATION` (§8.3);
- the admin endpoint's `user not found` (400 → 401 `USER_NOT_FOUND`, §8.3) `[R1:BA-r1-10]`.

A source never gets the re-classification: a source's 401 is a rejected credential. A policy's generic 401 (`UNAUTHORIZED`, or none) always goes through it, because the principal was authenticated a moment before and better-auth's session middleware cannot tell a lost session from a failed read (LEAD-V36).

**Errors thrown outside the guard** `[R1:SEC-r1-19]`. Param decorators (§7.8) and `BetterAuthService` run where the guard's transport mapping does not, so their errors reach each runtime unmapped: Nest's default 500 on HTTP, `Internal server error` on WS and RPC, and the error's own `message` and `extensions` on GraphQL. Both library error classes are therefore generic as thrown: a request-time `BetterAuthConfigurationError` (`atRequest`) and `BetterAuthInfrastructureError` carry a fixed message and `extensions` with the reason, and keep the specifics in own properties (`detail`, `site`, `hint`, the redacted `cause`) that neither GraphQL driver serializes (LEAD-EXP-7).

`AuthFailure` is transport-neutral, and only a transport's `toException` knows the transport's format. A new transport therefore gets the whole taxonomy by implementing one method, plus `toInternalException` if its runtime would expose error messages `[B]`.

### 13.4 Logging and redaction `[R1:SEC-r1-08]`

- **Denials are not errors.** HTTP and GraphQL mappings are `IntrinsicException`s, which Nest's filters do not log (LEAD-V9). Denials, origin-check failures included, are logged at `debug` by the guard.
- **Infrastructure failures are logged once per request, by Nest's exception layer, with a redacted cause.** Nest's `ConsoleLogger.error(err)` prints `util.inspect(err)`, which includes the `[cause]` chain and enumerable properties (LEAD-V31); pino/nestjs-pino serializers and Sentry's linked-errors integration read `error.cause` too. Driver errors commonly embed query parameters: drizzle-orm 0.45.2 builds `DrizzleQueryError` with the message `` `Failed query: ${query}\nparams: ${params}` `` (`errors.js:10-16`), and `findSession(token)` puts the session token in those params. v1 attached the raw cause, so a database timeout would have shipped live session and bearer tokens to log aggregators for every guarded request during the outage.

  v2's `ErrorRedactor` (U18) builds the cause instead:
  - **Secrets** are the request's credential values:
    - every cookie value in the `Cookie` header, and its URL-decoded form;
    - for signed values (`token.signature`), the part before the last `.` when at least 16 characters long, which is the form stored in the database;
    - the `authorization` value and its credential part after the scheme;
    - the values of every declared credential header (source `credentialHeaders`, e.g. `x-api-key`).
  - **The redacted cause** is a new `Error` with the original's `name` and its `code`, `errno` and `syscall` when present. Its message is the **first line** of the original message, truncated to 300 characters, with every secret replaced by `[REDACTED]`. Its `stack` is that header plus the original stack frames (frames are file positions only). Nested causes are redacted the same way, to a depth of 3.
  - **The raw cause** is kept under a non-enumerable `Symbol.for('nestjs-slightly-better-auth:raw-cause')` slot, which `util.inspect` does not print. It is reachable through `getRawCause(error)` only when `errors.exposeRawCause: true` (local debugging).
  - The same redaction applies on auth routes (`AuthExchange` knows the inbound credentials) and on the `WsConnectionAuth` path.

- **Never logged:** request headers, `Cookie`, `Set-Cookie`, bearer tokens and API keys. One alternative library logs full headers (R:ba-integrations §6.6). A hygiene conformance case (`S-log-redaction`) makes an adapter throw with the session token in its message and asserts the token never appears in captured logs.
- **better-auth's own logger** is outside this library's control. It logs `Failed to validate API key:` with the underlying error at ERROR for every failed key verification (LEAD-V20), and it logs origin failures at ERROR on auth routes. The docs recommend configuring better-auth's `logger` (level, or a redacting `log` function) in production (RK19).
- The docs warn that with `apiKey({ enableSessionForAPIKeys })`, the mocked session carries the raw key in `session.token`. Serializing `@CurrentSession()` into responses or logs leaks it (R:ba-authz §1.2). `apiKeyPrincipal()` never exposes the raw key.

### 13.5 Customization

```ts
export interface ErrorMappingOptions {
  /** Replace what a transport throws for a denial; return undefined to keep the transport's default. [C] */
  map?: (
    failure: AuthFailure,
    context: ExecutionContext,
    transport: string,
  ) => unknown;
  /** Keep the unredacted cause reachable through getRawCause() (local debugging only). Default false. [R1:SEC-r1-08] */
  exposeRawCause?: boolean;
}
```

- `errors.map` is a per-instance override: a runtime option (§5.2) of the instance whose plan produced the denial (§5.5). It is applied before the transport's `toException`, and receives the transport's id (§9.0).
- A deeper change is made by subclassing a transport (for example the HTTP transport) and listing it in `transports`, where it is selected before the built-in one `[A]`.
- Neither mechanism depends on exception filters, which do not reach WebSocket gateways in any Nest version (R:nest-di §5.2).
