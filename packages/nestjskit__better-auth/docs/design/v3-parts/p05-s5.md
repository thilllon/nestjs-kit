## 5. Module configuration

### 5.1 Registration API

`BetterAuthModule` is hand-written; it does not use `ConfigurableModuleBuilder` `[A][B][C]`. Builder extras reach only the transform callback and never a provider. They leak into the options value when their defaults object is empty. An explicit `undefined` overrides a default. Those traps caused reference issues #59, #88 and #159 (R:nest-di §1.2–1.3). The name `BetterAuthModule` avoids colliding with the `AuthModule` most applications already have, and `BetterAuthGuard` avoids `@nestjs/passport`'s `AuthGuard` `[A][B]` (ADR-24).

Three supported shapes, simplest first:

```ts
// (1) Static instance (recommended: the better-auth CLI can load auth.ts; R:ref-issues §3.19)
BetterAuthModule.forRoot({
  auth, // runtime
  platforms: [expressPlatform()], // app-level static (default instance only)
  transports: [apolloTransport(), socketIoTransport()], // app-level static (default instance only)
  principals: [apiKeyPrincipal()], // instance static (tried before the session where a route accepts 'api-key')
});

// (2) Static instance, runtime knobs from configuration
BetterAuthModule.forRootAsync({
  platforms: [fastifyPlatform()],
  transports: [mercuriusTransport()],
  imports: [ConfigModule],
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    auth,
    http: { bodyLimit: config.get("AUTH_BODY_LIMIT") ?? "1mb" },
    defaultAccess: config.get("AUTH_DEFAULT_ACCESS") ?? "authenticated",
  }),
});

// (3) Instance built from DI (e.g. a Prisma client); types via the factory's return type (no shadow instance, #62/#112)
// auth.ts
export const createAuth = (prisma: PrismaClient) =>
  betterAuth({
    database: prismaAdapter(prisma, { provider: "postgresql" }),
    plugins: [admin(), nestjs()],
  });
declare module "nestjs-slightly-better-auth" {
  interface Register {
    auth: ReturnType<typeof createAuth>;
  }
}
// auth.cli.ts (for the better-auth CLI only): export const auth = createAuth(new PrismaClient());
// app.module.ts
BetterAuthModule.forRootAsync({
  platforms: [expressPlatform()],
  imports: [PrismaModule],
  inject: [PrismaService],
  useFactory: (prisma: PrismaService) => ({ auth: createAuth(prisma) }),
});
```

Shape (3) with an asynchronously initialized dependency is safe under both bootstraps: platform preparation waits for whichever of "adapter known" and "platforms registered" happens last (§5.7, LEAD-EXP-3) `[R1:NEST-r1-03]`.

### 5.2 Static vs runtime options

| Kind                                                                 | Fields                                                                                                                                                                                                                                                                 | Why                                                                                                                                                                                              |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **App-level static** (`BetterAuthAppOptions`, default instance only) | `platforms`, `transports`                                                                                                                                                                                                                                              | One HTTP adapter and one transport registry per app. Declaring them once removes merge ambiguity; the named-instance overloads reject them at compile time and B25 at runtime `[R1:NEST-r1-09]`. |
| **Instance static** (`BetterAuthStaticOptions`)                      | `name`, `isGlobal`, `globalGuard`, `principals`                                                                                                                                                                                                                        | Each decides which providers, enhancers or exports exist. Nest fixes that when the dynamic module is created. Extensions may be DI classes, which must become providers.                         |
| **Runtime** (`BetterAuthRuntimeOptions`)                             | `auth`, `defaultAccess`, `defaultRequirements`, `session`, `http.{mount, bodyLimit, around, allowRootMount, allowRequestDerivedBaseURL, diagnostics}`, `cookies.forwardDirectCalls`, `originCheck.{mode, missingOrigin}`, `errors.{map, exposeRawCause}`, `logSummary` | Read by providers after DI resolution, so they may come from `useFactory`.                                                                                                                       |

The split is enforced twice `[C]`:

1. **At compile time.** `useFactory` must return `BetterAuthFactoryResult<A>`, which maps every static and app-level key to `StaticOptionMustBePassedToForRootAsync<K>`. Returning `{ auth, globalGuard: false }` fails with `Type 'boolean' is not assignable to type 'StaticOptionMustBePassedToForRootAsync<"globalGuard">'` (EXP-C9).
2. **At runtime.** The options provider rejects static keys found in a factory result with `BetterAuthConfigurationError: 'globalGuard' was returned from useFactory; pass it to BetterAuthModule.forRootAsync({ globalGuard, useFactory })`. This covers JavaScript users and `any`.

Toggles users commonly want to drive from configuration are runtime options, so they never hit this wall. Making a whole app public is `defaultAccess: 'public'`, not "remove the guard". Behavior that depends on runtime options is decided at runtime by always-registered providers, following the nestjs-cls pattern (R:nest-di §1.4). For example, the built-in session source is always registered, and `session: false` removes it from the chain when the options resolve.

### 5.3 How the typed instance flows `[A][C]`

```
auth.ts ──typeof auth──► Register augmentation ──► RegisteredAuth / AuthOf<N>
                                                     ├─► AuthSession<N> / AuthUser<N> / AuthPrincipal
                                                     ├─► BetterAuthService (default generic)         [DI: class / BETTER_AUTH_SERVICE]
                                                     ├─► AdminPermissions / OrgPermissions           [decorator arguments]
                                                     ├─► EndpointPath / AuthHookContext<P>           [hook decorators]
                                                     ├─► DatabaseHookData<E, Ph>                     [from BetterAuthOptions['databaseHooks']]
                                                     └─► forRoot<A> check: A must be RegisteredAuth for the default instance
forRoot({ auth }) ──infers A──► SessionOption<A> (customSession ⇒ session.userId mapper required)
```

1. `forRoot<A>` infers `A` from `auth`. It gives completion for `session.userId(s: SessionOf<A>)`. When the program has registered an instance, the default-instance overload also requires `A extends RegisteredAuth` (EXP-C2 case 9).
2. For non-generic injection sites and decorators, the user registers the type once with `interface Register { auth: typeof auth }`. Named instances go under `instances: { admin: typeof adminAuth }`.
3. At runtime, `InjectAuth()` resolves `getAuthToken('instance')` to the exact object the user passed, with no wrapper and no proxy. No runtime code reads `$Infer`.
4. Our declarations contain only conditional types over `Register`, evaluated in the user's program. Nothing deeply inferred from better-auth is emitted (§11.7).

### 5.4 Bootstrap validation (fail fast)

All checks run in `onModuleInit` of the internal core module. Nest orders lifecycle hooks by module distance, and every global module has the same distance, so they run in insertion order (LEAD-V27). The core module therefore runs before non-global user modules' hooks. It does **not** necessarily run before another global module imported ahead of `BetterAuthModule`. Code that seeds data through `auth.api` belongs in `onApplicationBootstrap`, and B26 reports better-auth calls that ran before Nest hooks were bound `[R1:NEST-r1-11]`. The core module's lifecycle work runs once per application: `NestMicroservice.init()` calls `onModuleInit` and `onApplicationBootstrap` twice (REV2-NEST:`exp4b-double-init.mjs`), and a repeated call returns at once (§5.7) `[R2:NEST-r2-05]`. Errors are **aggregated** `[C]`: one boot reports every problem found, each as a `BetterAuthConfigurationError` with a stable `code` and a copy-paste `hint`. Rows marked _warn_ or _info_ log instead of throwing. The numbers are identifiers, not an execution order: several checks validate the result of a boot step (hook discovery, binding, mount resolution) and run right after it, as §5.7 step 2 lists.

Plans for B14–B16 are compiled by scanning every controller and every provider's methods with `DiscoveryService` and `MetadataScanner`, one plan per (class, method), so two subclasses that inherit one handler function get two plans (§7.6). The scan is full, skips alias wrappers, and reads only our own `Symbol.for` metadata keys; transports read the Nest-owned keys they document when they claim handlers (§9). ### 5.5 Multiple instances `[A][C]`

The stance is one default instance per app, plus any number of **named** instances with explicit routing. Dynamically swappable instances are not supported (§17 Q10).

```ts
// auth.ts: distinct cookie prefixes, or the two instances overwrite and clear each other's cookies (B24)
export const auth = betterAuth({ /* … */ plugins: [organization(), nestjs()] });
export const adminAuth = betterAuth({
  /* … */ advanced: { cookiePrefix: "admin-auth" },
  basePath: "/api/admin-auth",
  plugins: [admin(), nestjs()],
});

@Module({
  imports: [
    BetterAuthModule.forRoot({ auth, platforms: [expressPlatform()] }), // 'default': app-level platforms/transports, global guard
    BetterAuthModule.forRoot({ name: "admin", auth: adminAuth }), // globalGuard: false by default; no platforms here
  ],
})
export class AppModule {}

@UseAuthInstance("admin") // the (single) guard evaluates this controller against 'admin'
@Controller("admin")
export class AdminController {
  constructor(
    @InjectBetterAuthService("admin")
    private readonly admin: BetterAuthService<AuthOf<"admin">>,
  ) {}
  @Get("me") me(@CurrentSession() s: AuthSession<"admin">) {
    return s.user;
  } // the plan's instance: 'admin'
}
// types: declare module '…' { interface Register { auth: typeof auth; instances: { admin: typeof adminAuth } } }
```

- Each instance has its own tokens (`getAuthToken(kind, name)`), its own `nestjs()` plugin binding, and its own mount path from its own `$context`. Mounts must not overlap (B10), and cookie names must not collide (B24) `[R1:SEC-r1-11]`.
- **Platforms and transports are app-wide and declared once**, on the default instance `[R1:NEST-r1-09]`. One platform serves every instance's mount. **Principal sources and runtime options are per instance.**
- There is one `BetterAuthGuard` and one scope interceptor, both in the static core module. The guard resolves the instance per route from `@UseAuthInstance` metadata (method over class, default `'default'`).
- Metadata keys carry no instance name, so every decorator works for every instance.
- Hooks bind to one instance through `HookOptions.instance` (default `'default'`).
- Memo keys include the instance name, so one request can be authenticated against two instances without confusion.

### 5.6 Double-import safety

`forRoot()` returns a new dynamic module on every call, and Nest identifies modules by reference, so importing it twice creates two modules (R:nest-di §1.3). The documented pattern is one import in the root module; the module is global, and decorators need no import. Three independent defences turn a mistake into a boot error instead of a silently doubled guard:

1. **Name uniqueness** in the app-scoped `InstanceRegistry` (B07) `[A][C]`.
2. **Exclusive plugin binding** (B06) `[B][C]`. The same better-auth instance cannot be bound twice, even from two copies of this library, because the handle lives on the plugin object.
3. **A per-server mount stamp** (B10) `[B]`. `Symbol.for(…:mounted)` on `httpAdapter.getInstance()` catches two mounts of the same path, again even across library copies.

The guard lives in the static core module, which Nest deduplicates by class, so a second `forRoot` can never register it twice. `APP_GUARD` is contributed only by the `forRoot` whose `globalGuard` is true (B07), and platforms and transports only by the default instance (B25).

All library constructors put an explicit `@Inject(token)` on every parameter, including `Reflector`, `ModuleRef`, `DiscoveryService`, `MetadataScanner`, `HttpAdapterHost` and `ApplicationConfig` (S5; §12.6). No library provider is request-scoped, because a request-scoped `APP_GUARD` makes every controller request-scoped (R:nest-di §3.3).

**Lifecycle** `[R1:NEST-r1-02, NEST-r1-03]`:

1. **Platform preparation: last arrival wins.** Two events must both have happened:
   - _adapter known_: `MountCoordinator` subscribes to `HttpAdapterHost.init$` (a `ReplaySubject`) in its constructor and records `host.httpAdapter ?? null`;
   - _platforms known_: the default instance's platform registry factory calls `coordinator.registerPlatforms(list)`.

   Whichever event comes second triggers `select` and `prepare()`, exactly once. Neither side depends on the order in which Nest constructs modules. That order is concurrent, and under `NestFactory` `init$` fires before any provider exists (LEAD-V27). LEAD-EXP-3 showed the result on 11.1.17 and 12.0.1:
   - `NestFactory.create`: `init$ → platforms registered → prepare`, all **before `create()` resolves**, so before `main.ts` code and before `init()` registers Nest's body parsers. This holds even when the platform registry waits on an async factory dependency.
   - `@nestjs/testing`: `platforms registered → compile() resolved → init$ → prepare`, all **before `createNestApplication()` returns**.
   - `createApplicationContext` and `createMicroservice`: `init$` fires with `httpAdapter === null`. The coordinator records "no HTTP": no `supports`, no `prepare`, no mount, `TransportKit.http = null`, B08 skipped.
   - `Test…compile()` + `moduleRef.init()`, and `Test…createNestMicroservice()`: `init$` never fires and `httpAdapter` is `undefined` (REV2-NEST:`exp4-testing-no-init.mjs`). If "adapter known" has not happened when the core module's `onModuleInit` runs, the coordinator records `host.httpAdapter ?? null` there, synchronously, which is "no HTTP" for these bootstraps. If `init$` later emits a non-null adapter (a `createNestApplication()` from the same testing module after `moduleRef.init()`), the coordinator logs `LATE_HTTP_ADAPTER` at ERROR and the application's next lifecycle call of the core module (its `init()`) throws `BetterAuthConfigurationError('LATE_HTTP_ADAPTER')`: auth routes would otherwise silently stay unmounted `[R2:NEST-r2-09]`.

   These bootstrap asymmetries are covered by matrix jobs for every bootstrap (§14.2).

2. **`onModuleInit`** of the global core module, **once per application** `[R2:NEST-r2-05]`. `NestMicroservice.init()` runs `onModuleInit` and `onApplicationBootstrap` twice (`super.init()`, then `registerModules()`; REV2-NEST:`exp4b-double-init.mjs`, `exp4c-microservice-init-twice.mjs`, on 11.1.17 and 12.0.1). `InstanceRegistry` holds the application's lifecycle state (`new` → `initialized` → `bootstrapped`), and a repeated `onModuleInit` or `onApplicationBootstrap` returns at once (after the `LATE_HTTP_ADAPTER` check above), so nothing below runs twice and `bind()` is never called again for the same application. The boot checks are interleaved with the steps they validate, in this order:
   - instance and plugin checks: B01–B05, then the app-structure checks B07 and B25;
   - hook discovery, with B11 (singletons) and B12 (hook patterns and instance names);
   - exclusive binding, with B06 (live owner or takeover) and B26 (the plugin's pre-bind dispatch counter, read at bind). Binding is skipped for an instance whose B01–B04 failed, because it has no usable handle;
   - mount path resolution, with B10;
   - the remaining platform, plan, transport and advice checks: B08, B09, B13–B15, then every transport's `validate()` and the coverage rule over its claims (B16), then B17–B21, B23, B24, B27 and B28 (B21 collects every `advise()`);
   - aggregate: if any check failed, throw once with every error (a binding made above never bootstraps, so the next app takes it over, B06). Otherwise print the boot summary (B22);
   - `platform.mount()` per instance.

   This all happens before Nest registers its 404 and error handlers (EXP-C5). On Fastify the auth scope's child error handler reads Nest's handler at request time, so the handler Nest installs later is the one used (§6.4.2, LEAD-EXP-2).

3. **`onApplicationBootstrap`**, once per application. Marks each binding `bootstrapped`. A binding that never reaches this point (a failed `init()`) can be taken over by the next app (B06).
4. **`onApplicationShutdown`.** Unbind the plugin handles (idempotent). This runs after the HTTP server has stopped accepting requests, so in-flight requests keep their hooks. `onModuleDestroy` would be too early, because `close()` runs destroy → before-shutdown → `dispose()` (closes the adapter) → shutdown (Nest 11.1.17 `core/nest-application-context.js:126-133`) `[C]`.

**Guard registration and overriding.** When `globalGuard` is true, the registration is `providers: [{ provide: APP_GUARD, useExisting: BetterAuthGuard }, { provide: APP_INTERCEPTOR, useExisting: BetterAuthScopeInterceptor }]`. `overrideProvider(BetterAuthGuard)` replaces what `APP_GUARD` aliases; that does not work with `useClass` (R:nest-di §9). `@UseBetterAuth()`/`@UseGuards(BetterAuthGuard)` sites create separate injectables that only `overrideGuard(BetterAuthGuard)` replaces (`core/injector/module.js:344-356`). The testing helper `overrideAuthGuard` therefore does both, for the guard and the interceptor (§14.8) `[R1:NEST-r1-08]`. With `globalGuard: false`, `@UseBetterAuth()` applies both enhancers where needed, and B16 reports every claimed handler that declares something and that nothing guards, and every unclaimed method with library metadata (§5.4) `[R2:NEST-r2-02]`.
