## 12. Packaging

### 12.1 Shared tsdown configuration `[MONOREPO]`

The implementation extends the root `tsdown.config.mts`; each package defines `build` directly in its `package.json`. A typed package `tsdown.config.mts` supplies only the multi-entry and plugin-isolation differences. The root owns Node 24 targeting, separate ESM/CJS declarations, external dependencies, source maps, cleaning, and strict `publint: { strict: true }` plus `attw: { level: "error" }`. Do not copy the standalone v6 toolchain or add a build wrapper.

The Nest-facing build has entries `index`, `platform`, `express`, `fastify`, `graphql`, `websockets`, `microservices`, `admin`, `organization`, `api-key`, `testing` and `testing/conformance`, backed by the corresponding flat `src/<entry>.ts` files (`testing/conformance` maps to `src/testing-conformance.ts`). The separate `plugin` entry uses `src/plugin.ts`; its runtime graph can contain only `better-auth/api`, `better-auth/cookies` and `defu`. Entries within the library build share chunks per format. Root `deps.neverBundle` keeps Nest/Better Auth and optional SDK peers external. Packaging checks inspect the complete graph, declarations and source maps rather than inferring purity from entry filenames.

Package `tsconfig.json` extends root `tsconfig.base.json`; package test configuration extends root `tsconfig.test.json`. Shared `${configDir}` source patterns include source and tests in the editor project, and test typechecking uses no emit. Bundling is confined to the explicit entries above, so tests do not enter published artifacts. Root decorator settings and real consumer injection tests remain mandatory (§12.6). Source and declarations have no top-level await; load all entries via both `require` and `import` on Node 24.11.0 and current Node 24 LTS.

The module-sync-first export map remains hand-authored (§12.3); build tooling must not replace it with plain import/require routing. Preserve real CJS fallback output as well as the canonical ESM identity. Strict publint/attw and the actual packed consumers must pass before claiming the package is ready.

### 12.2 Formats and extensions

- The package is `"type": "module"`. Each entry emits `dist/<entry>.mjs` (ESM), `.cjs` (CJS), `.d.mts` and `.d.cts`, plus shared chunks per format.
- The `.cjs` fallback requires ESM-only peers through require(esm). The supported package floor is Node 24.11.0, matching the monorepo; Node 22 research establishes historical mechanism evidence, not a supported floor. The Node 24 consumer matrix must verify both graphs contain no top-level await.

- **The map is §2.1, one to one.** The thirteen subpaths of §2.1 are the thirteen subpath keys here (`./package.json` aside) and the thirteen entries of §12.1 (twelve in the library build, one in the plugin build). This exact shape, packaging variant A, passed attw with all columns green and publint with only an `engines` suggestion (R:packaging §5.4).

### 12.4 Engines and peers (D1, D4)

- **`engines.node: ">=24.11.0"`.** The monorepo’s Node 24 LTS baseline is authoritative. Earlier Node 22 observations remain historical evidence only. No upper bound is imposed; broader major support requires actual consumer checks, not an assumption from require(esm) availability. [MONOREPO]
- **Peers:** Nest `^11 || ^12`; `@nestjs/graphql ^13 || ^14`; `graphql ^16.11 || ^17` (both GraphQL majors peer on that range); better-auth `>=1.7.0 <2`. The table is §2.4.
- **better-auth specifiers we import.** A peer range is only as good as the subpaths it guarantees, so the list is closed and CI-checked:

  Every specifier in the table is in the `exports` map of better-auth 1.7.0 as well (LEAD-V33). The 1.7.0 floor job also loads every entry and runs the conformance kits (§14.2), so a specifier that a later release drops or moves fails our CI, not a user's boot. `@better-auth/api-key` is **not** a peer: `./api-key` calls `auth.api.verifyApiKey` and reads `$context`, and never imports the package (§2.4). It is a devDependency, installed in the matrix at the same version as better-auth.

- **Nest-owned identifiers.** The transports' handler claims and core's coverage rule read Nest metadata (§5.4 B16, §9.1–§9.4). Where Nest exports the identifier from a package root, we import it: `GRAPHQL_MODULE_OPTIONS`, `RESOLVER_TYPE_METADATA`, `RESOLVER_PROPERTY_METADATA`, `RESOLVER_REFERENCE_METADATA` `[R4:NEST-r4-01]` and `PARAM_ARGS_METADATA` from `@nestjs/graphql` 13 and 14 (LEAD-V30, LEAD-V42, LEAD-V50, LEAD-V55). Where it does not, the unit that needs it holds the string literal: `'path'` and `'method'` (HTTP routes, `httpTransport()`), `'websockets:is_gateway'` (LEAD-V13) and `'websockets:message_mapping'` (the WS units), `'microservices:pattern'` (LEAD-V32), and `'__guards__'` and `'__interceptors__'` (core's coverage rule, to recognize `@UseGuards(BetterAuthGuard)` with `@UseInterceptors(BetterAuthScopeInterceptor)`) (LEAD-V42) `[R2:NEST-r2-02, NEST-r2-11, NEST-r2-12]`. There are **no deep imports** of Nest packages: 12.x packages have `exports` maps, and the specifiers differ between the two majors (LEAD-V29). Each literal is pinned by a CI test on both majors (§12.9 step 7) `[R1:NEST-r1-05, NEST-r1-06, NEST-r1-13]`, and since v4 also checked **at boot, on the installed Nest**: the unit that holds a literal applies the real decorator that writes it (`@Get()`, `@WebSocketGateway()`, `@SubscribeMessage()`, `@MessagePattern()`, `@UseGuards()`, `@UseInterceptors()`) to a private probe class and reads the literal back, and a mismatch fails boot with `NEST_METADATA_KEY_CHANGED` (B16). A renamed key therefore fails a boot, not only a CI run, and no heuristic has to guess whether an empty handler list is genuine `[R3:NEST-r3-08]`.
- **No version probing** `[R1:NEST-r1-13, SEC-r1-12]`. Nothing in the package reads a Nest package's version or probes an API to infer it. A skewed install (for example `@nestjs/core` 12 with `@nestjs/websockets` 11, which package managers only warn about) therefore cannot switch a check off: gateway, hybrid-RPC and field-resolver coverage are required on every major (ADR-40). Mixed Nest majors remain unsupported. One feature detection exists, and it gates no check: the gRPC carrier uses Nest 12's `Grpc*Exception` classes when a namespace import of `@nestjs/microservices` has them, and plain `RpcException` codes otherwise (§9.4).
- **Semver.** Dropping a Node, Nest or better-auth major is a semver-major change. Format and engines never change in a minor release (#108, #130, #141). A change of the plugin protocol version (`BridgeHandle.protocol`, B04) is a semver-minor change at least, and both halves ship in the same package version.

### 12.5 Dual-package hazard strategy (S5) `[A][B][C]`

**Primary: `module-sync` first, ESM canonical (packaging variant A).** On every Node version in our engines range, `import` and `require` both resolve the `module-sync` branch, so both load the ESM build. There is exactly one copy of every class (`BetterAuthModule`, `BetterAuthGuard`, `BetterAuthService`, `WsConnectionAuth`, platform and transport classes) per process. This was verified for this exports shape on 22.12.0, 22.22.0 and 26.7.0 ("both→mjs", R:packaging §5.4). The CJS build serves tools that resolve `require` without `module-sync` support, such as some bundlers and runners, which is exactly R3's purpose. For bundlers, `default`-condition handling is UNVERIFIED and is covered by the bundler fixtures (§14.6).

**Defense in depth, independent of routing:**

1. Public per-instance DI tokens are stable strings with readable alias suffixes; internal collaborator tokens, metadata keys and runtime slots use `Symbol.for('nestjs-slightly-better-auth:…')` (§2.3). That includes the tokens extension units export (`WS_CONNECTION_AUTH`) and the per-invocation slots (`ACTIVE_ORGANIZATION_ID`, `ACTIVE_MEMBER_ROLE`) `[R1:NEST-r1-12, NEST-r1-01]`. `Symbol()` and random `Reflector.createDecorator()` keys do not survive two copies (R:packaging §5.2: `Symbol()` tokens → `UnknownDependenciesException`; `Symbol()` metadata keys → hooks silently not discovered).
2. Class tokens have copy-safe aliases (`BETTER_AUTH_SERVICE`, a stable string via `useExisting`; `WS_CONNECTION_AUTH`, a `Symbol.for` token for `WsConnectionAuth`) used with Nest’s `@Inject(getBetterAuthServiceToken(alias))` directly, so injection works across copies.
3. The plugin-to-kernel link is a versioned protocol object on the plugin instance, found through `getPlugin()` (§10.2). It is never shared module state.
4. Requirement metadata carries policy objects by reference, so the guard of either copy just calls `evaluate`. Principal kinds, accepted kinds and param-kind constraints are plain strings (§7.6), which compare equal across copies.
5. There is no `instanceof` on our own classes across the package boundary:
   - `isAuthFailure` (§2.2.6) checks the failure's `Symbol.for` brand, and the composition root recognizes an `ExtensionDefinition` by its `EXTENSION_DEFINITION` brand (§2.2.1), not by class;
   - our own error classes carry a `Symbol.for` brand too. The guard and `normalizeThrown` recognize `BetterAuthInfrastructureError` and `BetterAuthConfigurationError` with `isInfrastructureError` / `isConfigurationError` (§2.2.6), so an error thrown by a source or policy compiled against the other copy is passed through, not wrapped again `[R1:SEC-r1-19]`;
   - better-auth errors use `isAPIError` (S6);
   - the HTTP, WS and RPC denials are Nest's own exception classes, with one copy per Nest major. `BetterAuthGraphqlDenial`, `BetterAuthGraphqlInternalError` and `BetterAuthGraphqlRepeatedInternalError` are read by the GraphQL drivers structurally (`extensions`), never by class;
   - B16 recognizes `BetterAuthGuard` and `BetterAuthScopeInterceptor` among the application's global enhancers by identity with the instances their class tokens resolve to (a test override included), and by their `enhancer` brand only when the enhancer was registered from the other copy, so such an enhancer still counts `[R3:NEST-r3-02]` `[R4:NEST-r4-02]`.
6. There is no module-level mutable state. Everything lives in a provider, on an extension instance or on the plugin object `[R1:SEC-r1-15, SEC-r1-16, SEC-r1-18, SEC-r1-05]`:

   | State                                                                                                                                                                                                                                                                                 | Lives in                                                                                                       |
   | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
   | request, connection, invocation and browser-leg state (origin verdicts); route-plan cache per (class, handler); registries; the lifecycle state of the application that owns the container, with its adapter `[R3:NEST-r3-03]`                                                        | kernel providers (`RequestScope`, `RoutePlanner`, `TransportRegistry`, `InstanceRegistry`, `MountCoordinator`) |
   | once-per-application flags and caps: `W_PROXY_UNTRUSTED`, the degraded-tier warning, the 100-path cap of the 404 diagnostics                                                                                                                                                          | `AuthExchange` and the platform provider                                                                       |
   | per-request records: readings (§7.8), errors already surfaced, the count of distinct authorization calls, the shared re-classification read `[R3:SEC-r3-08]` `[R4:SEC-r4-04]`; the hourly window of origin-denial WARN lines and its summary counts `[R3:SEC-r3-03]` `[R4:SEC-r4-05]` | `RequestScope` (WeakMaps keyed by the request, invocation and carrier objects); `OriginCheck`                  |
   | resolved policy instances `[R3:NEST-r3-04]`                                                                                                                                                                                                                                           | `PolicyResolver`                                                                                               |
   | the API-key outage-probe throttle                                                                                                                                                                                                                                                     | the `apiKeyPrincipal()` source instance                                                                        |
   | the client-IP header name, the binding and its state (`closed` included), the pre-bind dispatch counter, the set of endpoint-produced results, the `initTestApp` slot                                                                                                                 | the plugin object returned by `nestjs()` (one per better-auth instance, B03)                                   |

   "Once" in a warning's description therefore means once per Nest application, which is also once per process outside tests.

7. Double registration across copies is caught by the exclusive plugin binding (B06), the per-server mount stamp (B10) and the one-declaration rule for platforms and transports (B25) (§5.6).
8. CI loads both builds in one process and asserts that tokens, metadata, brands and the plugin handshake interoperate (§14.6).

**What remains.** Class identity for enhancers: a hand-written `overrideProvider(BetterAuthGuard)` or `overrideGuard(BetterAuthGuard)` must import the same copy the app resolved, which `module-sync` makes automatic on supported Node. `overrideAuthGuard` from `./testing` no longer depends on that at all: it overrides `GUARD_CORE` and `SCOPE_CORE`, which are `Symbol.for` tokens and therefore identical across copies `[R5:NEST-r5-01]`. No guard-class lookup is part of the helper. [R6:NEST observation] This is documented and covered by the dual-load test.

**Rejected alternatives** (ADR-20):

- **`node` → CJS routing:** it would make every Node consumer, including Nest 12 ESM apps, run the CJS build, against better-auth's and Nest 12's ESM direction. It also needs `.d.cts` under `node.import` to avoid attw "Masquerading as ESM".
- **An ESM wrapper over CJS:** it makes CJS canonical, for the same reason.
- **ESM-only:** it violates R3.
- **Plain `import`/`require` routing:** it leaves the class-identity hazard open.

### 12.6 Decorator-metadata guarantees `[A][B][C]`

- **Explicit `@Inject(token)`** on **every** library constructor parameter, so correctness never depends on `design:paramtypes`. Isolated transpilation (oxc) emits `Object` for interface and type-only-import parameters (R:packaging §4.1). This covers the classes v2 added or made injectable for users (`WsConnectionAuth`, the extension classes behind `ExtensionDefinition.exports`).
- **Root `tsconfig.base.json`**, inherited by the package’s `tsconfig.json` that tsdown reads, sets `experimentalDecorators` and `emitDecoratorMetadata`. Package configs do not duplicate these settings. Without the first, tsdown **builds successfully** but emits TC39 decorator syntax that throws `SyntaxError` at load. Metadata is still emitted for users' own injectables that extend library classes.
- **CI checks:**
  - `dist/**/*.{mjs,cjs}` contains no raw `@`-decorator syntax;
  - `dist/index.mjs` contains `__decorateMetadata("design:paramtypes"`;
  - every entry is imported from the packed artifact in both formats, and a real Nest app with default/named injection is booted and shut down from each. Require the real `.cjs` fallback directly with require(esm) enabled for ESM-only Better Auth peers; disabling require(esm) is not a supported authentication consumer.
- **Biome.** `style/useImportType` is off for `src/**`, because its "safe fix" rewrites injected classes into type imports and yields `design:paramtypes: [Object]`. `unsafeParameterDecoratorsEnabled: true`. `noUnusedPrivateClassMembers` is off for constructor-injected members. `vcs.useIgnoreFile: true`. The literal ban of §3.2 rule 5 is a Biome restricted-syntax rule scoped to `src/kernel-*.ts` (§14.7) `[R1:NEST-r1-07]`.

### 12.7 Optional peers via subpaths

- The root entry imports only required peers. Every optional peer is imported **statically** and only by its own subpath: `./graphql` → `@nestjs/graphql`; `./websockets` → `@nestjs/websockets`; `./microservices` → `@nestjs/microservices`; `./testing` → `@nestjs/testing`. A REST-only app never resolves them (reference #82, #97, #100).
- `./admin` and `./organization` import the kernel only. `./api-key` adds `better-auth/plugins/access` and nothing else. The better-auth plugins themselves are the user's imports in `auth.ts`; their presence is boot-checked (B13).
- **Not used:**
  - Nest's `loadPackage`: sync and `process.exit` on failure in 11, async and internal in 12 (R:nest-di §8.1);
  - `createRequire(import.meta.url)('peer')`, which is bundler-hostile (#147);
  - bare `require`;
  - top-level await;
  - lazy `import()` on hot paths;
  - deep imports of Nest packages (`@nestjs/<pkg>/<path>`, §12.4).
- **Import-graph checks in CI:**
  - `.` must not reach an optional peer or any `src/unit-*.ts` file other than the built-in units the composition root re-exports (`http`, `session`);
  - `./plugin` (including its chunks) must not reach `@nestjs/*` or `node:*`; its only runtime imports are `better-auth/api`, `better-auth/cookies` and `defu`;
  - an extension must not import another extension;
  - no source file imports a Nest deep specifier, `better-call` or `@better-auth/*`.

### 12.8 Monorepo toolchain (R5) `[MONOREPO]`

- Run from the repository root with `mise exec -- pnpm …`. Node follows root LTS (currently 24); pnpm is the pinned supported stable 12.4.2. CI installs with `--frozen-lockfile`; checks never install or mutate dependencies.
- Use the existing root TypeScript 7.0.2, tsdown 0.23.0, Vitest 5.0.1, Biome, Prettier and Turbo streaming setup. Do not replace it with the historical TypeScript 6/standalone Vite proposal. Add a package-specific compiler or transformer only when actual declaration/metadata tests demonstrate a need and the shared setup cannot satisfy it.
- Biome covers supported source/configuration formats; Prettier covers Markdown/YAML. Configurations/scripts use `.mts` and `tsx` where needed; tests use `*.test.ts`, with middleware `*.e2e.test.ts` separately. Root source/test configs remain authoritative; examples and scripts participate in relevant root checks.
- Default unit tests require no network, credentials, Docker or prebuilt `dist`. Artifact consumers run via `pnpm test:packaging` **after** `pnpm build`. Service-backed middleware E2E uses isolated Compose services with health checks, `docker:up`/`docker:down`, and guaranteed cleanup; run separately via `pnpm test:e2e`.
- Origin/security tests explicitly set `advanced.disableOriginCheck: false`; `NODE_ENV=production` alone does not override Better Auth’s truthy `TEST` default under Vitest. B19 tests separately exercise resolved skip flags and environment changes.
- Root Lefthook is installed through mise’s `postinstall = "lefthook install"`: pre-commit lint/format/staged Gitleaks, commit-msg commitlint, pre-push build/typecheck. Scripts retain `typecheck`, `build`, `dev` order where present; dependency fields stay last in peer/dependency/dev order.
- Changesets is the only release versioning engine. Keep this package private pending reviewed implementation, registry ownership/name audit, owner-authenticated first publication, and trusted publisher setup. Do not enable publication or claim npm availability from a design change. Preserve MIT notices and historical changelogs.
