## 7. Authentication (principal resolution)

Authentication answers "who is calling". It produces an `AuthPrincipal`, a discriminated union over the augmentable `PrincipalKinds`. Authorization (§8) answers "may they" and never re-resolves identity.

### 7.1 Guard flow `[A][B][C]` `[R2:NEST-r2-01, NEST-r2-03, NEST-r2-08, SEC-r2-01]` `[R3:NEST-r3-01, BA-r3-01, SEC-r3-08]` `[R4:NEST-r4-01, NEST-r4-03]`

The guard **never returns `false`**. A `false` return makes Nest throw an HTTP `ForbiddenException` on every transport, which Mercurius, WS and RPC then mis-deliver (R:nest-di §3.4, §5). The guard always throws the transport-native error.

**Order.** The plan comes first, because it needs only the class and the handler. v2 selected the transport first, so a `@Public()` handler in a context no transport serves (a credential-less TCP message, a third-party context type that global guards reach) answered 500 `NO_TRANSPORT` (REV2-NEST:`exp3-external-context-global-guard.mjs`). The origin check comes before resolution, as better-auth's router runs `validateOrigin` before the endpoint reads a session: a cross-site request costs no storage read, and no principal is memoized for a request that is denied anyway. v2's runtime comparison of the principal's kind with the handler's param decorators is gone: every plan comes from the planner, which checks it at boot (B15), including the kinds `defaultRequirements` name, now that the `planFor` subclass seam that produced unchecked plans is removed (§7.6).

Every comparison in this flow is between values extensions supplied: `principal.kind` against `plan.accepts` (source `kinds`, `@AcceptPrincipals`, `requires.principals`). Core names no kind and no credential scheme `[R1:NEST-r1-07]`.

**Public plans and lineage** `[R3:NEST-r3-01]`. ADR-55 made public plans return before transport selection, so that a public handler in a context no transport serves does no auth work. v4 keeps that and adds one side-effect-free question for the transport that handles the context, if any: its `lineage()`. A public GraphQL root field thereby records "no identity" at its position, so a field resolver nested in it reads `null` from `@CurrentPrincipal()` instead of throwing `NO_AUTH_RESULT`, and a sibling guarded root field's principal is never visible to it (§7.8). Only transports whose invocations nest implement `lineage()`; for HTTP, WS and RPC the step costs one `handles()` loop and nothing else. Since v5 a **nested** public plan (a `@Public()` field resolver) records nothing, because its guard runs only when `fieldResolverEnhancers` includes `'guards'`: v4 let readers below it read "no identity" with field guards and the operation's principal without them (NEST-r4-03) `[R4:NEST-r4-03]`.

**Inherit plans and their entry point** `[R4:NEST-r4-01]`. An `inherit` plan means that an enclosing invocation the guard ran for decided. Since v5 the guard checks that, with the same lookup readers use (§7.8 item 2, without the test stamp): when the handling transport supplies a lineage and no enclosing position holds a reading, it describes the call (synchronous, no I/O) and throws `BetterAuthConfigurationError.atRequest('NO_ENCLOSING_DECISION')`, which the flow's error footer maps with that transport's `toInternalException` and `repeated` keyed by `call.key` (a generic 500, logged once per request). v4 returned `true` at once, so with `fieldResolverEnhancers: ['guards']` the field resolvers of a federation entity that has no reference resolver served data for any caller through `_entities`, where no Nest handler, and so no guard, runs for the entry point (REV4-NEST:`exp1-federation-reference.mjs`; §9.2). The check does no I/O: one `handles()` loop (`TransportRegistry.find`, §4.2.3), the lineage, and a map lookup per enclosing position, plus `describe()` when it fails. It runs only where the guard runs for field resolvers at all. After that structural enclosure check, an inherited **form** plan continues to the enforcing origin check before returning; it never resolves or records its own principal. Ordinary inherited plans still return immediately. [R7:SEC-r7-01]

### 7.2 Resolver contract and memoization (S7) `[A][B][C]` `[R1:NEST-r1-01, SEC-r1-13]` `[R2:NEST-r2-16, SEC-r2-07]`

The port is in §2.2.2. The default `ChainPrincipalResolver` keeps three memo scopes apart:

| Scope                                                                 | Keyed by                                                                                                                                                      | Holds                                                                                                                                         | Lifetime                                                  |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **Principal**                                                         | `(call.key, instance, freshness, plan.sourceSet)`; `(call.connection, …)` instead when `principalTtlMs > 0` and the plan's freshness is not `'authoritative'` | the resolution promise                                                                                                                        | the logical request; a connection entry until `expiresAt` |
| **Policy I/O** (`AuthorizationContext.memo`, `PrincipalRequest.memo`) | `(call.key, instance, key)` where the key names concrete inputs as a serialized tuple (e.g. `["org:hasPermission","<orgId>",<permissions>]`)                  | promises of better-auth calls; the count of distinct policy keys, bounded by `limits.maxAuthorizationCallsPerRequest` (§8.1) `[R3:SEC-r3-08]` | the logical request, **never** a connection               |
| **Decision and per-invocation values**                                | `(call.invocation, instance, requirement expression)`                                                                                                         | the requirement's decision; values policies `provide()` (the resolved organization id)                                                        | one handler invocation                                    |

- **Storage.** `WeakMap<object, RequestState>` inside the singleton `RequestScope`. There is no module-level state and no DI request scope.
- **The principal promise is stored before it settles** `[A][B]`. GraphQL runs the guard once per root field, three times for three root fields in one request (R:nest-di §3.4; EXP-B:E8: 3 guard calls → **1** resolution). Concurrent invocations share one `getSession`. A rejection is memoized for the same request key too, so every root field fails the same way and a failing database sees no retry storm. The re-classification read a policy's generic 401 triggers is shared by the request the same way, in the policy I/O memo (§8.1) `[R4:SEC-r4-04]`. The scope also remembers that the rejection was surfaced, so on GraphQL only the first invocation throws a loggable error and later ones throw its intrinsic twin (§13.4) `[R3:SEC-r3-08]`.
- **Decisions are per invocation, never per request or connection.** A requirement object is created once, when the decorator is evaluated, so v1's "memoize by requirement identity per request" let two aliased root fields asking about different organizations share one allow, and let a WebSocket connection with a principal TTL reuse an allow across messages. Since v2 decisions are keyed by `call.invocation`: the GraphQL field's `info` (for a federation reference resolver, the representation, §9.2) `[R4:NEST-r4-01]`, the WS message's `args`, the HTTP request, the RPC context. Two guard runs of the **same** invocation (global guard plus `@UseBetterAuth()`) still share one decision. Policies that want cheap repeats dedupe their better-auth calls through `memo` keyed by their concrete inputs, so two identical checks cost one call and two different organizations cost two (Z6).
- **Source set.** The chain is filtered by the route's accepted kinds (§7.6). The planner records the filtered chain by **content**: the ordered indexes of the consulted sources in the instance's list, interned per instance (`RoutePlan.sourceSet`, e.g. `'0,2'`). That key is part of the principal key, so three root fields in three resolver methods with equal accepted kinds share one resolution, and root fields with different accepted kinds resolve each distinct set at most once. v2 said "the filtered list's identity", which a per-plan list would have split into one resolution per plan `[R2:NEST-r2-16]`.
- **Chain.** Resolution runs inside `handle.run({ cookies: call.cookies, forward: 'same-credential', inbound: call.headers, internal: true }, …)`, the same scope shape the evaluator uses (§8.1). That makes every nested better-auth call of every source cookie-aware (P2): refresh is suppressed where the transport cannot deliver cookies (§7.4), a `Set-Cookie` produced by a call that carries the request's own credential or none reaches the client through the bridge where it can, and the call is marked internal for hooks (§10.4). The built-in session source is the one exception, and it makes it itself: it wraps its `getSession` in a nested `run({ forward: 'none' })` and forwards that call's cookies through `returnHeaders`, so they are delivered exactly once (§7.3, ADR-09). A third-party source that also forwards a call's cookies by hand does the same; if it forgets, the kernel's cookie sink de-duplicates identical `Set-Cookie` values. The sources run in order: skip those whose `appliesTo` is false, stop at the first `authenticated` or `rejected`, and return `absent` if none applies (§4.3.3).
- **Connection entries** (WS, operations over a GraphQL WebSocket with `principalTtlMs > 0`). They store only settled `authenticated` and `absent` results, with an `expiresAt`. A `rejected` result (for example a transient 429) and an infrastructure failure are memoized per message only, and an infrastructure failure evicts the connection entry. A database blip therefore costs one failed message, not the TTL `[R1:SEC-r1-13]`. **Plans whose freshness is `'authoritative'` never use connection entries**: they resolve per message or per operation, so a TTL cannot delay a ban or a demotion on `@RequirePermission` handlers (§8.4) `[R2:SEC-r2-07]`.
- **Readers never touch the resolver.** v3's `peek(call, request)` let the scope interceptor and `principalFor` look up the settled entry under a plan's memo key, which is the lookup that handed a nested GraphQL field a sibling root field's principal (NEST-r3-01). Readers now read what the guard recorded (§7.8), and the port has `resolve` only `[R3:NEST-r3-01]`.
- **`reclassify: { sourceId }`** resolves once more through the one source that produced the principal, bypassing the principal memo. Only the evaluator's re-classification of a generic 401 uses it, and only for a `sessionBacked` source (§8.1) `[R2:BA-r2-03]` `[R3:BA-r3-01]`. The evaluator memoizes that call per logical request in the policy I/O memo, under `(call.key, instance, ["reclassify", sourceId])`, with the promise stored before it settles and counted against the authorization budget (§8.1), so every invocation of the request that meets a generic 401 shares one re-read and one outcome; v4 re-read once per invocation, outside the memo and the budget, so 300 aliases during a brownout made 300 uncached session reads and 300 ERROR lines (SEC-r4-04) `[R4:SEC-r4-04]`.

### 7.3 Built-in session source (S2) `[A][B][C]` `[R2:BA-r2-01, BA-r2-06]`

```ts
export const SESSION_PRINCIPAL_KIND = "session" as const;

export const sessionPrincipal = <S = AuthSession>(
  options: SessionPrincipalOptions<S> = {},
) =>
  definePrincipalSource<SessionPrincipal>({
    id: "better-auth:session",
    kinds: [SESSION_PRINCIPAL_KIND],
    acceptance: "default", // every authenticated route
    credentialHeaders: ["cookie", "authorization"], // bridge comparison and redaction (7.5, 13.4)
    sessionBacked: true, // its principal is getSession's answer: a generic 401 contradicts it (8.1) [R3:BA-r3-01]
    async resolve(r) {
      const ctx = await r.auth.context();
      const stateful = Boolean(
        ctx.options.database || ctx.options.secondaryStorage,
      ); // mirrors hasServerSessionStore
      const authoritative = r.freshness === "authoritative";
      const query: { disableCookieCache?: true; disableRefresh?: true } = {};
      if (authoritative && stateful) query.disableCookieCache = true; // stateless: the cookie IS the session
      if (r.cookies === null) query.disableRefresh = true; // belt; the plugin's skip flag is the braces (7.4)

      let result: { headers?: Headers | null; response: unknown };
      try {
        // forward: 'none' → this call's cookies are forwarded exactly once, through returnHeaders (no bridge duplicate)
        result = await r.auth.run(
          { cookies: r.cookies, forward: "none", internal: true },
          () =>
            r.auth.api.getSession({
              headers: r.headers,
              returnHeaders: true,
              query,
            }),
        );
      } catch (e) {
        const failure = AuthFailures.fromAPIError(e); // 401/403/429 (bad x-api-key, failed refresh, api-key rate limit + Retry-After)
        if (!failure) throw e; // ≥500 or non-APIError → infrastructure (S6)
        const cleanup = apiErrorSetCookies(e); // e.headers + hidden better-call:api-error-headers
        if (r.cookies && cleanup.length) r.cookies.append(cleanup);
        return rejected(failure);
      }
      if (r.cookies) {
        const setCookie = result.headers?.getSetCookie() ?? []; // a before-hook short-circuit returns no Headers (LEAD-V37)
        if (setCookie.length) r.cookies.append(setCookie); // ONLY set-cookie: never cache-control / pragma
      }
      if (result.response == null) return absent();
      // Authoritative: only what the get-session endpoint itself produced, never a session a before-hook supplied (an API key's
      // mocked session, a short-circuiting hook). That is the set better-auth's getAuthoritativeSessionFromCtx accepts (LEAD-V36, LEAD-EXP-8).
      if (authoritative && !r.auth.producedByEndpoint(result.response))
        return absent();
      const userId = (options.userId ?? defaultUserId)(result.response as S); // default s.user?.id; customSession → session.userId option
      if (userId === null)
        throw BetterAuthConfigurationError.atRequest(
          "SESSION_USER_ID",
          "session.userId returned null for a resolved session",
        );
      return authenticated({
        kind: SESSION_PRINCIPAL_KIND,
        source: "better-auth:session",
        userId,
        session: result.response as S,
      });
    },
    // jwt without disableSettingJwtHeader, bearer without requireSignature, and (api-key plugin present) W_API_KEY_FULL_SESSION /
    // W_API_KEY_SESSION_MULTIPLIER, which also reads ctx.policies and options.apiKeySessions (7.9, 8.3.1); and W_ORIGIN_CHECK_NATIVE_CLIENTS
    // when the expo plugin is present and ctx.originCheck.missingOrigin is 'reject' (7.10) [R3:SEC-r3-03]
    advise: (ctx) => costHints(ctx, options),
  });
```

- **`returnHeaders: true`** keeps the refresh and cookie-cache `Set-Cookie`s that a plain call drops. There are 9 code paths (R:ba-core §4.3). EXP-C1's baseline with `updateAge: 0` emits `session_token`. It works for `customSession` too, because it is a dispatch-level feature (`BA/api/dispatch.ts:467-477`).
- **A short-circuited dispatch returns no `Headers`.** When a before-hook answers `/get-session` itself (the api-key plugin with `enableSessionForAPIKeys`, or a Nest `@BeforeAuth('/get-session')` hook returning an object, §10.5), better-auth returns `{ headers: undefined, response }` unless a hook set a response header (LEAD-V37). v2 dereferenced the headers and answered 500 for every such request on cookie-capable transports (REV2-BA:`exp1-apikey-returnheaders.mjs`). `AuthLike.api.getSession` types the result accordingly (§11.3), and `S-short-circuit-session` pins it `[R2:BA-r2-01]`.
- **Only `set-cookie` is forwarded.** `getSession` also returns `cache-control: no-store` and `pragma: no-cache`, which must not leak onto app responses (R:ba-core §4.3). EXP-A:`exp-e2e.mjs` verified one `session_token` and `cache-control=null` on a guarded route on all four platform × major combinations.
- **Credential translation happens inside `getSession`.** Bearer, api-key session mocks (`enableSessionForAPIKeys`), jwt side effects, multi-session and `customSession` all take effect through better-auth's own hooks, so the source never parses credentials (R1). Hooks see the original request: the bearer plugin's cookie rewrite happens inside the dispatch and is invisible to other before-hooks (LEAD-V23).
- **`authoritative` accepts what better-auth's authoritative read accepts** `[R2:BA-r2-06]`. better-auth's admin and sensitive endpoints read the session with `getAuthoritativeSessionFromCtx`, which discards a session a hook placed in the context and re-reads through the plain `getSession()` function, where no hook runs (LEAD-V36). A key-mocked session therefore never reaches them: every admin endpoint answers 401 for a key under `enableSessionForAPIKeys` (REV2-BA:`exp6-apikey-session-admin.mjs`). v2's authoritative read went through the hook pipeline and accepted the mock, so a narrow CI key passed `@RequirePermission` with its owner's admin role. The source now keeps the two parts of better-auth's rule: the cookie cache is bypassed when a server-side store exists (`BA/api/routes/session.ts:520-539`) `[C]`, and the session must be one the get-session endpoint produced. The `nestjs()` plugin observes that: its after-hook records the object an endpoint returned, and a before-hook short-circuit skips every after-hook (LEAD-V37, §10.2). LEAD-EXP-8 compared the record with better-auth's own verdict for cookie, bearer, key-session, short-circuit and replaced-result requests, with and without `customSession`, on 1.7.0 and 1.7.4: they agree in every case but one. A request carrying both a session cookie and an API key is answered as the key's owner by better-auth's ordinary endpoints and as the cookie's user by its admin endpoints; the kernel answers `absent` (401) on an authoritative route, the stricter of the two (RK27). Routes with the default freshness accept a key session, exactly as better-auth's `sessionMiddleware` endpoints do (§8.3.1).
- **The user-id mapping lives in the source** (`session.userId` runtime option), not in `AuthHandle`, so core has no notion of a session shape `[R1:NEST-r1-07]`.

### 7.4 Cookie forwarding and refresh suppression per transport capability (S2)

`getSession` emits `Set-Cookie` on 9 code paths (R:ba-core §4.3). Two of them move server or cookie state:

- **row 7, sliding refresh:** the DB `expiresAt` is extended and `session_token` is re-set;
- **row 4, stateless refresh-cache:** `session_data` is re-issued and `session_token` is re-set, with no DB write.

If the cookie cannot be delivered, the browser cookie expires before the server session, which is the drift better-auth works to avoid (`BA/api/state/should-session-refresh.ts:3-10`; `nextCookies`). Where the transport can deliver cookies, they are forwarded. Where it cannot, the refresh itself is suppressed, not just its cookies dropped.

**How suppression works** `[A][B][C]`. It is construction-time plugin behavior, following the `nextCookies` precedent. The `nestjs()` plugin registers one before-hook:

- **matcher:** `ctx._flag !== 'router' && binding?.current()?.cookies === null`;
- **handler:** `await setShouldSkipSessionRefresh(true)`.

This is the only public way to set that flag. It lives in better-auth request state, which exists only inside a better-auth dispatch. `better-auth/api` exports the setter (LEAD-V2) but not `runWithRequestState`, which lives in `@better-auth/core/context`. A before-hook runs inside the dispatch's own store, so the flag lands exactly where `getSession` reads it (EXP-C1: "plugin skip-refresh set-cookie: []").

**Stateless refresh-cache branch.** Without a database or secondary storage, better-auth force-enables `cookieCache` with `refreshCache` (`BA/context/create-context.ts:104-116`). That branch checks **only** `getShouldSkipSessionRefresh()` (`BA/api/routes/session.ts:199-204`, LEAD-V3). `query.disableRefresh` returns early only later (`:309`), so on its own it does **not** stop the branch. EXP-A:`exp-plugin.mjs` and EXP-B:E2 show this:

- control, `disableRefresh` only: `session_data` and `session_token` emitted;
- with the skip flag: none emitted.

The session source still passes `disableRefresh: true` on cookie-less calls as a belt, because it also skips rows 6 and 9 (a pointless cookie-cache write).

**Why any path, not just `/get-session`.** `nextCookies` suppresses only on `/get-session` (LEAD-V14), but plugin endpoints that read the session internally slide it too. Policies call `hasPermission` and `getActiveMember`, for example. EXP-B:E3, re-run by A and C:

- without a scope, `getActiveMember` emits `session_token` and moves the DB expiry;
- inside a cookie-less scope, neither happens.

The matcher therefore covers every non-router call made inside a cookie-less scope.

**Cleanup cookies** (rows 1, 2, 3 and 5: expire a stale cache or delete an invalid token) are still computed by better-auth. On cookie-less transports they are dropped harmlessly, and the next cookie-capable request cleans up again.

**The plugin is mandatory** (B03). Without it the stateless branch and nested plugin-endpoint refreshes could not be suppressed, and the library's own policy calls could not forward the refreshed cookies they produce. That would be two behavior modes users cannot see (ADR-02).

### 7.5 Direct `auth.api.*` calls in application code `[A][C]` `[R1:BA-r1-02, SEC-r1-03]`

`BetterAuthScopeInterceptor`, a global `APP_INTERCEPTOR` registered with `useExisting`, handles each handler invocation:

1. It reads the plan first, then selects the transport without requiring credentials. No transport means no scope. For a handled context, `describe()` builds a nonthrowing structural envelope (§4.2, T11): missing upgrade requests and unrecognized/stale GraphQL requests remain deferred configuration errors.
2. It opens `RequestScope.run({ get cookies() { return call.cookies; }, forward: plan.forwardDirectCalls ? 'same-credential' : 'none', inbound: () => call.headers(), get browserHeaders() { return call.browser?.headers; }, internal: false, plan, reading }, …)` around the _subscription_ to `next.handle()`. `reading` is a **lazy getter** over §7.8's one lookup for this invocation: no identity on a public plan, the nearest enclosing reading on an inherit plan, the guard's recorded result otherwise `[R3:NEST-r3-01]`. It is lazy because the interceptor is global whatever `globalGuard` says (§5.7, ADR-70), so it also opens scopes for handlers no guard ran for; taking the reading or credential capabilities eagerly would throw `NO_AUTH_RESULT` there before the handler started, where the handler may never read a principal at all. The readers throw that same error themselves when they do read (§7.8 item 6), so nothing about the error or its call sites changes `[R5:SEC-r5-01]`:

```ts
intercept(ctx: ExecutionContext, next: CallHandler) {
  const scope = this.scopes.forExecution(ctx);                     // null when no transport handles ctx, or a scope is already open [R5:SEC-r5-01]
  return scope ? new Observable((sub) => scope.run(() => next.handle().subscribe(sub))) : next.handle();
}
```

**Scope creation must not consume authentication capabilities** `[R6:SEC-r6-02]`. `forExecution` never eagerly reads `call.headers()`, `browser`, `cookies`, `request`, `clientIp`, or the principal reading. The scope’s `checkCallerSession` is likewise installed through a deferred getter; merely opening the scope does not probe the browser leg. Structural `key`, `invocation` and lineage come from Nest arguments even if no credential request can be recognized. A public `ws` handler without `withUpgradeRequest` and a public GraphQL query with an unrecognized context therefore run normally. A guarded handler consumes the deferred accessors and throws the original configuration error; a public handler that calls `auth.api` also encounters that error before any endpoint side effect when the plugin consumes the scope capabilities. Never replace an unavailable browser leg with `undefined`, or an unavailable cookie sink with `null`: those mean a known non-browser/cookie-less transport, not failed extraction. No automatic `runOutsideScope` fallback is allowed. An inheriting reader validates the live request only before returning an authenticated enclosing reading; public/no-identity reads do not inspect auth infrastructure. The record reader must not return a principal from a finished GraphQL request.

A second run for the same invocation is a no-op: the interceptor is global and `@UseBetterAuth()` adds it again, so `forExecution(ctx)` returns `null` when a scope for this invocation is already open, exactly as duplicate guard runs are memo hits (§9.3). That was already the case under `globalGuard: true`; since v6 it also covers `globalGuard: false` plus `@UseBetterAuth()` `[R5:SEC-r5-01]`.

Nest invokes the handler and its param factories inside the interceptor chain (`router-execution-context.js:40-46`; WS: LEAD-V7), and `InterceptorsConsumer` binds each step with `AsyncResource`.

**Default: better-auth's server-call semantics.** A direct `auth.api.*` call from a handler or a service behaves as it does in plain better-auth: its `Set-Cookie` is **not** written to the caller's response. The one change is in cookie-less scopes (WS, RPC, subscriptions), where refresh is suppressed because nothing could deliver the cookie (S2). In plain better-auth a server call never touches the browser unless the developer adds a cookie plugin (`nextCookies`) or uses `returnHeaders`/`asResponse`. v1 forwarded every direct call, so an admin handler that ran `auth.api.signUpEmail({ body })` (auto sign-in is on by default) swapped the admin's browser session for the new user's (BA-r1-02), and a service that called `getSession` with a service-account bearer token could hand that session to the end user (REV-SEC:`probe-bridge-foreign.mjs`) `[R1]`.

**Opt-in forwarding** for handlers that proxy the caller's own login or logout is declared where the guard can see it, because a handler that can set auth cookies gets an enforcing form-CSRF check **on every HTTP method and GraphQL operation kind**, with or without an inbound cookie (§7.10):

- per handler or controller: `@ForwardAuthCookies()` (and `@ForwardAuthCookies(false)` to opt one handler out of a controller-level opt-in);
- per instance: `cookies: { forwardDirectCalls: true }` (B28 warns, because it applies to every handler).

v3 also offered a per-call-site switch, `service.forwardCookies(fn)`. It turned forwarding on inside any handler, so a `@Public()` login proxy written with it had origin-check mode `'cookie'`, the guard returned before any check, and a cross-site page could sign the victim's browser into the attacker's account (login CSRF, SEC-r3-04). It is gone `[R3:SEC-r3-04]`.

**Credential matching** (plugin entry 6, §10.2). B16 and the guard require the enforcing form check before any forwarding handler runs, irrespective of method or inbound cookies; credential-free login calls depend on that check, not the existing-session comparison. No second form check runs inside the plugin. [R7:SEC-r7-01] Where forwarding is on, the bridge forwards a direct call's `Set-Cookie` only if the call carried **no credential** (a login or sign-up) or **the caller's own credential**. The credential is compared as a triple: the session-token cookie, found by name through `$context.authCookies.sessionToken.name` and parsed with better-auth's `parseCookies`; the `authorization` header; and the values of every source's `credentialHeaders` (for example `x-api-key`). Anything else is dropped and logged once at debug with the endpoint path. Deliberate account switching (impersonation, "sign in as") wraps the call in `service.forwardForeignCookies(fn)`, which forwards every call inside `fn` and works only in a handler that already forwards; anywhere else it throws `FORWARDING_NOT_DECLARED` (§2.2.2) `[R1:SEC-r1-03]` `[R3:SEC-r3-04]`.

**Library-internal calls always forward.** The resolver chain (§7.2) and the evaluator (§8.1) both run in `forward: 'same-credential'` scopes. Policies and principal sources call `auth.api.*` with the request's own headers, so their cookies (for example a sliding refresh inside `hasPermission`) are the caller's own and reach the browser on cookie-capable transports: the credential matches. One exception is harmless: for a bearer client, the bearer plugin's before-hook adds the session cookie to the call's headers inside the dispatch (`BA/plugins/bearer/index.ts:100-115`), so the bridge sees a credential triple that differs from the inbound one and drops that call's `Set-Cookie`, which a bearer client does not use anyway (`reviews/round-2-BA.md`, BA's observation on BA-r1-02; the credential-matching unit test expects the drop, §14.5). A third-party source that presents a credential other than the request's gets that call's cookies dropped, like any foreign credential. The session source's own `getSession` is the one internal call that runs with the bridge off, because it forwards through `returnHeaders` (§7.3).

**Direct credential endpoints bypass better-auth's router protections.** A server-side `auth.api.signInEmail({ body })` skips better-auth's rate limiter and origin check, which run only in the router (`BA/api/index.ts:285-292, 310`; LEAD-V16). The docs therefore recommend letting clients call better-auth's own routes (through the mount) for sign-in, sign-up and password flows, and keeping direct credential calls for trusted back-office code. A handler that does proxy them should apply the app's own throttling. `@ForwardAuthCookies()` (or the instance option) is required for its cookies to reach the browser at all, so the pattern is always an explicit choice, and one the guard protects with the form-CSRF rule.

**No direct call acts with the caller's session on an unverified leg** `[R4:SEC-r4-02]` `[R5:SEC-r5-01, SEC-r5-02]`. "Public means no identity" (§7.6) kept `BetterAuthService` from resolving the caller in a `@Public()` handler, but not `auth.api` itself: `@Public() @Post('account/email') change(@Req() req, @Body() b) { return this.auth.api.changeEmail({ headers: this.auth.headersFrom(req), body: b }); }` acted as the victim for a cross-site form post, because the guard returns before the origin check on public plans and better-auth's own check is router-only (REV4-SEC:`probe-public-direct-call-csrf.mjs`: `updateUser` and `revokeSessions` succeeded cross-site while the router answered 403 `INVALID_ORIGIN`). **The trigger is the plan, not the HTTP method** `[R5:SEC-r5-02]`. The scope interceptor supplies a caller-session check (`ScopeView.checkCallerSession`, §10.2) to **every** handler scope whose transport exposes a browser leg at all and whose plan's origin check is not `'off'` — whether or not that leg _enforces_ the origin check. The plugin's before-hook entry 2 runs it for every non-router, non-internal call in such a scope that carries the scope's own session-token cookie (the first element of the credential triple above). It passes when any of these holds, and throws otherwise:

- the origin check already passed for this leg and instance (the memoized verdict, §7.10);
- the single kernel disable predicate in §7.10 item 4 holds. A boolean `skipOriginCheck` alone is not sufficient when `disableCSRFCheck` is explicitly false.

**A guard run is not evidence of a trusted origin.** The v6 third pass condition is removed: a resolved principal requires the same passing verdict as every other caller-session use. Guarded unsafe legs already have one; guarded safe legs can obtain an advisory verdict without denying the safe request (§7.10, Q40). An `absent`/authenticated resolution alone never passes. `[R6:SEC-r6-01, BA-r6-01]`

The throw is `BetterAuthConfigurationError.atRequest('PUBLIC_HANDLER_USED_CALLER_SESSION')`, before the endpoint runs, which the handler's call rethrows: a generic 500, logged with the hint "Make a state-changing proxy POST and use `@OptionalAuth()` (plus `@ForwardAuthCookies()` when returning auth cookies); send a trusted Origin. For a deliberate server-to-server route, explicitly use `@SkipOriginCheck()` after assessing its callers." Guarded safe-method proxies can now trip it when their advisory verdict fails; a public mutation field that runs after a guarded one in the same operation passes (mutation root fields run in order), because that guard verified the same HTTP request; and cookie-less legs, calls without the caller's session cookie (a sign-up with no headers, a bearer or API-key call) and `@SkipOriginCheck()` handlers are untouched.

Two cases this closes that v5's `enforce`-keyed trigger left open:

- **Safe methods.** v5 keyed presence on `browser.enforce`, which is false for GET, HEAD and OPTIONS (§7.10 item 2) and for a `@Public()` GraphQL **query** resolver over HTTP, so `@Public() @Get('logout') logout(@Req() req) { return this.auth.api.signOut({ headers: this.auth.headersFrom(req) }); }` — a shape the reference library's users commonly have — ran as the victim, and `<img src="…/logout">` on any page forced a logout; the same shape with `unlinkAccount`, `acceptInvitation` or `deleteUser` on a GET route changed account state. better-auth's own router skips safe methods too, but better-auth exposes no state-changing endpoint over GET, while this design hands app handlers `headersFrom(req)` and lets them call any endpoint from any method. v5 pinned the gap (`LIB-public-direct-call`: "from a GET route … is not affected") instead of closing it; the rule above closes it for public and guarded proxies. A cross-site guarded GET can still read its principal, but its subsequent caller-session direct call fails before changing state. A trusted-origin guarded GET retains a passing advisory verdict. [R6:SEC-r6-01]
- **Handlers no guard ran for.** Under `globalGuard: false` an undecorated handler has a `required` plan but no guard run and no verdict, so neither passing condition holds and the check throws — which is what SEC-r5-01 needs once the interceptor is global (§5.7). B16 still reports such a handler when it declares something; the check covers the one it cannot see, a direct `auth.api` call in a handler that declares nothing.

The check is not a second origin check: it only reads the verdict the guard computed, including an advisory safe-leg verdict, and fails closed without a pass unless the single kernel disable predicate holds (§17 Q37, §17 Q38). Verdicts are per instance, as trusted origins are: a handler whose plan belongs to one instance and that calls **another** instance's `auth.api` with that instance's session cookie, on a leg that carries it, fails the same way unless a plan of the same request checked the origin for that instance too; such a handler belongs to the instance it acts on (`@UseAuthInstance`), and the error's detail names both instances (RK32).

- **Why an interceptor rather than a platform-level scope opened at `init$`** (drafts B, C; ADR-11):
  - it is transport-neutral;
  - it runs after body parsing;
  - it gives param decorators a race-free source on WebSockets, where the per-message `args` array is not visible to param factories (LEAD-V7);
  - it keeps the platform contract small.

  An early scope would survive Express parsing (LEAD-V11), but it would cover HTTP only.

- **Coverage gaps, documented.** Code in middleware, in guards (including other libraries' guards) and in policies runs outside the scope. So do GraphQL field resolvers unless `fieldResolverEnhancers` includes `'interceptors'` (their continuations run outside the root resolver's scope), and gateways without `@UseBetterAuth()` (which B16 rejects). Since v6 `globalGuard: false` is **not** a gap: the scope interceptor is registered by the default instance whatever `globalGuard` says, so every handler a transport recognizes has a scope, with the caller-session check, refresh suppression and the cookie bridge (§5.7) `[R5:SEC-r5-01]`. The remaining explicit gap is `globalScope: false`, which B31 warns about at every boot; `runOutsideScope(fn)` remains the per-call-site escape. Such code gets plain better-auth semantics for direct calls; it can use `service.withoutCookies(fn)` or its own `returnHeaders`. Decorators there run the §7.8 lookup themselves. `BetterAuthService.getPrincipal()` throws `NO_AUTH_SCOPE` there; a guard or interceptor reads the principal with `service.principalFor(ctx)` (§7.8) `[R2:NEST-r2-07]`.
- **Opting out entirely.** `service.runOutsideScope(fn)` runs `fn` as if no scope existed: no forwarding, no suppression and no caller-session check `[C]`. It is a visible, deliberate choice in code; the docs name the CSRF consequence for unsafe public handlers `[R4:SEC-r4-02]`.
- **Committed responses.** If a handler has already sent the response itself (`@Res()` plus a manual send), the sink reports `false`. The bridge then logs one debug line and drops the cookies.

### 7.6 Public, optional and required semantics; accepted principal kinds `[A][B][C]`

**Plan compilation** (`RoutePlanner`, cached per (controller class, handler)) `[R2:NEST-r2-01, NEST-r2-04, NEST-r2-08]`:

0. **Cache key.** Plans are cached in a `WeakMap<Type, WeakMap<Function, RoutePlan>>` keyed by `ctx.getClass()`, then `ctx.getHandler()`, and never by the handler alone. Nest hands every subclass the **same** handler function for an inherited route method (REV2-NEST:`exp1-inherited-handler.mjs`, 11.1.17 and 12.0.1), while the plan depends on the class chain. v2 cached per handler, so in `abstract class CrudController { @Get() list() {} }` with a `@Public()` subclass and a `@RequirePermission` subclass, whichever route was requested first decided the other's plan. The boot scan compiles the same (class, method) pairs.
1. Read the access decorator (`@Public` / `@OptionalAuth` / `@RequireAuth`), `@AcceptPrincipals`, `@SkipOriginCheck`, `@ForwardAuthCookies` and the requirements at the **method** level and at the **class** level. For the class level, use the own metadata of each class in the prototype chain, most-derived first.
2. **Same-level contradiction** fails boot (B15). `@Public()` or `@OptionalAuth()` together with requirements at the same level is contradictory: an anonymous caller can never satisfy a principal requirement.
3. **Nested handlers first** `[R3:NEST-r3-05]`. The planner asks every registered transport's `defaultAccessFor(class, method)`; the first answer wins. An answer of `'inherit'` marks a **nested** handler (a GraphQL field resolver, §9.2), and for it the class level's access decorator, `@AcceptPrincipals`, requirements and `@SkipDefaultRequirements()` are not read. Its effective access is its method's access decorator, else `'required'` if the method has requirements, else `'inherit'`. v3 read class-level metadata first, so `@RequireOrgMember({ organization: fromParam('orgId') })` on a resolver class gave every field resolver of the class a real plan: boot failed by default (`FIELD_RESOLVER_UNGUARDED`), and after following the hint every list item answered 403, because a field resolver has no `orgId` argument, with no way to say "inherit" (REV3-NEST, NEST-r3-05). Class-level `@UseAuthInstance`, `@SkipOriginCheck` and `@ForwardAuthCookies` still apply to nested handlers: they choose an instance and origin handling, not who may call. An inheriting handler's readers take the enclosing reading whatever its instance (§7.8), so `@UseAuthInstance` changes what a nested handler reads only when the handler has a real plan `[R4:NEST-r4-03]`. The plan records `nested: true` either way. §17 Q30 records the choice.
   **Effective access** of every other handler is decided by the closest level that says anything:
   - the method's access decorator; else
   - `'required'` if the method has requirements; else
   - the class's access decorator; else
   - `'required'` if the class has requirements; else
   - `defaultAccess`.
4. **Effective requirements.** If access is `'required'`, they are the instance's `defaultRequirements` (unless `@SkipDefaultRequirements()` applies, method or class), then class requirements (base first; none for nested handlers), then method requirements, in declaration order. Otherwise there are none. A method-level `@Public()` or `@OptionalAuth()` is therefore an explicit, visible opt-out of class-level requirements (§17 Q3), and of `defaultRequirements` too; `@SkipDefaultRequirements()` opts a handler out of the defaults alone and keeps its own requirements, which is what a machine route under a company-wide `orgMember()` needs. Both are counted in the boot summary (B22), and a plan whose AND-ed requirements admit no common principal kind fails boot (B15 `UNSATISFIABLE_PRINCIPAL_KINDS`) `[R3:NEST-r3-06]`. `defaultRequirements` replaces v2's protected `BetterAuthGuard.planFor` seam: an overriding subclass could not be registered at the global guard, at `@UseBetterAuth()` sites or in the coverage check, its plans escaped boot validation, and the scope interceptor and decorators read different plans than the guard. A runtime option compiled into every plan has none of these gaps `[R2:NEST-r2-08]`.
5. **Accepted kinds** `[R1:SEC-r1-02, BA-r1-01]`:
   - the kinds named by the closest `@AcceptPrincipals(...)` (method over class); otherwise the instance's _default kinds_, the `kinds` of every source with `acceptance: 'default'` (by default only `'session'`);
   - **plus** every kind that an effective requirement names, through `requirement.principals ?? policy.requires.principals`, where `policy` is the instance `PolicyResolver` returns for the requirement's reference (a value, a provider class or a token, §4.4.3). `@RequireApiKeyPermission(p)` therefore admits `'api-key'` on its route without a second decorator, and only policies that can judge a kind make it reachable. v3 read `requires` from the reference itself, which for a provider class is the class, so an instance field never reached the plan `[R3:NEST-r3-04]`.

   A source whose kinds are all outside the set is not consulted for the route (§4.3.3). An API key or OAuth token therefore authenticates nothing on a route that did not ask for it: no quota is spent and the request is treated as if the header were absent. The consulted sources are recorded by content as `sourceSet` (§7.2).

6. **Principal param constraints.** Each `definePrincipalParam` decorator on the handler contributes `{ kind, reason }`. A handler that accepts kinds its param decorator rejects fails boot (B15 `PRINCIPAL_PARAM_CONFLICT`, hint: `@CurrentPrincipal()`). Every plan comes from the planner, lazily compiled ones included (§5.4), so **for a plan that resolves its own principal** no principal of a rejected kind reaches such a decorator.

   **An `inherit` plan is different, and the constraint is checked at read time there** `[R5:NEST-r5-03]`. A nested handler's own `accepts` is the instance's default kinds — class-level `@AcceptPrincipals` does not apply to it (step 3) — while the reading it receives comes from the _enclosing_ invocation, whose `accepts` may be wider (§7.8 item 2). B15 intersects the nested plan's own accepts with its decorators and finds no conflict, and it cannot do better: the set of operations that may reach a field resolver is not known at boot, and v5's "whatever its instance" rule (NEST-r4-03) widened it further to every instance's operations. So `@CurrentSession()` on a field resolver under an `@AcceptPrincipals('session', 'api-key')` query really does receive an `ApiKeyPrincipal`, whose `project: (p) => p.session` yields `undefined` typed `AuthSession` — a `TypeError` per list item in the honest form, or a silent `canEdit: false` for every row in the defensive one. The design's own two documented patterns produce it side by side. The fix is a read-time comparison in the reader (§7.8 item 5), not a new boot rule, and it is still core comparing data: the decorator's `kind` against `principal.kind`, neither named in core (§3.2 rule 5). The GraphQL units also warn at boot (`W_NESTED_PRINCIPAL_PARAM`, §9.2) so the loud error is not the first time a team hears about it.

7. **Freshness** is `'authoritative'` if `@RequireAuth({ authoritative: true })` is present at the effective level, `session.freshness` says so, or any effective requirement has `freshIdentity` (from the requirement or its resolved policy; the admin policy, §8.4) `[R1:SEC-r1-04]` `[R3:NEST-r3-04]`. An `'inherit'` plan does not resolve, so its freshness is irrelevant: its readers take the enclosing invocation's reading (§7.8).
8. **Origin check** is `'off'` with `@SkipOriginCheck()` (method or class) or `originCheck.mode: 'off'`; otherwise `'form'` when direct-call forwarding is on for the handler, else `'cookie'` (§7.10) `[R2:SEC-r2-08]`. **Direct-call forwarding** follows `@ForwardAuthCookies` (method over class), else `cookies.forwardDirectCalls`; nothing else turns it on (§7.5) `[R3:SEC-r3-04]`. Form mode requires guard reach even when access is inherited, and runs before that branch returns; it does not re-resolve or overwrite inherited identity. [R7:SEC-r7-01]
9. **`declares`** is B16's "declares something", computed from the same levels the plan used: method-level metadata, class-level metadata unless the handler is nested, and forwarding (§5.4) `[R3:NEST-r3-05, NEST-r3-07]`.

| Effective access                        | Principal I/O                                         | No credentials        | Presented but invalid credential (e.g. bad `x-api-key` on a route accepting keys) | Infrastructure failure                                        | `@CurrentSession()`                     |
| --------------------------------------- | ----------------------------------------------------- | --------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------- |
| `required` (default)                    | yes                                                   | 401 `UNAUTHENTICATED` | denial with better-auth's status and `reason`                                     | 5xx                                                           | `AuthSession`                           |
| `optional` (`@OptionalAuth()`)          | yes                                                   | allowed               | **denial** (a bad credential is never downgraded to anonymous)                    | 5xx                                                           | `AuthSession \| null`                   |
| `public` (`@Public()`)                  | **none**                                              | allowed               | not inspected                                                                     | form-check failure possible when forwarding; no principal I/O | boot error B15                          |

`@Public()` doing zero principal I/O fixes reference issue #159 (declared cookie forwarding still runs the form check, whose trusted-origins function can perform I/O): health probes no longer return 500 when the database is down. It also means a bad API key on a public route consumes no quota (R:ba-authz §4.2 #5). `@OptionalAuth()` is the "attach the session if present" mode.

**Public means no identity** `[R2:SEC-r2-04]`. `BetterAuthService.getPrincipal()` and `getSession()` return `null` in a public handler: they never start a resolution anywhere (§7.8). In v2 they resolved lazily there, so a cross-site form post to a `@Public()` unsafe route that called `getSession()` acted as the victim without any origin check, because the guard returns before the check on public plans. A handler that wants the caller's identity when there is one uses `@OptionalAuth()`, which resolves in the guard, after the origin check (§17 Q27). The one public case that needs the origin check without an identity, a login proxy, gets it through `@ForwardAuthCookies()` (§7.10). Since v5 the rule also covers `auth.api` itself: a public handler's direct call that carries the caller's session cookie on a browser leg nobody verified — any method, whenever the plan's origin check is not `'off'` — fails with `PUBLIC_HANDLER_USED_CALLER_SESSION` (§7.5) `[R4:SEC-r4-02]` `[R5:SEC-r5-02]`.

```ts
@Controller("reports")
export class ReportsController {
  @Get() list(@CurrentSession() s: AuthSession) {} // sessions only (default kinds)

  @AcceptPrincipals("session", "api-key") // both; read the union
  @Get("export")
  export(@CurrentPrincipal() p: AuthPrincipal) {}

  @RequireApiKeyPermission({ reports: ["read"] }) // admits 'api-key' by itself
  @Get("feed")
  feed() {}
}
```

**Known upstream limitations.**

- RK2: better-auth turns storage errors into "no session" in two places: `customSession` catches errors from its inner `getSession` (LEAD-V44), and `getSessionFromCtx`, which every `sessionMiddleware` endpoint uses, catches every error (LEAD-V36). In a `customSession` app a storage outage therefore looks like 401 instead of a 5xx, both for the guard's own read and for a policy call into a session-middleware endpoint: the re-classification read goes through `customSession`'s endpoint, which swallows the failure again, so the kernel sees "no session" and answers 401 (REV3-BA:`exp4-reclassify-customsession-outage.mjs`). No better-auth API reads the base session without that catch once `customSession` replaces `/get-session`, and reading it ourselves would reimplement `getSession` (R1). In apps without `customSession` the kernel does not pass a policy call's generic 401 on as a denial (§8.1) `[R2:BA-r2-03]` `[R3:BA-r3-05]`. Both are documented, and the upstream proposal asks better-auth to rethrow non-`APIError` failures in `getSessionFromCtx` and in `customSession`'s `.catch(() => null)`.
- RK18: `verifyApiKey` reports a storage failure as `INVALID_API_KEY` (LEAD-V20). `apiKeyPrincipal()` mitigates this with a latency signal and an outage probe (§8.3.1), which cover store-wide failures and slow failures of the key's own row but not every row-level failure, and we will propose an upstream change `[R3:SEC-r3-01]`.
- RK37: the organization plugin's `hasPermission` writes its module-level, never-evicted `cacheAllRoles` `Map` unconditionally — outside both the `useMemoryCache` and the `dynamicAccessControl` branches — and `/organization/has-permission`, the endpoint the shipped org policy calls on every check, goes through it (`BA/plugins/organization/has-permission.ts:75`, `permission.ts:33-38`, LEAD-V59). A multi-tenant process therefore holds one entry per organization it ever authorizes against until it restarts (§7.9, §8.3). It is bounded by membership, not by attacker input, so the design accepts it; the upstream proposal asks better-auth to bound `cacheAllRoles` with an LRU or to key it to the request `[R5:BA-r5-03]`.

### 7.8 Accessing the principal `[R2:NEST-r2-06, NEST-r2-07, NEST-r2-14, SEC-r2-04]` `[R3:NEST-r3-01, NEST-r3-02]` `[R4:NEST-r4-03]`

**Readers read what the guard recorded, through one lookup** `[R3:NEST-r3-01]`. Every reader of the principal (the param decorators, the scope interceptor that serves `BetterAuthService`, and `BetterAuthService.principalFor(ctx)`) takes the _reading_ of an invocation through the same lookup, and none of them calls the resolver. A handler with its own plan reads for its plan's instance (`@UseAuthInstance`, read from metadata; the decorators take no `instance` option, NEST-r2-14); an inheriting handler reads its enclosing invocation's reading, whatever that instance is. v3 had six paths that could answer differently for one invocation: the scope, `peek()` under the plan's memo key, the invocation stamp, an operation-wide carrier map by memo key with an "exactly one entry" rule, the test stamp and `principalFor`. In `{ me { id } reports { id canEdit } }`, where `reports` admits API keys and `canEdit` is an inheriting field resolver, `canEdit` threw `NO_AUTH_RESULT` or read the key's owner depending on which root field's guard settled first, and with `fieldResolverEnhancers: ['guards', 'interceptors']` it read `me`'s **session** principal while `reports` had authorized the key (REV3-NEST:`exp2-inherit-reader.mjs`, identical on 11.1.17 and 12.0.1; NEST-r2-06 was therefore still open).

**What the guard records**, under `Symbol.for('nestjs-slightly-better-auth:resolution')` (§7.1):

- on `call.invocation`, per instance: this invocation's own result (the HTTP request, a GraphQL field's `info`, a federation representation, an RPC message context, a WS message's `args` array);
- when the transport supplies `call.lineage`: the same result, tagged with its instance, on `lineage.carrier`, keyed by `lineage.position`, next to the transport’s `lineage.enclosing` and `lineage.assertReadable` functions, so readers without DI can walk the lineage and validate an authenticated read against their own invocation arguments. One position has one plan, so it holds one reading; the invocations that share a position (federation representations of one type, T6) record identical ones;
- for a public plan of a handler that is not nested: "no identity" at its lineage position, when the transport handling the context supplies one. **A nested public plan never records, whatever its origin-check mode** `[R4:NEST-r4-03]` `[R5:NEST-r5-05]`. This is the single statement of the rule; §7.1's two public branches and §3.1 U10 refer to it and must not restate it differently. v5 wrote it only into the first branch (`public` with an origin check other than `'form'`), so a `@Public()` field resolver under `cookies.forwardDirectCalls` or a class-level `@ForwardAuthCookies()` — whose mode is `'form'` (§7.6 step 8) and which therefore falls through to the second branch — still recorded "no identity". Readers below it then read `null` with `fieldResolverEnhancers: ['guards']` and the signed-in principal without, which is exactly the `fieldResolverEnhancers`-dependent divergence NEST-r4-03's fix and invariant T6 rule out. The window was narrow (forwarding plus a relaxed `fieldResolverCoverage`), but two branches of one flow disagreeing about one rule is what later edits amplify.

**The lookup**, for a plan and an invocation's `args`:

1. **A public plan** reads **no identity**: `null` from services and `@CurrentPrincipal()`, `{ outcome: 'no-identity' }` from `principalFor`. B15 keeps kind-constrained decorators off public handlers.
2. **An inherit plan** walks `lineage.enclosing(args)`, nearest first, and takes the first reading recorded at one of those positions, **whatever its instance**, and reports that instance. Before returning an authenticated reading it calls `lineage.assertReadable?.(args)`; GraphQL units validate the current request’s liveness there, while no-identity/absent reads remain structural. A nested invocation starts only after every enclosing invocation completed its guard run (T6), so the answer depends neither on the sibling fields an operation selects, nor on the order in which their guards settle, nor on `fieldResolverEnhancers`. A field resolver under `reports` reads `reports`' principal; one under a public root field reads no identity; one nested inside a field resolver that has its own real plan reads that field's result; one under a `@Public()` field resolver reads what that field's own enclosing invocation recorded; one under a federation entity reads its type's reference resolver's reading. v4 looked for a reading of the nested handler's **own** plan instance, so a field resolver shared by two instances' operations threw `NO_AUTH_RESULT` under the other instance's query (NEST-r4-03).
3. **Any other plan** reads the result recorded on its own invocation.
4. **The test stamp** `[R1:NEST-r1-08]`, when items 1 to 3 found nothing. `stampPrincipal()` and the `overrideAuthGuard` stand-in guard (§14.8) write it. Neither knows the transport, so the stamp is a record `{ elements, results }` under `Symbol.for('nestjs-slightly-better-auth:test-stamp')`, where `elements` is a copy of the stamping guard's `ctx.getArgs()` and `results` a `Map<instance, PrincipalResult>`. It is attached to that args array and to each of its extensible object elements. A reader looks on its own args array first, then on each object element, and accepts a record only if `elements` is element-wise identical (`===`) to its own `ctx.getArgs()`:
   - on GraphQL, RPC and WebSockets the guards and interceptors of one invocation share the args array itself (LEAD-V7, LEAD-V34), so the interceptor finds the record there and copies it into the scope it opens. This is the WebSocket path: gateways always have the interceptor (B16), and the socket-level copy is never needed;
   - on HTTP the router hands guards and interceptors separate `[req, res, next]` arrays with the same elements (LEAD-V34), so the record is found on `req` and still matches;
   - a record on a shared object (a socket, a GraphQL root value) does not match a sibling request, field or message, whose elements differ. The one theoretical collision, two concurrent messages with identical primitive payloads on one socket stamped with different principals, would matter only to a reader without the interceptor, which gateways never lack.

   Like every record, the test stamp is symbol-keyed, so no parsed request payload can carry one.

5. **Every kind-constrained reader whose reading carries another kind throws** `[R5:NEST-r5-03]`. After items 1 to 4 produced a reading, a `definePrincipalParam` decorator or the session unit’s `BetterAuthService.getSession()` projection compares its declared `kind` with `principal.kind`: for an `authenticated` reading whose kind differs, it throws `BetterAuthConfigurationError.atRequest(<the spec's `reason`>, …)` with the site and the hint `@CurrentPrincipal()` or `getPrincipal()` followed by narrowing `p.kind`, exactly as `NO_AUTH_RESULT` does (item 6) — a generic 500 logged once per logical request, never `undefined` projected into a typed parameter. For **param decorators**, only `inherit` plans can reach this: for every other plan B15 proved the accepted kinds compatible at boot (§7.6 step 6), so the comparison is a cheap assertion there and the real check for nested handlers, where boot cannot decide it. A `no-identity` or `absent` reading is unchanged: the decorator returns `null` where its handler's access allows one (`@OptionalAuth()`, a public enclosing operation) and is subject to the same B15 rules as before. A service call is not visible to B15 and can reach this on ordinary HTTP plans too. `getSession()` never maps an authenticated non-session principal to `null`; only `no-identity`/`absent` return `null`. The projection and its `SESSION_REQUIRED` reason belong to the session unit; core compares two data fields and names neither kind (§3.2 rule 5, ADR-41). `[R6:NEST-r6-03]`
6. **Otherwise** the reader throws. `principalFor` on a plan that is neither public nor inherit throws `BetterAuthConfigurationError.atRequest('PRINCIPAL_READ_BEFORE_GUARD', …)` (see "Guards and interceptors" below). Every other reader throws `BetterAuthConfigurationError.atRequest('NO_AUTH_RESULT', 'No authentication result: BetterAuthGuard did not run (globalGuard: false without @UseBetterAuth(), or a guard replaced in a test without stampPrincipal())', { site: 'SiteController.method' })`. This surfaces reference issue #12 as a clear error instead of an `undefined`. The decorator runs where the guard did not, so no transport's `toInternalException` can map this error, and a GraphQL driver copies `message` into the response. The error is therefore safe as thrown `[R1:SEC-r1-19]`: its `message` is the fixed `Authentication is misconfigured`, `extensions.reason` is `AUTH_MISCONFIGURED`, and the site, detail and hint are ordinary own properties, which Nest's exception layer logs (LEAD-V31) and neither GraphQL driver serializes (LEAD-EXP-7). A `defineInvocationParam` decorator with nothing published throws the same way, with its `missing` text as the `detail` (`NO_INVOCATION_VALUE`), and so does every other request-time configuration error, including one raised by `BetterAuthService.getPrincipal()` in a resolver body (§13.1). B16 fails boot for a claimed handler with such a decorator that no guard covers (§5.4) `[R2:NEST-r2-02]`, but that does not make the case unreachable. Coverage cannot be proven for every call site: a claim whose severity the user relaxed to `'warn'` or `'off'`, handlers in lazily loaded modules, guards applied through another library's composite guard, and guards replaced in tests all get past it. The error itself must therefore be safe as thrown, and `T-internal-error-generic` reaches it through a replaced guard.

**Reader error deduplication** `[R6:NEST-r6-02]`. Items 5 and 6, invocation-value readers (`NO_INVOCATION_VALUE`), and service readers use the same surfaced-error record as the guard. Prefer the current scope’s request record. Without a scope, use a `Symbol.for('nestjs-slightly-better-auth:surfaced')` record beside the lineage carrier, partitioned by operation identity for batched GraphQL operations; with no lineage use the invocation object. Guard and reader paths share that record rather than keeping two counters. Configuration errors use the stable key `(instance, reason, controller class, handler)`; list indices and fresh Error object identities are excluded, so one failing projection under 20 items logs once. Infrastructure failures continue to use the memoized error identity. The first throw is the normal safe `BetterAuthConfigurationError`; subsequent throws are its intrinsic twin with the **same generic message, extensions and reason**, so Nest does not repeat the ERROR log while every GraphQL field still receives an error. This is a transport-neutral error representation, with a copy-safe error brand, not a transport-name branch in core. A missing operation carrier does not invent global deduplication: it falls back to invocation lifetime. Never suppress a distinct reason, instance or handler. A zero-argument service `getSession()`/`getPrincipal()` with no handler scope has **no carrier or invocation context**: it throws `NO_AUTH_SCOPE` before projection and has no request-level deduplication guarantee. Each such fresh error is normally logged, so 20 unscoped field calls can produce 20 ERROR entries. Do not reuse a completed root scope or introduce process-global suppression. Parameter decorators differ because Nest supplies their invocation arguments, allowing lineage-only deduplication. [R7:NEST-r7-02] `T-internal-error-logged-once` covers both scope and lineage-only paths.

**Where the lookup runs.**

- **The scope interceptor** provides it lazily once per invocation, with the plan it compiles, and memoizes the reading only when a reader asks. Services and param decorators read the scope first. It is race-free on every transport `[L]`. WebSockets have no lineage on purpose: a WS invocation is the per-message `args` array, which the interceptor sees.
- **Param decorators without the interceptor** (HTTP, GraphQL and RPC handlers where the interceptor is not applied; GraphQL field resolvers without `'interceptors'` in `fieldResolverEnhancers`) have no DI access and so no plan. They run items 3, 2 and 4 in that order: their own invocation's record (an element of their args), then the lineage records (the carrier element of their args), then the test stamp, and throw otherwise. An inherit plan never has an own record, so it reaches item 2. A nested handler with a real plan whose guard did not run (its field guards are missing and its coverage severity was relaxed to `'warn'` or `'off'`) reads the enclosing reading too: the identity is still right, and the requirement that did not run is what B16 reported.
- **`BetterAuthService.principalFor(ctx)`** compiles or fetches the plan and runs items 1 to 4 and 6 with the transport's `describe()` (or `lineage()` for public plans); item 5 belongs to kind-constrained projections (param decorators and `getSession()`), which `principalFor` is not `[R5:NEST-r5-03]`.

**What each decorator returns:**

- `@CurrentSession()` `[R1:NEST-r1-10]` returns `principal.session` for a principal of kind `'session'`, or `null` on an optional route with no principal. It is built with `definePrincipalParam({ kind: SESSION_PRINCIPAL_KIND, reason: 'SESSION_REQUIRED', project: (p) => p.session })` by the session unit. The planner records the kind as data, and a route that could admit another kind fails boot (B15), so the handler never receives a `null` typed as `AuthSession`. In an inheriting field resolver it returns the enclosing reading's session, `null` under a public or optional operation without a principal, and — since v6 — a logged 500 (`SESSION_REQUIRED`, item 5) rather than `undefined` when the enclosing operation authorized a principal of another kind, which boot cannot rule out for a nested handler `[R5:NEST-r5-03]`. It is named `CurrentSession` rather than v1's `Session` because `@nestjs/common` exports a `Session` route-param decorator (it injects `req.session`), and an IDE auto-import into a file that already imports from `@nestjs/common` silently picked the wrong one.
- `@CurrentUser()` behaves the same way and returns `principal.session.user`.
- `@CurrentPrincipal()` returns `AuthPrincipal | null` and has no kind constraint; "no identity" reads as `null`.
- `@ActiveOrganizationId()` and `@ActiveMemberRole()` (`./organization`) are `defineInvocationParam` decorators. They return the value the org policy published for **this invocation** (§8.3), never a value from a sibling GraphQL field.

**Services** use `BetterAuthService.getPrincipal()` or `getSession()` inside a handler scope. They **never start a resolution** `[R2:SEC-r2-04]`: they return the scope's reading, `null` on a public plan (§7.6), and throw `NO_AUTH_RESULT` when the guard did not run for the handler. Calling them in a guarded handler does no additional auth I/O. `getSession()` applies item 5 and throws `SESSION_REQUIRED` for another authenticated kind; use `getPrincipal()` and narrow `p.kind` to handle mixed-kind routes. These configuration errors share the once-per-request surfaced record. [R6:NEST-r6-02, NEST-r6-03] **Outside any handler scope** (a guard, middleware, a policy, a GraphQL field resolver without `'interceptors'` in `fieldResolverEnhancers`, a background job) they throw `BetterAuthConfigurationError.atRequest('NO_AUTH_SCOPE', …)`: v2 returned `null` there, the same value as "anonymous", so a migrated `SubscriptionActiveGuard` rejected every paying user and a throttler keyed by user id put everyone in one bucket (NEST-r2-07).

**Session-unit advice** `[R6:NEST-r6-03]`. `sessionPrincipal().advise()` emits `W_MIXED_KIND_SESSION_READER` for every concrete required/optional handler whose compiled accepted kinds contain a non-session kind, across HTTP and other transports. It does not inspect constructor injection or guess whether `getSession()` will be called. The diagnostic says “If this handler reads `getSession()`, another authenticated kind throws `SESSION_REQUIRED`; use `getPrincipal()` and narrow `p.kind`,” and lists affected sites with the B21 cap. GraphQL’s schema-wide `W_NESTED_PRINCIPAL_PARAM` remains separate because a nested reader may inherit another instance’s plan.

**Guards and interceptors** read the principal with `BetterAuthService.principalFor(context)` `[R2:NEST-r2-07]` `[R3:NEST-r3-02]` `[R4:NEST-r4-03]`. It is synchronous, never performs I/O, and always answers: a `PrincipalReading` (a `PrincipalResult`, or `{ outcome: 'no-identity' }` on public plans and under public operations), tagged with the instance whose guard run recorded it (the plan's own, or for an inherit plan the enclosing reading's, whatever the plan's own instance is), or an error. v3 returned `undefined` both when the plan was public and when `BetterAuthGuard` had not run yet, and a guard could not tell the two apart.

**Order matters, and it is visible.** A guard that reads the principal must run after `BetterAuthGuard`. Nest runs the `APP_GUARD`s an application module declares itself **before** the ones of the modules it imports, so a guard declared as `APP_GUARD` in `AppModule`, where Nest's documentation places `ThrottlerGuard`, runs before the global `BetterAuthGuard` that `BetterAuthModule.forRoot()` contributes (REV3-NEST:`exp1-app-guard-order.mjs`, identical on 11.1.17 and 12.0.1 under `NestFactory` and `@nestjs/testing`). Such a guard gets `PRINCIPAL_READ_BEFORE_GUARD` on the first request whose plan resolves a principal, with the hint to register it:

- in a module imported **after** `BetterAuthModule.forRoot()` (its `APP_GUARD` then runs after the library's), or
- at controller or method level (`@UseGuards`), which always runs after global guards, or
- after `BetterAuthGuard` registered by the application itself: `globalGuard: false` plus `{ provide: APP_GUARD, useExisting: BetterAuthGuard }` and `{ provide: APP_INTERCEPTOR, useExisting: BetterAuthScopeInterceptor }` listed first in `AppModule` (B16 counts them, §5.7).

The boot summary prints the application's global guards in the order Nest runs them (B22). It does not warn about guards ahead of `BetterAuthGuard`: throttling by IP before authentication is a legitimate reason to run first, and only a guard that reads the principal is wrong there, which the request-time error names exactly. A throttler keyed by user reads `principalFor(ctx)` the same way and falls back to the client IP on `'no-identity'` and `'absent'`. The migration recipe for `request.user` in custom guards (§15.2):

```ts
@Injectable()
export class SubscriptionActiveGuard implements CanActivate {
  constructor(
    @Inject(BETTER_AUTH_SERVICE) private readonly auth: BetterAuthService,
  ) {}
  canActivate(ctx: ExecutionContext) {
    const r = this.auth.principalFor(ctx); // throws PRINCIPAL_READ_BEFORE_GUARD if registered ahead of BetterAuthGuard
    if (r.outcome === "no-identity") return true; // public route: nothing to check
    return (
      r.outcome === "authenticated" &&
      r.principal.kind === "session" &&
      r.principal.session.user.plan === "pro"
    );
  }
}
```

### 7.9 Cost per protected request

- **Session resolution.** One `getSession` per request, shared by all guard invocations, decorators and services. That is 0 storage reads on a cookie-cache hit, otherwise 1 read, plus 1 write when a refresh is due (R:ba-authz §1.0). An authoritative route (admin permission by default, §8.4) always reads storage once, and the admin policy adds one read of the stored user row, made by `userHasPermission` itself (a delegated principal whose owner has no role string: two) (§8.3) `[R3:BA-r3-02]` `[R4:BA-r4-01]`.
- **Public routes.** Zero.
- **API keys through `apiKeyPrincipal()`.** One `verifyApiKey` per request, on routes that accept keys only. Each verification counts against the key's usage and rate limit and writes to storage (usage counter, `updatedAt`) `[R1:SEC-r1-14]`. Org policies deny `'api-key'` principals without calling better-auth.
- **Rare paths.** The API-key outage probe (one read and one no-op write, at most once per second per instance, §8.3.1); the re-classification of a generic 401 a policy call met for a principal from a session-backed source (one authoritative resolution per logical request, §8.1) `[R4:SEC-r4-04]`; the default organization ref for a `customSession` shape without `session.activeOrganizationId` (one `getActiveMember` per request, §8.3).
- **Multipliers,** surfaced as boot advice (B21) by the units that know about them:
  - the jwt plugin without `disableSettingJwtHeader: true` signs a JWT and reads `jwks` on every `getSession` (session unit);
  - bearer without `requireSignature: true` pays a lookup for foreign tokens (session unit);
  - `apiKey({ enableSessionForAPIKeys: true })` validates the key on **every** better-auth call that carries it, not only `getSession` (LEAD-V21). A request that resolves the session and then evaluates `@RequireOrgPermission` and `@RequireOrgMember` spends the key's quota three times (REV-BA:`probe-apikey-policy.mjs`: `requestCount` 1 → 2 → 3). On an authoritative route the key session is not accepted at all (§7.3), so one validation is spent before the 401. The **session unit** announces it, because it is the unit registered in exactly this setup (an app that uses key sessions usually never imports `./api-key`). Its `advise()` emits `W_API_KEY_SESSION_MULTIPLIER` when `context.hasPlugin('api-key')` and any referenced policy declares `presentsCredentials`, and recommends `apiKeyPrincipal()` for key traffic. The option itself cannot be read from the plugin object, so the message is conditional unless `session.apiKeySessions` states the fact (§8.3.1) `[R1:BA-r1-05]`;
  - a quota-consuming source (`effects.consumesQuota`) on a WebSocket transport with `principalTtlMs: 0` verifies on every message (`W_QUOTA_PER_MESSAGE`, §9.3).
- **Policy I/O** is deduped per request by concrete inputs (Z6): `@RequireOrgPermission(p, org A)` twice on one request is one call; for org A and org B it is two.
- **Process memory, not per request** `[R5:BA-r5-03]`. Every `orgPermission()` / `@RequireOrgPermission` check also costs one insertion into better-auth's module-level `cacheAllRoles` `Map`, keyed by organization id and never evicted, because `hasPermission` writes it unconditionally (LEAD-V59). One entry per organization the process authorizes against, for the life of the process (RK37). A measurement of §17 Q9 must count it on **both** sides: the pure export writes the same entry.
- **GraphQL multiplies decisions, not resolutions** `[R3:SEC-r3-08]`. N aliases of a root field (or a guarded field resolver under a list of N items) are N invocations of one logical request: one principal resolution, N decisions, and up to N distinct policy calls when their inputs differ. `limits.maxAuthorizationCallsPerRequest` (default 100) bounds the distinct calls per request, and past it a requirement denies 429 `TOO_MANY_AUTHORIZATION_CHECKS` without calling better-auth (§8.1). It bounds the total, not the concurrency: the calls of one request still run in parallel, so GraphQL query-complexity or depth limits remain the application's first line (RK11).

### 7.10 Origin check for cookie-carrying operations `[R1:SEC-r1-01, BA-r1-03]` `[R2:SEC-r2-01, SEC-r2-03, SEC-r2-05, SEC-r2-08, NEST-r2-13]` `[R3:SEC-r3-02, SEC-r3-03, SEC-r3-07]` `[R4:SEC-r4-02, SEC-r4-05]`

better-auth protects cookie-bearing requests on its own routes with an origin check, and that check is **router-only**. `validateOrigin` is registered as router middleware and returns early without `ctx.request` (LEAD-V16). Every `auth.api.getSession({ headers })` the guard makes is therefore unprotected, and v1 wrongly listed "origin/CSRF" as something `auth.handler` does for the whole app. In a probe, the guard's `getSession` accepted an evil-origin cookie request that the router rejected with 403 (REV-SEC:`probe-bridge-foreign.mjs`). With better-auth's documented cross-domain cookie settings (`sameSite: 'none'`), or with an attacker on a sibling subdomain (same-site), this allowed:

- cross-site form posts to Nest routes;
- cross-site GraphQL mutations;
- Cross-Site WebSocket Hijacking (browsers attach cookies to WebSocket upgrades, CORS does not apply, and the attacker reads the replies), including GraphQL queries sent over the socket.

The kernel mirrors better-auth’s origin/header rules on app surfaces, with the deliberate divergences explicitly listed below and pinned by `LIB-origin-differential`; it does not silently inherit every router-only bypass. `[R6:BA-r6-01]`

**No exemption better-auth does not make** `[R2:SEC-r2-01]`. v2 skipped the check when the request also carried an "explicit" credential (a `Bearer`/`DPoP` authorization, a source's credential header), on the theory that such a credential authenticated the call. It never checked that it did. On socket.io and graphql-ws those headers are built from `handshake.auth` and `connectionParams`, which the attacking page chooses and no CORS preflight governs: a junk token switched the check off while `bearer()` ignored it and the victim's cookie authenticated the socket (REV2-SEC:`probe-origin-bearer-exempt.mjs`). better-auth's router validates whenever the request carries **any** cookie (`origin-check.ts:231, 247`). Since v3 the kernel does the same, reads the cookie from the browser leg's own headers only, and keeps no list of credential schemes in core (NEST-r2-13). A cross-origin client that sends cookies already needs credentialed CORS, so its origin is known and belongs in `trustedOrigins`.

**When it applies.** All of the following hold:

1. The plan’s origin check is not `'off'` (not `@SkipOriginCheck()`, not `originCheck.mode: 'off'`). Public and inherit plans are checked only in `'form'` mode; B16 does not count their access as coverage for form mode, so a forwarding handler must have a reachable guard (§5.4). An inheriting plan still takes its enclosing identity and does no principal resolution. [R7:SEC-r7-01]
2. The transport exposes a browser leg (`call.browser`). **Form mode always enforces**, whatever the HTTP method or GraphQL operation kind, including cookie-free GET login proxies and forwarding query resolvers. In **cookie mode only**, enforcement requires `call.browser.enforce`:
   - HTTP cookie mode: methods other than GET/HEAD/OPTIONS, better-auth’s own split;
   - GraphQL over HTTP: mutations (a cross-site page cannot read a query's response);
   - WebSocket messages, and **every GraphQL operation a WebSocket carries**, subscriptions, queries and mutations alike, because a hijacked socket reads every reply (§9.2) `[R2:SEC-r2-03]`.

   RPC has no browser leg.

3. In `'cookie'` mode (the default): the browser leg's own headers carry a `cookie` header, whatever else the request carries and whether or not a principal authenticates. In `'form'` mode (handlers that forward auth cookies, §7.6 step 8): always, following better-auth's form-CSRF rule below `[R2:SEC-r2-08]`.
4. The **single kernel disable predicate** is `$context.skipCSRFCheck || ($context.skipOriginCheck === true && $context.options.advanced?.disableCSRFCheck === undefined)`. Both the guard and `ScopeView.checkCallerSession` use this predicate. `[R6:BA-r6-01]` `$context.skipCSRFCheck` (`advanced.disableCSRFCheck`), and the backward-compatible `skipOriginCheck === true && disableCSRFCheck === undefined`, turn off the kernel check (LEAD-V18). The second includes better-auth's test default, `disableOriginCheck ?? isTest()`, and `isTest()` is true for `NODE_ENV=test` **or any truthy `TEST`**, which vitest sets in every worker (LEAD-V48). B19 warns whenever `skipCSRFCheck` or a boolean `skipOriginCheck` is true and names both surfaces’ effective states, and suites that test the check set `advanced.disableOriginCheck: false` explicitly (§14.1, §14.4) `[R3:SEC-r3-07]`. Path-array `skipOriginCheck` entries name auth-route paths and are ignored here. **Deliberate divergence (Q39):** `skipOriginCheck === true` with explicit `disableCSRFCheck: false` still disables `validateOrigin` in better-auth 1.7.0–1.7.4 (the third early return), but keeps the kernel check on. B19 must warn even though app routes remain protected. With `disableCSRFCheck: true`, the first predicate disables both. `LIB-origin-differential` records these separate rows, plus the path-array divergence, rather than claiming exact parity. [R6:BA-r6-01]

**Advisory safe-leg verdict (Q40)** `[R6:SEC-r6-01]`. For a required or optional plan in **cookie mode**, the guard also evaluates the same rule when the leg carries a cookie and `browser.enforce` is false. Form mode never uses this advisory branch: forwarding makes its verdict enforcing on every method and operation kind. [R7:SEC-r7-01] It memoizes the verdict without denying the safe request; an invalid origin does not prevent an ordinary GET from reading data. Only a subsequent caller-session `auth.api` call consults it (§7.5). A thrown `trustedOrigins` calculation leaves no passing verdict, does not fail the safe request, and causes that later direct call to fail closed. `recordAdvisoryFailure` is an internal guard diagnostic, not a new public API. It is logged with the bounded origin diagnostic, not once per field. Plain public plans still return before transport extraction and compute no advisory verdict; their direct session calls continue to fail closed. Use the existing `(browser.key, instance, mode)` memo with one in-flight calculation per leg; no new origin logic or plugin-side lookup is introduced. Infrastructure throws remain unmemoized as in the existing `checkOrigin` contract; an enforcing use retries and propagates its redacted failure. Absence of a verdict never authorizes a direct call. Cookie-free safe legs in cookie mode do no extra work. Cookie-free forwarding legs still run the enforcing form rule.

**The rule, `'cookie'` mode** (mirrors `validateOrigin`, LEAD-V16):

1. The origin to validate is `Origin`, else `Referer`. `Origin: null` with `Sec-Fetch-Site: same-origin` is inferred from the browser leg's URL origin. better-auth's router does this from 1.7.2 on; the kernel applies it on every version in the peer range, which on 1.7.0 and 1.7.1 makes it more lenient than the router for this one same-origin case (LEAD-V33, RK20).
2. Missing or `null`: with `originCheck.missingOrigin: 'reject'` (default, better-auth's behavior) deny 403 `MISSING_OR_NULL_ORIGIN`. With `'allow-non-browser'`, allow only when `Origin`, `Referer` and `Sec-Fetch-Site` are all absent. Every current browser sends at least one of them on a cross-site unsafe request.
3. Otherwise the origin must be trusted by the instance, as computed by `TrustedOrigins` (U17):
   - `ctx.trustedOrigins`, the init-time list (baseURL origin, user `trustedOrigins`, `BETTER_AUTH_TRUSTED_ORIGINS`);
   - ∪ the post-init `ctx.options.trustedOrigins`, which carries the plugin-contributed origins (LEAD-V17). A function-valued one is evaluated with a lightweight `new Request(browser.url, { headers: browser.headers() })`, like better-auth's router does per request;
   - ∪ the browser leg's own origin, **only when `baseURL` is unset** (not a dynamic config) and `ctx.baseURL` is therefore empty: development, or `http.allowRequestDerivedBaseURL` in production (B23). For an HTTP leg that origin is the one the platform builds (`HttpRequestAccessor.request(req).url`), which is the URL `AuthExchange` hands better-auth's router for auth routes, so the router trusts the same origin (LEAD-V47). For a WebSocket leg it is the socket's TLS state and `Host`, never `X-Forwarded-Host` or `X-Forwarded-Proto` (`upgradeRequestUrl()`, §2.2.10). Behind a proxy with `advanced.trustedProxyHeaders` the router would also trust the forwarded origin, so here the kernel is stricter than the router, never more lenient; such a deployment sets `baseURL` or lists its origin in `trustedOrigins`.
   - A **dynamic `{ allowedHosts }` config adds no leg origin**: `ctx.trustedOrigins` already holds every `allowedHosts` origin and the `fallback`, which is all better-auth's router trusts for such a config (LEAD-V47). v3 added the leg's own origin here, built from `X-Forwarded-Host`. A socket.io polling handshake is a preflighted XHR, so a cross-site page could set `X-Forwarded-Host: evil.example` on it, make `https://evil.example` a trusted origin, and hijack the victim's socket with its cookie; an HTTP unsafe request from a CORS-allowed origin missing from `trustedOrigins` could do the same under `trust proxy` (REV3-SEC:`probe-origin-dynamic-baseurl-xfh.mjs`: the router answered 403, the kernel allowed) `[R3:SEC-r3-02]`.

   Matching is better-auth's `matchesOriginPattern`, reached through `ctx.isTrustedOrigin.call({ trustedOrigins: merged }, origin)`. It handles full Referer URLs, wildcards and custom schemes exactly as on auth routes. An untrusted origin is denied 403 `INVALID_ORIGIN`.

**The rule, `'form'` mode** (mirrors `validateFormCsrf`, LEAD-V39), for every handler declaring direct-cookie forwarding (`@ForwardAuthCookies()` or `cookies.forwardDirectCalls`), public and inheriting ones included, regardless of HTTP method or GraphQL operation kind. [R7:SEC-r7-01] A custom login or sign-up proxy is the one handler that deliberately sets auth cookies without a principal, so v2's check, which needed an authenticated principal, never ran there, and a cross-site page could sign the victim's browser into the attacker's account (login CSRF, SEC-r2-08). better-auth protects its own sign-in, sign-up, magic-link and email-OTP routes with this rule:

1. With a cookie on the leg: the `'cookie'` rule.
2. Without one, when any of `Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-Dest` is present: `Sec-Fetch-Site: cross-site` with `Sec-Fetch-Mode: navigate` is denied 403 `CROSS_SITE_NAVIGATION_LOGIN_BLOCKED`; otherwise the origin is validated as in the `'cookie'` rule, steps 1 to 3, even without a cookie.
3. Without fetch metadata: a present `Origin` or `Referer` is validated the same way; a request with none of them (a non-browser client) is allowed.

**Where and how often it runs.** In the guard, after the plan and before resolution (§7.1), as better-auth's router runs its check before the endpoint reads a session. The browser leg of HTTP is the request. For WebSockets it is the handshake: `socket.io` uses `client.handshake.headers`, `ws` the recorded upgrade request (`withUpgradeRequest`), graphql-ws `extra.request`, Mercurius the upgrade request `mercuriusSubscriptionContext()` stores. `WsConnectionAuth` applies the same check at connect time, through `AuthHandle.checkOrigin` (§9.3).

- **One verdict per leg** `[R2:SEC-r2-05]`. `checkOrigin` memoizes its verdict, a failure included, in `RequestScope` by `(browser.key, instance, mode)`. The leg's `Origin` cannot change during a connection, so a socket pays for a function-valued `trustedOrigins` (possibly a database lookup) once, not per message. A throw while computing the verdict (a failing `trustedOrigins` function) is an infrastructure error with the generic message and is not memoized. The caller-session check of direct calls reads these memoized verdicts: a leg with a passing verdict for the instance, in either mode, is verified (§7.5) `[R4:SEC-r4-02]`.
- **Absolute leg URLs** `[R2:SEC-r2-05]` `[R3:SEC-r3-02]`. The URL feeds the `Origin: null` inference, the trust of the leg's own origin for an unset `baseURL` and function-valued `trustedOrigins`. A WebSocket handshake's URL is a bare path (`/socket.io/?EIO=4&transport=websocket`), for which `new Request(url)` throws, which v2 would have turned into an ERROR-logged 500 on every cookie-carrying message. WebSocket transports build it with `upgradeRequestUrl()` (§2.2.10): the socket's TLS state, `Host` and the path. v3 also read `X-Forwarded-Proto` and `X-Forwarded-Host`, on the assumption that a browser cannot set them on an upgrade; it can on socket.io's polling handshake (SEC-r3-02).
- **Denials are visible without flooding** `[R3:SEC-r3-03]` `[R4:SEC-r4-05]`. Within a one-hour window, the first denial for each distinct `(reason, origin)` pair is logged at WARN, with the origin sanitized (control characters removed, at most 100 characters), the instance's trusted-origin count and the hint to add the origin to `trustedOrigins` or to send `Origin` from non-browser clients. After 100 distinct pairs in a window, further new pairs go to debug, and the first denial after the window ends logs one WARN summary of the closed window (the count of further denials per reason and the most frequent origins) before a new window starts, so no timer keeps the process alive. A window opens at its first denial and is measured with `Date.now()`, so a test closes it by moving the clock (vitest's `vi.setSystemTime`, which mocks `Date` without faking timers, so in-process HTTP still runs) instead of waiting an hour (§14.4). The window is per application and on in production too, where a misconfigured `trustedOrigins` or a broken native client has to surface. When the validated value is a `Referer`, the line logs only its origin (`new URL(referer).origin`, which is also what the matcher compares), never its path or query, which can hold tokens such as a reset link's. Every denial is also logged at debug. v3 logged them at debug only, so a mobile client broken by the default rule looked healthy from the server (SEC-r3-03); v4's cap lasted for the life of the process, so 100 anonymous requests with a junk `Cookie` and random `Origin`s silenced every later WARN line, and it logged a `Referer`'s path and query (SEC-r4-05).

**Non-browser clients.** Server-side callers that forward a user's cookie on unsafe requests, such as an SSR server calling the Nest API, must send an `Origin` header (a trusted one). That is the same requirement better-auth already imposes on its own routes when such a server calls, say, `/sign-out` with forwarded cookies. Node's built-in `fetch` sends `sec-fetch-mode: cors` and no `Origin` (LEAD-EXP-4), so a "no browser signals" exemption would not cover it anyway. Machine clients should use bearer tokens or API keys without cookies; cookie mode does not inspect them. A handler declaring cookie forwarding still has form mode, whose headerless non-browser allowance is defined above. Routes that deliberately serve cookie-bearing server-to-server calls use `@SkipOriginCheck()`. §17 Q14, Q15 and Q26 record these defaults.

**Native apps** `[R3:SEC-r3-03]`. better-auth's Expo integration tells apps to call their own server with the session cookie in a `Cookie` header (`authClient.getCookie()`), and React Native's `fetch` sends no `Origin`, `Referer` or `Sec-Fetch-*`. better-auth's own routes cope because `expoClient` adds `expo-origin` and the `expo()` plugin copies it into `Origin` in a router-only `onRequest` hook, which app routes never run. Under the default `missingOrigin: 'reject'`, every unsafe app route and GraphQL mutation such an app calls answers 403 `MISSING_OR_NULL_ORIGIN`. The **session unit** knows when that setup is present, so its `advise()` emits `W_ORIGIN_CHECK_NATIVE_CLIENTS` when `context.hasPlugin('expo')` and the instance's `missingOrigin` is `'reject'`, naming the two working options: `originCheck.missingOrigin: 'allow-non-browser'` (React Native sends none of the three browser signals), or an `Origin: <app scheme>://` header on the app's own requests, which the Expo guide already puts in `trustedOrigins`. §17 Q15 weighs mobile clients next to SSR servers.
