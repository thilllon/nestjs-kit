## 0. Summary and principles

### 0.1 Summary

better-auth defines its own integration contract. Its handler is a Web-standard `handler(Request): Promise<Response>`. Framework bridging is done by plugins (`nextCookies`, `sveltekitCookies`, `tanstackStartCookies`, `expo`), server code calls `auth.api.*`, and authorization runs on access control. This design binds NestJS to exactly that contract and reimplements nothing better-auth already does. It has three parts:

1. **The `nestjs()` better-auth plugin** `[A][B][C]`. The user adds it last to `betterAuth({ plugins })`, following the `nextCookies()` precedent, and a boot check makes it mandatory. It is the only code that runs inside better-auth's pipeline, and it does six things:
   - bridges Nest hook providers and database hooks, preserving better-auth's return-value semantics per operation. Once an application has bound them, they keep running until another application binds, also after `app.close()` started, so work that drains during shutdown cannot skip them `[R4:SEC-r4-01]`;
   - forwards `Set-Cookie` from the library's own `auth.api.*` calls (principal sources and policies) into the current response. Application code's direct calls are forwarded only in handlers that opt in, and only when the call used the caller's own credential or none `[R1:BA-r1-02, SEC-r1-03]`;
   - stops application code's direct calls from acting with the caller's session cookie on a browser leg — any method — whose origin the guard did not verify and for which no guard resolved the principal, which is what a `@Public()` handler that hands the request's headers to `auth.api` would otherwise do (§7.5) `[R4:SEC-r4-02]` `[R5:SEC-r5-02]`;
   - suppresses session refresh on any endpoint dispatched from a cookie-less scope, which also covers the stateless refresh-cache branch;
   - declares an unguessable client-IP header, random per plugin instance and never leaving the process, through `init()` `[R1:SEC-r1-18]`;
   - records which answers an endpoint itself produced, as opposed to a before-hook short-circuit, so that an authoritative identity read accepts exactly the sessions better-auth's own admin and sensitive endpoints accept `[R2:BA-r2-06]`.

   It imports only `better-auth/api`, `better-auth/cookies` and `defu`, never `@nestjs/*`, so the better-auth CLI can still load `auth.ts`.

2. **A small kernel** `[B][C]`: the module, guard, scope interceptor, principal resolver, authorization evaluator, origin check, boot validator and error model. It depends only on its own extension contracts and on better-auth's public surface. It never branches on a platform, transport, principal-kind or policy name; the data it compares (principal kinds, credential header names) is supplied by extensions.
3. **Extension units** `[A][B][C]` for the five extension points:
   - HTTP platforms: Express and Fastify ship; third parties plug in their own;
   - transports: HTTP, GraphQL (Apollo and Mercurius), WebSockets (socket.io and ws), and RPC;
   - principal sources: the better-auth session, API keys, or a third party's;
   - authorization policies: thin adapters over better-auth's permission APIs;
   - hook providers.

   Built-in units register through exactly the same contract a third party uses. Their behavior is proven identical by runner-agnostic conformance kits shipped in `./testing/conformance`.

**Auth routes.** Every request under better-auth's own mount path, for every method, goes to `auth.handler`. The platform produces a Web `Request` with the exact body bytes, a trust-proxy-aware origin and client IP, and HTTP/2-safe headers. It writes the `Response` back verbatim: status, every `Set-Cookie`, redirects and streams. The Express binding uses two phases: bounded raw capture once the HTTP adapter and the platform are both known (inside `NestFactory.create()` / `createNestApplication()`), then dispatch at `onModuleInit`, after the user's CORS and middleware. The Fastify binding is an encapsulated plugin with a `parseAs: 'buffer'` catch-all parser, a body limit, and a child error handler that hands failures to Nest's error pipeline.

**App routes and messages.** A single transport-neutral guard resolves the principal lazily, at most once per logical request (and per connection where the transport opts in). It calls `auth.api.getSession({ headers, returnHeaders: true })` and forwards only `set-cookie`, and only where the transport can carry cookies. Principals that act for a user with a narrower grant (API keys, OAuth tokens) are admitted only on routes that name their kind. Unsafe operations whose browser leg carries a cookie pass better-auth's own origin rule, whatever credential authenticated them `[R2:SEC-r2-01]`. Authorization then runs through requirement expressions whose policies travel by reference in route metadata, and every decision is made per handler invocation.

**The common case** needs three lines plus one platform import:

```ts
// auth.ts: static and CLI-friendly; imports no Nest code
export const auth = betterAuth({ database, emailAndPassword: { enabled: true },
  plugins: [admin(), organization(), nestjs()] });                    // nestjs() last
declare module 'nestjs-slightly-better-auth' { interface Register { auth: typeof auth } }

// app.module.ts
@Module({ imports: [BetterAuthModule.forRoot({ auth, platforms: [expressPlatform()] })] })
export class AppModule {}

// any controller: no generics, typed from `typeof auth`
@Get('me') me(@CurrentSession() s: AuthSession) { return s.user.role; }
@RequireOrgPermission({ project: ['delete'] }, { organization: fromParam('orgId') })   // typo = compile error
@Delete(':orgId/projects/:id') remove() {}
@Public() @Get('health') health() {}                                                   // zero auth I/O
```

The user never sets `bodyParser: false`, never adds `hooks: {}` placeholders, writes no generics at use sites, and gets no CORS side effects.

### 0.4 What this design optimizes for and what it costs

- **Optimizes for:**
  - zero reimplementation of better-auth;
  - identical behavior across platforms, proven by kits rather than asserted;
  - third-party extension without forking;
  - fail-fast configuration, including every surface the guard cannot reach;
  - zero generics in the common case.
- **Costs** (accepted in §16):
  - one line in `auth.ts` (`nestjs()`);
  - one platform import in `forRoot` (`platforms: [expressPlatform()]`);
  - `@UseBetterAuth()` on every WebSocket gateway, on both Nest majors (§9.3);
  - an `Origin` header on unsafe requests that carry a cookie, from non-browser clients (SSR servers, native apps) and from cross-origin clients that also send a token, exactly as better-auth already requires on its own routes (§7.10);
  - `NODE_ENV=development` in local development, because every other environment gets the production boot checks (§5.4) `[R3:SEC-r3-07]`;
  - one stored-user read on routes with an admin requirement, made by better-auth's `userHasPermission` itself (§8.3) `[R3:BA-r3-02]` `[R4:BA-r4-01]`;
  - `fieldResolverEnhancers: ['guards']` in GraphQL federation subgraphs with field or reference resolvers, because `_entities` makes entity fields entry points (§9.2) `[R4:NEST-r4-01]`. That setting belongs to `@nestjs/graphql`, not to this library, and it attaches **every** application global guard and interceptor to every field-resolver invocation, so a global `ThrottlerGuard` counts one hit per field per list item and the fast field-resolver path is disabled app-wide; boot names the affected enhancers (`W_FIELD_GUARDS_MULTIPLY_GLOBAL_ENHANCERS`) and the escapes (§9.2) `[R5:NEST-r5-04]`;
  - a handler that deliberately acts on the caller's session through `auth.api` needs `@OptionalAuth()` (or `@ForwardAuthCookies()`), on every HTTP method and whatever `globalGuard` says, because the caller-session check now covers safe methods and unguarded handlers too (§7.5) `[R5:SEC-r5-01, SEC-r5-02]`;
  - one never-evicted entry per organization the process authorizes against, inside better-auth's own `cacheAllRoles` `Map` (RK37) `[R5:BA-r5-03]`;
  - a boot-time metadata scan;
  - a small hook-dispatch mirror kept in parity with `BA/api/dispatch.ts` and `BA/db/with-hooks.ts` by a property test.
- **Product decisions.** The owner answered the product questions Q13 to Q34 on 2026-09-17 and, on the same day, issued a standing decision that every question in §17 — including any a later review round adds — is decided as its recommended option. **No question is open.** The defaults behind the costs above (the origin check and its strict missing-origin rule, opt-in cookie forwarding, authoritative admin reads, fail-closed coverage, production unless `NODE_ENV` says otherwise) are decisions, and so are the four reviewer-proposed ones: Q35 the rate-limiter warning, Q36 federation strictness, Q37 direct calls with the caller's session in public handlers, and Q38, added in v6, the scope interceptor being registered independently of `globalGuard` (§17.1) `[R5:SEC-r5-01]`.
