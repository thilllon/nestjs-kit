## 12. Packaging

### 12.1 tsdown configuration (tsdown 0.23.x, pinned exactly with its rolldown) `[A][B][C]`

```ts

const neverBundle = [
  /^@nestjs\//,
  /^better-auth(\/|$)/,

const common = {

  fixedExtension: true, // .mjs/.cjs + .d.mts/.d.cts (0.23 default on node; explicit on purpose)

export default defineConfig([
  {
    ...common,
    name: "library",
    entry: {
      // one entry per subpath of §2.1
      index: "src/index.ts", // kernel + composition root; re-exports src/extensions/{http,session}
      platform: "src/shared/platform/index.ts",
      express: "src/extensions/express/index.ts",
      fastify: "src/extensions/fastify/index.ts",
      graphql: "src/extensions/graphql/index.ts",
      websockets: "src/extensions/websockets/index.ts",
      microservices: "src/extensions/microservices/index.ts",
      admin: "src/extensions/admin/index.ts",
      organization: "src/extensions/organization/index.ts",
      "api-key": "src/extensions/api-key/index.ts",
      testing: "src/testing/index.ts",
      "testing/conformance": "src/testing/conformance/index.ts",
    },
    publint: true,
    attw: { profile: "node16", level: "error" },
  },
  {
    ...common,
    name: "plugin", // separate build: its import graph can never reach @nestjs/* or node:* [A]
    entry: { plugin: "src/plugin/index.ts" },
  },
]);
```

- Within the library build, subpath entries share chunks per format. `.`, `./express` and `./graphql` therefore share one instance of the kernel, contracts and tokens within a format (R:packaging §3.4). The same holds for declarations: `Register` and `PrincipalKinds` are declared once per format, so an augmentation reaches every subpath (§12.3).
- The plugin has its own build, so a chunking decision can never make `./plugin` import kernel code. Only the tiny protocol types and constants are duplicated, and that is safe because the handle is found through a `Symbol.for` key (§10.2).
- The plugin stays runtime-agnostic. v2's duties use only `better-auth/cookies` (`parseCookies`, for credential matching) and Web Crypto (`globalThis.crypto.randomUUID()`, for the client-IP header name), and import no `node:crypto` `[R1:SEC-r1-03, SEC-r1-18]`. v3's duties need no import at all: the endpoint-result observer (after-hook entry 4, a `WeakSet`) and the counter of database writes while unbound (in the DB dispatchers) are plain language features, so no `node:*` specifier enters either `[R2:BA-r2-06, NEST-r2-10]`. The purity check (§12.9 step 5) pins the complete list of allowed specifiers.
- A top-level await cannot slip in. The CJS build fails with rolldown `UNSUPPORTED_FEATURE`, and CI `require()`s every ESM entry on Node 22.12 to catch `ERR_REQUIRE_ASYNC_MODULE` (R:packaging §3.5, §6.1).

### 12.2 Formats and extensions

- The package is `"type": "module"`. Each entry emits `dist/<entry>.mjs` (ESM), `.cjs` (CJS), `.d.mts` and `.d.cts`, plus shared chunks per format.
- The `.cjs` files `require()` ESM-only peers (better-auth, and `@nestjs/*` on Nest 12) through require(esm). That works on Node ≥ 22.12 because neither graph has top-level await (R:packaging §1.4, §2.2), which is why engines is `>=22.12.0` (D1).
- 22.12.0 prints an `ExperimentalWarning`; 22.13+ does not.

- **The map is §2.1, one to one.** The thirteen subpaths of §2.1 are the thirteen subpath keys here (`./package.json` aside) and the thirteen entries of §12.1 (twelve in the library build, one in the plugin build). A CI check compares the three lists, so an entry cannot ship without its export or the other way round.
- **Condition order.** Within `exports`, the most specific condition (`module-sync`) comes first. Within each branch, `types` comes first and `default` last (publint `EXPORTS_TYPES_SHOULD_BE_FIRST`, `EXPORTS_DEFAULT_SHOULD_BE_LAST`). This exact shape, packaging variant A, passed attw with all columns green and publint with only an `engines` suggestion (R:packaging §5.4).
- **Types under `module-sync`.** TypeScript ignores `module-sync` and resolves `import`/`require` to `.d.mts`/`.d.cts`, whose contents are identical.
- **Augmentations from our own subpaths.** `./api-key` adds its principal kind with `declare module 'nestjs-slightly-better-auth' { interface PrincipalKinds { … } }` inside its own declaration file (§2.2.15). That is a package self-reference from a file under `node_modules`. TypeScript resolves it through the `exports` map, and the augmentation applies only in programs that import `./api-key` (LEAD-EXP-5). The consumer type matrix asserts both directions (§12.9 step 10).
- **No default exports anywhere.** Named exports only, per publint `CJS_WITH_ESMODULE_DEFAULT_EXPORT`.
- **`sideEffects: false` is honest.** Nothing runs at import time, and no entry keeps module-level state (§12.5).
- **No `typesVersions`.** `node10` is unsupported (§11.8).

### 12.4 Engines and peers (D1, D4)

- **`engines.node: ">=22.12.0"`.** This is the require(esm) line: it is unflagged in 22.12.0, and 22.11 fails (R:packaging §1.4). Node 20 is EOL (2026-04-30). It is the floor any CJS consumer of better-auth 1.7 or Nest 12 already has, whatever we ship (R:packaging §2.6). There is no upper bound, because the reference's `<23` broke Node 24 users (#130).
- **Peers:** Nest `^11 || ^12`; `@nestjs/graphql ^13 || ^14`; `graphql ^16.11 || ^17` (both GraphQL majors peer on that range); better-auth `>=1.7.0 <2`. The table is §2.4.
- **better-auth specifiers we import.** A peer range is only as good as the subpaths it guarantees, so the list is closed and CI-checked:

  | Entry                            | better-auth specifiers (runtime)                                                                                                                                           | Verified in 1.7.4  |
  | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
  | `.` and the Nest-facing subpaths | `better-auth/api` (`isAPIError`)                                                                                                                                           | LEAD-V2, LEAD-V5   |
  | `./plugin`                       | `better-auth/api` (`createAuthMiddleware`, `setShouldSkipSessionRefresh`), `better-auth/cookies` (`parseCookies`)                                                          | LEAD-V2, LEAD-V19  |
  | `./api-key`                      | `better-auth/plugins/access` (`role`)                                                                                                                                      | LEAD-V15           |
  | `./testing`                      | `better-auth` only; `authHeadersFor` uses the `testUtils()` plugin that the user's test instance already includes                                                          | LEAD-V15           |
  | `./testing/conformance`          | `better-auth` (`betterAuth`), `better-auth/api` (`createAuthEndpoint`, for `conformanceProbePlugin()`), `better-auth/plugins` (`testUtils`), `better-auth/adapters/memory` | LEAD-V15, LEAD-V33 |
  | declarations                     | `better-auth` (types only, §11.7)                                                                                                                                          | EXP-C11            |

  Every specifier in the table is in the `exports` map of better-auth 1.7.0 as well (LEAD-V33). The 1.7.0 floor job also loads every entry and runs the conformance kits (§14.2), so a specifier that a later release drops or moves fails our CI, not a user's boot. `@better-auth/api-key` is **not** a peer: `./api-key` calls `auth.api.verifyApiKey` and reads `$context`, and never imports the package (§2.4). It is a devDependency, installed in the matrix at the same version as better-auth.

- **Nest-owned identifiers.** The transports' handler claims and core's coverage rule read Nest metadata (§5.4 B16, §9.1–§9.4). Where Nest exports the identifier from a package root, we import it: `GRAPHQL_MODULE_OPTIONS`, `RESOLVER_TYPE_METADATA` and `RESOLVER_PROPERTY_METADATA` from `@nestjs/graphql` 13 and 14 (LEAD-V30, LEAD-V42). Where it does not, the unit that needs it holds the string literal: `'path'` and `'method'` (HTTP routes, `httpTransport()`), `'websockets:is_gateway'` (LEAD-V13) and `'websockets:message_mapping'` (the WS units), `'microservices:pattern'` (LEAD-V32), and `'__guards__'` and `'__interceptors__'` (core's coverage rule, to recognize `@UseGuards(BetterAuthGuard)` with `@UseInterceptors(BetterAuthScopeInterceptor)`) (LEAD-V42) `[R2:NEST-r2-02, NEST-r2-11, NEST-r2-12]`. There are **no deep imports** of Nest packages: 12.x packages have `exports` maps, and the specifiers differ between the two majors (LEAD-V29). Each literal is pinned by a CI test on both majors (§12.9 step 7) `[R1:NEST-r1-05, NEST-r1-06, NEST-r1-13]`.
- **No version probing** `[R1:NEST-r1-13, SEC-r1-12]`. Nothing in the package reads a Nest package's version or probes an API to infer it. A skewed install (for example `@nestjs/core` 12 with `@nestjs/websockets` 11, which package managers only warn about) therefore cannot switch a check off: gateway, hybrid-RPC and field-resolver coverage are required on every major (ADR-40). Mixed Nest majors remain unsupported. One feature detection exists, and it gates no check: the gRPC carrier uses Nest 12's `Grpc*Exception` classes when a namespace import of `@nestjs/microservices` has them, and plain `RpcException` codes otherwise (§9.4).
- **Semver.** Dropping a Node, Nest or better-auth major is a semver-major change. Format and engines never change in a minor release (#108, #130, #141). A change of the plugin protocol version (`BridgeHandle.protocol`, B04) is a semver-minor change at least, and both halves ship in the same package version.

### 12.5 Dual-package hazard strategy (S5) `[A][B][C]`

**Primary: `module-sync` first, ESM canonical (packaging variant A).** On every Node version in our engines range, `import` and `require` both resolve the `module-sync` branch, so both load the ESM build. There is exactly one copy of every class (`BetterAuthModule`, `BetterAuthGuard`, `BetterAuthService`, `WsConnectionAuth`, platform and transport classes) per process. This was verified for this exports shape on 22.12.0, 22.22.0 and 26.7.0 ("both→mjs", R:packaging §5.4). The CJS build serves tools that resolve `require` without `module-sync` support, such as some bundlers and runners, which is exactly R3's purpose. For bundlers, `default`-condition handling is UNVERIFIED and is covered by the bundler fixtures (§14.6).

**Defense in depth, independent of routing:**

1. Every DI token, metadata key and runtime slot is `Symbol.for('nestjs-slightly-better-auth:…')` (§2.3). That includes the tokens extension units export (`WS_CONNECTION_AUTH`) and the per-invocation slots (`ACTIVE_ORGANIZATION_ID`, `ACTIVE_MEMBER_ROLE`) `[R1:NEST-r1-12, NEST-r1-01]`. `Symbol()` and random `Reflector.createDecorator()` keys do not survive two copies (R:packaging §5.2: `Symbol()` tokens → `UnknownDependenciesException`; `Symbol()` metadata keys → hooks silently not discovered).
2. Class tokens have `Symbol.for` aliases (`BETTER_AUTH_SERVICE` via `useExisting`, `WS_CONNECTION_AUTH` for `WsConnectionAuth`) plus helper decorators (`@InjectBetterAuthService()`), so injection works across copies.
3. The plugin-to-kernel link is a versioned protocol object on the plugin instance, found through `getPlugin()` (§10.2). It is never shared module state.
4. Requirement metadata carries policy objects by reference, so the guard of either copy just calls `evaluate`. Principal kinds, accepted kinds and param-kind constraints are plain strings (§7.6), which compare equal across copies.
5. There is no `instanceof` on our own classes across the package boundary:
   - `isAuthFailure` (§2.2.6) checks the failure's `Symbol.for` brand, and the composition root recognizes an `ExtensionDefinition` by its `EXTENSION_DEFINITION` brand (§2.2.1), not by class;
   - our own error classes carry a `Symbol.for` brand too. The guard and `normalizeThrown` recognize `BetterAuthInfrastructureError` and `BetterAuthConfigurationError` with `isInfrastructureError` / `isConfigurationError` (§2.2.6), so an error thrown by a source or policy compiled against the other copy is passed through, not wrapped again `[R1:SEC-r1-19]`;
   - better-auth errors use `isAPIError` (S6);
   - the HTTP, WS and RPC denials are Nest's own exception classes, with one copy per Nest major. `BetterAuthGraphqlDenial` and `BetterAuthGraphqlInternalError` are read by the GraphQL drivers structurally (`extensions`), never by class.
6. There is no module-level mutable state. Everything lives in a provider, on an extension instance or on the plugin object `[R1:SEC-r1-15, SEC-r1-16, SEC-r1-18, SEC-r1-05]`:

   | State                                                                                                                                                         | Lives in                                                                                                       |
   | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
   | request, connection, invocation and browser-leg state (origin verdicts); route-plan cache per (class, handler); registries; the application's lifecycle state | kernel providers (`RequestScope`, `RoutePlanner`, `TransportRegistry`, `InstanceRegistry`, `MountCoordinator`) |
   | once-per-application flags and caps: `W_PROXY_UNTRUSTED`, the degraded-tier warning, the 100-path cap of the 404 diagnostics                                  | `AuthExchange` and the platform provider                                                                       |
   | the API-key outage-probe throttle                                                                                                                             | the `apiKeyPrincipal()` source instance                                                                        |
   | the client-IP header name, the binding, the pre-bind dispatch counter, the set of endpoint-produced results, the `initTestApp` slot                           | the plugin object returned by `nestjs()` (one per better-auth instance)                                        |

   "Once" in a warning's description therefore means once per Nest application, which is also once per process outside tests.

7. Double registration across copies is caught by the exclusive plugin binding (B06), the per-server mount stamp (B10) and the one-declaration rule for platforms and transports (B25) (§5.6).
8. CI loads both builds in one process and asserts that tokens, metadata, brands and the plugin handshake interoperate (§14.6).

**What remains.** Class identity for enhancers: `overrideProvider(BetterAuthGuard)` and `overrideGuard(BetterAuthGuard)` must import the same copy the app resolved, which `module-sync` makes automatic on supported Node. `overrideAuthGuard` from `./testing` takes the class from the library build's shared chunk, so it always matches the copy that `.` resolved in the same format (§14.8). This is documented and covered by the dual-load test.

**Rejected alternatives** (ADR-20):

- **`node` → CJS routing:** it would make every Node consumer, including Nest 12 ESM apps, run the CJS build, against better-auth's and Nest 12's ESM direction. It also needs `.d.cts` under `node.import` to avoid attw "Masquerading as ESM".
- **An ESM wrapper over CJS:** it makes CJS canonical, for the same reason.
- **ESM-only:** it violates R3.
- **Plain `import`/`require` routing:** it leaves the class-identity hazard open.

### 12.6 Decorator-metadata guarantees `[A][B][C]`

- **Explicit `@Inject(token)`** on **every** library constructor parameter, so correctness never depends on `design:paramtypes`. Isolated transpilation (oxc) emits `Object` for interface and type-only-import parameters (R:packaging §4.1). This covers the classes v2 added or made injectable for users (`WsConnectionAuth`, the extension classes behind `ExtensionDefinition.exports`).
- **`tsconfig.build.json`**, the exact file tsdown reads, sets `experimentalDecorators` and `emitDecoratorMetadata`. Without the first, tsdown **builds successfully** but emits TC39 decorator syntax that throws `SyntaxError` at load. Metadata is still emitted for users' own injectables that extend library classes.
- **CI checks:**
  - `dist/**/*.{mjs,cjs}` contains no raw `@`-decorator syntax;
  - `dist/index.mjs` contains `__decorateMetadata("design:paramtypes"`;
  - every entry is imported from `dist` in both formats, and a minimal app is booted from each.
- **Biome.** `style/useImportType` is off for `src/**`, because its "safe fix" rewrites injected classes into type imports and yields `design:paramtypes: [Object]`. `unsafeParameterDecoratorsEnabled: true`. `noUnusedPrivateClassMembers` is off for constructor-injected members. `vcs.useIgnoreFile: true`. The literal ban of §3.2 rule 5 is a Biome restricted-syntax rule scoped to `src/core/**` (§14.7) `[R1:NEST-r1-07]`.

### 12.7 Optional peers via subpaths

- The root entry imports only required peers. Every optional peer is imported **statically** and only by its own subpath: `./graphql` → `@nestjs/graphql`; `./websockets` → `@nestjs/websockets`; `./microservices` → `@nestjs/microservices`; `./testing` → `@nestjs/testing`. A REST-only app never resolves them (reference #82, #97, #100).
- `./admin` and `./organization` import the kernel only. `./api-key` adds `better-auth/plugins/access` and nothing else. The better-auth plugins themselves are the user's imports in `auth.ts`; their presence is boot-checked (B13).
- **Not used:**
  - Nest's `loadPackage`: sync and `process.exit` on failure in 11, async and internal in 12 (R:nest-di §8.1);
  - `createRequire(import.meta.url)('peer')`, which is bundler-hostile (#147);
  - bare `require`;
  - top-level await;
  - lazy `import()` on hot paths;
  - deep imports of Nest packages (`@nestjs/<pkg>/<path>`, §12.4).
- **Import-graph checks in CI:**
  - `.` must not reach an optional peer or any `src/extensions/**` file other than the built-in units the composition root re-exports (`http`, `session`);
  - `./plugin` (including its chunks) must not reach `@nestjs/*` or `node:*`; its only runtime imports are `better-auth/api`, `better-auth/cookies` and `defu`;
  - an extension must not import another extension;
  - no source file imports a Nest deep specifier, `better-call` or `@better-auth/*`.

### 12.8 Toolchain (R5)

- **pnpm.** A workspace with the library at the root and fixtures under `fixtures/*` (§14.6), each an explicit package. Because of pnpm's strict layout, every module a test imports is an explicit devDependency; the current repo's `rxjs` was unresolvable (R:current-repo). That includes `@better-auth/api-key` and the optional Nest peers, which the conformance jobs need.
- **tsdown 0.23.x**, pinned exactly with its rolldown. A caret pairing produced hashed `.d.ts` names in the current repo.
- **TypeScript 6.x** as the devDependency. rolldown-plugin-dts's `tsc` generator needs the classic JS API that TS 7 lacks (R:packaging §2.4).
- **vitest 5 on Vite 8.** It honors `emitDecoratorMetadata` from tsconfig without `unplugin-swc` (R:packaging §4.3). Vite 8 is pinned. The security suite runs as its own vitest project with `NODE_ENV=production` (§14.4), because better-auth switches its origin checks off under `NODE_ENV=test`.
- **biome**, with the rules in §12.6.
- **lefthook** pre-commit: `biome check` and `tsc --noEmit`. A tsdown build succeeds despite type errors, so the separate typecheck is mandatory.
- **Release:** changesets and npm OIDC trusted publishing with provenance.
