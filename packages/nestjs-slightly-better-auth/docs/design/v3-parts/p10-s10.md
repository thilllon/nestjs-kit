## 10. Hooks

### 10.1 Why a plugin (S1) `[A][B][C]`

The reference library wraps `auth.options.hooks.before/after` and `databaseHooks` _after_ `betterAuth()` has run. That works only because `ctx.options` is a shallow copy that shares the nested objects, which is why users had to pre-declare `hooks: {}` (R:ref-impl §5.2; reference issues #42 and #103; PR #138 broke it with `{ source, hooks }`). The wrappers also drop return values, so `{ context }` rewrites, short-circuits and DB `false`/`{ data }` all stop working.

better-auth's documented alternative is a plugin:

- plugin `hooks.before/after` are **arrays of matcher + handler** (`CORE/types/plugin.ts:89-100`);
- plugins contribute database hooks through `init() → { options: { databaseHooks } }` (LEAD-V4);
- the docs say "if you need to reuse a hook across multiple endpoints, consider creating a plugin" (`docs/concepts/hooks.mdx:326-328`).

`betterAuth()` cannot take plugins after construction (R:ba-core §2.1), so the user adds `nestjs()` in `auth.ts`. Nest-discovered hooks bind to it late, through a registry. Nothing in `auth.options` is ever written.

### 10.2 The plugin (`./plugin`)

```ts
// imports only better-auth/api, better-auth/cookies and defu — never @nestjs/*, never node:* (runtime-agnostic; CI-enforced)
import {
  createAuthMiddleware,
  setShouldSkipSessionRefresh,
} from "better-auth/api";
import { parseCookies } from "better-auth/cookies";

const HANDLE = Symbol.for("nestjs-slightly-better-auth:bridge");

/** Versioned protocol object on the plugin instance; core finds it via (await auth.$context).getPlugin(id)[HANDLE]. [B][C] */
export interface BridgeHandle {
  readonly protocol: 3; // checked by core (B04); v3 added producedByEndpoint and DB-write counting [R2:BA-r2-06, NEST-r2-10]
  readonly clientIpHeader: string | null; // single source of truth for the header name (§6.8)
  readonly bound: boolean;
  /** Endpoint dispatches and database-hook dispatches (writes) seen while no app was bound, since the last unbind (B26). */
  readonly unboundDispatches: number;
  /**
   * Returns unbind. A binding from the same owner (the same application) is a no-op that returns the existing registration
   * (NestMicroservice.init() runs lifecycle hooks twice). Throws INSTANCE_ALREADY_BOUND if another bootstrapped app is bound;
   * takes over a never-bootstrapped one (B06). [R2:NEST-r2-05]
   */
  bind(binding: BridgeBinding): { unbind(): void; tookOverFrom?: string };
  /** true when an endpoint returned `value` (an object) in a non-router dispatch observed while bound; false for before-hook short-circuits (LEAD-V37). */
  producedByEndpoint(value: unknown): boolean;
}
export interface BridgeBinding {
  /** The application: compared by identity for the same-owner no-op; `description` goes into the B06 message. */
  readonly owner: { readonly description: string };
  /** Set by the kernel in onApplicationBootstrap. */
  bootstrapped: boolean;
  /** View of the kernel's RequestScope; the plugin never owns an AsyncLocalStorage. [C] */
  current(): ScopeView | undefined;
  /** Credential header names declared by the instance's principal sources (credential matching, §7.5). */
  readonly credentialHeaders: readonly string[];
  readonly before: readonly CompiledHook[]; // sorted by order, then discovery order
  readonly after: readonly CompiledHook[];
  readonly database: Readonly<
    Record<
      DatabaseHookTarget,
      {
        readonly before: readonly DbBeforeFn[];
        readonly after: readonly DbAfterFn[];
      }
    >
  >;
  /** Debug log when the bridge drops a direct call's cookies because its credential is foreign. */
  onDropped(path: string): void;
}
export interface ScopeView {
  readonly cookies: CookieSink | null;
  readonly forward: "none" | "same-credential" | "any";
  readonly inbound: (() => Headers) | undefined;
  readonly internal: boolean;
}
export interface CompiledHook {
  /**
   * A throwing user predicate makes matches() return TRUE, so that run() rethrows it: as APIError 500 from before-hooks
   * (better-auth logs and converts before-hook matcher throws) and raw from after-hooks (better-auth propagates them),
   * LEAD-V23. v1 returned false and silently skipped the hook. [R1:BA-r1-06]
   */
  matches(ctx: HookEndpointContext, scope: ScopeView | undefined): boolean;
  run(ctx: HookEndpointContext): Promise<unknown>;
}

export function nestjs(options: NestjsPluginOptions = {}) {
  let binding: BridgeBinding | null = null;
  let unboundDispatches = 0;
  const endpointResults = new WeakSet<object>(); // objects endpoints returned; after-hooks never run for a short-circuit
  const scope = () => binding?.current();
  const isRouter = (ctx: object) =>
    "_flag" in ctx && (ctx as { _flag?: string })._flag === "router";
  const clientIpHeader =
    options.clientIpHeader === false
      ? null
      : (options.clientIpHeader ??
        `x-nsba-ip-${globalThis.crypto.randomUUID().replaceAll("-", "")}`); // per plugin instance (per nestjs() call), process-local [R1:SEC-r1-18]
  const handle: BridgeHandle = {
    protocol: 3,
    clientIpHeader,
    get bound() {
      return binding !== null;
    },
    get unboundDispatches() {
      return unboundDispatches;
    },
    bind(b) {
      if (binding && binding.owner === b.owner) {
        const same = binding;
        return {
          unbind: () => {
            if (binding === same) binding = null;
          },
        };
      }
      if (binding?.bootstrapped)
        throw new Error(
          `INSTANCE_ALREADY_BOUND: bound to ${binding.owner.description}`,
        );
      const tookOverFrom = binding?.owner.description; // a failed init() never bootstrapped: take over, kernel warns
      binding = b;
      unboundDispatches = 0;
      return {
        tookOverFrom,
        unbind: () => {
          if (binding === b) binding = null;
        },
      };
    },
    producedByEndpoint: (value) =>
      typeof value === "object" && value !== null && endpointResults.has(value),
  };
  return {
    id: "nestjs-slightly-better-auth",
    [HANDLE]: handle,
    init: () => ({
      options: {
        databaseHooks: createDatabaseDispatchers(
          () => binding,
          () => {
            unboundDispatches++;
          },
        ), // 4 models × 3 ops × before/after (§10.6); counts writes while unbound
        ...(clientIpHeader
          ? { advanced: { ipAddress: { ipAddressHeaders: [clientIpHeader] } } }
          : {}), // default; user wins (§6.8)
      },
    }),
    hooks: {
      before: [
        {
          // 1. refresh suppression: every non-router endpoint dispatched from a cookie-less scope (§7.4); also counts pre-bind dispatches
          matcher: (ctx) => {
            if (!binding) {
              unboundDispatches++;
              return false;
            }
            return !isRouter(ctx) && scope()?.cookies === null;
          },
          handler: createAuthMiddleware(async () => {
            await setShouldSkipSessionRefresh(true);
          }),
        },
        {
          // 2. Nest @BeforeAuth dispatcher
          matcher: (ctx) =>
            binding?.before.some((h) => h.matches(ctx, scope())) ?? false,
          handler: createAuthMiddleware((ctx) =>
            runBefore(binding!, ctx, scope()),
          ),
        },
      ],
      after: [
        {
          // 3. Nest @AfterAuth dispatcher
          matcher: (ctx) =>
            binding?.after.some((h) => h.matches(ctx, scope())) ?? false,
          handler: createAuthMiddleware((ctx) =>
            runAfter(binding!, ctx, scope()),
          ),
        },
        {
          // 4. endpoint-result observer: records the final returned object of a non-router dispatch; a before-hook short-circuit skips
          //    every after-hook, so a session a hook supplied is never recorded (LEAD-V37, LEAD-EXP-8) [R2:BA-r2-06]
          matcher: (ctx) => binding !== null && !isRouter(ctx),
          handler: createAuthMiddleware(async (ctx) => {
            const r = ctx.context.returned;
            if (typeof r === "object" && r !== null) endpointResults.add(r);
          }),
        },
        {
          // 5. cookie bridge (nextCookies pattern), only where the scope enables forwarding; last, so it also sees cookies Nest after-hooks set
          matcher: (ctx) => {
            const s = scope();
            return !isRouter(ctx) && !!s?.cookies && s.forward !== "none";
          },
          handler: createAuthMiddleware(async (ctx) => {
            const s = scope()!;
            if (
              s.forward === "same-credential" &&
              !sameCredential(ctx, s, binding!.credentialHeaders)
            ) {
              binding!.onDropped(ctx.path);
              return; // foreign credential: never hand it to this caller [R1:SEC-r1-03]
            }
            const setCookie = ctx.context.responseHeaders?.getSetCookie() ?? [];
            if (setCookie.length) s.cookies!.append(setCookie);
          }),
        },
      ],
    },
  } satisfies BetterAuthPlugin;
}

/** Session-token cookie (better-auth's own name and parser), authorization, and declared credential headers. */
const SEP = "\u0000"; // cannot occur in header values
const NO_CREDENTIAL = (extra: readonly string[]) =>
  SEP.repeat(extra.length + 1);
function credentialOf(
  headers: Headers | undefined,
  ctx: HookEndpointContext,
  extra: readonly string[],
): string {
  if (!headers) return NO_CREDENTIAL(extra);
  const token =
    parseCookies(headers.get("cookie") ?? "").get(
      ctx.context.authCookies.sessionToken.name,
    ) ?? "";
  return [
    token,
    headers.get("authorization") ?? "",
    ...extra.map((h) => headers.get(h) ?? ""),
  ].join(SEP);
}
function sameCredential(
  ctx: HookEndpointContext,
  s: ScopeView,
  extra: readonly string[],
): boolean {
  const call = credentialOf(ctx.headers, ctx, extra);
  return (
    call === NO_CREDENTIAL(extra) ||
    call === credentialOf(s.inbound?.(), ctx, extra)
  ); // login/sign-up, or the caller's own
}
```

- **Entry order** follows `nextCookies` (`BA/integrations/next-js.ts:47-144`):
  - Suppression runs before any Nest before-hook. Nested `auth.api` calls made inside a hook share the dispatch's request state and inherit the flag.
  - The observer runs after the Nest after-hooks, so it records the value a Nest after-hook put in `ctx.context.returned`, which is the value the caller receives. It records only objects, in a `WeakSet` on the plugin instance, and costs one set insertion per non-router call while bound.
  - The cookie bridge runs after the Nest after-hooks, so it also forwards cookies they set with `ctx.setCookie`.
- **Placement** `[R1:BA-r1-07]`. The plugin must be **last** in `plugins`, the `nextCookies` rule: later plugins' after-hooks could set cookies the bridge never sees, because plugin hooks run in plugin order after `options.hooks` (LEAD-V1). B05 warns otherwise. Being last does **not** let Nest before-hooks see other plugins' before-hook effects (v1 wrongly said so). Every before-hook receives the original input, and `{ context }` results such as `bearer()`'s cookie conversion are merged only after all before-hooks ran (LEAD-V23). A before-hook that short-circuits pre-empts every later one and all after-hooks. For example, the api-key plugin answers `/get-session` itself when `enableSessionForAPIKeys` is on, so no Nest hook on `/get-session` runs for API-key callers (LEAD-V21).
- **Construction time only.** The plugin writes nothing into `auth.options` after construction. Its `init()` contributions are merged by better-auth itself during construction.
- **Fixed entries and a late-bound registry, not per-hook entries pushed at bind time** `[A][C]`. Pushing entries into our own `hooks.before` array at bind time would get better-auth's composition for free. It would, however, depend on better-auth re-reading plugin arrays on every dispatch. That is true in 1.7.4 (LEAD-V1: `getHooks` runs per dispatch) but is an implementation detail; if it were ever cached at init, every Nest hook would silently stop, which is the reference's #42 failure mode (ADR-07).
- **Runtime-agnostic** `[C]`. The plugin imports only `better-auth/api`, `better-auth/cookies` and `defu`, and uses Web Crypto for the header name. The `AsyncLocalStorage` lives in the kernel and is reached through `binding.current()`, so `auth.ts` stays loadable in every runtime better-auth supports, and by the better-auth CLI.
- **Inert before binding and after unbinding.** All matchers return `false` and the DB dispatchers are no-ops, so the same `auth.ts` can be shared with scripts and non-Nest code. The pre-bind counter, which the first before-hook matcher and every DB dispatcher increment while unbound, only feeds B26 `[R2:NEST-r2-10]`.
- **Dual-package safety.** Core finds the handle through `getPlugin(id)`, which returns the user's own plugin object (EXP-B:E2, EXP-C1), under a `Symbol.for` key. A plugin imported from the ESM build and a kernel loaded from the CJS build still find each other.

### 10.3 Discovery and validation `[A][B][C]`

`HookBinder` runs in the core module's `onModuleInit`. Among non-global modules this runs first; other global modules imported before `BetterAuthModule` may run their `onModuleInit` earlier (LEAD-V27), which is why seeding belongs in `onApplicationBootstrap` and B26 reports calls made before binding `[R1:NEST-r1-11]`. Steps:

1. `discovery.getProviders()` across all modules. It is a full scan, because the `metadataKey` filter misses `useFactory`/`useValue` providers (R:nest-di §6.2). Wrappers without an instance and `isAlias` wrappers are skipped.
2. `MetadataScanner.getAllMethodNames(prototype)`, then read `Symbol.for(…:hook)` and `Symbol.for(…:db-hook)` metadata per method. No class marker is required `[C]`.
3. Validate:
   - a non-static provider (`wrapper.isDependencyTreeStatic() === false`) fails boot (B11), because discovery would see a prototype-only instance with no dependencies (R:nest-di §6.3);
   - unknown string patterns fail boot with a "did you mean" (B12);
   - an unknown `instance` fails boot;
   - the same class provided in two modules registers twice, and boot warns with both module names.
4. Compile matchers, bind `instance[method]` to the instance, sort by `order` ascending then discovery order, and bind the tables (plus the instance's source `credentialHeaders`) to each instance's plugin handle.

Lazily loaded modules are not discovered, because Nest gives them no lifecycle hooks. This is documented (risk RK7).

### 10.4 Matching `[A][B][C]`

- **Patterns.** `ctx.path` is the endpoint's **route pattern** (`'/callback/:id'`), not the concrete URL (`BA/api/dispatch.ts:348`). A string matches a pattern exactly. An array matches any of its patterns. A predicate `(ctx) => boolean` is the escape hatch for anything else. No argument means every endpoint. Pattern strings autocomplete from `EndpointPath` (§11.4) and are validated at boot against `auth.api[*].path`: 67 of 69 endpoints expose `.path` at runtime (EXP-C8).
- **`calls`.** `'http'` matches requests routed by `auth.handler` (`ctx._flag === 'router'`). `'server'` matches direct `auth.api.*` calls. `'all'` is the default.
- **`skipInternal`.** The library's own calls (the guard's `getSession`, policy checks) run in scopes marked `internal: true`, and `skipInternal: true` ignores them. The **default is `false`**, which is faithful to better-auth, where user hooks also run for server calls (R:ba-core §4.1). The docs warn that a path-less hook therefore runs on every guarded request, the unexplained "hooks run twice" of reference issue #103, and that `skipInternal: true` is the one-flag fix for audit-style hooks. Draft B's opposite default was rejected (ADR-08).
- **Security rules belong where every path passes** `[R1:BA-r1-07]` `[R2:BA-r2-07]`.
  - A `@BeforeAuth('/get-session')` that looks up the user from the request would fail open, because before-hooks see the original request (a bearer-token client presents no session cookie there) and the api-key short-circuit skips it entirely. A path-less `@BeforeAuth` is no alternative, for the same reason.
  - An `@AfterAuth('/get-session')` that inspects or replaces `ctx.context.returned` runs for cookie and bearer callers of **`getSession` dispatches**: the guard's resolution and every other `auth.api.getSession` call. It is therefore a place for rules that apply to **Nest routes only**. It does **not** reach better-auth's own endpoints: they resolve the session with `getSessionFromCtx`, which calls `getSession` as a plain function, and a plain call skips hooks (`BA/api/dispatch.ts:317-318`; LEAD-V36). A "suspended user" rule written this way answers 401 on Nest routes while the same cookie keeps working on `/update-user`, `/change-email`, `/organization/*` and `/api-key/create` through the mount (REV2-BA:`exp7-afterhook-get-session-scope.mjs`). It also misses API-key callers (the short-circuit skips after-hooks).
  - A rule that must hold **everywhere** changes state that better-auth itself consults on every path: better-auth's admin ban (it revokes the user's sessions and blocks new ones through its `session.create` hook), revoking the user's sessions, or a `@BeforeDatabase('session.create')` hook, which sees every sign-in path.

  The repository test `LIB-hook-bearer-client` (§14.5) pins the before-hook visibility rule and the after-hook's scope.

Hook methods receive better-auth's own context objects: `HookEndpointContext` for endpoint hooks, and `(data, ctx | null)` for DB hooks, where `ctx` is `null` outside an endpoint. Nothing is re-wrapped, so `ctx.setCookie`, `ctx.json` and `ctx.redirect` behave as in native hooks. `ctx.body` is the raw input: better-auth validates the body only when the endpoint itself runs, after the before-hooks (better-call `context.ts:203-219`), so the hook types mark body values `unknown` (§11.3) `[R1:BA-r1-08]`.

**Parity guarantee.** A property test (`LIB-dispatcher-parity`) registers the same randomly generated hook functions two ways: as N native plugins, and as N Nest hooks behind one `nestjs()` dispatcher. It asserts identical responses, headers and DB effects for create, update, updateMany and delete, and for throwing matchers (§14.5). That is how the mirror stays faithful across better-auth releases.

### 10.6 `databaseHooks`, ordering, lifecycle, teardown, multiple apps

- **Coverage.** Models `user`, `session`, `account` and `verification`; operations `create`, `update` and `delete`; phases before and after. `init()` contributes one delegating dispatcher per target, mirroring better-auth per operation (LEAD-V22) `[R1:BA-r1-06]`:

  ```ts
  before: async (data, ctx) => {
    const binding = getBinding();
    if (!binding) { countUnbound(); return undefined; }                       // B26 also counts writes while unbound [R2:NEST-r2-10]
    const fns = binding.database[target].before;
    if (op === 'delete') {                                                    // only false is honored
      for (const fn of fns) if ((await fn(data, ctx)) === false) return false;
      return undefined;
    }
    let acc = {}, changed = false;                                            // ONLY what hooks return [R2:BA-r2-02]
    for (const fn of fns) {
      const r = await fn(op === 'create' ? { ...data, ...acc } : data, ctx);  // create chains; update: every hook sees the ORIGINAL payload
      if (r === false) return false;                                          // abort, like better-auth
      if (r && typeof r === 'object' && 'data' in r) { acc = { ...acc, ...r.data }; changed = true; }
    }
    return changed ? { data: acc } : undefined;                               // better-auth merges it over its own accumulator
  },
  after: async (data, ctx) => {
    const binding = getBinding();
    if (!binding) { countUnbound(); return; }
    for (const fn of binding.database[target].after) await fn(data, ctx);
  },
  ```

  v2 returned `{ ...originalPayload, ...hookData }` for updates. better-auth merges a hook's result over the data earlier plugins already changed (`with-hooks.ts:136-139`), so the original values of every payload key overwrote those changes: a preceding plugin's `name.trim()` was undone whenever a Nest hook returned only `{ image }` (REV2-BA:`exp2-db-update-clobber.mjs`). Returning only the hooks' own data is what N native plugins produce (LEAD-EXP-10).

- **Ordering.** For endpoint hooks, better-auth runs the user's `options.hooks` first, then earlier plugins, then Nest hooks (`order` ascending, then discovery order). For DB hooks, **Nest's run before the user's `databaseHooks`** in `auth.ts`, because better-auth appends user DB hooks last (LEAD-V4). This is documented.
- **Bind and unbind** `[B][C]`. Binding happens in `onModuleInit`, after discovery and B03/B04, once per application; a second `bind()` from the same application is a no-op (§5.7) `[R2:NEST-r2-05]`. The kernel sets `binding.bootstrapped = true` in `onApplicationBootstrap`. Unbinding happens in `onApplicationShutdown`, after the server stops accepting requests (§5.7), and is idempotent. Nothing on `auth.options` needs reverting, because nothing was changed.
- **Exclusive binding** `[B][C]`. One **live** Nest application per better-auth instance. A second `bind()` while a bootstrapped app is bound throws (B06). That catches forgotten `app.close()` calls in tests and double imports, instead of silently running hooks twice or leaking them across apps; the reference accumulated wrappers on a shared singleton (R:ref-impl §5.3). In practice:
  - sequential lifetimes are fine: close, then boot the next app. `initTestApp` closes a previous test app bound to the same instance before initializing the next one, which makes `beforeEach`-built apps work (§14.8) `[R1:SEC-r1-15]`;
  - an app whose `init()` failed never bootstrapped, so the next `bind()` takes over its binding and the kernel logs `W_INSTANCE_TAKEN_OVER`, instead of every later test failing with `INSTANCE_ALREADY_BOUND` and hiding the original error;
  - concurrent apps need one instance each (shape 3 in §5.1);
  - vitest isolates test files by default, so per-file module-level instances are already separate;
  - hybrid apps share one container, so there is one binding.
- **Calls outside any scope** (cron jobs, CLI scripts using an application context) still run bound Nest hooks. `current()` is `undefined` there, so there is no cookie capture and no suppression, which is plain better-auth behavior.
- **Named instances** each have their own plugin instance and therefore their own binding.

| Mechanism     | mutates `auth.options.hooks`/`databaseHooks` after construction | construction-time plugin with fixed entries and a late-bound registry                                                     |
| Prerequisite  | `hooks: {}` and `databaseHooks: {}` in the user's config        | `plugins: [..., nestjs()]` (boot-checked)                                                                                 |
| Return values | dropped (user hook and Nest hook)                               | better-auth semantics per operation, parity-tested                                                                        |
| Matching      | exact path equality only                                        | route patterns validated at boot, arrays, predicates, `calls`, `skipInternal`, `order`                                    |
| Typing        | `any`                                                           | `AuthHookContext<P>` (paths autocomplete, body values `unknown`), DB payloads from better-auth's own option types (§11.4) |
| Teardown      | none (leaks across apps)                                        | exclusive bind, takeover of failed inits, unbind on shutdown                                                              |
