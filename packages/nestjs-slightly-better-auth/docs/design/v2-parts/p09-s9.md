## 9. Transports

Every transport is an extension unit implementing `AuthTransport` (§4.2). The guard, resolver, evaluator, origin check and error taxonomy are identical for all of them. Transports differ only in context extraction, cookie capability, browser exposure, coverage checks and error delivery, as better-auth's own integrations imply (R:ba-integrations §9.4). D2's breadth costs one small object per transport and never a branch in core `[B]`.

### 9.1 HTTP (built-in, root entry)

```ts
describe(ctx, kit) {
  const http = ctx.switchToHttp();
  const req = http.getRequest(), res = http.getResponse();
  const a = kit.http!;                                    // B08 guarantees a platform when an HTTP adapter exists
  const key = a.key(req), request = a.request(req);
  return { key, invocation: key, carrier: req, headers: () => a.headers(req), clientIp: a.clientIp(req),
           cookies: a.cookieSink(req, res), request, param: (n) => a.param(req, n),
           browser: { enforce: !['GET', 'HEAD', 'OPTIONS'].includes(request.method), headers: () => a.headers(req),
                      url: request.url, ambientCookie: a.headers(req).has('cookie') } };
}
```

- **Cookies.** Express uses `res.append('set-cookie', v)` and Fastify uses `reply.header('set-cookie', v)`, both appending. The sink returns `false` once headers are sent. EXP-B:E7 showed guard-appended cookies arriving alongside handler-set cookies on both platforms and both majors.
- **Origin check.** Unsafe methods authenticated by the cookie need a trusted `Origin`/`Referer` (§7.10). Safe methods never do, which mirrors better-auth's router.
- **Denial.** An `HttpException` subclass: `UnauthorizedException`, `ForbiddenException` or `HttpException(…, 429)`. It carries the payload `{ statusCode, error, code, reason?, message }`, which is Nest's default body shape plus a stable `code`; reference issue #148 asked for this. These are `IntrinsicException`s, so Nest does not log them (LEAD-V9). A `challenge` is written as `WWW-Authenticate` through Nest's public `httpAdapter.setHeader(res, …)`. `Retry-After` is copied for 429.
- **Infrastructure.** `BetterAuthInfrastructureError` (not intrinsic, redacted cause) goes through Nest's filters, which answer 500 and log it. The HTTP transport has no `toInternalException`: Nest's default 500 body never includes the error message.

### 9.2 GraphQL: Apollo and Mercurius (`./graphql`)

**Shared behavior** `[A][B][C]`:

- `gql = GqlExecutionContext.create(ctx)`. The operation kind comes from `gql.getInfo().operation.operation`.
- **Queries and mutations share the HTTP request's principal.** The key is `kit.http.key(gql.getContext().req)`, so three root fields resolve the principal once (EXP-B:E8), and a sliding refresh on a GraphQL POST reaches the browser as `Set-Cookie`.
- **Decisions are per field** `[R1:NEST-r1-01]`. `invocation` is `gql.getInfo()` (`args[3]`). Each root field, alias and batched operation has its own `info` object, and every guard run of the same field sees the same one. `query { a: projects(orgId: "A") b: projects(orgId: "B") }` therefore evaluates the org requirement twice, with two different `fromParam('orgId')` values, while the principal is resolved once.
- **Cookie sink.** Mercurius uses `gql.getContext().reply`. Apollo on Express uses `req.res`. Apollo on Fastify uses `kit.http.responseFor(req)`, because the Apollo driver keeps only the request in its Fastify context (LEAD-V8); `FastifyPlatform.prepare` records `request.raw → reply` in a `WeakMap` from a root `onRequest` hook.
- **The carrier** is the GraphQL context object (`args[2]`), one per operation, for the principal stamp. Per-invocation values are stamped on `info`. Field resolvers without guards still read both.
- **`param(name)`** reads the resolver args first, then the route params.
- **Browser leg** (§7.10):
  - queries and mutations use the HTTP request, with `enforce` for mutations only;
  - subscriptions use the WebSocket upgrade request (`enforce` always).

  `ambientCookie` is true when the leg carried a cookie that `connectionParams` did not replace.

- **Denial.** `BetterAuthGraphqlDenial extends IntrinsicException` carries `extensions: { code: 'UNAUTHENTICATED' | 'FORBIDDEN' | 'RATE_LIMITED', reason?, statusCode }` `[L]`. graphql-js copies `originalError.extensions` into the formatted error (`graphql` 16 `error/GraphQLError.js:130-143`), so the code survives on both drivers. The HTTP status stays 200, the GraphQL-over-HTTP norm for field errors. LEAD-EXP-1 on Apollo showed:
  - the codes are preserved for 401, 403 **and 429**;
  - Nest logs nothing.

  The alternatives each fail somewhere. A plain `GraphQLError` (drafts A and C) is logged at ERROR on every denial, because it is not intrinsic. An `HttpException` (draft B) has its `extensions.code` rewritten by Apollo's `autoTransformHttpErrors`, so 429 becomes `INTERNAL_SERVER_ERROR` (LEAD-V8).

- **Infrastructure and configuration errors** `[R1:SEC-r1-19]`. GraphQL drivers put `err.message` into `errors[i].message`, even in production (LEAD-EXP-7), so request-time `BetterAuthConfigurationError` details would reach clients (handler and instance names, better-auth error text). Two layers prevent it. Request-time configuration errors are generic as thrown (`atRequest`, §7.8, §13.3), which covers errors raised where the guard did not run. For errors the guard catches, the GraphQL transports implement `toInternalException`, which returns `BetterAuthGraphqlInternalError`:
  - message `'Internal server error'`;
  - `extensions: { code: 'INTERNAL_SERVER_ERROR', reason: 'AUTH_UNAVAILABLE' | 'AUTH_MISCONFIGURED', statusCode: 500 }`;
  - `cause` = the original error (already redacted for infrastructure errors).

  It is not intrinsic, so Nest logs it once, `[cause]` included (LEAD-V31), and the details stay in server logs.

- **Field-resolver coverage** `[R1:NEST-r1-06, SEC-r1-10]`. `@ResolveField` resolvers get guards only when `fieldResolverEnhancers` includes `'guards'`; the default is `[]` (LEAD-V30). A requirement on a field resolver, or on its class, is otherwise silently not enforced. For example, `@RequirePermission({ salary: ['read'] }) @ResolveField() salary()` would leak salaries to any authenticated caller who reaches an `Employee` through another query.

  The GraphQL transports' `validate()` reads the driver options with `moduleRef.get(GRAPHQL_MODULE_OPTIONS, { strict: false })` (`'GqlModuleOptions'`, exported by `@nestjs/graphql` 13 and 14). If `'guards'` is missing, it fails boot with `FIELD_RESOLVER_UNGUARDED` for every method carrying `RESOLVER_PROPERTY_METADATA` (`'graphql:resolve_property'`) that either has an effective plan with requirements (method or inherited class) or has its own access or acceptance decorator other than `@Public()`. The hint reads `fieldResolverEnhancers: ['guards', 'interceptors']`, or `@Public()` on the field resolver to state that it needs no check. The per-field guard run costs no extra principal I/O (shared key); only per-field decisions run. `fieldResolverCoverage: 'warn' | 'off'` relaxes the check.

- **Versions.** `@nestjs/graphql` 13 serves Nest 11 and 14 serves Nest 12. Version 14 removed `subscriptions-transport-ws`, so only `graphql-ws` is supported.

### 9.3 WebSockets: socket.io and ws (`./websockets`)

**Credentials:**

- **socket.io** `[A][B][C]` takes them from `client.handshake.headers`. The handshake is an HTTP request, so it carries cookies for same-site browsers or with `withCredentials`. Then `credentials(client)` supplies more and **replaces** same-named headers, for example `handshake.auth.token` → `authorization: Bearer <token>` for the `bearer()` plugin. The default mapping copies `handshake.auth.token` when no `authorization` header exists. `ambientCookie` is true only when the handshake's own `cookie` header survives into the credentials.
- **ws** `[B][C]` has a problem: the bare `WebSocket` has no headers, and the upgrade request is passed only to the `connection` event (`@nestjs/platform-ws` `adapters/ws-adapter.js:144`). `withUpgradeRequest(Base)` is a mixin over any `WsAdapter` subclass. It overrides `bindClientConnect(server, cb)` and records `{ headers: toWebHeaders(request.headers), url, remoteAddress }` on the client under `UPGRADE_REQUEST` before delegating. A mixin composes with users' own adapters (Redis, custom) and needs no `@nestjs/platform-ws` import. Custom adapters call `recordUpgradeRequest(client, request)` directly.

  ```ts
  app.useWebSocketAdapter(new (withUpgradeRequest(WsAdapter))(app)); // main.ts
  ```

  A guarded message from a client without a recorded request throws `BetterAuthConfigurationError`, which includes this snippet.

**Origin check: Cross-Site WebSocket Hijacking** `[R1:BA-r1-03, SEC-r1-01]`. Browsers attach cookies to WebSocket upgrades, and CORS does not apply to them. A malicious page can open `new WebSocket('wss://api.example.com/socket.io/?EIO=4&transport=websocket')`, the victim's cookie authenticates the socket, and the page reads every reply. The browser leg is the handshake (socket.io `handshake.headers` and `handshake.url`; ws the recorded upgrade request), and `enforce` is always true. A cookie-authenticated message is therefore allowed only if the handshake's `Origin` is trusted by better-auth (§7.10). Token-authenticated sockets (`handshake.auth` → bearer) are unaffected.

**Memo, revalidation and decorators.**

- `principalTtlMs: 0` is the default `[A][C]`. Each guarded message resolves once, memoized across the guards of that message through the shared `args` array (LEAD-V7). With the session source this adds no writes, because refresh is suppressed. Sources that consume quota or write per resolution (`effects`, for example `apiKeyPrincipal()`, which writes the usage counter) verify on every message. The WS units' `advise()` warns `W_QUOTA_PER_MESSAGE` when such a source is registered and `principalTtlMs` is 0, and recommends connection-time authentication plus a TTL `[R1:SEC-r1-14]`.
- `principalTtlMs > 0` caches **authenticated and absent** results per socket (`call.connection`) for chat-style traffic. Rejections and infrastructure failures are never cached on the socket (§7.2). Decisions are always per message, so a socket that joined org A cannot reuse that allow to join org B `[R1:NEST-r1-01]`. The docs state the revocation delay a TTL implies.
- Param decorators read the resolution from the scope interceptor. The socket is deliberately **not** used as a carrier, because concurrent messages on one socket would race (§7.8).

**Guard behavior by Nest major** (LEAD-V6, LEAD-V29, R:nest-di §3.4 runtime table):

|                                                            | Nest 11 | Nest 12                                                 |
| ---------------------------------------------------------- | ------- | ------------------------------------------------------- |
| `APP_GUARD` runs for `@SubscribeMessage` handlers          | **no**  | yes                                                     |
| `APP_INTERCEPTOR` wraps them                               | **no**  | yes                                                     |
| An `HttpException` thrown by a guard reaches the client as | n/a     | `{ status: 'error', message: 'Internal server error' }` |
| Global exception filters apply to gateways                 | no      | no                                                      |

**Design consequences** `[C]` `[R1:NEST-r1-13, SEC-r1-12]`:

1. The WS transports always throw `WsException({ status: 'error', statusCode, code, reason, message })` themselves. `BaseWsExceptionFilter` emits an object payload as-is, and filters never reach gateways (R:nest-di §5.2).
2. **Every gateway needs `@UseBetterAuth()` (or `@Public()`), on both majors.** v1 skipped the requirement on Nest 12 through a capability probe (`AbstractHttpAdapter.prototype.mapException`). That API belongs to `@nestjs/core`, while the behavior is decided by `@nestjs/websockets` (`getContextCreator(container)` on 11.1.17 vs `getContextCreator(container, config, …)` on 12.0.1, LEAD-V29). The probe could therefore report "covered" for a skewed install (core 12 with websockets 11), or for an 11.x release that backported the HTTP API, and leave every gateway open. A probe of `@nestjs/websockets` itself would need a deep import of an unexported module whose specifier differs between the two majors' packaging. v2 drops the probe. The WS transports' `validate()` (B16) enumerates gateway classes through Nest's `'websockets:is_gateway'` class metadata (not publicly exported, LEAD-V13; pinned by a CI test on both majors). It fails boot (`gatewayCoverage: 'error'`) for any gateway that has neither `@Public()` nor `@UseBetterAuth()` (or `@UseGuards(BetterAuthGuard)`) at class level or on every `@SubscribeMessage` method, with the message: "ChatGateway is not protected by BetterAuthGuard. Add @UseBetterAuth() (or @Public() to opt out). Global guards do not reach gateways on NestJS 11, and this check does not depend on the version." On Nest 12 with a global guard the second guard run is a memo hit, with no extra I/O and no log line.
3. **Connection-time authentication** `[B]` `[R1:NEST-r1-12]`. Guards never run on connect (`handleConnection` is never guarded). The socket.io and ws definitions provide `WsConnectionAuth` and export it under `WS_CONNECTION_AUTH` (`ExtensionDefinition.exports`, re-exported globally by the default `forRoot`). It reuses the transport's credential mapping, applies the origin check to the handshake, resolves with refresh suppressed, and caches authenticated/absent results on the client for `principalTtlMs`. It takes an `instance` option for named instances:

   ```ts
   @WebSocketGateway()
   @UseBetterAuth()
   export class ChatGateway implements OnGatewayInit, OnGatewayConnection {
     constructor(
       @Inject(WS_CONNECTION_AUTH) private readonly wsAuth: WsConnectionAuth,
     ) {}
     afterInit(server: Server) {
       server.use(this.wsAuth.socketIoMiddleware({ required: true }));
     } // socket.io
   }
   // ws: async handleConnection(client) {
   //   const r = await this.wsAuth.authenticate(client);
   //   if (r.outcome !== 'authenticated') client.close(r.outcome === 'rejected' ? wsCloseCodeFor(r.failure) : 4401, 'UNAUTHENTICATED');
   // }
   ```

4. **`param(name)`** reads `switchToWs().getData()?.[name]`.

### 9.4 Microservices / RPC (`./microservices`) `[A][B][C]`

RPC messages have no cookies of their own and no browser leg; credentials travel in transport metadata. `rpcTransport({ carriers })` uses the first carrier whose `matches(ctx)` is true (default: `defaultCarriers`):

| Carrier                             | Matches                                                             | Credential source (headers copied into `Headers`)                                                                |
| ----------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `grpcCarrier()`                     | `getArgByIndex(1)` is a gRPC `Metadata` (duck-typed `get`/`getMap`) | metadata entries (`authorization`, `cookie`, `x-api-key`)                                                        |
| `natsCarrier()`                     | the context has `getHeaders()`                                      | NATS message headers                                                                                             |
| `kafkaCarrier()`                    | the context has `getMessage().headers`                              | Kafka headers (Buffer values decoded as UTF-8)                                                                   |
| `rmqCarrier()`                      | the context has `getMessage().properties`                           | `properties.headers`                                                                                             |
| `mqttCarrier()`                     | the context has `getPacket()`                                       | MQTT 5 `userProperties` (MQTT 3 has no headers)                                                                  |
| `payloadCarrier({ field: 'auth' })` | the payload has an object at `field`                                | `data.auth` (TCP and Redis carry no headers). The docs warn this is weaker: credentials are visible to every hop |

- **Credentials** are ordinary better-auth credentials: `authorization: Bearer <session token>` with the `bearer()` plugin, a `cookie` header, or `x-api-key`. `getSession` and `apiKeyPrincipal()` work unchanged (keys still need a route that accepts `'api-key'`, §7.6). Forwarding browser cookies between services is discouraged.
- **Memo key, invocation and carrier:** `switchToRpc().getContext()`, one object per message. **Cookies:** `null`, so refresh is suppressed. **Browser leg:** none, so the origin check never applies: no browser can send an RPC message.
- **Denial:** `new RpcException({ status: 'error', statusCode, code, reason, message })`. `BaseRpcExceptionFilter` passes an `RpcException` object through as-is and turns anything else into "Internal server error".
- **gRPC:** the carrier's `toException` returns `RpcException({ code: 16 | 7 | 8, message })` (UNAUTHENTICATED, PERMISSION_DENIED, RESOURCE_EXHAUSTED). On Nest 12, if `@nestjs/microservices` exports `GrpcUnauthenticatedException` / `GrpcPermissionDeniedException`, the carrier uses them. That is feature-detected by export presence inside the RPC unit, not in core. **UNVERIFIED at runtime** on Nest 11 (grpc-js reads `code` from the error object).
- **Guard registration and hybrid coverage** `[R1:NEST-r1-05, SEC-r1-09]`. Standalone microservices (`createMicroservice`) apply `APP_GUARD`. A hybrid app's `connectMicroservice(options)` gets a **fresh** `ApplicationConfig` unless `{ inheritAppConfig: true }` is passed (LEAD-V32), so without it `APP_GUARD` never runs for `@MessagePattern`/`@EventPattern` handlers and any publisher can invoke them unauthenticated. The RPC transport's `validate()` makes this fail closed:
  - It runs when the app has an HTTP adapter (so it can be hybrid; `TransportValidationContext.hasHttpAdapter`). It enumerates message and event handlers through `'microservices:pattern'` method metadata (not re-exported from the package root, LEAD-V32; pinned by a CI test on both majors).
  - It fails boot (`hybridCoverage: 'error'`, `RPC_HANDLER_UNGUARDED`) for every such handler without `@UseBetterAuth()` (or `@UseGuards(BetterAuthGuard)`) or `@Public()` at class or method level.
  - The check is skipped when the user asserts `rpcTransport({ inheritAppConfig: true })`, meaning every `connectMicroservice` call passes `{ inheritAppConfig: true }`. The unit cannot observe `connectMicroservice` itself. Its `advise()` then prints a reminder of what the assertion means.
  - Duplicate guard runs (global plus `@UseBetterAuth()`) are memo hits. `'warn' | 'off'` relaxes the check.
- **`param(name)`** reads `switchToRpc().getData()?.[name]`.
