## 16. Decision log

Every entry records the decision, where it came from, the alternatives rejected (including those proposed by other drafts or by reviewers), the rationale, and the evidence. Draft ADR numbers are given as `A-ADR-n`, `B-ADR-n` and `C-ADR-n`, and the drafts' own open questions as `A-Qn`, `B-Qn` and `C-Qn`, so that neither is mistaken for this document's ADR-nn, Qn or Bnn ids.

- **ADR-01 to ADR-33** are the v1 decisions. Each states the decision **as it stands in v2**. Where review round 1 changed one, a _Revised in v2_ line names the findings that forced the change and says what changed; the v1 position then appears among the rejected alternatives.
- **ADR-34 to ADR-53** are decisions v2 introduced. Each cites the findings that forced it.

**ADR-01. Auth routes are raw platform routes that call `auth.handler` with a `Request` we build.**

- _From:_ [A] A-ADR-1, [B] B-ADR-01, [C] C-ADR-02. All three drafts agree.
- _Rejected:_
  - better-call `toNodeHandler` (the reference): loses the query string under some mounts, crashes on HTTP/2, trusts `x-forwarded-proto`, re-serializes consumed bodies, has no chunked body limit;
  - a Nest `@All` controller: gets the global prefix and versioning; `*path` fails on Fastify; Fastify's `@All` ignores version constraints;
  - `MiddlewareConsumer` mounting: path semantics differ per platform, it bypasses `@fastify/cors`, and prefix exclusion needs Nest internals.
- _Rationale:_ this is better-auth's own seam (P1/P2). It bypasses Nest's router, prefix and versioning by construction, and it gives full control of header hygiene, IP and body limits.
- _Revised in v2_ `[R1:SEC-r1-01, BA-r1-09]`: the claim that went with this decision in v1, "origin/CSRF is handled inside `auth.handler`", is true **for auth routes only**; app surfaces get ADR-34. The exchange no longer converts a thrown `APIError` when the user set `onAPIError.throw` (ADR-50).
- _Evidence:_ R:nest-platform §5, §6.1; R:ref-issues cluster 1 (seven mount rewrites); EXP-B:E4; EXP-A:`exp-e2e.mjs`; EXP-C4–C6.

**ADR-02. The `nestjs()` plugin is mandatory and validated at boot (B03), even for apps without hooks.**

- _From:_ [A] A-ADR-3, [C] C-ADR-01.
- _Rejected:_
  - [B] B-Q2: optional-with-degradation, required only once hooks exist;
  - no plugin, with cookies handled only in the guard;
  - mutating `auth.options`, which S1 forbids.
- _Rationale:_ several requirements can only be met from inside a better-auth dispatch:
  - suppressing the stateless refresh-cache branch needs `setShouldSkipSessionRefresh`, and nested plugin-endpoint refreshes need an any-path hook (S2);
  - the client-IP header must be declared through `init()` (ADR-44);
  - the library's own policy calls produce refreshed cookies that must reach the browser, and forwarding them is better-auth's own `nextCookies` pattern.

  B's degraded mode creates two behavior modes users cannot see: some cookies are silently lost, and some plugin endpoints refresh on cookie-less transports (B's own §7.4 table). The cost is one line in `auth.ts`, backed by a boot check with a copy-paste fix.

- _Revised in v2_ `[R1:BA-r1-02]`: BA-r1-02 pointed out that the plugin is mandatory for reasons unrelated to application code, so bundling an always-on cookie bridge into it silently changed better-auth's server-call semantics for every app. The plugin stays mandatory; forwarding for application direct calls became opt-in (ADR-48).
- _Evidence:_ EXP-A:`exp-plugin.mjs` (control row); EXP-B:E2, E3; EXP-C1; LEAD-V2, LEAD-V3.

**ADR-03. Express uses two phases: bounded raw capture in `prepare()` (inside `NestFactory.create()` / `createNestApplication()`), dispatch in `onModuleInit`, and a deferred 413.**

- _From:_ [A] A-ADR-4, [B] B-ADR-08, [C] C-ADR-03. The drain-and-flag 413 is from [A][B].
- _Rejected:_
  - requiring `bodyParser: false`: breaks `rawBody`, limits and `@nestjs/testing` (#16, #88, #101, #111);
  - mounting everything in phase A: bypasses the user's CORS and middleware;
  - pre-empting parsers by function name: loses `rawBody` and is defeated by `useBodyParser`;
  - accepting re-serialization: lossy, and breaks Stripe signatures;
  - answering 413 inside phase A: EXP-A showed it lacks CORS headers.
- _Rationale:_ this is the only combination that gives byte-exact bytes, host middleware and CORS, controller precedence, Nest-native parsing elsewhere, and identical behavior under both bootstraps and both majors.
- _Revised in v2_ `[R1:NEST-r1-03]`: v1 installed phase A from inside the `HttpAdapterHost.init$` callback. Under `NestFactory` that callback runs before any provider exists, so with an async `forRootAsync` factory no platform was known and phase A was silently skipped. Phase A now runs in `prepare()`, which the last-arrival coordinator calls (ADR-38). It still precedes Nest's parsers.
- _Evidence:_ EXP-A:`exp-express.mjs`, `exp-e2e.mjs`; EXP-B:E1 (413 with ACAO); EXP-C4/C5; `body-parser/lib/read.js:40-44`; LEAD-EXP-3.

**ADR-04. Fastify uses an encapsulated plugin with a `'*'` `parseAs: 'buffer'` parser and `bodyLimit`, writing back through `reply` (never `hijack`, never `reply.send(Response)`), with a child error handler (ADR-39).**

- _From:_ [A] A-ADR-17. The write-back rules are shared by [A][B][C].
- _Rejected:_
  - [B]: a pass-through parser plus a hand-rolled bounded reader (works, EXP-B:E4, but duplicates Fastify's limit logic);
  - [C] C-ADR-04: a root route answering from a route-level `onRequest` (works, EXP-C6, but runs handler logic in a hook, and C's claim that encapsulated routes load only at `ready()` is contradicted by EXP-B:E10);
  - middie middleware: bypasses `@fastify/cors` and `onSend`;
  - replacing the root parsers (the reference): loses proto-poisoning protection.
- _Rationale:_ Fastify enforces the limit natively, and the answer goes through the reply lifecycle, so CORS survives. The bytes are exact, including requests without a content-type. Parsers are isolated per context.
- _Revised in v2_ `[R1:NEST-r1-04]`: v1 let Fastify's own 413 body through and assumed failures reach Nest's filters. Both were wrong for an awaited registration: the 413 body differed from Express's (H4), and failures got Fastify's default 500, skipped every `APP_FILTER` and went unlogged (H8). The v1 evidence did not cover the case, because the cited research experiment registered its plugin without `await`. The child error handler of ADR-39 fixes both.
- _Evidence:_ LEAD-V10; EXP-A:`exp-e2e.mjs` (byte-exact; 413 with ACAO); EXP-B:E10; R:nest-platform §3.2, §6.3; LEAD-EXP-2.

**ADR-05. HTTP platforms, transports and principal sources register through explicit static lists of `ExtensionRef`s. Express and Fastify live in their own subpaths and must be listed (`platforms: [expressPlatform()]`).**

- _From:_ explicit registration is [A] A-ADR-5 and [B] B-ADR-02, B-ADR-03. The `ExtensionRef` union (class | instance | definition) merges [A]'s `ExtensionDefinition` with [B]'s `ExtensionProvider`. Additive lists with built-ins appended last are from [A][C].
- _Rejected:_
  - [C] C-ADR-14: Express and Fastify in the root entry, auto-selected. Zero-config, but it blurs "each is an extension unit" (D2), and the root would ship platform code;
  - [B]: transport lists that _replace_ the defaults. More ceremony (`...defaultTransports()`) for no gain;
  - discovery for everything: order between principal sources becomes implicit;
  - a passport-style global registry filled by constructor side effects.
- _Rationale:_ registration is deterministic where order matters (sources, transports), core never names an extension, and a missing platform fails boot with the exact import to add (B08). The DX cost is one import (§17 Q12).
- _Revised in v2_ `[R1:NEST-r1-09, NEST-r1-12, SEC-r1-02]`: platforms and transports are listed once, on the default instance (ADR-45). Principal sources stay per instance, and the chain is filtered per route by the kinds the route accepts (ADR-35). `ExtensionDefinition` gained `exports`.
- _Evidence:_ R:nest-di §2.3, §3.3, §6.2; R:nest-platform §8.1 (`getType()` is an open set).

**ADR-06. Refresh suppression is an any-path plugin before-hook (`setShouldSkipSessionRefresh(true)` in cookie-less scopes, gated on `_flag !== 'router'`) plus `disableRefresh` on the session source.**

- _From:_ [A], [B] B-ADR-05, [C] C-ADR-08. All agree; the `_flag` gate is from [A].
- _Rejected:_
  - `disableRefresh` only: misses the stateless refresh-cache branch and nested plugin endpoints;
  - `runWithRequestState` from `@better-auth/core/context`: an extra peer, and state set outside the endpoint's own store is not seen;
  - the `nextCookies`-style `/get-session`-only matcher: misses `hasPermission` and `getActiveMember` refreshes.
- _Rationale:_ the flag is set inside the dispatch's own request state, exactly where `getSession` reads it. It reuses the mechanism better-auth uses for RSC.
- _Evidence:_ LEAD-V2, LEAD-V3, LEAD-V14; EXP-A:`exp-plugin.mjs`; EXP-B:E2, E3; EXP-C1.

**ADR-07. Nest hooks enter better-auth through fixed dispatcher entries plus a late-bound registry; the dispatcher mirrors `dispatch.ts` and `with-hooks.ts` semantics per operation, using `defu`.**

- _From:_ [A] A-ADR-2, [B] B-ADR-06, [C] C-ADR-07. All agree on the mechanism. Using `defu` (better-auth's own dependency) instead of a hand-rolled merge is from [A]; the parity property test is from [A][C].
- _Rejected:_
  - mutating `auth.options.hooks` (the reference): S1, fragile (#42), drops return values;
  - pushing one entry per Nest hook into the plugin's arrays at bind time: exact composition for free, but it depends on better-auth re-reading plugin arrays per dispatch, an implementation detail (LEAD-V1);
  - requiring hooks to be written in `auth.ts`: no DI;
  - [C]'s local ~15-line merge: divergence risk.
- _Rationale:_ it relies only on the public plugin contract and preserves every return semantic. The parity test keeps it faithful across releases.
- _Revised in v2_ `[R1:BA-r1-06]`: the v1 dispatcher used the `create` rule (chain the merged data) for every database operation and swallowed throwing matchers. The mirror is now per operation (ADR-49).
- _Evidence:_ LEAD-V1, LEAD-V22, LEAD-V23; EXP-A:`exp-merge.mjs` (SAME); EXP-B:E2; EXP-C10.

**ADR-08. Hook discovery needs no class marker, and hooks include library-internal calls by default (`skipInternal` opt-out). String patterns are validated at boot.**

- _From:_ no marker and boot validation are [C]; the internal-calls default is [A][C].
- _Rejected:_
  - [A] `@BetterAuthHooks()` and [B] `@AuthHooks()` class markers: forgetting the marker silently disables hooks;
  - [B] excluding internal calls by default (`includeInternalCalls` opt-in): a rule on the resolved session, such as an `@AfterAuth('/get-session')` that rejects sessions without a second factor, would silently not apply to guarded routes, because the guard's own `getSession` is an internal call;
  - [B] `*`/`**` wildcard patterns: they cannot be validated against the endpoint list. Predicates cover the need.
- _Rationale:_ this is faithful to better-auth, where user hooks also run for server calls, and follows Nest's own `@OnEvent`/`@Cron` discovery idiom. Unknown paths fail boot with a "did you mean".
- _Revised in v2_ `[R1:BA-r1-07]`: v1 argued this with a `@BeforeAuth('/get-session')` hook that blocks banned users. That example fails open whatever the default: before-hooks see the original request (no session cookie for bearer clients), and the api-key plugin short-circuits `/get-session` before Nest hooks run (LEAD-V21, LEAD-V23). The decision stands; the example was replaced (§10.4), and v1's claim that Nest before-hooks see other plugins' before-hook effects was withdrawn.
- _Evidence:_ R:ba-core §4.1; R:ref-issues #103; EXP-C8, EXP-C9.

**ADR-09. Guard-side `getSession` uses `returnHeaders: true` and forwards only `set-cookie`, with the plugin bridge off for that one call. The library's other calls (every principal source's and every policy's) use the bridge with the request's own credential. The kernel's cookie sink de-duplicates.**

- _From:_ [A] A-ADR-16 (bridge off for the guard call); [C] (sink de-duplication); S2.
- _Rejected:_
  - [B] B-ADR-07: an `AuthApiInvoker` through which every internal call must pass. It works, but third-party sources and policies must remember to use it, and the bridge already covers them;
  - relying on the bridge alone: S2 requires `returnHeaders` for `getSession` explicitly;
  - forwarding all headers: leaks `cache-control: no-store`.
- _Rationale:_ S2 literally, one forwarding path per call, and third-party authors call `auth.api` normally.
- _Revised in v2_ `[R1:BA-r1-02, SEC-r1-03]`: in v1 the bridge also forwarded every direct call that application code made under the scope interceptor. It now forwards the library's own calls and application calls only by opt-in and only with the caller's credential or none (ADR-48). "The library's own calls" are the resolver chain and the evaluator: both run with `forward: 'same-credential'` and `inbound: call.headers` (§7.2, §8.1), where the credential always matches for calls made with the request's headers. Only the session source's `getSession` nests a `forward: 'none'` scope, which is the "one call" of this ADR's title, so invariant P2 and the rejected-alternative argument above hold for third-party sources as well as policies.
- _Evidence:_ EXP-A:`exp-e2e.mjs` (single cookie, `cache-control=null`); EXP-B:E7; R:ba-core §4.3.

**ADR-10. The principal is memoized per `(request key, instance, freshness, source set)` in a `WeakMap`, with the promise stored before it settles. Rejections are memoized per request, never per connection.**

- _From:_ [A] A-ADR-9, [B] §7.5, [C] C-ADR-19.
- _Rejected:_
  - a request-scoped provider: it makes every controller request-scoped;
  - `req.session`/`req.user`: collides with express-session and Passport;
  - [B]'s 300 s per-connection default key for WebSockets (see ADR-18).
- _Rationale:_ S7, including GraphQL root fields sharing one resolution, and no retry storms against a failing DB.
- _Revised in v2_ `[R1:NEST-r1-01, SEC-r1-13, SEC-r1-02]`:
  - v1 kept authorization decisions in the same per-request state, keyed by requirement identity. That was an authorization bypass, and decisions moved to their own scope (ADR-37);
  - connection entries (WS and subscriptions with a TTL) hold only `authenticated` and `absent`. A memoized infrastructure failure turned a 2 s database blip into minutes of failures per socket;
  - the key includes the source set, because the chain is now filtered per route (ADR-35).
- _Evidence:_ EXP-B:E8 (3 guard calls → 1 resolution); R:nest-di §3.3, §3.4.

**ADR-11. The per-invocation scope comes from `BetterAuthScopeInterceptor` plus explicit internal scopes (`handle.run`), not from a platform-level scope opened at `init$`.**

- _From:_ [A] (interceptor + `handle.run`); [L] (race analysis).
- _Rejected:_ [B] and [C] open an ALS scope in the platform's earliest hook. Their "scope is lost after parsing" concern does **not** apply to body-parser (LEAD-V11), so the rejection rests on other grounds:
  1. it covers HTTP only; WS and RPC would still need an interceptor;
  2. param decorators on WebSockets cannot find a per-message resolution by key, because param factories get a fresh `args` array (LEAD-V7), and stamping it on the socket races across concurrent messages. The interceptor sees the guards' `args` and publishes the resolution race-free;
  3. it enlarges every third-party platform's contract (C's conformance case P13 exists because it is easy to get wrong, EXP-C5).
- _Rationale:_ transport-neutral, it runs after body parsing, it gives race-free decorators, and the platform contract stays small. The gap (middleware and other libraries' guards run outside the scope) is documented, with `withoutCookies`/`returnHeaders` as the workaround.
- _Revised in v2_ `[R1:BA-r1-02, SEC-r1-03, NEST-r1-01]`: the scope the interceptor opens now also carries the forwarding mode and a view of the inbound credential (ADR-48), and the values policies published for this invocation (ADR-37). The mechanism is unchanged.
- _Evidence:_ LEAD-V6, LEAD-V7, LEAD-V11; EXP-A:`exp-e2e.mjs` (bridge through the interceptor on Nest 11/12 × Express/Fastify).

**ADR-12. Requirements carry their policy by reference (value or DI class/token); there is no policy registry.**

- _From:_ [B] B-ADR-03, [C] C-ADR-09.
- _Rejected:_
  - [A] A-ADR-5: a `Map<kind, policy>` registry filled from a `policies` list. It needs registration in `forRoot`, and a missing entry is only a boot error;
  - the reference's `if` chain.
- _Rationale:_ a new policy is a new value with nothing to register, which is pure OCP. References survive a dual-package load, DI-backed policies are ordinary providers, and boot validation still resolves every reference (B14).
- _Revised in v2_ `[R1:BA-r1-01, SEC-r1-04]`: a requirement can override two of its policy's declarations, `principals` and `freshIdentity` (`RequirementOptions`). Both are data the planner reads; there is still nothing to register.
- _Evidence:_ R:ba-authz §5.4; R:nest-di §10.6.

**ADR-13. "Denials are values, exceptions are infrastructure": principal sources return a `PrincipalResult` union and policies return `AuthorizationDecision`s, with a kernel safety net for thrown `APIError`s.**

- _From:_ [B] (result union, invariants P1/Z1); the decision helpers are from [A][B][C]; the safety-net mapping is from [A] (policy 401 → 403) and [C] (other 4xx → configuration error).
- _Rejected:_ [A] and [C] let sources throw a denial (`AuthDenial` / `AuthError`). That is less explicit, and a forgotten catch turns a denial into an unintended path.
- _Rationale:_ the rule is teachable, LSP-checkable, and keeps S6 airtight.
- _Revised in v2_ `[R1:BA-r1-10, BA-r1-04, SEC-r1-05]`: the net's "another 4xx is our bug" rule stays, but built-in units must map the outcomes they can expect **before** the net sees them. v1's admin policy let better-auth's 400 `user not found` (a deleted user with a warm cookie cache) become a 500 with an ERROR log per request; it is now a 401 `USER_NOT_FOUND`. `verifyApiKey` returns failures as values, so the API-key source maps them by table (ADR-42). Errors the library already classified pass through the net by brand (§13.2).
- _Evidence:_ R:ba-authz §5.3; R:ref-impl §6.1; LEAD-V20, LEAD-V24.

**ADR-14. Auth routes live at better-auth's own path, resolved from `(await $context).baseURL` (falling back to `options.basePath || '/api/auth'` for unset or dynamic `baseURL`), outside Nest's global prefix and versioning.**

- _From:_ [A], [B] B-ADR-04, [C] C-ADR-20.
- _Rejected:_
  - honoring the global prefix: two sources of truth, and the `/api/api/auth` regression that forced the revert of PR #80;
  - reading `auth.options.basePath`: wrong when `baseURL` has a path.
- _Rationale:_ S3. better-auth's client, callbacks and trusted origins derive from `baseURL`.
- _Revised in v2_ `[R1:SEC-r1-07]`: the unset-`baseURL` branch still resolves a path, but it is a development-only configuration. In production it fails boot (ADR-46).
- _Evidence:_ EXP-B:E11; R:ba-core §3.7; `BA/api/index.ts:280`.

**ADR-15. The client IP travels in a plugin-declared header that core strips and sets from the platform's trust-proxy-aware IP. The header's name is random per plugin instance (ADR-44).**

- _From:_ [A] A-ADR-6, [B] B-ADR-15, [C] C-ADR-06.
- _Rejected:_
  - passing `x-forwarded-for` through: spoofable unless better-auth's `trustedProxies` duplicates the proxy config;
  - requiring `trustedProxies`: easy to forget, and production collapses into one bucket;
  - overwriting `x-forwarded-for`: rewrites a header other code may read;
  - a fixed, documented name (v1's `x-nsba-client-ip`, from [A][B]; [C]'s `x-nestjs-client-ip`): see ADR-44.
- _Rationale:_ one trust configuration (the platform's), spoof-proof, a user list keeps precedence (defu), and it feeds both rate limiting and session IP recording.
- _Revised in v2_ `[R1:SEC-r1-18, SEC-r1-06]`: the fixed public name let any code path that forwards raw client headers to better-auth choose its own rate-limit bucket, and the design said nothing about the platform's trust setting being wrong. Both are covered by ADR-44.
- _Evidence:_ EXP-A:`exp-e2e.mjs`; EXP-B:E9; EXP-C7 (all with the fixed name; the name plays no part in the path they verify); LEAD-V4.

**ADR-16. The error model is a transport-neutral `AuthFailure` value with a stable `code` (UNAUTHENTICATED/FORBIDDEN/RATE_LIMITED) plus a detailed `reason`. Infrastructure is `BetterAuthInfrastructureError` (5xx, logged, redacted cause); transports own the mapping, including what clients see of internal errors.**

- _From:_ two-level code/reason is [C]; the value object is [B]; mapping in transports is [A] A-ADR-13, [B] B-ADR-09, [C] C-ADR-17.
- _Rejected:_
  - [A]'s better-auth code as the top-level `code` (an unbounded set for clients to switch on);
  - [C]'s `AuthError` class hierarchy (`instanceof`-prone across copies; thrown classes still need per-transport mapping);
  - exception filters as the mapping point (they never reach gateways; hybrid RPC needs `inheritAppConfig`).
- _Rationale:_ S6. Clients switch on three codes and get detail in `reason`. A new transport gets the whole taxonomy by implementing one method.
- _Revised in v2_ `[R1:SEC-r1-08, SEC-r1-19, BA-r1-04]`: the cause of an infrastructure error is redacted, and transports whose runtime exposes error messages implement `toInternalException` (ADR-43). `AuthFailures.fromAPIError` also derives `Retry-After` from `body.details.tryAgainIn`, because better-auth's API-key rate limit carries no header.
- _Evidence:_ R:nest-di §5; R:ref-impl §6.1.

**ADR-17. GraphQL denials are an `IntrinsicException` subclass carrying `extensions` (`BetterAuthGraphqlDenial`).**

- _From:_ [L]. It resolves a conflict between [A]/[C] and [B].
- _Rejected:_
  - [A] A-ADR-13 and [C] C-Q10, a plain `GraphQLError`: Nest's `ExternalExceptionFilter` logs it at ERROR on every denial;
  - [B] B-ADR-09, an `HttpException` with `extensions`: Apollo's `autoTransformHttpErrors` overwrites `extensions.code` and maps 429 to `INTERNAL_SERVER_ERROR`.
- _Rationale:_ codes are preserved for 401, 403 and 429, nothing is logged, and graphql-js copies `originalError.extensions` for both drivers.
- _Revised in v2_ `[R1:SEC-r1-19]`: a sibling class, `BetterAuthGraphqlInternalError`, carries request-time infrastructure and configuration errors. It is deliberately **not** intrinsic, so Nest logs it, and its message is generic (ADR-43).
- _Evidence:_ LEAD-EXP-1 (Nest 11.1.17 + Apollo 13.2.4); LEAD-V8, LEAD-V9. Mercurius and Nest 12 are pinned by `T-error-shape` (RK3).

**ADR-18. WebSockets use message-level guards with a per-message default (`principalTtlMs: 0`). Every gateway needs `@UseBetterAuth()` or `@Public()`, on every Nest major, and boot fails otherwise. `ws` upgrade headers come from a `withUpgradeRequest` mixin. The WS units provide `WsConnectionAuth` for connection time.**

- _From:_ the per-message default is [A][C]; the explicit guard on both majors is [A] A-ADR-14; the mixin is [B][C]; `WsConnectionAuth` is [B].
- _Rejected:_
  - v1's decision, [C] C-ADR-18: require the decorator only where a capability probe says global enhancers do not reach gateways. The probe (`AbstractHttpAdapter.prototype.mapException`, LEAD-V12) belongs to `@nestjs/core`, while `@nestjs/websockets` decides the behavior. It reports "covered" for a skewed install (core 12 with websockets 11) or an 11.x backport of that HTTP API, and then every gateway is open. v1 failed closed only for an _inconclusive_ probe, not for a false positive;
  - probing `@nestjs/websockets` instead (both reviewers' first suggestion): the deciding code is in `SocketModule`, which the package root does not export, and whose deep specifier differs between the two majors' packaging (LEAD-V29);
  - [B] B-Q11, documentation only: Nest 11 gateways stay silently open;
  - [B] a 300 s per-connection cache default: revocation lag by default;
  - [A] shipping `BetterAuthIoAdapter`/`BetterAuthWsAdapter` subclasses: they conflict with Redis or custom adapters.
- _Rationale:_ secure by default without any version detection. The cost v1 wanted to avoid, a redundant decorator on Nest 12, is one memo hit per message: no I/O and no log line.
- _Revised in v2_ `[R1:NEST-r1-13, SEC-r1-12, NEST-r1-12, SEC-r1-13, SEC-r1-14, BA-r1-03]`: the probe was dropped (above; ADR-40 states the general rule). `WsConnectionAuth` is now actually provided, through `ExtensionDefinition.exports` (ADR-45). Connection entries never cache failures (ADR-10). A quota-consuming source with `principalTtlMs: 0` triggers `W_QUOTA_PER_MESSAGE`, and v1's "no writes" claim now names the session source only. Cookie-authenticated sockets pass the origin check on the handshake (ADR-34).
- _Evidence:_ LEAD-V6, LEAD-V13, LEAD-V29; R:nest-di §3.4 runtime table; EXP-B:E6.

**ADR-19. Types come from `Register` augmentation (better-auth's idiom), generics are the escape hatch, and C's type-level enforcement is adopted. There is no typed factory.**

**ADR-34. The kernel applies better-auth's origin rule to every operation that an ambient browser cookie authenticated: unsafe HTTP methods, GraphQL mutations, and every WebSocket message and subscription. It is on by default and strict about a missing origin.**

- _Forced by:_ `[R1:SEC-r1-01]` (blocker), `[R1:BA-r1-03]`. v1 listed "origin/CSRF" as something `auth.handler` does. It does, but only for its own routes: `validateOrigin` is router middleware and returns early without `ctx.request` (LEAD-V16). In REV-SEC:`probe-bridge-foreign.mjs` the guard's `getSession` accepted an evil-origin cookie request that the router rejected with 403. With `sameSite: 'none'` cookies, which better-auth documents for cross-domain setups, or an attacker on a sibling subdomain, that meant cross-site form posts to Nest routes, cross-site mutations and Cross-Site WebSocket Hijacking.
- _Decision:_ one kernel step (`OriginCheck`, §7.10), fed by data every transport supplies (`TransportCall.browser`). It reuses better-auth's trusted-origin set (post-init, ADR-33), its matcher (`$context.isTrustedOrigin`), its skip flags and its error codes. Explicit credentials (`Bearer`/`DPoP` authorization, source-declared `credentialHeaders`) are never checked, and RPC has no browser leg. Opt-outs: `@SkipOriginCheck()` per route, `originCheck.mode: 'off'` per instance (B19 warns in production).
- _Rejected:_
  - host responsibility (v1; BA's option 1): the library creates these cookie-authenticated surfaces and knows which credential authenticated the call; the host knows neither. CORS does not apply to form posts or WebSocket upgrades at all;
  - opt-in only, a `@RequireSameOrigin()` requirement or a module flag that is off by default (BA's option 3): secure by default (P8) means the unsafe configuration is the one you have to ask for;
  - a per-transport option (`originCheck: 'cookie' | 'always' | 'off'` on the WS and GraphQL transports, BA's suggested fix): the rule would be implemented once per transport, third-party transports would have to reimplement it, and HTTP app routes would still be uncovered. Transports supply facts; the kernel owns the rule;
  - our own origin matcher or allow-list: a second, drifting definition of "trusted" (R1). We call `isTrustedOrigin` with the merged set;
  - SEC's proposed default for a missing origin, "allow when no browser signal is present at all". better-auth's own routes answer 403 `MISSING_OR_NULL_ORIGIN` in that case, so the strict default is the faithful one. The exemption also misses the client it was meant for: Node's `fetch`, which SSR servers use, sends `sec-fetch-mode: cors` with no `Origin` (LEAD-EXP-4). The lenient rule ships as `originCheck.missingOrigin: 'allow-non-browser'`, keyed on `Origin`, `Referer` and `Sec-Fetch-Site` only (§17 Q15);
  - relying on `SameSite` cookies: better-auth's cross-domain guidance turns it off, and it never separates sibling subdomains.
- _Rationale:_ it extends better-auth's secure-by-default cookie model to exactly the surfaces this library adds, with better-auth's own notion of trust, and leaves bearer, API-key and RPC callers alone. The cost is a trusted `Origin` header on cookie-bearing unsafe requests from non-browser clients, which better-auth already demands on its own routes (§17 Q14, RK21).
- _Known limit:_ better-auth exposes no function for this rule, so the kernel **mirrors** it. The mirror was written against 1.7.4; the `Origin: null` + `Sec-Fetch-Site: same-origin` inference reached better-auth's router only in 1.7.2, so on 1.7.0 and 1.7.1 the kernel is more lenient than the router for that one same-origin case (LEAD-V33). A differential test against the router on every better-auth version in the matrix detects further drift (§14.5, RK20).
- _Evidence:_ LEAD-V16, LEAD-V17, LEAD-V18, LEAD-V33; LEAD-EXP-4; REV-SEC:`probe-bridge-foreign.mjs`; `BA/api/index.ts:285-292`.

**ADR-35. Principal kinds are admitted per route, and delegated principals are never widened. Sources declare `kinds` and `acceptance` (default `'explicit'`); a route accepts the instance's default kinds or `@AcceptPrincipals(...)`, plus the kinds its requirements name; a policy that does not name a kind never receives a principal with `delegation`; built-in policies AND the owner's rights with the credential's own grant (Z5).**

- _Forced by:_ `[R1:BA-r1-01]` and `[R1:SEC-r1-02]` (both blockers). In v1 one source chain served every route, and the admin policy accepted "any kind with a `userId`". A leaked CI key scoped to `{ reports: ['read'] }` and owned by an admin could ban users: `userHasPermission({ userId })` judges the _owner's_ role and never sees the key's permissions. The design's own OAuth example gave a token granted `openid` the user's full rights. Because `PrincipalKinds` is open (R4), every future kind would have inherited the same escalation.
- _Rejected:_
  - BA's minimal fix alone, `requires.principals: ['session']` on the admin policy: authenticated-only routes and every third-party policy that compares `principal.userId` (§4.4.4) would still accept keys and tokens as their owner;
  - accepting every kind everywhere and relying on each policy to check scopes: that is v1, and the PR #94 pitfall in the reference ("never merge role sources implicitly", R:_digest);
  - `acceptance: 'default'` as the default for new sources: registering a source would silently widen every existing route;
  - verifying an unaccepted credential and then answering 403: it spends key quota, writes usage rows and tells an attacker whether a key is valid on routes that never asked for keys. The chain is filtered instead, so the header is treated as absent;
  - an option on `@RequireAuth` (`@RequireAuth({ principals })`, SEC's suggestion) instead of `@AcceptPrincipals`: acceptance is independent of access (`@OptionalAuth()` routes accept kinds too), and a separate decorator composes class-level acceptance with method-level access;
  - core rules for specific kinds ("API keys never pass user-role policies"): R4. The gate compares strings that extensions supply and tests for the presence of a `delegation` field.
- _Rationale:_ a narrow credential reaches a route only if the route, or a policy that can judge it, names its kind. In better-auth's own model such a credential never yields a session, so its admin and organization endpoints are unreachable with it; this reproduces that on Nest routes. `@RequireApiKeyPermission` admits keys on its own route, so the common case needs no second decorator.
- _Evidence:_ `AK/routes/verify-api-key.ts:116-131` (key permissions are a separate scope, checked with `role().authorize`); LEAD-V24 (`hasPermission` grants everything to `adminUserIds`); cases `Z-delegation-scope`, `Z-delegation-unnamed-denied`, `Z-admin-rejects-api-key`, `T-acceptance`.

**ADR-36. Admin-grade decisions read identity authoritatively. A policy declares `requires.freshIdentity`; the planner raises the route's freshness; the admin `permission()` defaults to `freshness: 'authoritative'` and passes the role from that session.**

- _Forced by:_ `[R1:SEC-r1-04]`, `[R1:BA-r1-10]`. v1 read the role fresh (by `userId`) but identity from the cookie cache, and claimed parity with better-auth's admin endpoints. REV-SEC:`probe-stale-admin.mjs` disproved it: after admin A was banned, with 0 session rows left, the guard still authenticated A from `session_data` and `userHasPermission(userId)` returned success, while better-auth's `listUsers` answered 401. For a deleted user the same call threw 400 `user not found`, which v1 turned into a 500 per request for up to `cookieCache.maxAge`.
- _Rejected:_
  - keeping cookie-cache identity and documenting the lag (SEC's option 2): a ban that does not take effect on admin routes for five minutes is not what `@RequirePermission` reads like. It remains available per requirement as `freshness: 'cached'` or `'role'`;
  - passing `headers` to `userHasPermission`, so that better-auth does its own authoritative read: a second read, a second API-key validation with `enableSessionForAPIKeys`, and `body.userId`/`body.role` are then ignored (LEAD-V24);
  - forcing authoritative reads on every route: it discards the cookie cache the user configured in `auth.ts`, for routes that make no admin-grade decision;
  - a core rule "admin routes are authoritative": core cannot name a policy (R4). `freshIdentity` is data any policy can declare, and §15.3's role recipe uses it too.
- _Rationale:_ exact parity with `adminMiddleware` (an authoritative session, then that session user's role), at one storage read, the read the route needs anyway. A banned or signed-out admin gets 401 on the next request.
- _Evidence:_ LEAD-V24; REV-SEC:`probe-stale-admin.mjs`; `BA/plugins/admin/routes.ts:32-45, 1857-1900`; cases `Z-admin-banned`, `Z-admin-deleted-user`; §17 Q16.

**ADR-37. Three memo scopes with three different keys: the principal per logical request (`call.key`; a connection only with a TTL), policy I/O per logical request keyed by concrete inputs, and decisions per handler invocation (`TransportCall.invocation`). Decisions are never keyed by a connection.**

- _Forced by:_ `[R1:NEST-r1-01]` (blocker), `[R1:SEC-r1-13]`. v1 memoized decisions "per request by requirement object identity". A requirement object is created once, when its decorator is evaluated, and GraphQL root fields share the request key by design (S7). `query { a: projects(orgId: "A") b: projects(orgId: "B") }` therefore evaluated `hasPermission` for org A only, and field `b` reused the allow. Apollo batching behaved the same way, and a WebSocket with a principal TTL reused `join A`'s allow for `join B` for the life of the socket.
- _Rejected:_
  - v1's single per-request state;
  - an optional `cacheKey(params, ctx)` on policies (the reviewer's alternative): every policy author has to list every input in the key, and one forgotten input is the same bypass again. The safe default is to share nothing; sharing is opt-in and explicit through `ctx.memo`, where the key _is_ the input;
  - no decision memo at all: B16 makes `@UseBetterAuth()` mandatory on gateways, so on Nest 12 the guard runs twice per message. Without a memo that doubles policy I/O and debug logs. The same invocation always has the same inputs, so sharing within it is safe;
  - caching rejections and infrastructure failures on a connection: a 2 s database blip became minutes of failures per socket.
- _Rationale:_ the two goals of v1's memo are kept apart. S7 (resolve the principal once) needs a request-wide key. Correct authorization needs a key no wider than one evaluation's inputs. Built-in policies keep repeats cheap by deduping better-auth calls on `(endpoint, organization, permissions)`.
- _Evidence:_ EXP-B:E8; LEAD-V7 (one `args` array per WS message, shared by its guards); graphql-js builds one `info` object per field execution, which is code-derived and pinned by `T-invocation-decisions` (RK3); cases `T-invocation-decisions`, `Z-per-invocation`.

**ADR-38. The mount coordinator prepares the platform on the later of two events, "adapter known" (`HttpAdapterHost.init$`) and "platforms registered" (the default instance's registry factory). A `null` adapter means the app has no HTTP.**

- _Forced by:_ `[R1:NEST-r1-02]`, `[R1:NEST-r1-03]`. v1 selected and prepared the platform inside the `init$` callback, on two wrong assumptions:
  - _"adapter-less bootstraps never emit `init$`"_. They do, with `httpAdapter === null` (LEAD-V26), so `createMicroservice` and `createApplicationContext` crashed in `supports(null)` or failed B08;
  - _"the platforms are known by then"_. Under `NestFactory` the replay runs inside the coordinator's constructor, before any `forRoot` kernel behind an async dependency exists (LEAD-V27).

  Both passed under `@nestjs/testing`, which emits later or not at all, so CI would have stayed green while production could not boot.

- _Rejected:_
  - looking platforms up through `ModuleRef` inside the callback: they do not exist yet;
  - moving Express phase A to `onModuleInit`: Nest has registered its body parsers by then;
  - asking users to call a `prepare(app)` helper in `main.ts`: it breaks `@nestjs/testing` parity and re-creates the reference's "one more required step" support load;
  - letting `platforms` come from `useFactory`: the registry must not wait on runtime options (ADR-22).
- _Rationale:_ nothing depends on the order in which Nest constructs modules, which is concurrent and differs between the two bootstraps. `prepare()` still runs before `NestFactory.create()` resolves and before `createNestApplication()` returns, which is early enough for Express phase A.
- _Evidence:_ REV-NEST:`exp1-init-emission.cjs`, `exp3b-core-module-order-async.cjs`; LEAD-V26, LEAD-V27; LEAD-EXP-3 (event orders on 11.1.17 and 12.0.1, both bootstraps and both adapter-less bootstraps); cases `H-async-options-factory`, `H-no-adapter`.

**ADR-39. The Fastify auth scope installs a child error handler. It answers the canonical 413 for `FST_ERR_CTP_BODY_TOO_LARGE` and hands everything else to the root instance's error handler, which it looks up at request time.**

- _Forced by:_ `[R1:NEST-r1-04]`. Fastify routes capture the error handler that is current when their plugin loads. With `await instance.register()` in `onModuleInit` that is Fastify's default, because Nest calls `setErrorHandler` later, in `registerRouterHooks`. An infrastructure error on an auth route therefore got Fastify's own 500 body, skipped every `APP_FILTER` (Sentry, custom formatting) and was never logged, since Nest creates Fastify with logging off. The 413 body differed from Express's. That broke H8 and H4.
- _Rejected:_
  - registering without `await`, so that the plugin loads at `ready()`, after Nest's handler exists: it also reaches Nest's filters, but route availability then depends on who calls `ready()` and when, and it reopens the draft C claim that EXP-B:E10 refuted;
  - catching in the route handler and invoking Nest's exception layer ourselves: there is no public API for that outside a Nest execution context;
  - setting the **root** error handler ourselves: it would replace Nest's, or be replaced by it;
  - letting Fastify's native 413 body through: "identical on every platform" (H4) is what makes the conformance kit meaningful for third-party platforms.
- _Rationale:_ the handler is explicit and works whenever the plugin loads. `FastifyAdapter.setErrorHandler` always targets the root instance, even with a global prefix (LEAD-V28), so `root.errorHandler` is Nest's by the time a request fails.
- _Evidence:_ REV-NEST:`exp2-fastify-error.cjs`; LEAD-V28; LEAD-EXP-2 (the `APP_FILTER` sees the error and the canonical 413 keeps its CORS header, on 11.1.17 and 12.0.1, both bootstraps, with a global prefix); cases `H-errors-filter-sees`, `H-limit-canonical-body`.

**ADR-40. Every surface the global guard cannot reach fails boot, on every Nest major, by default: WebSocket gateways (`gatewayCoverage`), hybrid-RPC message handlers (`hybridCoverage`) and GraphQL field resolvers that carry requirements (`fieldResolverCoverage`). Each check lives in its transport's `validate()` and can be relaxed to `'warn'` or `'off'`.**

- _Forced by:_ `[R1:NEST-r1-05]`/`[R1:SEC-r1-09]`, `[R1:NEST-r1-06]`/`[R1:SEC-r1-10]`, `[R1:NEST-r1-13]`/`[R1:SEC-r1-12]`. v1 failed closed for one gap (Nest 11 gateways, behind a probe) and only documented the other two. A hybrid app that calls `connectMicroservice()` without `inheritAppConfig` gets a fresh `ApplicationConfig`, so `APP_GUARD` never runs for message handlers and any publisher can invoke `billing.refund`. A `@RequirePermission` on a `@ResolveField` is silently not enforced unless `fieldResolverEnhancers` includes `'guards'`, and the default is `[]`.
- _Rejected:_
  - warn by default (the reviewer's option 2): the failure mode is "every requirement on the surface is silently skipped", the same class the design already treated as a boot error for WebSockets;
  - the version probe, and a probe of `@nestjs/websockets` (ADR-18);
  - applying the guard ourselves, by writing guard metadata onto gateways and handlers at boot: it mutates user classes, and its order relative to the user's own guards would be ours to define;
  - detecting `inheritAppConfig`: `connectMicroservice` is called from `main.ts` after the module graph exists, and no provider can observe its second argument. The user asserts it (`rpcTransport({ inheritAppConfig: true })`), and `advise()` prints what the assertion means (RK22);
  - flagging **every** field resolver when `'guards'` is missing: only those whose effective plan carries requirements, or an own access or acceptance decorator other than `@Public()`, would lose a check. Plain field resolvers are untouched.
- _Rationale:_ a requirement the user wrote is either enforced or the app does not start. Where the explicit decorator duplicates a global guard (Nest 12 gateways, hybrid apps that do inherit), the second run is a memo hit (ADR-37).
- _Evidence:_ LEAD-V6, LEAD-V29, LEAD-V30, LEAD-V32; `core/nest-application.js:207-213` (12.0.1); `graphql/dist/services/resolvers-explorer.service.js:90-104`; the WS, hybrid-RPC and GraphQL matrix jobs (§14.2); §17 Q19.

**ADR-41. Core names no extension. Kind constraints travel as data (`definePrincipalParam`), the no-transport error is generic, every contract can contribute boot advice (`advise()`), and the session's user-id mapping belongs to the session unit.**

- _Forced by:_ `[R1:NEST-r1-07]`. v1 stated R4 and then broke it four times: `principal.kind !== 'session'` in the guard; a `NO_TRANSPORT` message that named `apolloTransport` and its subpath, which needs a context-type-to-package table in core; a boot check (B21) that inspected the jwt, bearer and api-key plugins' options; and an RPC reminder in B22. Each needs a literal that the design's own architecture test bans, so the test would have failed, or the features would have been dropped quietly during implementation.
- _Rejected:_
  - exempting `'session'` from the literal ban: the ban then proves nothing, and a third-party kind that also carries a better-auth session could never satisfy `@CurrentSession()`-style decorators without a core edit;
  - a separate `BootAdvisor` extension point (the reviewer's alternative): a sixth registration list, for something every unit can carry as one optional member;
  - keeping helpful, specific hints in core messages: the hint moves to the unit that knows it. The generic message prints the context type and the registered ids, with a docs link.
- _Rationale:_ the session unit warns about API keys that become sessions (`enableSessionForAPIKeys`; it is the unit registered in that setup, §8.3.1), the RPC unit about hybrid apps, the organization unit about ignored `:orgId` params and the WS units about per-message quota, and core knows none of them. A third-party unit gets the same voice in the boot log.
- _Evidence:_ §3.2 rule 5; §14.7 (the ban now holds for v2's pseudo-code); §4 `BootAdvice`.

**ADR-42. `apiKeyPrincipal()` maps `verifyApiKey` results by an explicit table, probes storage when the result is the ambiguous `INVALID_API_KEY`, takes the owner from a `references` option, and declares its side effects as data.**

- _Forced by:_ `[R1:BA-r1-04]`, `[R1:SEC-r1-05]`, `[R1:BA-r1-05]`, `[R1:SEC-r1-14]`. v1 assumed that `verifyApiKey` throws 401 and 429 errors and that `referenceId` is a user id. Neither holds in 1.7.4 (LEAD-V20):
  - the endpoint never throws. A rate-limited key is `{ valid: false, error: { code: 'RATE_LIMITED', details: { tryAgainIn } } }`, so clients got 401 and treated their keys as revoked;
  - a database outage comes back as `INVALID_API_KEY`, the code a missing key gets, so an outage looked like mass key revocation and monitoring saw 4xx (S6);
  - with `references: 'organization'` the id is an organization's.

  Separately, with `enableSessionForAPIKeys` every better-auth call that carries the key spends its quota again (measured 1 → 2 → 3, REV-BA:`probe-apikey-policy.mjs`), and on WebSockets a key is verified, with a write, per message.

- _Rejected:_
  - `valid: false` → 401 across the board (v1);
  - treating `INVALID_API_KEY` as 5xx: anyone can then raise 5xx alarms with random keys;
  - SEC's unthrottled sentinel read on every `INVALID_API_KEY`: a flood of bad keys doubles storage reads. The probe runs at most once per second per instance, and concurrent callers share its result;
  - validating keys against the adapter ourselves: R1. The probe is one read of a random id, a health check;
  - `userId = referenceId` always: an organization id would be judged as a user. Organization keys get `userId: null` and `organizationId`;
  - hiding the quota multiplier by memoizing across different checks: deduping is by concrete inputs only (ADR-37). The multiplier is documented, tested and announced by the session unit's `W_API_KEY_SESSION_MULTIPLIER`; policies flag `presentsCredentials`. The trigger is the api-key plugin's presence, because its options cannot be read, and `session.apiKeySessions` lets the user state the fact (§8.3.1);
  - a default per-connection TTL for quota-consuming sources on WebSockets (SEC's first option): it would introduce revocation lag by default (ADR-18). `effects` drives a boot warning, `W_QUOTA_PER_MESSAGE`, instead.
- _Rationale:_ S6 for a source whose upstream reports failures as values: 429 with `Retry-After` where the key is throttled, 401 where it is bad, 5xx where storage is down.
- _Residual:_ keys held only in secondary storage stay ambiguous (RK18); better-auth logs every failed verification at ERROR (RK19). Both go upstream as a proposal to rethrow non-`APIError` failures.
- _Evidence:_ LEAD-V20, LEAD-V21; REV-BA:`probe-apikey-policy.mjs`; REV-SEC:`probe-apikey-infra.mjs`; `AK/index.ts:166-170` (the plugin object exposes no configuration); cases `S-apikey-results`, `S-apikey-outage`, `S-apikey-org-key`, `Z-apikey-quota-per-request`.

**ADR-43. Infrastructure errors carry a redacted cause that is built fresh from an allow-list, the raw cause is kept behind a non-enumerable slot and an explicit debug option, and transports whose runtime exposes error messages return a generic internal error (`toInternalException`). Request-time configuration errors are generic as thrown (`BetterAuthConfigurationError.atRequest`), because param decorators and services throw them where no transport maps them.**

- _Forced by:_ `[R1:SEC-r1-08]`, `[R1:SEC-r1-19]`. v1 logged infrastructure errors "with their cause chain". Nest's `ConsoleLogger` prints `util.inspect(err)`, which follows `[cause]` and prints enumerable properties (LEAD-V31); pino serializers and Sentry's linked-errors integration read `error.cause` as well. drizzle-orm's `DrizzleQueryError` puts the query parameters into its message **and** into an enumerable `params` property, and `findSession(token)` makes the session token a parameter. A database timeout would have shipped live session and bearer tokens to log aggregators on every guarded request. On GraphQL, request-time `BetterAuthConfigurationError` messages (handler names, instance names, better-auth error text) reached clients, because drivers copy `err.message` into `errors[i].message` even in production. The first fix (`toInternalException`) left the decorators' "No authentication result for SiteController.method" error untouched: it fires exactly when the guard did not run, so no transport mapping applies (post-revision audit of SEC-r1-19).
- _Rejected:_
  - relying on `toInternalException` alone: see above; the param decorators, `defineInvocationParam` decorators and `BetterAuthService` in a resolver body throw outside the guard;
  - a boot check that every handler with a principal or invocation param decorator is covered by `BetterAuthGuard` (the auditor's alternative): coverage cannot be proven for handlers in lazily loaded modules, guards applied through another library's composite guard, or guards replaced in tests;
  - scrubbing the original error's `message` and `stack` in place: the token survives in `params` (LEAD-EXP-6: `util.inspect` still printed it once, and a JSON serializer once). A new `Error` with `name`, `code`, `errno`, `syscall` and a truncated, scrubbed first line carries nothing we did not choose;
  - dropping the cause: operators lose the only diagnostic (`ETIMEDOUT`, the driver's error name);
  - leaving redaction to the user's logger: `pino.redact` matches paths, not substrings of a message;
  - redacting by pattern ("looks like a token"): the kernel knows the exact credential values of the request, which is both stricter and free of false positives;
  - making internal errors intrinsic on GraphQL so that nothing is exposed: nothing would be logged either;
  - genericizing messages on every transport in core: HTTP, WS and RPC runtimes already answer a generic 500 or "Internal server error". The member is optional, so a transport declares its own need. Making the error objects themselves generic (a fixed `message`, the specifics in own properties) needs no transport knowledge, which is why it complements the member rather than replacing it.
- _Rationale:_ §13.4's promise that tokens are never logged now holds for errors the library did not write, and the case `S-log-redaction` pins it on the real logger and on a JSON serializer.
- _Residual:_ values a driver transformed before failing (hashed, truncated, re-encoded) and secrets that are not request credentials (a database password in a connection error) are not scrubbed. First-line truncation bounds the exposure (RK23).
- _Evidence:_ LEAD-V31; LEAD-EXP-6; LEAD-EXP-7 (Apollo 4.13.0 and Mercurius 16.10.0 send a thrown error's `message` and `extensions`, never its other own properties); drizzle-orm 0.45.2 `errors.js:10-19`; cases `S-log-redaction`, `T-internal-error-generic` (including the unguarded-resolver fixture).

**ADR-44. The client-IP header's name is random per plugin instance (Web Crypto) unless the user pins one, and platforms report how they trust proxies (`proxyTrust()`), so the two silent rate-limit misconfigurations become visible.**

- _Forced by:_ `[R1:SEC-r1-18]`, `[R1:SEC-r1-06]`.
  - v1's fixed, documented `x-nsba-client-ip` was trusted first by better-auth. Any code path that forwards raw client headers to better-auth (a custom proxy controller, or better-auth's documented `fromNodeHeaders(req.headers)` idiom) let a client pick its rate-limit bucket and its recorded IP. v1 mitigated this with documentation only (RK13).
  - Behind a load balancer with the platform's trust setting at its default, every client has the proxy's IP. Sign-in is limited to 3 per 10 s for the whole user base, and one attacker can lock everyone out. better-auth's own "shared bucket" warning never fires, because the library always supplies a valid IP. With trust-all, clients choose their IP.
- _Rejected:_
  - signing the header value: better-auth's `getIP` reads a header and cannot verify anything;
  - failing boot when trust is `'none'`: that is the correct setting for an app with no proxy in front, and boot cannot tell. The runtime can: the first production request that carries a forwarding header while trust is `'none'` logs `W_PROXY_UNTRUSTED` once;
  - a `node:crypto` random name: the plugin must stay runtime-agnostic (ADR-20);
  - requiring better-auth's `trustedProxies` too: two places to keep in sync (ADR-15).
- _Rationale:_ the name never leaves the process, so it cannot be guessed or probed. Core also strips every inbound `x-nsba-ip-*` header. Proxy trust stays configured once, in the platform, and B27 plus the boot summary make the setting visible.
- _Evidence:_ `CORE/utils/ip.ts:353-384`; `BA/api/rate-limiter/index.ts:342-359, 442-451`; EXP-A:`exp-e2e.mjs`, EXP-B:E9, EXP-C7 (the path, verified with the fixed name); cases `H-ip-spoof`, `H-proxy-trust`; migration step 8 (§15.1).

**ADR-45. App-level extensions (platforms, transports) are declared once, on the default instance: a compile error on named instances and B25 at runtime. An `ExtensionDefinition` can export injectables, which the `forRoot` module re-exports.**

- _Forced by:_ `[R1:NEST-r1-09]`, `[R1:NEST-r1-12]`. v1 merged every instance's lists and de-duplicated by `id`. Two `socketIoTransport()` entries with different `credentials` mappers silently lost one, two unrelated third-party units with the same id lost one, and both contradicted §4.1.1, which says core prints ids and never compares them. Separately, the design told users to inject `WsConnectionAuth`, but nothing provided it, and `ExtensionDefinition` could not export anything.
- _Rejected:_
  - merging with de-duplication by reference and a boot error on id collisions (the reviewer's option 2): it removes the silent drop, but core would compare ids after all, and "which `forRoot` owns the transport list" stays ambiguous;
  - a separate `BetterAuthModule.forApp({ platforms, transports })` call: a second import for the most common, single-instance app;
  - providing `WsConnectionAuth` from the core module: core would import and name an extension (ADR-41). With `exports`, third-party units can offer helper services the same way.
- _Rationale:_ an app has one HTTP adapter and one transport registry, so one declaration site matches reality. An app with named instances must therefore have a default one (`NO_DEFAULT_INSTANCE`). `WsConnectionAuth` is exported under a `Symbol.for` token (`WS_CONNECTION_AUTH`), so it survives a dual-package load.
- _Evidence:_ §4.1.1; R:nest-di §2.3, §3.3; §17 Q20.

**ADR-46. A production boot without a `baseURL` fails (B23 `UNSAFE_BASE_URL`), unless `baseURL` is a dynamic `{ allowedHosts }` config or the user sets `http.allowRequestDerivedBaseURL`.**

- _Forced by:_ `[R1:SEC-r1-07]`. With no `baseURL`, better-auth derives the base URL, token links and a trusted origin from each request. The Express platform builds the URL from `req.host`, that is, from the client's `Host` header. REV-SEC:`probe-unset-baseurl.mjs` requested a password reset for a victim with `Host: evil.example`, and the mailed link pointed at `https://evil.example`: account takeover. better-auth only logs a warning at init, and v1 had no check.
- _Rejected:_
  - a warning: better-auth already prints one, and the consequence is an account takeover, not a degraded feature;
  - a Host allow-list of our own in `AuthExchange`: that is better-auth's `allowedHosts`, reimplemented (R1);
  - failing in every environment: zero-config local development would break, and the attack needs a deployed, reachable app;
  - substituting a guessed origin such as `http://localhost:<port>`: wrong behind any proxy.
- _Rationale:_ fail fast with a copy-paste hint, which is how the design treats every other unsafe configuration. The escape hatch downgrades the error to `W_REQUEST_DERIVED_BASE_URL` for deployments that sanitize `Host` at the edge and accept the residual risk.
- _Evidence:_ `BA/auth/base.ts:76-100`; `BA/context/create-context.ts:152-154`; REV-SEC:`probe-unset-baseurl.mjs`; the security e2e case (§14.4).

**ADR-47. Two better-auth instances in one app must not share cookie names on overlapping scopes (B24 `COOKIE_NAME_COLLISION`).**

- _Forced by:_ `[R1:SEC-r1-11]`. Named instances (ADR-26) keep better-auth's default prefix unless told otherwise, so both used `__Secure-better-auth.session_token` on `Path=/`. With different databases, the admin instance does not know the customer's token and clears the cookie, which logs the customer out of the main app. With a shared database and secret, the customer's token authenticates on the admin instance. Signing in on one mount overwrites the other's session.
- _Rejected:_
  - prefixing cookies per instance ourselves: it means changing `auth.options` after construction (S1), and better-auth's client and other services rely on the names;
  - comparing `advanced.cookiePrefix` only: `advanced.cookies` can rename individual cookies. The check compares the resolved `$context.authCookies` names with their `domain` and `path`;
  - documentation only: the failure is silent cross-instance logout or acceptance.
- _Evidence:_ LEAD-V19; `BA/cookies/index.ts:95-100` (`advanced.cookies.<name>.name` overrides the prefixed name); `BA/api/routes/session.ts:89-92, 288-291`; the §5.5 example sets distinct prefixes; the security e2e case (§14.4).

**ADR-48. Direct `auth.api.*` calls in application code follow better-auth's server-call semantics: their `Set-Cookie` is not forwarded unless the handler, the instance or the call site opts in, and then only for calls that carry the caller's own credential or none.**

- _Forced by:_ `[R1:BA-r1-02]`, `[R1:SEC-r1-03]`. v1's bridge forwarded every non-router call made under the scope interceptor.
  - An admin handler calling `auth.api.signUpEmail({ body })` swapped the admin's browser session for the new user's, because `autoSignIn` is on by default.
  - A service calling `getSession` with a service-account bearer token could hand that session to the end user (REV-SEC:`probe-bridge-foreign.mjs` captured the service account's `session_token`), or clear the user's own cookie when the foreign token had expired.

  In plain better-auth a server call never touches the browser unless the developer adds a cookie plugin or uses `returnHeaders`, and v1's only opt-out was wrapping each call in `runOutsideScope()`.

- _Rejected:_
  - on by default (v1; BA's option 1): the mandatory plugin would keep changing server-call semantics for reasons unrelated to cookies (ADR-02);
  - on by default with a module switch and a boot warning that lists handlers calling credential endpoints (BA's option 3): such calls sit in services and helper functions, and no metadata scan can find them;
  - a hash "fingerprint" of the inbound credential (SEC's sketch): both values live only in the request's memory and are compared, never stored or logged, so hashing adds cost without protection. The comparison is a triple: the session-token cookie (better-auth's own name and parser), `authorization`, and every declared credential header;
  - an allow-list of endpoint paths (sign-in, sign-out): the endpoint set is open, since plugins add their own;
  - a separate `@NoAuthCookies()` decorator (ADR-24).
- _Rationale:_ forwarding is a deliberate act, as adding `nextCookies()` is in better-auth. It needs `@ForwardAuthCookies()`, `cookies.forwardDirectCalls` (B28 warns, because it applies to every handler) or `service.forwardCookies(fn)`. Account switching is explicit too: `{ anyCredential: true }`. The library's own policy calls always forward, because they carry the request's credential by construction. The docs also state that direct credential calls bypass better-auth's rate limiter and origin check, which are router-only.
- _Evidence:_ `BA/api/routes/sign-up.ts:431-441`; `BA/integrations/next-js.ts:95-139`; REV-SEC:`probe-bridge-foreign.mjs`; cases `S-bridge-third-party-signup`, `S-bridge-foreign-credentials`; §17 Q13, RK14.

**ADR-49. Hook fidelity: the database dispatcher mirrors better-auth per operation, database-hook types are derived from `BetterAuthOptions['databaseHooks']`, a throwing matcher propagates as it does in better-auth, and hook bodies are typed as unvalidated input.**

- _Forced by:_ `[R1:BA-r1-06]`, `[R1:BA-r1-07]`, `[R1:BA-r1-08]`. Four places where v1 promised more, or something other, than better-auth delivers:
  - it chained merged data through `update.before` hooks, where better-auth passes every hook the **original** payload and chains only on create;
  - it typed `update` payloads as the full model (they are `Partial`) and allowed `{ data }` from `delete.before` (better-auth ignores it);
  - it swallowed a throwing predicate, so the hook silently did not run, where better-auth answers 500 for before-hook matchers and propagates after-hook ones;
  - it typed `ctx.body` with the endpoint's validated schema, although hooks run before validation: `ctx.body.email.toLowerCase()` type-checked and then threw on `{ "email": 123 }`, turning a 400 into a 500.
- _Rejected:_
  - hand-written payload types: they drift. Types evaluated in the user's program follow the better-auth version that is installed there;
  - `DeepPartial<BodyAt<P>>` for bodies (the reviewer's first suggestion): it still claims value types, and plain `unknown` loses key autocomplete. `UnvalidatedBody<B>` keeps the keys and types every value `unknown`;
  - validating the body ourselves before the before-hooks: it reimplements better-call's validation (R1) and would run it twice.
- _Rationale:_ a Nest hook must be indistinguishable from the same function written as a native plugin. The parity property test now covers update, updateMany, delete and throwing matchers.
- _Evidence:_ LEAD-V22, LEAD-V23; better-call `context.ts:203-219`; `CORE/types/init-options.ts:1405-1470`; §14.5, including the test `LIB-hook-bearer-client`.

**ADR-50. With `onAPIError: { throw: true }`, `AuthExchange` rethrows an `APIError` unchanged to the host error pipeline. Without it, a thrown `APIError` becomes its Response.**

- _Forced by:_ `[R1:BA-r1-09]`. Teams set that option so auth-route errors reach their Nest filters. better-auth's router then rethrows out of `auth.handler` (LEAD-V25). v1 caught the error with `isAPIError` and rebuilt a JSON Response, so the option silently did nothing. The conversion was also a hand-written copy of better-call's `toResponse`.
- _Rejected:_
  - always converting (v1);
  - always rethrowing: `auth.handler` also throws `APIError`s that are not the user's choice (an init failure, a disallowed dynamic host). Those would surface as Nest's default 500 and lose better-auth's status and its cleanup cookies.
- _Rationale:_ the user's better-auth configuration decides, as it does everywhere else. The error keeps its hidden `better-call:api-error-headers`, so a filter can restore cookies. On Fastify the rethrow goes through the child error handler to Nest's (ADR-39).
- _Evidence:_ LEAD-V25; `BA/auth/base.ts:107-108`; H13; case `H-errors-apierror-throw`.

**ADR-51. Consumer test helpers cover both guard registrations and cooperate with exclusive binding: `overrideAuthGuard` overrides the provider **and** the guard (and the interceptor) and can stamp a principal; `stampPrincipal()` is public; `initTestApp` closes the previous test app bound to the same instance.**

- _Forced by:_ `[R1:NEST-r1-08]`, `[R1:SEC-r1-15]`.
  - `overrideProvider` replaces only what `APP_GUARD` aliases, and `overrideGuard` replaces only the injectables that `@UseGuards` creates per host module. B16 makes `@UseBetterAuth()` mandatory on gateways, so v1's helper left the real guard running exactly there. Where the override did apply, `@CurrentSession()` threw, because a stand-in guard had no way to publish a resolution.
  - v1's `initTestApp` closed apps in `afterAll`, so an app built per test hit `INSTANCE_ALREADY_BOUND` on the second test.
- _Rejected:_
  - documenting "call both override methods": that is the trap the helper exists to remove;
  - making the param decorators tolerate a missing resolution: it would bring back the reference's silent `undefined` (#12; ADR-30);
  - registering close with `afterEach` when one is in scope: the helper is runner-agnostic, and it would not cover a failed `init()` (ADR-25). An explicit `closeWith` option covers runners.
- _Rationale:_ `overridePrincipal` stays the recommended tool, because it keeps the real guard, acceptance, origin check and policies. The guard override exists for tests that want none of them.
- _Refined after the post-revision audit:_ a stand-in guard publishes through a test stamp verified by args-element identity (§7.8 item 3), and both scope interceptors copy it into the scope. The carrier stamp alone did not work on WebSocket gateways, which have no carrier, and the stand-in interceptor now explicitly opens the scope.
  - _Rejected:_ stamping the socket (races across concurrent messages); stamping only the args array (on HTTP the router passes guards and interceptors different arrays, LEAD-V34); having `stampPrincipal()` look up the transport (a free function in a test has no DI access).
- _Evidence:_ `core/injector/module.js:344-356`; LEAD-V7; LEAD-V34; §14.8, tests `LIB-testing-override-principal` and `LIB-testing-stamp-mock-guard`.

**ADR-52. Diagnostics never change a response. Unknown paths under the mount stay better-auth's bodiless 404s, and outside production each one is logged once with a "did you mean", capped at 100 distinct paths.**

- _Forced by:_ `[R1:SEC-r1-16]`. A client `baseURL` of `/api/auth/api/auth`, or a call to `/api/auth/signin/email`, reaches better-auth, which answers 404 with no body, and nothing is logged. Misconfiguration was about 20% of the reference's issues, and this was its largest cluster (R:_digest, ref-issues cluster 1).
- _Rejected:_
  - adding a body or a header to the 404: auth-route responses are verbatim (H7), and clients may depend on better-auth's exact shape;
  - on in production by default: scanners would turn every probed path into a WARN line. It is off there unless `http.diagnostics: true`, and capped either way;
  - failing boot on "suspicious" base paths: no static signal separates a wrong client URL from a right one.
- _Rationale:_ the log line names the resolved base path and the closest of `auth.api[*].path`, the list B12 already builds, which is what a developer needs to see the doubled prefix or the typo. `W_PROXY_UNTRUSTED` (ADR-44) follows the same rule: say it once, never touch the response.
- _Evidence:_ R:ref-issues cluster 1; §6.3 step 7; case `H-diagnostics-404`.

**ADR-53. Hooks bind in the core module's `onModuleInit`. better-auth calls made before that are counted by the plugin and reported at boot (B26); they are not prevented.**

- _Forced by:_ `[R1:NEST-r1-11]`. v1 claimed that the global core module always initializes first. Nest gives every global module the same distance and keeps insertion order among them (LEAD-V27), so a `@Global() DatabaseModule` imported before `BetterAuthModule` whose `onModuleInit` seeds users through `auth.api.signUpEmail` runs **before** hooks are bound. The plugin is inert until binding, so `@BeforeDatabase('user.create')` normalization and audit hooks were silently skipped for the seeded users.
- _Rejected:_
  - binding earlier, in a constructor: hook providers from other modules may not exist yet, and discovery needs the whole graph;
  - throwing on a dispatch before binding: the plugin must stay inert when unbound, because the same `auth.ts` serves scripts, the better-auth CLI and non-Nest code (§10.2);
  - queueing early calls until binding: a seeding call awaits its result, so that deadlocks.
- _Rationale:_ the claim is narrowed to what Nest guarantees (the core module runs before non-global modules' hooks). The plugin's first before-hook matcher counts dispatches while unbound, at no cost on the bound path, and `W_CALLS_BEFORE_BIND` tells the user how many calls ran without hooks and to move seeding to `onApplicationBootstrap`.
- _Evidence:_ LEAD-V27; `core/injector/container.js:104-109`; §5.4, §10.3.
