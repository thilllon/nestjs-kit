## 0. Summary and principles

### 0.1 Summary

better-auth defines its own integration contract. Its handler is a Web-standard `handler(Request): Promise<Response>`. Framework bridging is done by plugins (`nextCookies`, `sveltekitCookies`, `tanstackStartCookies`, `expo`), server code calls `auth.api.*`, and authorization runs on access control. This design binds NestJS to exactly that contract and reimplements nothing better-auth already does. It has three parts:

1. **The `nestjs()` better-auth plugin** `[A][B][C]`. The user adds it last to `betterAuth({ plugins })`, following the `nextCookies()` precedent, and a boot check makes it mandatory. It is the only code that runs inside better-auth's pipeline, and it does four things:
   - bridges Nest hook providers and database hooks, preserving better-auth's return-value semantics per operation;
   - forwards `Set-Cookie` from the library's own `auth.api.*` calls (principal sources and policies) into the current response. Application code's direct calls are forwarded only in handlers that opt in, and only when the call used the caller's own credential or none `[R1:BA-r1-02, SEC-r1-03]`;
   - suppresses session refresh on any endpoint dispatched from a cookie-less scope, which also covers the stateless refresh-cache branch;
   - declares an unguessable client-IP header, random per plugin instance and never leaving the process, through `init()` `[R1:SEC-r1-18]`.

   It imports only `better-auth/api`, `better-auth/cookies` and `defu`, never `@nestjs/*`, so the better-auth CLI can still load `auth.ts`.

2. **A small kernel** `[B][C]`: the module, guard, scope interceptor, principal resolver, authorization evaluator, origin check, boot validator and error model. It depends only on its own extension contracts and on better-auth's public surface. It never branches on a platform, transport, principal-kind or policy name; the data it compares (principal kinds, credential header names) is supplied by extensions.
3. **Extension units** `[A][B][C]` for the five extension points:
   - HTTP platforms: Express and Fastify ship; third parties plug in their own;
   - transports: HTTP, GraphQL (Apollo and Mercurius), WebSockets (socket.io and ws), and RPC;
   - principal sources: the better-auth session, API keys, or a third party's;
   - authorization policies: thin adapters over better-auth's permission APIs;
   - hook providers.

   Built-in units register through exactly the same contract a third party uses. Their behavior is proven identical by runner-agnostic conformance kits shipped in `./testing/conformance`.

**Auth routes.** Every request under better-auth's own mount path, for every method, goes to `auth.handler`. The platform produces a Web `Request` with the exact body bytes, a trust-proxy-aware origin and client IP, and HTTP/2-safe headers. It writes the `Response` back verbatim: status, every `Set-Cookie`, redirects and streams. The Express binding uses two phases: bounded raw capture once the HTTP adapter and the platform are both known (inside `NestFactory.create()` / `createNestApplication()`), then dispatch at `onModuleInit`, after the user's CORS and middleware. The Fastify binding is an encapsulated plugin with a `parseAs: 'buffer'` catch-all parser, a body limit, and a child error handler that hands failures to Nest's error pipeline.

**App routes and messages.** A single transport-neutral guard resolves the principal lazily, at most once per logical request (and per connection where the transport opts in). It calls `auth.api.getSession({ headers, returnHeaders: true })` and forwards only `set-cookie`, and only where the transport can carry cookies. Principals that act for a user with a narrower grant (API keys, OAuth tokens) are admitted only on routes that name their kind. Operations authenticated by an ambient browser cookie pass better-auth's own origin rule. Authorization then runs through requirement expressions whose policies travel by reference in route metadata, and every decision is made per handler invocation.

**The common case** needs three lines plus one platform import:

```ts
// auth.ts: static and CLI-friendly; imports no Nest code
export const auth = betterAuth({ database, emailAndPassword: { enabled: true },
  plugins: [admin(), organization(), nestjs()] });                    // nestjs() last
declare module 'nestjs-slightly-better-auth' { interface Register { auth: typeof auth } }

// app.module.ts
@Module({ imports: [BetterAuthModule.forRoot({ auth, platforms: [expressPlatform()] })] })
export class AppModule {}

// any controller: no generics, typed from `typeof auth`
@Get('me') me(@CurrentSession() s: AuthSession) { return s.user.role; }
@RequireOrgPermission({ project: ['delete'] }, { organization: fromParam('orgId') })   // typo = compile error
@Delete(':orgId/projects/:id') remove() {}
@Public() @Get('health') health() {}                                                   // zero auth I/O
```

The user never sets `bodyParser: false`, never adds `hooks: {}` placeholders, writes no generics at use sites, and gets no CORS side effects.

### 0.2 How the design embodies better-auth's philosophy (R1)

| better-auth principle (R:ba-core §1.1)                                             | How this design honors it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1/P2: framework-agnostic; the Web `Request → Response` handler is the single seam | Auth routes are raw platform routes that call `auth.handler` with a `Request` we build (§6). No auth endpoint is re-declared as a Nest controller. Routing, 404/415, the origin/CSRF check **for auth routes**, rate limiting, `disabledPaths` and plugin `onRequest`/`onResponse` all stay inside `auth.handler`. better-auth's origin check is router-only (LEAD-V16), so the cookie-authenticated surfaces this library creates (app routes, GraphQL mutations, WebSocket handshakes) get the same rule applied by the kernel, with better-auth's own trusted-origin set, matcher and disable flags (§7.10) `[R1:SEC-r1-01, BA-r1-03]`.                                                                                                                                                                                                                                                                                                  |
| P3/P4: plugin-first; customize inside the pipeline with hooks                      | Everything that must run _during_ a better-auth call enters through the `nestjs()` plugin, added at construction (§10). `auth.options` is never mutated (S1).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| P5: type safety through inference                                                  | Types flow from `typeof auth` through a `Register` augmentation, which is better-auth's own `BetterAuthPluginRegistry` idiom. Permission arguments, hook contexts, DB hook payloads and endpoint paths are inferred from better-auth's own option and endpoint types (§11). Core accepts a structural `AuthLike`, never bare `Auth`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| P6: server code calls `auth.api`                                                   | The session principal comes from `auth.api.getSession` (§7). Policies call `userHasPermission`, `hasPermission`, `getActiveMemberRole` and `role().authorize()` (§8). API keys are verified by `verifyApiKey`. Nothing parses session cookies for authentication or queries the database itself (the API-key outage probe is a read-only health check, §8.3.1).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| P8: secure by default                                                              | The global guard is on by default. `@Public()` performs zero auth I/O. Delegated principals (API keys, OAuth tokens) are admitted only where a route names them, and built-in policies never widen them beyond their own grant (Z5). Cookie-authenticated unsafe operations must come from a trusted origin. `Origin`, `Referer`, `Sec-Fetch-*`, `Cookie`, `Authorization` and `Content-Type` are never rewritten. The client IP is trust-proxy-aware and anti-spoofed, and a production app with no `baseURL` fails boot. Auth-route bodies are bounded. Bad credentials are never downgraded to anonymous. Infrastructure failures are 5xx and are logged with credentials redacted. Surfaces the global guard may not reach (WebSocket gateways on every Nest major, hybrid RPC handlers, GraphQL field resolvers that carry requirements) fail boot unless they are covered explicitly. Misconfiguration fails at compile time or boot. |
| P10: framework cookie bridging is a plugin                                         | The `nestjs()` after-hook, gated on `ctx._flag !== 'router'`, forwards `Set-Cookie` of direct calls where forwarding is enabled. This is the `nextCookies` pattern (`BA/integrations/next-js.ts:47-144`, LEAD-V14). As with `nextCookies`, forwarding for application code is a deliberate opt-in; it is not a side effect of adding the plugin `[R1:BA-r1-02]`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| P11: ESM-first                                                                     | ESM is the canonical build. The exports map is `module-sync`-first, so on the supported Node range a single ESM copy serves both `import` and `require` (§12).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| "Do not reimplement" (R:ba-core §9)                                                | Not reimplemented: routing, auth-route CSRF, rate limiting, body parsing of auth routes, cookie names and parsing (`better-auth/cookies`), permission and role evaluation, trusted-origin matching (`$context.isTrustedOrigin`), IP extraction, error envelopes, API-key validation. The integration supplies only what better-auth leaves to the host: the mount, a faithful `Request`, a client IP, cookie write-back, refresh control where cookies cannot be written, and better-auth's origin rule on surfaces better-auth's router never sees.                                                                                                                                                                                                                                                                                                                                                                                        |

### 0.3 SOLID mapping

| Letter | Concrete design elements                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **S**  | Each unit has one reason to change (§3.1):<br>• `MountCoordinator`: lifecycle timing.<br>• `AuthExchange`: `Request` construction, header hygiene, `auth.handler`, error conversion.<br>• `RequestScope`: the per-request ALS and state.<br>• `PrincipalResolver`: the source chain and memoization.<br>• `AuthorizationEvaluator`: requirement composition.<br>• `OriginCheck`: better-auth's origin rule for ambient-cookie operations.<br>• `TrustedOrigins`: the post-init trusted-origin set.<br>• `ErrorRedactor`: credential-free error causes.<br>• `HookBinder`: discovery into the plugin registry.<br>• `BootValidator`: fail-fast checks and advice collection.<br>• `BetterAuthGuard`: orchestration only; it holds no policy logic, no transport branch and no better-auth call of its own.<br>Platforms only translate I/O; transports only extract context and map errors.                                       |
| **O**  | Five extension points, each added by a new class, value or package, never by editing core (§4):<br>• `HttpPlatform`, selected by its own `supports()`;<br>• `AuthTransport`, selected by its own `handles()`;<br>• `PrincipalSource`, an ordered chain filtered by the kinds each route accepts;<br>• `AuthorizationPolicy`, carried by reference inside requirement metadata, so there is no registry to edit;<br>• hook methods, discovered.<br>Every extension contract has an optional `advise()` member, so a unit contributes its own boot hints without core knowing about it `[R1:NEST-r1-07]`. Param decorators for principal kinds and per-invocation values are built with public factories (`definePrincipalParam`, `defineInvocationParam`). Core contains no `switch`/`if` on platform, transport, principal-kind or policy names, and names none of them in messages. An architecture test enforces this (§14.7). |
| **L**  | Every contract lists its invariants: exact bytes, every `Set-Cookie`, a stable memo key per logical request, decisions per invocation, "denials are values, exceptions are infrastructure", delegated principals never widened, and more. Runner-agnostic conformance kits check them, and the built-in units and any third-party unit must pass the same kits (§14.1). Principals form a discriminated union, so policies narrow instead of casting.                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **I**  | Contracts are small, and optional members add progressive disclosure:<br>• `HttpPlatform` separates lifecycle (`prepare`/`mount`) from per-request access (`HttpRequestAccessor`), so GraphQL-over-HTTP uses the accessor without mounting anything.<br>• `CookieSink` has one method.<br>• `AuthorizationPolicy` needs only `id` and `evaluate`.<br>• `PrincipalSource` needs only `id`, `kinds` and `resolve`.<br>• A transport without a browser leg (RPC) simply omits `TransportCall.browser`.<br>• Policies see an `AuthorizationContext`, never an `ExecutionContext` unless they ask for it.                                                                                                                                                                                                                                                                                                                             |
| **D**  | Core depends on `AuthLike`, its own contracts and `Symbol.for` tokens. It reaches the plugin through a versioned protocol object found with `$context.getPlugin(id)`, never through an import. The principal resolver sits behind a token (`PRINCIPAL_RESOLVER`) so tests can substitute it. Platform and transport units depend on the contracts and their own peer framework, never on each other.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

### 0.4 What this design optimizes for and what it costs

- **Optimizes for:**
  - zero reimplementation of better-auth;
  - identical behavior across platforms, proven by kits rather than asserted;
  - third-party extension without forking;
  - fail-fast configuration, including every surface the guard cannot reach;
  - zero generics in the common case.
- **Costs** (accepted in §16):
  - one line in `auth.ts` (`nestjs()`);
  - one platform import in `forRoot` (`platforms: [expressPlatform()]`);
  - `@UseBetterAuth()` on every WebSocket gateway, on both Nest majors (§9.3);
  - an `Origin` header on cookie-authenticated unsafe requests from non-browser clients (SSR servers), exactly as better-auth already requires on its own routes (§7.10);
  - a boot-time metadata scan;
  - a small hook-dispatch mirror kept in parity with `BA/api/dispatch.ts` and `BA/db/with-hooks.ts` by a property test.
