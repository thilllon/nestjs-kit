## 15. Migration guide sketch from @thallesp/nestjs-better-auth

Target: apps on `@thallesp/nestjs-better-auth` 2.x (the v2.8.0 surface, R:ref-impl). This is a clean break (D3). Most changes are mechanical renames, and several of the old library's "requirements" disappear. A few deliberate security changes need one decision each (steps 8–14).

This section retains the historical proposal’s compatibility analysis for review continuity. It is not a newly published migration guide and does not claim this private package can already replace another library. Current implementation documentation belongs in the package README and working examples; the retired standalone migration guide must not be recreated. [MONOREPO]

### 15.1 Checklist

1. Target better-auth `>=1.7.0 <2` and Node `>=24.11.0`; confirm the actual compatibility matrix before release.
2. This private workspace has no installable release promised by this document. Test a local packed artifact only after implementation; an npm installation command belongs in the current package README only after registry-confirmed publication.
3. In `auth.ts`, add the plugin **last** and delete the empty hook placeholders:
   ```ts
   import { nestjs } from "nestjs-slightly-better-auth/plugin";
   export const auth = betterAuth({
     /* … */ plugins: [admin(), organization(), nestjs()],
   }); // no hooks: {} / databaseHooks: {}
   declare module "nestjs-slightly-better-auth" {
     interface Register {
       auth: typeof auth;
     }
   }
   ```
   With several better-auth instances, give each a distinct `advanced.cookiePrefix` (boot check B24) and its own `nestjs()` call, never a shared plugins array (B03) `[R4:BA-r4-05]`.
4. In `main.ts`, delete `bodyParser: false`. Nest's parsers, `rawBody: true` and body limits work again, and auth routes still get raw bytes. Configure CORS on the host. For app routes use an explicit allow-list of the browser origins that may read them. For the auth mount you may follow better-auth's exact trusted origins, scoped to the mount (§6.9):
   ```ts
   // Express (the cors package's per-request options delegate): one CORS middleware, two policies
   const authOrigin = betterAuthCorsOrigin(auth); // exact trusted origins; allowPatterns for wildcards
   app.use(
     cors((req, cb) =>
       cb(null, {
         origin: isUnder(req.path, "/api/auth")
           ? authOrigin
           : ["https://app.example.com"], // helper on the auth mount only
         credentials: true,
       }),
     ),
   );
   // Fastify: the same split in an @fastify/cors delegator keyed on the request path
   ```
   Do not apply the helper app-wide: every exact entry of `trustedOrigins`, including partner origins listed only for `callbackURL`, would gain credentialed read access to every route (§6.9).
5. Replace the module: `BetterAuthModule.forRoot({ auth, platforms: [expressPlatform()] })`, or `fastifyPlatform()`. Platforms and transports go on the default instance only.
6. Rename decorators and move role checks to permissions (§15.2). `@Session()` becomes `@CurrentSession()`. Then remove the `UserSession<typeof auth>` and `AuthService<typeof auth>` generics.
7. Register non-HTTP transports: `apolloTransport()`, `mercuriusTransport()`, `socketIoTransport()`, `wsTransport()` or `rpcTransport()`. Then close the coverage gaps; boot fails until you do (B16):
   - add `@UseBetterAuth()` to every gateway, on Nest 11 and 12 (a plain `@UseGuards(AuthGuard)` becomes `@UseBetterAuth()`, not `@UseGuards(BetterAuthGuard)`: gateways need the scope interceptor too);
   - in hybrid apps, pass `{ inheritAppConfig: true }` to `connectMicroservice` and assert it with `rpcTransport({ inheritAppConfig: true })`, or decorate message controllers;
   - set `fieldResolverEnhancers: ['guards']` in GraphQL if field resolvers carry method-level requirements. Field resolvers without method-level metadata inherit their operation's decision and cost no auth I/O, and class-level decorators on a resolver class apply to its queries, mutations and subscriptions only (§9.2) `[R3:NEST-r3-05]`;
   - in a federation subgraph, set `fieldResolverEnhancers: ['guards']` whenever it has field or reference resolvers, give every entity type whose fields must not be public a `@ResolveReference()` (it is an entry point: class-level and default access apply to it), or set `federationCoverage: 'warn'` for a subgraph only an authenticating router can reach (§9.2) `[R4:NEST-r4-01]`;
   - pass a context **function** to `GraphQLModule.forRoot` that builds a new object per request (`context: ({ req }) => ({ req, loaders: createLoaders() })`); a context object fails boot (`GRAPHQL_STATIC_CONTEXT`) `[R4:SEC-r4-03]`;
   - with `disableGlobalAuthGuard` migrated to `globalGuard: false`, add `@UseBetterAuth()` to every controller whose routes declare something (B16: access other than `@Public()`, acceptance, requirements, principal or invocation params, or direct-call forwarding, which includes a `@Public()` login proxy with `@ForwardAuthCookies()`); boot names the ones you missed (`ROUTE_UNGUARDED`). `defaultRequirements` alone does not make an undecorated route need the guard. A forgotten transport shows up as `UNGUARDED_AUTH_METADATA` `[R2:NEST-r2-02, SEC-r2-08]`. `globalGuard: false` does **not** switch off the scope interceptor: since v6 the default instance registers it whatever `globalGuard` says, so handlers that call `auth.api` still get the caller-session check, refresh suppression and the cookie bridge. A handler that calls `auth.api` with `headersFrom(req)` and the caller's session cookie on a browser leg no guard verified now fails closed with `PUBLIC_HANDLER_USED_CALLER_SESSION`; give it `@UseBetterAuth()` with `@OptionalAuth()` (or `@ForwardAuthCookies()` for a login or logout proxy). Only an explicit `globalScope: false` removes the scope, and boot then warns `W_NO_GLOBAL_SCOPE` at every start `[R5:SEC-r5-01, SEC-r5-02]`.
8. **Proxy trust.** Behind a load balancer, set Express `app.set('trust proxy', <hops>)` or Fastify `trustProxy` to the real number of hops. Never set it to `true` in production. The boot summary prints the setting; B27 and `W_PROXY_UNTRUSTED` point at both misconfigurations (§6.8).
9. **`baseURL`, secret and `NODE_ENV`.** Set `baseURL` (or `BETTER_AUTH_URL`) and `BETTER_AUTH_SECRET` in production. A production boot without a `baseURL` fails with `UNSAFE_BASE_URL` (B23), because better-auth would otherwise build reset links from the client's `Host` header, and one with better-auth's default secret fails with `DEFAULT_SECRET` (B29). The library treats every environment as production unless `NODE_ENV` is `development`, `dev` or `test`, so set `NODE_ENV=development` locally `[R3:SEC-r3-07]`. better-auth itself enables its rate limiter only for `NODE_ENV=production`: a deployment without it (or with `staging`) gets `W_RATE_LIMIT_DISABLED` and should set `NODE_ENV=production` or `rateLimit: { enabled: true }`, or `rateLimit: { enabled: false }` when a gateway limits auth traffic (B30) `[R4:BA-r4-02]`. **Set `NODE_ENV` in the process environment, not in `.env`** `[R5:BA-r5-02]`: better-auth snapshots `NODE_ENV` when `auth.ts` first imports it (LEAD-V58), and `ConfigModule.forRoot({ envFilePath: '.env' })` runs after that import, so a `NODE_ENV=production` that lives only in `.env` leaves better-auth's limiter off and its default-secret guard disarmed while `process.env.NODE_ENV` reads `production`. The library's own checks are unaffected (B29 compares `$context.secret`, B30 `$context.rateLimit.enabled`), and B30 and the boot summary name this case explicitly.
10. **API keys.** Mark routes that machine clients call with API keys: `@AcceptPrincipals('session', 'api-key')` or an API-key requirement (`@RequireApiKeyPermission`). Keys are no longer accepted on every route, and never judged by their owner's admin role unless a requirement opts in (§7.6, §8.3).
11. **Direct `auth.api` calls that must set cookies** (a custom login or logout controller, a GraphQL `login` mutation): add `@ForwardAuthCookies()` to the handler. Other direct calls no longer write cookies to the caller's response, and there is no per-call-site switch; an impersonation flow wraps its call in `forwardForeignCookies(fn)` inside such a handler (§7.5) `[R3:SEC-r3-04]`. A former `@AllowAnonymous()` handler that hands the request's headers to `auth.api` to act on the caller's session (change email, revoke sessions) becomes `@OptionalAuth()` (or `@RequireAuth()`) on POST with a trusted Origin; returning auth cookies also requires `@ForwardAuthCookies()`. On safe methods a guard run without a passing advisory verdict still cannot authorize the direct call. On any route, a `@Public()` handler's call with the caller's session cookie fails with `PUBLIC_HANDLER_USED_CALLER_SESSION` (§7.5) `[R4:SEC-r4-02]` `[R5:SEC-r5-02]`.
12. **Clients that send cookies without an `Origin`** on unsafe requests: SSR servers and BFFs that forward browser cookies, and native apps that send the session cookie themselves, such as better-auth's Expo client calling your own API. Send a trusted `Origin` header (an Expo app can send its scheme, `myapp://`, which the Expo guide already puts in `trustedOrigins`), set `originCheck.missingOrigin: 'allow-non-browser'`, or mark those routes `@SkipOriginCheck()` (§7.10). With the `expo()` plugin installed and the strict default, boot advises exactly this (`W_ORIGIN_CHECK_NATIVE_CLIENTS`), and each denied pair of reason and origin is logged once at WARN `[R3:SEC-r3-03]`. The same holds for browser clients on another origin that send the API's cookie **and** a bearer token: add their origin to better-auth's `trustedOrigins` (§17 Q26) `[R2:SEC-r2-01]`.
13. **Custom guards that read `request.user`**: read the principal with `BetterAuthService.principalFor(ctx)` (§7.8), which answers `'no-identity'` on public routes. Register such a guard where it runs after `BetterAuthGuard`: in a module imported after `BetterAuthModule.forRoot()`, at controller level, or after `BetterAuthGuard` registered by `AppModule` itself (`globalGuard: false`, §5.7). An `APP_GUARD` declared in `AppModule` next to `forRoot` runs first and gets `PRINCIPAL_READ_BEFORE_GUARD`; the boot summary prints the order. `getPrincipal()` throws outside a handler scope, and returns `null` in `@Public()` handlers; handlers that want the session when present use `@OptionalAuth()` `[R2:NEST-r2-07, SEC-r2-04]` `[R3:NEST-r3-02]`.
14. **Company-wide requirements** that a subclassed guard used to add: `defaultRequirements: [orgMember()]` in the module options (§7.6) `[R2:NEST-r2-08]`. Routes that machine clients call (API keys, service accounts without an active organization) get `@SkipDefaultRequirements()`; boot names every route the defaults would make unsatisfiable (B15 `UNSATISFIABLE_PRINCIPAL_KINDS`) `[R3:NEST-r3-06]`. That includes a company policy that names no principal kinds (`definePolicy({ id, evaluate })`): it judges only principals without delegation, so it can never pass an API key `[R4:NEST-r4-04]`.
15. Boot the app once. The diagnostics (B01–B31) point at every remaining mistake with a fix.
16. Re-run your e2e tests with origin checks **on** (§14.4).

### 15.3 Role names without the old `@Roles`

The preferred path is to model roles as access-control statements (`createAccessControl`) and use `@RequirePermission`. For teams that need role names now, a custom policy takes a few lines. It follows better-auth's storage format (comma-joined, **no trimming**) but deliberately does not replicate `adminUserIds`/`defaultRole`, so the choice stays explicit in application code (§17 Q1):

```ts
export const hasRole = definePolicy<{ roles: string[] }, "session">({
  id: "app:has-role",
  requires: { plugins: ["admin"], principals: ["session"] },
  evaluate: ({ roles }, ctx) => {
    const userRoles = String(
      (ctx.principal.session.user as { role?: string | null }).role ?? "",
    ).split(","); // no trim, like better-auth
    return roles.some((r) => userRoles.includes(r))
      ? allow()
      : deny({ reason: "MISSING_ROLE" });
  },
});
export const RequireRole = (...roles: string[]) =>
  Require(hasRole({ roles }, { freshIdentity: true })); // authoritative, like admin
```

The recipe reads `session.user.role` from the principal's session, which is the application's shape. With `customSession` that is not necessarily the stored role better-auth's admin plugin evaluates; the built-in `permission()` reads the stored role instead (§8.3) `[R3:BA-r3-02]`.

### 15.4 Behavior changes to verify after migrating

- **Refreshed session cookies now reach the browser on ordinary routes.** This fixes a latent expiry drift. CDN and proxy rules keyed on the absence of `Set-Cookie` should be reviewed.
- **Direct `auth.api` calls in handlers no longer write cookies** unless the handler opts in with `@ForwardAuthCookies()` (the reference never forwarded them either; v1 of this design did).
- **Cookie-authenticated unsafe requests need a trusted `Origin`**, on app routes, GraphQL mutations and WebSocket handshakes, exactly as on better-auth's own routes. Browsers send it automatically; SSR servers and scripts that forward cookies must add it.
- **API keys and other delegated credentials are accepted only where a route asks for them.**
- **`@RequirePermission` reads identity authoritatively and the role from the stored user** (one session read and one user read per request on such routes, even with the cookie cache). Bans and revocations take effect immediately, also on TTL sockets and for API keys a route opts in. There is no cheaper mode, API keys turned into sessions by `enableSessionForAPIKeys` are rejected there, as on better-auth's admin endpoints, and a `customSession` shape's `user.role` plays no part `[R3:BA-r3-02, SEC-r3-06]`.
- **`@Public()` no longer attaches a session.** Handlers that read `@CurrentSession()` on public routes need `@OptionalAuth()`, and B15 tells you which ones. `BetterAuthService.getSession()` returns `null` in a public handler.
- **Cookie-carrying unsafe requests need a trusted `Origin` even when they also carry a token**, and login or logout proxies with `@ForwardAuthCookies()` get better-auth's form-CSRF rule.
- **Authorization infrastructure failures are now 5xx, not 403**, including the ones better-auth's session checks report as the generic 401 in apps without `customSession` (§8.1; with `customSession` better-auth swallows them into a 401 we cannot tell apart, RK2), and a store that reads but cannot write, or a key row locked past `slowMs`, no longer turns valid API keys into 401s. A better-auth 401 with a specific code, such as "not a member of the organization", is a 403 denial `[R3:BA-r3-01, BA-r3-05, SEC-r3-01]`. Monitoring may see new 5xx where 403s used to hide outages. Their causes are logged with credentials redacted.
- **Nest hooks can now short-circuit or rewrite input.** A hook that returned an object "for logging" now short-circuits the endpoint.
- **Path-less hooks still see the guard's `/get-session` calls**, as in better-auth. Use `skipInternal: true` for audit-style hooks.
- **The auth path comes from better-auth** (a `baseURL` path beats `basePath`), not from `auth.options.basePath`. Check that the client's `baseURL` agrees.
- **The rate-limit IP comes from the platform** (`trust proxy` / `trustProxy`). Configure it behind a proxy (checklist step 8).
- **Class-level decorators on GraphQL resolver classes reach queries, mutations and subscriptions, not field resolvers.** Put a requirement for field-level data on the field resolver method `[R3:NEST-r3-05]`.
- **Every environment is production unless `NODE_ENV` says `development`, `dev` or `test`.** A deployment that never set `NODE_ENV` now gets the production boot checks (`UNSAFE_BASE_URL`, `DEFAULT_SECRET`) and warnings `[R3:SEC-r3-07]`, among them `W_RATE_LIMIT_DISABLED`, because better-auth leaves its rate limiter off there `[R4:BA-r4-02]`.
- **Nest hooks outlive `app.close()`.** Work that another module finishes during shutdown still runs through your `@BeforeAuth`, `@AfterAuth` and database hooks, and so does a direct `auth.api` call a script or test makes on the same instance after `close()`, until the next application binds it. A hook whose dependencies are already shut down makes that call fail `[R4:SEC-r4-01]`.
- **GraphQL federation subgraphs are guarded at their entry points.** Reference resolvers are authorized like root fields, `_entities` never serves an entity type's inheriting field resolvers without a guarded reference resolver, and boot requires field guards (§9.2) `[R4:NEST-r4-01]`.
- **Upgrading to Nest 12:** global guards reach WebSocket gateways and third-party context types there. A handler that declares nothing in a context no registered transport handles (a gateway without a WS transport, an `'rmq'` consumer) answers 500 `NO_TRANSPORT` at request time while boot passes: register the transport, or mark the handler `@Public()` `[R3:NEST observation on NEST-r2-03]`.
- **Unprotected surfaces now fail boot.** This covers WebSocket gateways without `@UseBetterAuth()` on both majors, hybrid RPC handlers without `inheritAppConfig`, guarded GraphQL field resolvers without `fieldResolverEnhancers: ['guards']`, controller routes with library decorators under `globalGuard: false`, and handlers with library decorators that no registered transport serves. Fix them, or mark them `@Public()`.
- **On Fastify:**
  - `@fastify/cors`, helmet and `onSend` hooks now apply to auth routes, and auth-route failures reach your global exception filters;
  - the app's JSON parser is Fastify's secure one again (the reference had replaced it and dropped proto-poisoning protection);
  - the `qs` optional peer is no longer needed.
