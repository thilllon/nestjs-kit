## 9. Transports

Every transport is an extension unit implementing `AuthTransport` (§4.2). The guard, resolver, evaluator, origin check and error taxonomy are identical for all of them. Transports differ only in context extraction, cookie capability, browser exposure, coverage checks and error delivery, as better-auth's own integrations imply (R:ba-integrations §9 item 4). D2's breadth costs one small object per transport and never a branch in core `[B]`.

### 9.0 Matrix

### 9.1 HTTP (built-in, root entry)

```ts
describe(ctx, kit) {
  const http = ctx.switchToHttp();
  const req = http.getRequest(), res = http.getResponse();
  const a = kit.http!;                                    // B08 guarantees a platform when an HTTP adapter exists
  const key = a.key(req), request = a.request(req);
  return { key, invocation: key, headers: () => a.headers(req), clientIp: a.clientIp(req),
           cookies: a.cookieSink(req, res), request, param: (n) => a.param(req, n),
           browser: { enforce: !['GET', 'HEAD', 'OPTIONS'].includes(request.method), headers: () => a.headers(req),
                      url: request.url, key } };
},
validate(v) {                                              // B16 claims; 'path'/'method' are Nest's route metadata keys (LEAD-V42)
  canary(Get, ['path', 'method']);                          // @Get('/x') on a private probe class must read back under both keys, else NEST_METADATA_KEY_CHANGED
  for (const { target, method, path } of controllerRoutes(v.discovery, 'path', 'method'))
    v.claim(target, method, 'global', { code: 'ROUTE_UNGUARDED', inputs: routeParamNames(path),
      hint: 'Register the global guard (globalGuard: true) or add @UseBetterAuth() to the controller.' });
}
```

- **Cookies.** Express uses `res.append('set-cookie', v)` and Fastify uses `reply.header('set-cookie', v)`, both appending. The sink returns `false` once headers are sent. EXP-B:E7 showed guard-appended cookies arriving alongside handler-set cookies on both platforms and both majors.
- **Origin check.** Unsafe methods that carry a cookie need a trusted `Origin`/`Referer`, whatever other credential they carry, and a handler with `@ForwardAuthCookies()` gets the form-CSRF rule (§7.10). Safe methods never do, which mirrors better-auth's router.
- **Coverage.** Routes are claimed `'global'`. With `globalGuard: true` every route is covered. With `globalGuard: false`, a route that declares something in B16's sense (§5.4) and carries no `@UseBetterAuth()` fails boot with `ROUTE_UNGUARDED`. That covers access other than `@Public()`, acceptance, requirements, principal or invocation params, and direct-call forwarding, so a `@Public() @ForwardAuthCookies()` login proxy is included. A route that declares nothing stays the app's choice, even with `defaultRequirements` set. The exception is an instance with `cookies.forwardDirectCalls`, which makes every route forward `[R2:NEST-r2-02, SEC-r2-08]`.
- **Denial.** An `HttpException` subclass: `UnauthorizedException`, `ForbiddenException` or `HttpException(…, 429)`. It carries the payload `{ statusCode, error, code, reason?, message }`, which is Nest's default body shape plus a stable `code`; reference issue #148 asked for this. These are `IntrinsicException`s, so Nest does not log them (LEAD-V9). A `challenge` is written as `WWW-Authenticate` through Nest's public `httpAdapter.setHeader(res, …)`. `Retry-After` is copied for 429.
- **Infrastructure.** `BetterAuthInfrastructureError` (not intrinsic, redacted cause) goes through Nest's filters, which answer 500 and log it. The HTTP transport has no `toInternalException`: Nest's default 500 body never includes the error message.

### 9.2 GraphQL: Apollo and Mercurius (`./graphql`)

**Shared behavior** `[A][B][C]`:

- `gql = GqlExecutionContext.create(ctx)`.
- **Selection and the driver** `[R3:NEST-r3-09]`. Both units' `handles()` is `ctx.getType() === 'graphql'`: an app runs one GraphQL driver, so no per-request probe of a user-shaped context is needed. v3's Apollo unit rejected contexts containing `reply`, so Apollo on Fastify with a custom `(request, reply) => ({ req: request, reply })` context answered 500 `NO_TRANSPORT` on every non-public operation while boot passed. Each unit's `validate()` instead reads `GqlModuleOptions.driver` and walks its prototype chain: a class named after the **other** framework (`Mercurius*` for `apolloTransport()`, `Apollo*` for `mercuriusTransport()`, federation and gateway drivers included) fails boot with `GRAPHQL_DRIVER_MISMATCH`; a driver it cannot identify (a custom driver, names mangled by a bundler) passes, because the user registered the unit deliberately. Registering both units therefore fails boot for one of them.
- **The context is per request** `[R4:SEC-r4-03]`. `validate()` also reads `GqlModuleOptions.context`: when it is set and is not a function, boot fails with `GRAPHQL_STATIC_CONTEXT`, hint `context: ({ req }) => ({ req, loaders: createLoaders() })`. Both drivers turn a context object into one object shared by every request, and keep the first request in its `req` (LEAD-V56): with `context: { loaders }`, v4's HTTP branch recognized Alice's request in Bob's operation, and every later caller, anonymous ones included, resolved as Alice for the life of the process (REV4-SEC:`gql/probe-static-context.mjs`). The option is typed `any`, so nothing else catches it. A context **function** that returns a cached object behaves the same and cannot be seen at boot; the HTTP branch below therefore also requires the platform's `isLive(req)`, where implemented, and a finished request fails with `BetterAuthConfigurationError.atRequest('GRAPHQL_CONTEXT_STALE_REQUEST')` (a generic 500), never with another caller's principal. That runtime check closes the case once the first request has been answered; while that request is still running, a shared context stays indistinguishable from a live one, which is why the boot check is the primary defense (RK36).
- **Carrier first, operation kind second** `[R2:SEC-r2-03]` `[R3:SEC-r3-05]`. graphql-ws executes every operation it receives, not only subscriptions (graphql-ws calls `execute` for queries and mutations: 6.0.7 `dist/server-3ewaJSjp.js:209-214` and 6.2.1 `dist/server-DHPI7HHW.js:210-215`, the versions @nestjs/graphql 13.2.4 and 14.0.0 pin), and Nest passes `execute` to `useServer` (@nestjs/graphql 13.2.4 `gql-subscription.service.js:31-36`, 14.0.0 `:17-26`); Mercurius does the same with `subscription: { fullWsTransport: true }` (`subscription-connection.js:247-266`). v2 classified by operation kind, so a query sent over a hijacked socket took the HTTP branch: its browser leg was treated as a same-origin HTTP request with `enforce` false, and its memo key was the connection-lifetime upgrade request. The transport now first decides whether **a WebSocket carries the operation**, from the context shape:
  - Apollo, Nest's default context: `context.req` is the graphql-ws context, which has `connectionParams` and `extra.request` (`apollo-base.driver.js:196-228`);
  - Apollo, a custom context that exposes the upgrade request (e.g. `({ req, extra }) => ({ req: req ?? extra?.request })`): `context.req` or `context.extra?.request` is a request whose `upgrade` header is `websocket`;
  - Mercurius: the context carries `_connectionInit` or the upgrade request `mercuriusSubscriptionContext()` stores under its `Symbol.for` key (copied into every operation's context, LEAD-V35).

  The HTTP branch is taken only on **positive** recognition: `kit.http.isRequest(context.req)` for Apollo, `kit.http.isRequest(context.reply?.request)` for Mercurius (§4.1.1), and, where the platform implements `isLive`, only for a request whose response is not yet sent (`GRAPHQL_CONTEXT_STALE_REQUEST` otherwise, see above) `[R4:SEC-r4-03]`. A context that matches neither the WebSocket shapes above nor the platform's request (for example a custom context that copies `{ headers: { cookie } }` into a plain `req` object over graphql-ws) is **not** treated as HTTP: `describe()` throws `BetterAuthConfigurationError.atRequest('GRAPHQL_CONTEXT_UNRECOGNIZED', …)` with the hint to keep the request, or the upgrade request, reachable as `context.req` or `context.extra.request` (or to use `mercuriusSubscriptionContext()`). v3 fell back to the HTTP branch for any shape it did not recognize, which gives queries `enforce: false`, so a query on a hijacked graphql-ws socket under such a context skipped the origin check and read the victim's data (SEC-r3-05). An unrecognized shape now fails closed and loudly, not open.

  **Over a WebSocket**, every operation (subscription, query or mutation) gets: credentials from the upgrade request's headers with allow-listed `connectionParams` replacing same-named ones (or `subscriptionCredentials`, whose result gets the upgrade request's `host`, `x-forwarded-host` and `x-forwarded-proto` unless it sets them: without `Host`, better-auth answers every call 500 under a dynamic `baseURL` without `fallback`, REV4-BA:`exp3-hostless-override.mjs`, T5) `[R4:BA-r4-03]`; `cookies: null` (refresh suppressed); the operation's context object as `key`; `info` as `invocation`; the upgrade request as `connection`, used only under `subscriptionPrincipalTtlMs > 0` and never for authoritative plans; and the upgrade request as the browser leg with `enforce: true`. **Over HTTP**, the operation kind decides `enforce` (mutations). Until the conformance cases for queries and mutations over graphql-ws and over Mercurius `fullWsTransport`, under both Apollo context shapes, pass (§14.1), this path is marked UNVERIFIED (RK3).

- **Over HTTP, queries and mutations share the HTTP request's principal.** The key is `kit.http.key(gql.getContext().req)`, so three root fields resolve the principal once (EXP-B:E8), and a sliding refresh on a GraphQL POST reaches the browser as `Set-Cookie`.
- **Decisions are per field** `[R1:NEST-r1-01]`. `invocation` is `gql.getInfo()` (`args[3]`). Each root field, alias and batched operation has its own `info` object, and every guard run of the same field sees the same one. `query { a: projects(orgId: "A") b: projects(orgId: "B") }` therefore evaluates the org requirement twice, with two different `fromParam('orgId')` values, while the principal is resolved once.
- **Cookie sink.** Mercurius uses `gql.getContext().reply`. Apollo on Express uses `req.res`. Apollo on Fastify uses `kit.http.responseFor(req)`, because the Apollo driver keeps only the request in its Fastify context (LEAD-V8); `FastifyPlatform.prepare` records `request.raw → reply` in a `WeakMap` from a root `onRequest` hook.
- **Lineage** `[R2:NEST-r2-06]` `[R3:NEST-r3-01]`. Each field's own result and its per-invocation values are recorded on its `info`; a federation reference resolver's are recorded on its representation, at the position `'<op>:_entities#<__typename>'` ("Federation entry points" below) `[R4:NEST-r4-01]`. `describe()` and `lineage()` supply `{ carrier: the GraphQL context (args[2]), position, enclosing }`: the position is an id of `info.operation` (assigned per carrier, because batched operations can share a context) plus the response path serialized from `info.path` (keys and list indexes, so aliases and list items are distinct), and `enclosing(args)` walks `info.path.prev` from the args' own `info`, nearest first. graphql-js resolves a field before it executes the field's selections, so every enclosing field's guard run has completed and recorded when a nested field reads (§7.8). A reader in a field resolver therefore takes its own ancestor's reading, never a sibling root field's.
- **`param(name)`** reads the resolver args first, then the route params. Claims report the `@Args('name')` names of each handler as its inputs, read from `PARAM_ARGS_METADATA`, which `@nestjs/graphql` exports (LEAD-V50) `[R3:NEST-r3-10]`.
- **Browser leg** (§7.10): over HTTP, the request (`enforce` for mutations); over a WebSocket, the upgrade request's own headers (never `connectionParams`), its absolute URL from `upgradeRequestUrl()`, and the upgrade request as the leg key (`enforce` always).
- **Denial.** `BetterAuthGraphqlDenial extends IntrinsicException` carries `extensions: { code: 'UNAUTHENTICATED' | 'FORBIDDEN' | 'RATE_LIMITED', reason?, statusCode }` `[L]`. graphql-js copies `originalError.extensions` into the formatted error (`graphql` 16 `error/GraphQLError.js:130-143`), so the code survives on both drivers. The HTTP status stays 200, the GraphQL-over-HTTP norm for field errors. LEAD-EXP-1 on Apollo showed:
  - the codes are preserved for 401, 403 **and 429**;
  - Nest logs nothing.

  The alternatives each fail somewhere. A plain `GraphQLError` (drafts A and C) is logged at ERROR on every denial, because it is not intrinsic. An `HttpException` (draft B) has its `extensions.code` rewritten by Apollo's `autoTransformHttpErrors`, so 429 becomes `INTERNAL_SERVER_ERROR` (LEAD-V8).

- **Infrastructure and configuration errors** `[R1:SEC-r1-19]`. GraphQL drivers put `err.message` into `errors[i].message`, even in production (LEAD-EXP-7), so request-time `BetterAuthConfigurationError` details would reach clients (handler and instance names, better-auth error text). Two layers prevent it. Request-time configuration errors are generic as thrown (`atRequest`, §7.8, §13.3), which covers errors raised where the guard did not run. For errors the guard catches, the GraphQL transports implement `toInternalException`, which returns `BetterAuthGraphqlInternalError`:
  - message `'Internal server error'`;
  - `extensions: { code: 'INTERNAL_SERVER_ERROR', reason: 'AUTH_UNAVAILABLE' | 'AUTH_MISCONFIGURED', statusCode: 500 }`;
  - `cause` = the original error (already redacted for infrastructure errors).

  It is not intrinsic, so Nest logs it, `[cause]` included (LEAD-V31), and the details stay in server logs. Nest's external exception handler logs every non-intrinsic error **per resolver invocation**, so 500 aliased root fields during an outage would write 500 ERROR entries for one request. When the guard reports `repeated: true` (an earlier invocation of the same request key already surfaced this error, §7.1), `toInternalException` returns `BetterAuthGraphqlRepeatedInternalError` instead: the same message and `extensions`, but intrinsic, so the outage costs one ERROR line per request `[R3:SEC-r3-08]`.

- **Field resolvers are nested and inherit** `[R2:NEST-r2-04, SEC-r2-09]` `[R3:NEST-r3-05]` `[R4:NEST-r4-01]`. Outside federation, a field resolver (`RESOLVER_PROPERTY_METADATA`, `'graphql:resolve_property'`) runs only inside an operation whose root field the guard already authorized. In a federation subgraph it may also run under `_entities`, where the enclosing decision comes from the entity type's guarded reference resolver, or, when there is none, its `inherit` plan fails with `NO_ENCLOSING_DECISION` ("Federation entry points" below, §7.1). The GraphQL transports' `defaultAccessFor` answers `'inherit'` for it, which makes it a nested handler: class-level access, acceptance and requirements on its resolver class do not apply to it (§7.6 step 3), and a field resolver **without method-level access, acceptance or requirement metadata** gets an `inherit` plan: when field guards run, the guard returns at once, with no I/O and no decision. v2 gave it `defaultAccess` instead, so the moment an app enabled `fieldResolverEnhancers: ['guards']` (the fix B16 itself suggested), every undecorated field resolver demanded authentication and every public query that traversed one failed for anonymous callers, once per list item (REV2-NEST:`exp2-field-resolver-default-access.mjs`, identical on 11.1.17/13.2.4 and 12.0.1/14.0.0: `data: null`, `UNAUTHENTICATED` at `posts.0.author`). A field resolver that declares its own access (`@RequireAuth()`, `@OptionalAuth()`, `@Public()`), acceptance or requirements **at method level** gets a real plan and is enforced per field; its guard run shares the principal memo, so only its decisions add work (one per field per item, with policy I/O deduped by inputs). `@CurrentSession()` in an inheriting field resolver reads its enclosing field's reading through the lineage (§7.8).

  **Class-level metadata reaches the operations only** `[R3:NEST-r3-05]`. `@Resolver(() => Project) @RequireOrgMember({ organization: fromParam('orgId') })` protects the class's queries, mutations and subscriptions, which carry `orgId`, and not its `tasks` field resolver, which inherits from whichever operation reached it. That is how Nest applications use class-level guards on resolvers in practice (field resolvers get enhancers only with `fieldResolverEnhancers`, whose default is `[]`), and it keeps a class-level requirement from running once per field per list item. v3 applied the class level to field resolvers: boot failed by default for that pattern, following the hint made every item answer 403 (a field resolver has no `orgId` argument), and neither `@Public()` (B15 `PUBLIC_READS_PRINCIPAL`) nor `@OptionalAuth()` (a real plan again) was an escape. A field that exposes data its operations do not authorize, such as `salary` on an `Employee` reachable from several queries, carries its own method-level requirement. The GraphQL units' `advise()` prints `I_CLASS_METADATA_OPERATIONS_ONLY` (info, once per resolver class, capped) for resolver classes that carry class-level access, acceptance or requirements and also field resolvers without method-level metadata, so the scope of each class-level declaration is visible at boot (§17 Q30, RK29).

  An inheriting field resolver is as open as the operation that reaches it. The GraphQL units' `advise()` therefore warns `W_FIELD_RESOLVER_INHERITS` when a schema has `@Public()` or `@OptionalAuth()` root fields and inheriting field resolvers, listing both (capped), with the hint to put `@RequireAuth()` (plus `fieldResolverEnhancers: ['guards']`) on a field resolver that must never be served anonymously; B22 counts inheriting handlers separately.

- **Field-resolver coverage** `[R1:NEST-r1-06, SEC-r1-10]`. `@ResolveField` resolvers get guards only when `fieldResolverEnhancers` includes `'guards'`; the default is `[]` (LEAD-V30). A method-level requirement on a field resolver is otherwise silently not enforced. For example, `@RequirePermission({ salary: ['read'] }) @ResolveField() salary()` would leak salaries to any authenticated caller who reaches an `Employee` through another query.

  The GraphQL transports' `validate()` reads the driver options with `moduleRef.get(GRAPHQL_MODULE_OPTIONS, { strict: false })` (`'GqlModuleOptions'`, exported by `@nestjs/graphql` 13 and 14) and claims handlers (§5.4 B16): root resolver methods (`RESOLVER_TYPE_METADATA`) as `'global'`, field resolvers as `'global'` when `'guards'` is present and `'none'` otherwise, with code `FIELD_RESOLVER_UNGUARDED`, the hint `fieldResolverEnhancers: ['guards', 'interceptors']` (or remove the method-level declaration so that the field resolver inherits), and severity `fieldResolverCoverage`, each with its `@Args` names as inputs. Core then fails boot for a field resolver with a real, non-public plan that no guard can reach; inheriting ones are covered by definition, and class-level metadata no longer turns a field resolver into a real plan.

- **Federation entry points** `[R4:NEST-r4-01]` `[R4:NEST decision]`. In a federation subgraph, the router's `_entities` query reaches an entity type's fields without any root resolver the guard runs for: @apollo/subgraph calls the type's `@ResolveReference()` handler once per representation, or, when the type has none, uses the representation itself as the entity, and then runs the type's field resolvers. v4 knew only root and field resolvers. A reference resolver carries neither `RESOLVER_TYPE_METADATA` at method level nor `RESOLVER_PROPERTY_METADATA`, so no unit claimed it, and it gets guards only through `fieldResolverEnhancers` (LEAD-V55): an anonymous `{ _entities(representations: [{ __typename: "User", id: "1" }]) { ... on User { email secretNote } } }` returned the data the `user(id)` query denied, while B16 passed; with field guards every representation shared one `info`, so v4's per-invocation decisions were reused across entities, and `fromParam` found no arguments (REV4-NEST:`exp1-federation-reference.mjs`). The GraphQL units now treat federation as follows, all inside the units:
  - **Reference resolvers are entry points.** A method with `RESOLVER_REFERENCE_METADATA` (imported from `@nestjs/graphql`) is never nested: `defaultAccessFor` does not answer `'inherit'` for it, so class-level access, acceptance and requirements and `defaultAccess` apply. `validate()` claims it with `everyHandler`, as `'global'` when `fieldResolverEnhancers` includes `'guards'` and `'none'` otherwise, code `REFERENCE_RESOLVER_UNGUARDED`, hint "`fieldResolverEnhancers: ['guards', 'interceptors']`, or `@Public()` on the reference resolver", severity `federationCoverage`.
  - **Federation subgraphs need field guards.** When the driver's class chain names a federation driver, or any handler carries `@ResolveReference()`, and the schema has field or reference resolvers, `validate()` requires `fieldResolverEnhancers` to include `'guards'` (`FEDERATION_FIELD_GUARDS_REQUIRED`, severity `federationCoverage`): only a guard run can tell, at request time, that a field resolver under `_entities` has no authorized entry point (below). `'warn'` suits a subgraph that only an authenticating router can reach, which the library cannot observe (§17 Q36, RK34).
  - **Each representation is an invocation.** For a reference resolver, `describe()` takes the representation (`gql.getRoot()`; `GqlExecutionContext` normalizes @apollo/subgraph's three-argument call, and the Mercurius federation driver passes four) as `invocation`, so each entity gets its own decisions (T7), and `param(name)` reads the representation's fields. Param factories, which get raw arguments, apply the same normalization.
  - **Positions per entity type.** A reference resolver records its reading at `'<op>:_entities#<__typename>'`, and `enclosing(args)` of a field under `_entities.N` yields that position, taken from the `typename` of the path entry below the list index, before `'<op>:_entities'`. Representations of one type share the position and the plan, so their readings are identical (T6); two types in one `_entities` call never share one.
  - **No entry point, no data.** A field resolver of an entity type that has no reference resolver runs under `_entities` with no enclosing reading. Its `inherit` plan then fails with `NO_ENCLOSING_DECISION` (§7.1) instead of serving `@Parent()` data built from attacker-chosen representations; a field resolver with its own method-level access is judged on its own plan. The error names the type and the hint "add a guarded `@ResolveReference()` for this type, or declare access on the field resolver".
  - **Advice.** `W_FIELD_RESOLVER_INHERITS` counts `@Public()` and `@OptionalAuth()` reference resolvers as public entry points.

  Mercurius federation is **UNVERIFIED at runtime** (RK3); `T-reference-resolver` pins both drivers before 1.0.

- **Versions.** `@nestjs/graphql` 13 serves Nest 11 and 14 serves Nest 12. Version 14 removed `subscriptions-transport-ws`, so only `graphql-ws` is supported.

### 9.3 WebSockets: socket.io and ws (`./websockets`)

**Credentials:**

- **socket.io** `[A][B][C]` takes them from `client.handshake.headers`. The handshake is an HTTP request, so it carries cookies for same-site browsers or with `withCredentials`. Then `credentials(client)` supplies more and **replaces** same-named headers, for example `handshake.auth.token` → `authorization: Bearer <token>` for the `bearer()` plugin. The default mapping copies `handshake.auth.token` when no `authorization` header exists. The mapping feeds the principal sources only; the browser leg of the origin check stays the handshake's own headers (§7.10) `[R2:SEC-r2-01]`.
- **ws** `[B][C]` has a problem: the bare `WebSocket` has no headers, and the upgrade request is passed only to the `connection` event (`@nestjs/platform-ws` `adapters/ws-adapter.js:144`). `withUpgradeRequest(Base)` is a mixin over any `WsAdapter` subclass. It overrides `bindClientConnect(server, cb)` and records `{ headers: toWebHeaders(request.headers), url, remoteAddress, encrypted }` on the client under `UPGRADE_REQUEST` before delegating. A mixin composes with users' own adapters (Redis, custom) and needs no `@nestjs/platform-ws` import. Custom adapters call `recordUpgradeRequest(client, request)` directly.

  ```ts
  app.useWebSocketAdapter(new (withUpgradeRequest(WsAdapter))(app)); // main.ts
  ```

  A guarded message from a client without a recorded request throws `BetterAuthConfigurationError`, which includes this snippet.

**Origin check: Cross-Site WebSocket Hijacking** `[R1:BA-r1-03, SEC-r1-01]`. Browsers attach cookies to WebSocket upgrades, and CORS does not apply to them. A malicious page can open `new WebSocket('wss://api.example.com/socket.io/?EIO=4&transport=websocket')`, the victim's cookie authenticates the socket, and the page reads every reply. The browser leg is the handshake (socket.io `handshake.headers` and `handshake.url`; ws the recorded upgrade request), and `enforce` is always true. Every message on a socket whose handshake carried a cookie is therefore allowed only if the handshake's `Origin` is trusted by better-auth (§7.10), whatever `handshake.auth` holds: a cross-site page that adds a junk `auth.token` no longer switches the check off while the victim's cookie authenticates (REV2-SEC:`probe-origin-bearer-exempt.mjs`) `[R2:SEC-r2-01]`. Sockets whose handshake carries no cookie (native and server clients with tokens) are unaffected. The verdict is computed once per socket, from an absolute URL built with `upgradeRequestUrl()` (socket.io `handshake.secure` and `handshake.url`; ws the recorded `encrypted` flag and `url`) `[R2:SEC-r2-05]`.

**Memo, revalidation and decorators.**

- `principalTtlMs: 0` is the default `[A][C]`. Each guarded message resolves once, memoized across the guards of that message through the shared `args` array (LEAD-V7). With the session source this adds no writes, because refresh is suppressed. Sources that consume quota or write per resolution (`effects`, for example `apiKeyPrincipal()`, which writes the usage counter) verify on every message. The WS units' `advise()` warns `W_QUOTA_PER_MESSAGE` when such a source is registered and `principalTtlMs` is 0, and recommends connection-time authentication plus a TTL `[R1:SEC-r1-14]`.
- `principalTtlMs > 0` caches **authenticated and absent** results per socket (`call.connection`) for chat-style traffic. Rejections and infrastructure failures are never cached on the socket (§7.2). Handlers with authoritative freshness (`@RequirePermission`, `@RequireAuth({ authoritative: true })`) never use the TTL, so a banned admin loses admin access on the next message `[R2:SEC-r2-07]`. Decisions are always per message, so a socket that joined org A cannot reuse that allow to join org B `[R1:NEST-r1-01]`. The docs state the revocation delay a TTL implies for other handlers.
- Param decorators read the resolution from the scope interceptor. The socket is deliberately **not** used as a carrier, because concurrent messages on one socket would race (§7.8).

**Guard behavior by Nest major** (LEAD-V6, LEAD-V29, R:nest-di §3.4 runtime table):

|                                                            | Nest 11 | Nest 12                                                 |
| ---------------------------------------------------------- | ------- | ------------------------------------------------------- |
| `APP_GUARD` runs for `@SubscribeMessage` handlers          | **no**  | yes                                                     |
| `APP_INTERCEPTOR` wraps them                               | **no**  | yes                                                     |
| An `HttpException` thrown by a guard reaches the client as | n/a     | `{ status: 'error', message: 'Internal server error' }` |
| Global exception filters apply to gateways                 | no      | no                                                      |

**Design consequences** `[C]` `[R1:NEST-r1-13, SEC-r1-12]`:

1. The WS transports always throw `WsException({ status: 'error', statusCode, code, reason, message })` themselves. `BaseWsExceptionFilter` emits an object payload as-is, and filters never reach gateways (R:nest-di §5.2).
2. **Every gateway needs `@UseBetterAuth()` (or `@Public()`), on both majors.** v1 skipped the requirement on Nest 12 through a capability probe (`AbstractHttpAdapter.prototype.mapException`). That API belongs to `@nestjs/core`, while the behavior is decided by `@nestjs/websockets` (`getContextCreator(container)` on 11.1.17 vs `getContextCreator(container, config, …)` on 12.0.1, LEAD-V29). The probe could therefore report "covered" for a skewed install (core 12 with websockets 11), or for an 11.x release that backported the HTTP API, and leave every gateway open. A probe of `@nestjs/websockets` itself would need a deep import of an unexported module whose specifier differs between the two majors' packaging. v2 dropped the probe. The WS transports' `validate()` enumerates gateway classes through Nest's `'websockets:is_gateway'` class metadata (LEAD-V13) and their message handlers through `'websockets:message_mapping'` method metadata (neither re-exported from the package root, LEAD-V42; both checked by a canary at boot and pinned by a CI test on both majors), and **claims** every message handler as `'explicit'` with `everyHandler`, code `GATEWAY_UNGUARDED` and severity `gatewayCoverage` (§5.4 B16) `[R2:NEST-r2-02, NEST-r2-12]`. Core then fails boot for any handler that has neither `@Public()` nor `@UseBetterAuth()` at class or method level, with the hint: "Add @UseBetterAuth() to ChatGateway (or @Public() to opt out). Global guards and interceptors do not reach gateways on NestJS 11, and this check does not depend on the version."
   - **Guard and interceptor.** An `'explicit'` claim is covered only by `@UseBetterAuth()` or by both `@UseGuards(BetterAuthGuard)` and `@UseInterceptors(BetterAuthScopeInterceptor)`. v2 accepted `@UseGuards(BetterAuthGuard)` alone; on Nest 11 no global interceptor reaches a gateway and WS has no carrier, so `@CurrentSession()` threw `NO_AUTH_RESULT` on every message, and direct `auth.api` calls in the handler slid the session without suppression (NEST-r2-11). The literal `'__interceptors__'` is pinned next to `'__guards__'` (§12.4).
   - **A renamed key cannot pass vacuously** `[R2:NEST-r2-12]` `[R3:NEST-r3-08]`. Before they enumerate, the WS units run a canary: they apply `@WebSocketGateway()` and `@SubscribeMessage('probe')` from the installed `@nestjs/websockets` to a private probe class and read `'websockets:is_gateway'` and `'websockets:message_mapping'` back. A mismatch fails boot with `NEST_METADATA_KEY_CHANGED` (B16). A gateway without message handlers is then genuinely one, such as a push-only gateway that only emits through `@WebSocketServer()`, and is not claimed. v3 claimed the class of any gateway with non-lifecycle methods and no discovered handler, so `NotificationsGateway { notifyUser() {} }` failed boot with `GATEWAY_UNGUARDED` and a misleading hint, and the workaround inflated the public count.

   On Nest 12 with a global guard the second guard run is a memo hit, with no extra I/O and no log line.

3. **Connection-time authentication** `[B]` `[R1:NEST-r1-12]`. Guards never run on connect (`handleConnection` is never guarded). The socket.io and ws definitions provide `WsConnectionAuth` and export it under `WS_CONNECTION_AUTH` (`ExtensionDefinition.exports`, re-exported globally by the default `forRoot`). It reuses the transport's credential mapping, applies the origin check to the handshake, resolves with refresh suppressed, and caches authenticated/absent results on the client for `principalTtlMs`. It takes an `instance` option for named instances:

   ```ts
   @WebSocketGateway()
   @UseBetterAuth()
   export class ChatGateway implements OnGatewayInit, OnGatewayConnection {
     constructor(
       @Inject(WS_CONNECTION_AUTH) private readonly wsAuth: WsConnectionAuth,
     ) {}
     afterInit(server: Server) {
       server.use(this.wsAuth.socketIoMiddleware({ required: true }));
     } // socket.io
   }
   // ws: async handleConnection(client) {
   //   const r = await this.wsAuth.authenticate(client);
   //   if (r.outcome !== 'authenticated') client.close(r.outcome === 'rejected' ? wsCloseCodeFor(r.failure) : 4401, 'UNAUTHENTICATED');
   // }
   ```

4. **`param(name)`** reads `switchToWs().getData()?.[name]`.

### 9.4 Microservices / RPC (`./microservices`) `[A][B][C]`

RPC messages have no cookies of their own and no browser leg; credentials travel in transport metadata. `rpcTransport({ carriers })` handles every `'rpc'` context. Its `describe()` uses the first carrier whose `matches(ctx)` is true (default: `defaultCarriers`); when none matches, the message carries no credentials: `headers()` returns empty `Headers`, a required handler answers 401 `UNAUTHENTICATED`, and a public one runs. v2 made a carrier match part of `handles()`, so a credential-less TCP or Redis message (no `auth` object in the payload) answered 500 `NO_TRANSPORT`, public handlers included (NEST-r2-03) `[R2:NEST-r2-03]`:

| Carrier                             | Matches                                                             | Credential source (headers copied into `Headers`)                                                                                                                                                 |
| ----------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `grpcCarrier()`                     | `getArgByIndex(1)` is a gRPC `Metadata` (duck-typed `get`/`getMap`) | metadata entries (`authorization`, `cookie`, `x-api-key`)                                                                                                                                         |
| `natsCarrier()`                     | the context has `getHeaders()`                                      | NATS message headers                                                                                                                                                                              |
| `kafkaCarrier()`                    | the context has `getMessage().headers`                              | Kafka headers (Buffer values decoded as UTF-8)                                                                                                                                                    |
| `rmqCarrier()`                      | the context has `getMessage().properties`                           | `properties.headers`                                                                                                                                                                              |
| `mqttCarrier()`                     | the context has `getPacket()`                                       | MQTT 5 `userProperties` (MQTT 3 has no headers)                                                                                                                                                   |
| `payloadCarrier({ field: 'auth' })` | the payload has an object at `field`                                | `data.auth` (TCP and Redis carry no headers). The docs warn this is weaker: credentials are visible to every hop. A primitive payload or one without the field matches no carrier: no credentials |

- **Credentials** are ordinary better-auth credentials: `authorization: Bearer <session token>` with the `bearer()` plugin, a `cookie` header, or `x-api-key`. `getSession` and `apiKeyPrincipal()` work unchanged (keys still need a route that accepts `'api-key'`, §7.6). Forwarding browser cookies between services is discouraged.
- **Memo key, invocation and carrier:** `switchToRpc().getContext()`, one object per message. **Cookies:** `null`, so refresh is suppressed. **Browser leg:** none, so the origin check never applies: no browser can send an RPC message. **No `Host`:** carriers copy no host, so every `auth.api` call made for an RPC message is host-less; the unit declares `requires.hostlessCalls`, and a dynamic `baseURL` without `fallback` fails boot (B20) instead of answering 500 per message `[R2:BA-r2-05]`.
- **Denial:** `new RpcException({ status: 'error', statusCode, code, reason, message })`. `BaseRpcExceptionFilter` passes an `RpcException` object through as-is and turns anything else into "Internal server error".
- **gRPC:** the carrier's `toException` returns `RpcException({ code: 16 | 7 | 8, message })` (UNAUTHENTICATED, PERMISSION_DENIED, RESOURCE_EXHAUSTED). On Nest 12, if `@nestjs/microservices` exports `GrpcUnauthenticatedException` / `GrpcPermissionDeniedException`, the carrier uses them. That is feature-detected by export presence inside the RPC unit, not in core. **UNVERIFIED at runtime** on Nest 11 (grpc-js reads `code` from the error object).
- **Guard registration and hybrid coverage** `[R1:NEST-r1-05, SEC-r1-09]` `[R2:NEST-r2-02, NEST-r2-11]`. Standalone microservices (`createMicroservice`) apply `APP_GUARD`. A hybrid app's `connectMicroservice(options)` gets a **fresh** `ApplicationConfig` unless `{ inheritAppConfig: true }` is passed (LEAD-V32), so without it `APP_GUARD` never runs for `@MessagePattern`/`@EventPattern` handlers and any publisher can invoke them unauthenticated. The RPC transport's `validate()` claims every message and event handler, found through `'microservices:pattern'` method metadata (not re-exported from the package root, LEAD-V32; checked at boot by a canary that applies `@MessagePattern('probe')` to a private probe class, and pinned by a CI test on both majors), and core's coverage rule makes this fail closed (§5.4 B16):
  - without an HTTP adapter (a standalone microservice), or when the user asserts `rpcTransport({ inheritAppConfig: true })`, handlers are claimed `'global'`;
  - with an HTTP adapter and no assertion, they are claimed `'explicit'` with `everyHandler`, code `RPC_HANDLER_UNGUARDED` and severity `hybridCoverage`: every handler needs `@UseBetterAuth()` (guard and interceptor, so direct calls in the handler get refresh suppression) or `@Public()`;
  - the unit cannot observe `connectMicroservice` itself, so the assertion is the user's. Its `advise()` prints what the assertion means at every boot (RK22);
  - an app that **forgot** `rpcTransport()` in a hybrid app has nobody claiming its message handlers: any of them whose metadata is on B16's trigger list fails boot with core's `UNGUARDED_AUTH_METADATA`, naming the registered transports (NEST-r2-02);
  - duplicate guard runs (global plus `@UseBetterAuth()`) are memo hits. `'warn' | 'off'` relaxes the transport's own check.
- **`param(name)`** reads `switchToRpc().getData()?.[name]`.
