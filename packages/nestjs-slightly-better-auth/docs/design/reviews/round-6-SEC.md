# Round 6 review: SEC (security / SRE)

Input: `design-v6.md`. Verdict: **reject**.

Experiments: `/tmp/nsba/tmp-r6-review-SEC/` (better-auth 1.7.4, `NODE_ENV=production`, `TEST` unset, `advanced.disableOriginCheck: false`, static `baseURL`, memory adapter). Probe outputs are saved as `*.out` next to each script. Source re-reads this round: `BA/api/middlewares/origin-check.ts:67-77, 219-290`, `BA/api/index.ts:275-295`, `BA/context/helpers.ts:23-96`, `BA/auth/base.ts:30-110`, `BA/context/create-context.ts:260-300`.

## Summary

v6 closes all three round-5 SEC findings, and two of them by widening a mechanism rather than patching it. The scope interceptor is now registered by the default instance whatever `globalGuard` says, with a lazy `reading`, a `globalScope: false` opt-out, B31's `W_NO_GLOBAL_SCOPE` and a B22 line (SEC-r5-01); the caller-session check is keyed on the plan instead of `browser.enforce` and compares the call's token against the union of the scope's inbound headers and the leg's own (SEC-r5-02); `HttpRequestAccessor.isLive` is required and the Hono sketch implements it (SEC-r5-03). I re-verified the trusted-origin merge §7.10 step 3 performs against better-auth's own per-request recomputation (`base.ts:97` recomputes `handlerCtx.trustedOrigins` from the **post-init** options for every router request, so merging `ctx.trustedOrigins` with the post-init array is a faithful mirror, not a widening) and found no divergence.

Two new majors, both consequences of the two widenings.

**SEC-r6-01.** The caller-session check's third pass condition — "the guard resolved the principal for this invocation" — has no origin verdict behind it on a **safe method**, because §7.10 item 2 gates the whole origin check on `browser.enforce`, which is false for GET/HEAD/OPTIONS. So `@OptionalAuth() @Get('logout') { auth.api.signOut({ headers: headersFrom(req) }) }` runs as the victim for `<img src>` — and `@OptionalAuth()` is exactly what the `PUBLIC_HANDLER_USED_CALLER_SESSION` hint, RK32 ("the fix is one decorator") and §17 Q37 tell the developer to add when v6's new `@Public() @Get()` rule fires. v6 closed the GET hole for public plans and left the documented remedy open. §14.4 pins the hole as expected behavior ("the same call from a `@RequireAuth() @Get()` route succeeds"). Reproduced on 1.7.4 (`probe-guarded-get-proxy.out`): the guard's `getSession` resolves the victim from an `<img>`-shaped request (`Cookie`, no `Origin`, `Sec-Fetch-Site: cross-site`), and `signOut` on those same headers leaves 0 session rows.

**SEC-r6-02.** Making the scope interceptor unconditional also made `AuthTransport.describe()` run for `public` and `inherit` plans, which §7.1 and ADR-55 deliberately keep away from transport selection. `describe()` is allowed to throw a request-time configuration error, and two shipped transports do: the `ws` transport when no upgrade request was recorded (§9.0 table), and both GraphQL transports with `GRAPHQL_CONTEXT_UNRECOGNIZED` / `GRAPHQL_CONTEXT_STALE_REQUEST`. A `@Public()` message handler on a gateway that did not install `withUpgradeRequest` therefore answers a 500 through the interceptor although §9.3 promises the error only for a **guarded** message, and no boot check can catch it because `useWebSocketAdapter()` runs after `onModuleInit`. That reintroduces the class of failure `@Public()` exists to prevent (reference issue #159, cited in §7.6).

One minor: `LIB-coverage-rule` (§14.5) still specifies the pre-v6 coverage test ("covered when `BetterAuthGuard` **and** `BetterAuthScopeInterceptor` appear among the global enhancers … and not when only the guard does"), the exact rule B16 says it replaced and whose failure mode B16 names.

Checked and not raised:

- **The trusted-origin merge is not a widening.** §7.10 step 3 merges `ctx.trustedOrigins` with the post-init `ctx.options.trustedOrigins`. better-auth's `validateOrigin` uses `ctx.context.trustedOrigins` when the option is an array — but `auth.handler` replaces that field per request with `getTrustedOrigins(ctx.options, request)` computed from the **post-init** options (`base.ts:75-100`), and `runPluginInit` folds plugin-contributed static origins into `options.trustedOrigins` (`helpers.ts:62-83`). The two sets agree.
- **`Origin: null` inference.** The kernel mirrors `origin === "null" && sec-fetch-site === "same-origin"` (`origin-check.ts:252-262`). A client that can forge `Sec-Fetch-Site` can forge `Origin`, so the inference adds no reachable exemption.
- **`carriesInboundSession` keys on the session-token cookie only.** `getSessionFromCtx` needs that cookie before it will read `session_data`, so a cookie-cache-only request authenticates nothing; there is no second ambient cookie the check would miss.
- **`@ForwardAuthCookies()` on a safe method** gets no origin check either (§7.10 item 2 gates `'form'` mode too), but a _public_ forwarding GET still fails closed, because neither a verdict nor a guard resolution exists. Only the `@OptionalAuth()`/`@RequireAuth()` branch is open; that is SEC-r6-01, not a second finding.
- **`W_ORG_PARAM_MISSING`, the API-key outage probe, `cacheAllRoles` (RK37) and the hourly origin-denial window** are unchanged from v5 and still hold; the window's per-reason closing summary still surfaces a misconfiguration behind 100 attacker-chosen pairs.

## Findings

### SEC-r6-01 (major): The caller-session check passes on a _safe method_ whenever the guard resolved a principal, although no origin check ran there — and `@OptionalAuth()`, the fix the check's own hint recommends, is what turns the check off

- **Section:** §7.5 ("No direct call acts with the caller's session on an unverified leg", pass condition 3 and the throw's hint); §7.10 "When it applies" item 2 (`browser.enforce`: "HTTP: methods other than GET/HEAD/OPTIONS"); §9.1 "Origin check" ("Safe methods never do"); §10.2 `ScopeView.checkCallerSession`; §14.4 (the v6 GET row); §17 Q37; RK32; ADR-70.
- **Failure scenario:** A team runs the v6 library and has the logout proxy the reference library's users commonly have. v6's new rule fires on it:

  ```ts
  @Public() @Get('logout')
  logout(@Req() req) { return this.auth.api.signOut({ headers: this.auth.headersFrom(req) }); }
  ```

  1. First request: `PUBLIC_HANDLER_USED_CALLER_SESSION`, a generic 500, logged with the hint §7.5 specifies verbatim: _"use `@OptionalAuth()` (the guard then checks the origin before resolving) or `@ForwardAuthCookies()` for a login or logout proxy"_. RK32 repeats it ("the fix is one decorator") and §17 Q37's decided answer names the same two decorators.
  2. The developer does what the hint says and changes `@Public()` to `@OptionalAuth()`.
  3. The parenthetical is **false on a safe method**. §7.10 item 2 is a conjunct of "when it applies": with `browser.enforce === false` for GET, the guard runs **no** origin check and memoizes **no** verdict. It does resolve the principal, so §7.5's third pass condition — "the guard resolved the principal for this invocation — a `required` or `optional` plan the guard ran, whatever its outcome" — holds, `checkCallerSession` returns, and the direct call proceeds.
  4. `https://evil.example` serves `<img src="https://api.example.com/account/logout">`. The browser attaches the victim's `sameSite: 'none'` cookie (or the page is on a sibling subdomain, SEC-r1-01), sends no `Origin`, and `Sec-Fetch-Site: cross-site`. `auth.api.signOut` runs as the victim: forced logout, and with `revokeSessions` every device. The same shape with `unlinkAccount`, `acceptInvitation` or `deleteUser` on a GET route changes account state.

  The same holds for `@RequireAuth() @Get()`, which §14.4 pins explicitly as _expected_: "the same call from a `@RequireAuth() @Get()` route succeeds". So the design documents the hole as a test assertion.

  This is not the SEC-r5-02 scenario re-reported: v5's gap was that the check was **absent** on safe methods for public plans, and v6 closed that. The new gap is that the check is **present and passes** on safe methods for guarded plans, through a condition v6 introduced, and that the library's own remediation text moves handlers from the first state into the second. §7.5's justification — "on a safe method the caller's own credential is what the guard itself just read" — conflates "the guard read the session" with "the request is not cross-site". Reading a cookie proves the browser sent it; it proves nothing about which page caused the request, which is the entire content of the origin check.

  better-auth's own router skips safe methods too (`origin-check.ts:67-77`), and that is sound **for better-auth**, because it exposes no state-changing endpoint over GET. This design hands app handlers `headersFrom(req)` and lets them call any endpoint from any method — §7.5 says so itself when it justifies closing the public GET case. The justification applies unchanged to the guarded GET case.

- **Evidence:**
  - `probe-guarded-get-proxy.mjs` / `.out` (better-auth 1.7.4, `NODE_ENV=production`, `TEST` unset, `advanced.disableOriginCheck: false`, static `baseURL`, `trustedOrigins: ['https://app.example.com']`), with the exact `<img>` header shape (`cookie`, no `origin`, `sec-fetch-site: cross-site`, `sec-fetch-mode: no-cors`, `sec-fetch-dest: image`):
    - `[router] GET /get-session cross-site -> 200 (origin check skipped for GET by design)`;
    - `[guard @OptionalAuth @Get] resolved principal -> user victim@example.com` — pass condition 3 holds;
    - `[handler] auth.api.signOut(headersFrom(req)) -> {"success":true} | sessions left: 0`.
  - `BA/api/middlewares/origin-check.ts:67-77`: `originCheckMiddleware` returns before `validateOrigin` for `GET`, `OPTIONS` and `HEAD`, so no verdict can exist for a safe method on any path.
  - Design text: §7.10 "When it applies" item 2, "The transport exposes a browser leg (`call.browser`), and `call.browser.enforce` is true: HTTP: methods other than GET/HEAD/OPTIONS"; §7.5 pass condition 3 and the hint string; §14.4 "while the same call from a `@RequireAuth() @Get()` route succeeds"; RK32 "the fix is one decorator"; §17 Q37 recommendation "(a) fail closed: throw `PUBLIC_HANDLER_USED_CALLER_SESSION` … with the hint `@OptionalAuth()` or `@ForwardAuthCookies()`".
- **Suggested fix:**
  1. **Make the third pass condition require a verdict, not a guard run.** Change it to: the guard resolved the principal **and** the origin check applied to this leg (`browser.enforce` was true) and passed. On unsafe methods nothing changes — a guarded unsafe request always has a passing verdict, or the guard already denied it — so no existing guarded route gains a denial there.
  2. **Give safe methods an advisory verdict so the second condition can cover them.** In the guard, when the plan's origin check is not `'off'`, the browser leg carries a cookie and `enforce` is false, compute and memoize the same verdict **without denying the request** (the request itself stays allowed, exactly as today; only `checkCallerSession` reads the result). Cost: one memoized comparison per safe request that carries a cookie, on the same code path §7.10 already has, and one entry in the existing `(browser.key, instance, mode)` memo. A guarded GET from a trusted origin then still passes; the cross-site `<img>` fails closed with `PUBLIC_HANDLER_USED_CALLER_SESSION`, which is the SEC-r4-02 contract.
  3. **Correct the remediation text.** The hint must not claim that `@OptionalAuth()` makes the guard check the origin: on a safe method it does not. Name the working fixes for a logout proxy: make it a POST (better-auth's own `/sign-out` is a POST), or `@SkipOriginCheck()` where the route deliberately serves server-to-server callers. Correct RK32's "the fix is one decorator" and §7.10's "Safe methods never do" with a pointer to the advisory verdict.
  4. **Tests.** Replace §14.4's assertion "the same call from a `@RequireAuth() @Get()` route succeeds" with its opposite for a cross-site request and keep it for a trusted-origin one, and add an `@OptionalAuth() @Get()` row to `LIB-public-direct-call` (cross-site `<img>` shape → generic 500, sessions intact; trusted `Origin` → succeeds).

### SEC-r6-02 (major): The now-unconditional scope interceptor calls `describe()` for `public` and `inherit` plans, so a transport that cannot describe the context turns a `@Public()` handler into a 500 — the failure mode ADR-55 and `@Public()` exist to prevent

- **Section:** §7.5 step 1 and the `intercept` snippet (`this.scopes.forExecution(ctx)`, "null when no transport handles ctx, or a scope is already open"); §5.7 "Scope registration is independent of the guard"; §7.1 (the guard's `public` and `inherit` branches use `transports.find(ctx)` and only `lineage()`, never `describe()`); §9.0 matrix, `ws` row ("`describe` throws a configuration error with the `withUpgradeRequest` snippet when none is recorded"); §9.3 ("A **guarded** message from a client without a recorded request throws"); §9.2 (`GRAPHQL_CONTEXT_UNRECOGNIZED`, `GRAPHQL_CONTEXT_STALE_REQUEST` thrown from `describe()`); §7.6 ("`@Public()` doing zero I/O fixes reference issue #159"); ADR-55; ADR-70.
- **Failure scenario:** A gateway with mixed access, on either Nest major:

  ```ts
  @WebSocketGateway() @UseBetterAuth()            // B16 satisfied at class level
  export class FeedGateway {
    @Public() @SubscribeMessage('ticker') ticker(@MessageBody() d) { return this.prices.latest(d.symbol); }
    @SubscribeMessage('portfolio') portfolio(@CurrentSession() s) { … }
  }
  ```

  The app uses `@nestjs/platform-ws` and `main.ts` does **not** wrap the adapter with `withUpgradeRequest`.

  1. Boot passes. B16 is satisfied (`@UseBetterAuth()` on the class), no boot check can see the WebSocket adapter at all: `app.useWebSocketAdapter()` runs in `main.ts`, after `NestFactory.create()` has resolved and therefore after the core module's `onModuleInit` (§5.7 step 1).
  2. A `'ticker'` message arrives. `@UseBetterAuth()` applies the interceptor (and on Nest 12 the global one does too), so `BetterAuthScopeInterceptor.intercept` runs `forExecution(ctx)`. `wsTransport().handles()` is true (a `'ws'` context whose client has no `handshake`), so the interceptor proceeds to step 1, "selects the transport and builds `call` (sync)".
  3. `describe()` needs the recorded upgrade request to build `call.headers` **and** `call.browser` — `browser.url` is a value, not a thunk (§2.2 `TransportCall.browser.url`, "Absolute URL of the leg"), built by `upgradeRequestUrl()` from the recorded request. There is none, so `describe()` throws `BetterAuthConfigurationError`. §7.5's `intercept` has no `catch`.
  4. Every `'ticker'` message — a handler that declares `@Public()` precisely to say "this needs no authentication" — answers a 500 / `WsException`. §9.3 promised the error only for a _guarded_ message; §9.0's table says `describe` throws unconditionally. The two statements disagree, and under the v6 interceptor the stricter one wins.

  The same shape reaches GraphQL: a `@Public()` query resolver in an app whose custom `context` the unit cannot classify gets `GRAPHQL_CONTEXT_UNRECOGNIZED` from the interceptor although the guard returned at §7.1's public branch without ever selecting a transport. And a `@Public()` field resolver with an `inherit` plan under `fieldResolverEnhancers: ['guards','interceptors']` and a context function that cached its object gets `GRAPHQL_CONTEXT_STALE_REQUEST` — a defense against reading _another caller's principal_, applied to a handler that reads no principal at all.

  This is a regression of a principle the design states twice. ADR-55 moved the public branch ahead of transport selection exactly because "a `@Public()` handler in a context no transport serves … answered 500 `NO_TRANSPORT`" (NEST-r2-03), and §7.6 sells `@Public()` with "health probes no longer return 500 when the database is down". The v6 interceptor puts a second, unguarded transport-dependent step in front of every handler, including the ones the guard is careful to leave alone. Before v6 the blast radius was `globalGuard: true` apps only; v6 extends it to every app, and to `globalGuard: false` apps whose handlers carry `@UseBetterAuth()`.

  Operationally the worst part is that nothing reports it at boot and the symptom is a generic 500 on the one handler class the operator believes cannot fail.

- **Evidence:**
  - §7.5, the `intercept` body verbatim: `const scope = this.scopes.forExecution(ctx);` with the comment "null when no transport handles ctx, or a scope is already open" — no third case, and no error handling. Step 1: "It selects the transport and builds `call` (sync)", unconditionally, before the plan's access is consulted (the plan is only read in step 2, for `forward` and `reading`).
  - §7.1, the guard, for contrast: the `inherit` branch uses `transports.find(ctx)` and calls `describe()` **only** on the failure path; the `public` branch calls `transports.find(ctx)?.lineage?.(ctx)` and never `describe()`, with the comment "no transport handles ctx → nothing to record; never an error".
  - §9.0 matrix, `ws` row, Credentials column: "recorded upgrade headers (`describe` throws a configuration error with the `withUpgradeRequest` snippet when none is recorded)", against §9.3: "A **guarded** message from a client without a recorded request throws `BetterAuthConfigurationError`, which includes this snippet."
  - §9.2: "`describe()` throws `BetterAuthConfigurationError.atRequest('GRAPHQL_CONTEXT_UNRECOGNIZED', …)`" and "a finished request fails with `BetterAuthConfigurationError.atRequest('GRAPHQL_CONTEXT_STALE_REQUEST')`".
  - §5.7 step 1 and the §9.3 `main.ts` snippet (`app.useWebSocketAdapter(new (withUpgradeRequest(WsAdapter))(app))`) together show that no boot check can observe the adapter: `prepare()` and `onModuleInit` both run inside `NestFactory.create()`.
  - §7.6, §9.4 and ADR-55 for the principle: `@Public()` performs no auth I/O and must not fail for auth-infrastructure reasons.
- **Suggested fix:**
  1. **The interceptor must not open a scope it cannot build.** Make `forExecution(ctx)` read the plan first, exactly as the guard does, and:
     - for a `public` plan whose origin check is `'off'`, and for an `inherit` plan, skip the scope entirely (there is no `checkCallerSession` to supply and no reading to hold that the readers cannot fetch themselves through the lineage);
     - otherwise, wrap `describe()` and, when it throws a `BetterAuthConfigurationError`, **log it once per request key at WARN and run the handler without a scope** for a `public` plan, while keeping the throw for every plan the guard also resolves. A public handler then behaves as it did before v6 (plain better-auth semantics for direct calls, which is what `runOutsideScope` gives anyway), and the diagnostic still reaches the operator.
  2. **Or make `describe()` non-throwing for the parts a public plan needs.** Add to the transport contract (§4.2, invariant T-series) that `describe()` must not throw for a context its own `handles()` accepted: it returns `headers: () => { throw … }` and `browser: undefined` when the transport cannot build them. The `ws` transport then degrades to "no credentials, no browser leg" without a recorded upgrade request — a guarded message still fails closed at the guard with the existing `withUpgradeRequest` error (a required plan with empty headers resolves `absent` → 401, so raise it in `headers()`), a public one runs, and §9.3's "a **guarded** message … throws" becomes true as written. Do the same for the GraphQL units: `GRAPHQL_CONTEXT_UNRECOGNIZED` and `GRAPHQL_CONTEXT_STALE_REQUEST` are thrown from `headers()` / `browser`, so they still fail closed for every plan that reads an identity and stay invisible to a plan that does not.
  3. **Reconcile the two statements.** Whichever option is taken, §9.0's `ws` row and §9.3 must say the same thing, and §7.5's "Coverage gaps, documented" should state what a public handler gets when its transport cannot describe the context.
  4. **Tests.** Add to `T-public-unclaimed-context` a sibling case: a `@Public()` `ws` message handler on an adapter without `withUpgradeRequest` runs and returns its payload, while a guarded handler on the same socket answers the configuration error; and a `@Public()` GraphQL query under a context shape the unit cannot classify runs, while a guarded one answers the generic 500.

### SEC-r6-03 (minor): `LIB-coverage-rule` still specifies the pre-v6 coverage test — "covered … and not when only the guard does" — which is the rule B16 says it replaced and whose failure mode B16 names

- **Section:** §14.5 `LIB-coverage-rule`; §5.4 B16 ("**Coverage keys on the guard alone since v6**"); §5.4 B31; §5.7 "Scope registration is independent of the guard".
- **Failure scenario:** The implementer writes the tests from §14.5 and the rule from §5.4, which contradict each other, and the tests are the executable spec.

  `LIB-coverage-rule` says: "a `'global'` claim is covered when `BetterAuthGuard` **and** `BetterAuthScopeInterceptor` appear among the global enhancers however they were registered, **and not when only the guard does**". Only the later "Since v6" sentence mentions B31, and it does not retract that sentence.

  B16 says the opposite, and names the consequence of the old wording: "under `globalScope: false` with `globalGuard: true` the old wording would have failed boot with `ROUTE_UNGUARDED` for **every** claimed handler while B31 and §5.7 promise a warning. `globalScope: false` therefore has exactly one severity, B31's _warn_."

  An implementation that satisfies the test as written makes `globalScope: false` a boot error for every claimed route in the application — the documented escape hatch becomes unusable, and the boot failure names `ROUTE_UNGUARDED`, which points at the guard the app does have. Since `globalScope: false` is the option the design offers to an app that wants no library enhancers, the contradiction is load-bearing, not cosmetic.

- **Evidence:** §14.5 `LIB-coverage-rule`, verbatim: "a `'global'` claim is covered when `BetterAuthGuard` and `BetterAuthScopeInterceptor` appear among the global enhancers however they were registered, and not when only the guard does; since v5 `[R4:NEST-r4-02]` also when the global entries are what `overrideProvider(BetterAuthGuard).useValue(mock)` … put there". §5.4 B16, verbatim: "**Coverage keys on the guard alone since v6** `[R5:SEC-r5-01]`: until v5 the guard and the scope interceptor were contributed by the same `forRoot`, so demanding both was the same test, but they are now registered independently (§5.7)". §5.4 B31: "this is the **only** report `globalScope: false` produces". §14.5's own "Since v6" sentence adds the B31 assertion without removing the contradicting one.
- **Suggested fix:** Rewrite that clause to match B16: "a `'global'` claim is covered when `BetterAuthGuard` appears among the global guards however it was registered; the scope interceptor's presence never affects coverage, and its absence is reported only by B31." Keep the `overrideProvider`/brand rows as they are, and add an explicit row: with `globalGuard: true` and `globalScope: false`, every `'global'` claim is covered, boot succeeds, and the only output is `W_NO_GLOBAL_SCOPE` plus `scope: off` in the summary.

## Proposed user decisions

- **Q39 — Should the origin check produce a verdict on safe methods that carry a cookie, so that the caller-session check can require one there?** (Fix of SEC-r6-01; it keeps §17 Q37's decision — fail closed with `PUBLIC_HANDLER_USED_CALLER_SESSION` — and only changes which legs count as verified.)
  - Option (a), **advisory verdict on safe methods**: when the plan's origin check is not `'off'`, the browser leg carries a cookie and `enforce` is false, the guard computes and memoizes the §7.10 verdict **without denying the request**. The caller-session check's third condition becomes "the guard resolved the principal **and** a passing verdict exists for this leg". A guarded GET that proxies `auth.api` from a trusted origin keeps working; the cross-site `<img>` fails closed. Cost: one memoized origin comparison per cookie-carrying safe request (a `trustedOrigins` function is evaluated once per leg, as today), and a guarded GET proxy called by a client that sends no `Origin` — an SSR server, a native app — now fails closed with a 500 instead of acting, until it sends an `Origin` or the route takes `@SkipOriginCheck()`.
  - Option (b), **keep the current pass and fix only the documentation**: leave the rule as v6 has it and change the hint, RK32 and §17 Q37 to stop recommending `@OptionalAuth()` for a safe-method proxy, telling developers to make such a route a POST instead. Cheaper and adds no request-time work, but the protection then depends on someone reading a hint, and §14.4 keeps asserting that the guarded GET proxy succeeds cross-site.
  - Recommendation: **(a)**. The design's own argument for closing the public GET case — "better-auth exposes no state-changing endpoint over GET, while this design hands app handlers `headersFrom(req)` and lets them call any endpoint from any method" — is equally true for a guarded GET, and (b) leaves the library's own remediation advice as the path into the hole. The extra cost lands only on safe requests that carry a cookie _and_ whose handler calls `auth.api` with the caller's session, because the verdict is read only by `checkCallerSession`; nothing else in the flow consults it, and no request is ever denied by it.
